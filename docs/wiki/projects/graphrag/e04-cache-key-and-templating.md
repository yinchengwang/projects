# 缓存键与模板引擎

## 一句话职责

两件支撑性的事：把「一次模型调用」的参数集合**用一个显式的排除表**折成一个缓存键（而不是把整个 `kwargs` 直接哈希），并提供一个「模板引擎 + 模板管理器」的两层抽象让提示可以从文件或代码里加载并渲染。

## 机制是什么

两者的共同点是**都在定义「什么算同一件事」**：

- **缓存键在定义「哪两次调用是同一个调用」** —— 键相同即复用结果。
- **模板引擎在定义「哪两次渲染是同一个渲染」** —— 同一模板名 + 同一 context 即同一输出。

而这个定义**必须靠排除而不是靠包含来写**，因为包含的写法会在每次新增参数时自动失效。

## 怎么实现的

### 一、`create_cache_key`：排除表而非白名单

**它的全部逻辑是一个剔除 + 一次哈希。**

```
def create_cache_key(input_args: dict[str, Any]) -> str:
    cache_key_parameters = _get_parameters(input_args=input_args)
    return default_create_cache_key(cache_key_parameters)

def _get_parameters(input_args: dict[str, Any]) -> dict[str, Any]:
    excluded_keys = [
        "metrics", "stream", "stream_options", "mock_response", "timeout",
        "base_url", "api_base", "api_version", "api_key",
        "azure_ad_token_provider", "drop_params",
    ]
    parameters: dict[str, Any] = {k: v for k, v in input_args.items() if k not in excluded_keys}
    return parameters
```

**十一个被排除的键，而它们分成三类，每类有不同理由：**

| 被排除的键 | 类别 | 为什么不影响结果 |
|---|---|---|
| `metrics` | 输出容器 | 它是**收集指标的字典**，不是输入 |
| `stream` / `stream_options` | 传输方式 | 流式与否不改变内容（且流式本身就被缓存跳过） |
| `mock_response` | 测试注入 | 假响应不该被缓存 |
| `timeout` | 控制参数 | 不改变模型输出 |
| `base_url` / `api_base` / `api_version` / `api_key` / `azure_ad_token_provider` | 连接与凭证 | 换端点/换密钥不改变「问的是什么」 |
| `drop_params` | 请求构造 | 客户端侧的参数裁剪 |

**注意 `model_config` 不在列表里，但它也不在 `input_args` 里** —— 模型身份由调用方在 `input_args` 里带上（如 `model` 键），或者压根不进键。

**这个「排除表」的选择是整个缓存正确性的核心判据。** 排除太多 → 该区分的没区分（缓存返回错误结果）；排除太少 → 不该区分的被区分（换密钥就全部失效）。

**而 `metrics` 的排除有一个特别之处：它必须被排除，因为它是**可变的输出容器**。** 而 `with_cache` 在调用前把所有东西塞进 `kwargs`（见 e02 那页），其中就有 `metrics`。若它进了键，则**每个请求的 `metrics` 都是新字典，哈希不同，缓存永不命中**。

**`_get_parameters` 上有一行被注释掉的参数。**

```
def _get_parameters(
    # model_config: "ModelConfig",
    input_args: dict[str, Any],
) -> dict[str, Any]:
```

**这说明 `model_config` 曾经是缓存键的一部分而被移除。** 而移除的理由可以从版本号注释推断出来：

```
_CACHE_VERSION = 4
"""
If there's a breaking change in what we cache, we should increment this version number to invalidate existing caches.

fnllm was on cache version 2 and though we generate similar cache keys, the objects stored in cache by fnllm and litellm are different.
Using litellm model providers will not be able to reuse caches generated by fnllm thus we start with version 3 for litellm.

graphrag-llm package is now on version 4.
This is to account for changes to the ModelConfig that affect the cache key and
occurred when pulling this package out of graphrag.
graphrag-llm, now that is supports metrics, also caches metrics which were not cached before.
"""
```

**这段注释记录了一次完整的版本演进，而它的价值在于说明了「版本号不是给格式用的，是给语义用的」：**

| 版本 | 变更 |
|---|---|
| 2 | 上一个库（`fnllm`）的版本 |
| 3 | 换成 `litellm`，缓存内容结构不同，无法复用旧缓存 |
| 4 | 从 `graphrag` 抽出 `ModelConfig` 时字段变化；且开始缓存指标 |

**注意版本 3 的理由不是「格式变了」而是「对象不同」** —— 键类似但值不可互换。**这是缓存版本号最重要的一类用途：键相同但值语义变了。**

**而 `default_create_cache_key` 委托给 `graphrag_cache.create_cache_key`，后者只是 `hash_data(input_args)`。** 于是哈希算法在另一个包里，而 `graphrag-llm` 只负责「决定哈希什么」。

**版本号没有出现在这个函数的返回值里** —— 它在 `graphrag_cache.create_cache_key` 或后端实现里。**这一点值得注意**：本模块的 `_CACHE_VERSION` 常量实际没有被 `create_cache_key` 引用（代码里没有对它的读取）。**它是一个文档化的常量**，而真正的版本隔离由缓存命名空间（`Cache.child(name)`，见 f01 那页）承担。

### 二、`TemplateEngine`：一个方法 + 一个属性

**抽象只有两个成员：**

```
class TemplateEngine(ABC):
    @abstractmethod
    def __init__(self, *, template_manager: "TemplateManager", **kwargs: Any) -> None: ...
    @abstractmethod
    def render(self, template_name: str, context: dict[str, Any]) -> str: ...
    @property
    @abstractmethod
    def template_manager(self) -> "TemplateManager": ...
```

**`render` 的文档声明了两类 `KeyError`：**

> `KeyError`：模板未找到，或 context 里缺必需的键。

**「模板未找到」与「context 缺键」被归到同一个异常类型** —— 而这是一个刻意的选择：对调用方来说，「我要渲染的东西没法渲染」是同一类失败。**而具体原因可以从消息里看出来（见下）。**

**`template_manager` 作为属性暴露，而不是仅内部持有** —— 于是外部可以拿到管理器去注册模板或列出现有模板名。

### 三、`JinjaTemplateEngine`：编译缓存与两类异常的映射

**`render` 的第一步是查编译缓存。**

```
jinja_template = self._templates.get(template_name)
if jinja_template is None:
    template_contents = self._template_manager.get(template_name)
    if template_contents is None:
        msg = f"Template '{template_name}' not found."
        raise KeyError(msg)
    jinja_template = Template(template_contents, undefined=StrictUndefined)
    self._templates[template_name] = jinja_template
```

**它缓存的是编译后的 `Template` 对象，不是模板源文本。** 于是同一个模板名第二次渲染不必重新解析——但因为 `FileTemplateManager.get` 每次都读文件，**这个缓存同时起到了「避免重复 I/O」的作用**。

**代价是一个重要的语义：模板的修改在引擎实例的生命周期内不生效。** 注册了新版本的同名模板，引擎仍会用手上编译好的旧版本。**这是一个没有失效机制的缓存** —— 对本用途（进程内一次性配置）足够，但对「热重载模板」不可行。

**`StrictUndefined` 是正确性的关键。**

```
jinja_template = Template(template_contents, undefined=StrictUndefined)
```

**Jinja 默认的 `Undefined` 在变量缺失时会渲染成空字符串**。对提示模板来说那是灾难：一个少传的变量会让提示里出现一个空洞，而模型照样回答——**错误被吞掉且无法察觉**。

**`StrictUndefined` 让缺失变量在渲染时抛 `UndefinedError`**，于是变成显式失败。**这是模板引擎里最重要的一行配置。**

**两类异常被映射成不同消息。**

```
try:
    return jinja_template.render(**context)
except UndefinedError as e:
    msg = f"Missing key in context for template '{template_name}': {e.message}"
    raise KeyError(msg) from e
except Exception as e:
    msg = f"Error rendering template '{template_name}': {e!s}"
    raise RuntimeError(msg) from e
```

**`UndefinedError` → `KeyError`（消息里说「context 缺键」）、其它 → `RuntimeError`。**

**这个映射的依据是「调用方能不能修」**：缺键是调用方传参的问题（改 context），而其它渲染错误是模板本身的问题（改模板）。**两种原因要改的东西不同，所以不能合并成一个异常。** 而两者都带上了模板名，于是多模板场景下能定位到具体哪一个。

**注意第一支用的是 `e.message` 而不是 `str(e)`** —— `UndefinedError` 的消息里有具体的变量名（如 `'foo' is undefined`），而 `e.message` 是它的原始文本。**这一行决定了错误消息里有没有变量名。**

### 四、`FileTemplateManager`：延迟读取 vs 立即写入的不对称

**`get` 每次都读文件，`register` 每次都写文件。**

```
def get(self, template_name: str) -> str | None:
    template_file = self._templates_dir / f"{template_name}{self._templates_extension}"
    if template_file.exists() and template_file.is_file():
        return template_file.read_text(encoding=self._encoding)
    return None

def register(self, template_name: str, template: str) -> None:
    self._templates[template_name] = template
    template_path = self._templates_dir / f"{template_name}{self._templates_extension}"
    template_path.write_text(template, encoding=self._encoding)

def keys(self) -> list[str]:
    return list(self._templates.keys())

def __contains__(self, template_name: str) -> bool:
    return template_name in self._templates
```

**`get` 走文件系统，`keys` 与 `__contains__` 走内存字典 `self._templates`。** 两者是**两套不一致的真相来源**：

| 操作 | 数据来源 |
|---|---|
| `get(name)` | 磁盘文件 |
| `keys()` | 内存字典（只含本次进程 `register` 过的） |
| `name in manager` | 内存字典 |

**后果很具体**：磁盘上已有的模板（比如随包分发的内置提示）`get` 拿得到，但 `keys()` 列不出来、`in` 判为 `False`。**只有通过 `register` 注册过的才在内存字典里。**

**这是实现里的一个真实缺陷**，而它的影响有限是因为典型用法是「按名字 `get`」（提示名在代码里写死），而不是「枚举可用模板」。**但任何依赖 `keys()` 做「模板是否存在」检查的代码都会得到错误答案。**

**文件名构造有两个约束：**

```
template_file = self._templates_dir / f"{template_name}{self._templates_extension}"
```

1. **`template_name` 没有做路径校验** —— 一个含 `../` 的名字会逃出 `_templates_dir`。**这个抽象本身不防路径穿越**（对比：`SQLiteCache` 对 `database_name` 做了严格的「必须是纯文件名」校验，见 f01 那页）。**攻击面取决于模板名是否来自不可信输入** —— 在 graphrag 里模板名都是代码常量，所以实际风险低，但这个差别值得记。
2. **扩展名默认为 `.jinja`，是配置项**（`template_extension`）。

**而构造期的目录校验是严格的。**

```
self._templates_dir = Path(base_dir).resolve()
if not self._templates_dir.exists() or not self._templates_dir.is_dir():
    msg = f"Templates directory '{base_dir}' does not exist or is not a directory."
    raise ValueError(msg)
```

**它在 `__init__` 里就检查目录存在，于是「模板目录配错」在启动时暴露而不是在第一次渲染时。** `resolve()` 把相对路径转成绝对路径 —— 这对后面的文件名拼接是必要的（否则工作目录变化会让路径失效）。

**注意文档字符串声明了「若 `template_extension` 是空字符串则抛 `ValueError`」，但代码里没有这个校验。** 与 e03 那页 `SlidingWindowRateLimiter` 的同类问题一致：**文档声明的校验没实现**。空扩展名的后果是模板文件名等于模板名（可能可行），不是崩溃。

**`register` 的两步顺序值得注意：先写内存、后写磁盘。**

**若磁盘写入失败（权限、磁盘满），内存里已经有了而磁盘没有** —— 于是 `get` 拿不到（它读磁盘），但 `keys()` 列得出来。**这个不一致会在异常路径上留下脏状态。** 反过来（先磁盘后内存）更安全，因为「磁盘有而内存没有」正是这个类的正常状态（内置模板）。

### 五、两层抽象的收益

**为什么要分成 `TemplateEngine` 与 `TemplateManager` 两个接口而不是一个类？**

| | Engine | Manager |
|---|---|---|
| 知道 | 怎么渲染 | 模板从哪来 |
| 依赖 | 一个渲染库（Jinja2） | 一个存储位置（文件/代码） |
| 可变维度 | 换渲染语法（Jinja / 其他） | 换来源（文件 / 数据库 / 内置常量） |

**两个维度正交，所以需要两个接口。** 若合并成一个类，则「用每文件存的模板 + 非 Jinja 语法」这种组合就无法表达。

**而 `JinjaTemplateEngine` 持有的是 `TemplateManager` 抽象**（不是 `FileTemplateManager` 具体类），于是「Jinja + 数据库模板」是可组合的。

**`FileTemplateManager` 的文档字符串却写着「Abstract base class for template managers」** —— 而它继承了 `TemplateManager` 并实现了全部抽象方法，所以它是**具体类**。**这是从 `TemplateManager` 复制过来的文档没改**。小的不一致，但读者会困惑。

## 关键取舍

**源码事实：** 缓存键用**排除表**（十一个键）而不是白名单：`metrics`、`stream`、`stream_options`、`mock_response`、`timeout`、`base_url`、`api_base`、`api_version`、`api_key`、`azure_ad_token_provider`、`drop_params`。

**源码事实：** `metrics` 必须被排除，因为它是可变的输出容器——若进键，则每个请求都是新字典，缓存永不命中。

**源码事实：** `_get_parameters` 里 `model_config` 参数被注释掉了，说明它曾进键后被移除。

**源码事实：** `_CACHE_VERSION = 4` 的注释记录了三次语义变更：`fnllm`(v2) → `litellm`(v3，键类似但值不可互换) → 从 graphrag 抽出（v4，`ModelConfig` 字段变化 + 开始缓存指标）。**这个常量在 `create_cache_key` 里没有被引用**——真正的版本隔离由缓存命名空间承担。

**源码事实：** `JinjaTemplateEngine` 缓存**编译后的 `Template` 对象**而非源文本，且**没有失效机制**——`register` 新版本后引擎仍用旧版本。

**源码事实：** `Template(..., undefined=StrictUndefined)` 是正确性关键：Jinja 默认把缺失变量渲染成空串，对提示模板是灾难（错误被吞且不可察觉）。

**源码事实：** 异常映射按「调用方能不能修」分：`UndefinedError` → `KeyError`（缺 context 键）、其它 → `RuntimeError`（模板本身问题）；第一支用 `e.message` 以保留变量名。

**源码事实：** `FileTemplateManager.get` 读磁盘、`keys()` / `__contains__` 读内存字典——**两套不一致的真相来源**，于是磁盘上已有但未经 `register` 的模板 `get` 得到、`keys()` 列不出、`in` 判假。

**源码事实：** `template_name` 未做路径校验（含 `../` 会逃出模板目录），与 `SQLiteCache` 严格校验 `database_name` 形成对照；实际风险低因为模板名都是代码常量。

**源码事实：** 构造期检查模板目录存在且是目录并 `resolve()` 成绝对路径；但文档声明的「`template_extension` 为空则抛 `ValueError`」未实现。

**源码事实：** `register` 先写内存后写磁盘，磁盘写入失败会留下「内存在、磁盘不在」的脏状态；而「磁盘在、内存不在」恰是这个类的正常状态（内置模板）。

**源码事实：** `FileTemplateManager` 的文档字符串写「Abstract base class for template managers」，但它是实现了全部抽象方法的具体类——文档未更新。

**架构推论：** 「缓存键用排除表」这个选择意味着**新增一个调用参数时缓存会自动区分它**（除非显式排除）。这是安全的默认：**误区分只是降低命中率（性能问题），误合并是返回错误结果（正确性问题）**。所以排除表必须短、每项都必须有明确理由——而 `base_url` / `api_key` 这类「连接参数不改变内容」的排除是最值得复核的：**若某天不同 `base_url` 指向了不同版本的模型，这个排除就错了。**

**架构推论：** 「引擎与来源分成两个接口」的收益在换一个维度时兑现。而它的成本是**每次调用都要穿过两层（`engine.render(name)` → `manager.get(name)` → 渲染）**，且第二层的结果被第一层缓存——于是「缓存该归谁」变得模糊。当前实现把缓存放在引擎侧，导致「管理器换了模板但引擎不知道」这个缺陷。**把缓存放在正确的层（由管理器负责）就能同时解决不一致与失效问题。**

## 与主核 / AI 的关系

缓存键的设计与主核的**查询计划缓存的键**是同一个问题，而两者的判据不同。

数据库的计划缓存键必须包含「影响计划的一切」：SQL 文本、参数类型、表的统计信息版本、`search_path`。而它**必须不包含**不影响计划的东西（比如连接的用户名，除非有行级安全）。**一类一个都不能错**：少包含会用错误的计划执行（正确性问题），多包含会让缓存无谓失效（性能问题）。

**这里的排除表里最值得复核的两项是 `api_key` 与 `base_url`。** 数据库里对应的是「连接字符串是否进计划缓存键」——答案是「不进，但 `search_path` 进」。判据是**「它能不能改变执行结果」**：`api_key` 不改变模型回答，`base_url` 通常也不改变（但如果不同端点部署了不同版本的模型，它就改变了）。**这条边界需要业务知识，代码无法自证。**

**`StrictUndefined` 与数据库的 `NOT NULL` 约束是同一类防护**：都是把「缺失」从「静默的默认值」变成「显式失败」。**默认值是最危险的错误处理方式**——它让程序继续跑下去而输出是错的，而错误要到最后才暴露（甚至永不暴露）。

**「两套真相来源」（`get` 读盘 vs `keys` 读内存）在数据库里是严重的反模式**，因为数据库必须保证「读到什么」与「元数据说什么」一致（`catcache` 与系统表的一致性由锁保证）。而这里的不一致之所以能存在，是因为**模板这个数据几乎没有并发与一致性的需求**——它是配置，进程启动时确定，之后不变。**同一个设计缺陷在低要求的场景里不成为缺陷，这正是判据所在。**

对 agent 工程的直接价值有三条。其一，**缓存键要用排除表而不是白名单**。白名单的问题是「新增参数忘了加」→ 键不变 → 返回错误结果；排除表的问题是「新增参数忘了排除」→ 键变了 → 只是不命中。**后者的失效模式安全得多。** 其二，**用 `StrictUndefined` 之类让缺失变量报错**。提示模板里一个空字符串比一次崩溃危险得多——它让模型在缺信息的情况下自信作答。其三，**元数据接口与内容接口必须来自同一个真相**。若 `keys()` 说「有」而 `get()` 返回 `None`（或反之），任何基于枚举的逻辑都会错。
