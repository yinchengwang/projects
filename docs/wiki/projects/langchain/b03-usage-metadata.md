# 用量元数据

## 一句话职责

把各家供应商五花八门的 token 计数统一成一套三层结构：总量、输入明细、输出明细。其中明细只要求「报了什么就有什么」，明确注明无需齐全、无需相加等于总量——这让缓存命中与推理这两类**真正影响成本**的分档得以表达。

## 机制是什么

成本核算的最小需求是三个数：输入多少 token、输出多少 token、总共多少。但真实场景下这三个数远远不够：

| 需求 | 为什么总量不够 |
|---|---|
| 缓存命中率 | 缓存读的 token 单价远低于正常输入，混在总量里算不出真实成本 |
| 推理开销 | 思维链 token 可能按输出价计也可能不计，必须单独知道 |
| 多模态计费 | 音频 token 单独计价 |
| 缓存写入 | 缓存未命中时模型要「写缓存」，这部分可能按另一档计价 |

所以这套结构的设计问题是：**如何在「供应商只报一部分」的前提下表达完整的分档**。

答案是把「明细」做成**三个宽松约定**，逐条都写在文档里：

1. `Does not need to sum to full input token count.`
2. `Does not need to have all keys.`
3. `May also hold extra provider-specific keys.`

这三条共同构成一个「尽力而为」的契约。它承认供应商之间不可能对齐，所以不做校验、不要求补齐——**报了什么就有什么**。

## 怎么实现的

**三层结构：总量必填、明细可选。**

```python
class UsageMetadata(TypedDict):
    input_tokens: int
    output_tokens: int
    total_tokens: int
    input_token_details: NotRequired[InputTokenDetails]
    output_token_details: NotRequired[OutputTokenDetails]
```

三处：

- **三个总量字段是 `int` 而不是 `Optional[int]`**。所以「有这个结构」就意味着三个数一定在。注释也给了语义约定：`total_tokens` 是「`input_tokens` + `output_tokens`」的和。
- **两个明细字段用 `NotRequired`**。因为很多供应商只报总量，不报分档。
- **它是 `TypedDict` 而不是 pydantic model**。这与 b02 的块一致——用字典便于无损透传，也便于上游直接构造（很多供应商适配器就是直接把响应里的数字塞进来）。

注意这里有一个**隐含的不对称**：明细字段用 `NotRequired`，但一旦出现就必须是 `InputTokenDetails`/`OutputTokenDetails` 的合法形状。所以「缺」是允许的，「畸形」不是。

**`InputTokenDetails` 只有三个标准键，而注释的措辞揭示了「谁该负责什么」。**

```python
class InputTokenDetails(TypedDict, total=False):
    audio: int
    cache_creation: int
    cache_read: int
```

`total=False` 让所有键都可选——这是 `NotRequired` 之外的另一条路（也在类型层表达「无需齐全」）。

两个缓存键的注释是这一页最需要准确理解的部分：

> `cache_creation` — Input tokens that were cached and there was a **cache miss**. Since there was a cache miss, the cache was **created** from these tokens.
>
> `cache_read` — Input tokens that were cached and there was a **cache hit**. Since there was a cache hit, the tokens were **read** from the cache. More precisely, the model state given these tokens was read from the cache.

读法：**两个键都是从「缓存」的角度命名，而不是从「计费」的角度**。

- `cache_creation` 是「这次没命中，所以现在把它写进缓存」——通常单价更高（相当于正常输入价）。
- `cache_read` 是「这次命中了，从缓存读」——通常单价低得多。

这个区分是成本核算的基础。若只有一个「cache」字段，就无法区分「写缓存」与「读缓存」，而这两个的单价可能差一个数量级。

而 `cache_read` 注释里那句「More precisely, the model state given these tokens was read from the cache」值得单记。它说的是：**缓存的不是文本，而是「给这些 token 的模型状态」**。这个精确化对理解「为什么缓存命中能便宜」很关键——省掉的是前向计算的状态，不只是存储。

`audio` 是第三个键，对应多模态输入。它的存在说明这套结构已经在考虑「不同模态不同价」这件事。

**`OutputTokenDetails` 只有 `audio` 与 `reasoning` 两个键，而 `reasoning` 的定义很特殊。**

```python
class OutputTokenDetails(TypedDict, total=False):
    audio: int
    reasoning: int
```

`reasoning` 的注释：

> Tokens generated by the model in a chain of thought process that are **not returned as part of model output**.

两个要点：

1. **「不返回给用户」的 token 也算输出用量**。所以 `output_tokens` 里包含推理 token，而 `reasoning` 是它的子集。这正是「明细无需相加等于总量」的实际含义——推理 token 既在总量里，又单独列一份。
2. **`reasoning` 是 `int` 而不是布尔**。因为推理可能有不同长度，用户关心的是「花了多少」不只是「有没有」。

注意输出明细里**没有** `cache_creation` 之类的键。缓存机制在多数供应商那里是输入侧特性，输出侧没有对应的分档。这个不对称本身反映了真实计费结构的差异。

**相加：`add_usage` 用递归字典加法，并特意用 `max(le - ri, 0)` 做减法。**

```python
def add_usage(left: UsageMetadata | None, right: UsageMetadata | None) -> UsageMetadata:
    if not (left or right):
        return UsageMetadata(input_tokens=0, output_tokens=0, total_tokens=0)
    if not (left and right):
        return cast("UsageMetadata", left or right)
    return cast(
        "UsageMetadata",
        _dict_int_op(cast("dict[str, Any]", left), cast("dict[str, Any]", right), operator.add),
    )
```

三个分支：

1. **两边都没有 → 返回全零的三字段结构**。这很重要：不能返回 `None`，因为调用方期望拿到 `UsageMetadata`。所以「都没有用量」被表达成「用量为零」，而这是唯一一处允许把「未知」压成 `0` 的地方——因为加法的单位元就是零。
2. **只有一边 → 直接返回那一边**。不构造新字典，不补齐缺失字段。这保留了「供应商只报一部分」的信息（若补齐成零，就分不清「报了 0」与「没报」）。
3. **两边都有 → 递归字典相加**。

`_dict_int_op` 的实现有两个关键设计：

```python
for k in set(left).union(right):
    if isinstance(left.get(k, default), int) and isinstance(right.get(k, default), int):
        combined[k] = op(left.get(k, default), right.get(k, default))
    elif isinstance(left.get(k, {}), dict) and isinstance(right.get(k, {}), dict):
        combined[k] = _dict_int_op(left.get(k, {}), right.get(k, {}), op, default=default, depth=depth + 1, max_depth=max_depth)
    else:
        types = [type(d[k]) for d in (left, right) if k in d]
        msg = f"Unknown value types: {types}. Only dict and int values are supported."
        raise ValueError(msg)
```

四处：

- **`set(left).union(right)`**：遍历**两侧键的并集**。这样只有一侧有的键也会被处理（用 `default=0` 补齐另一侧）。于是 `left` 有 `cache_read` 而 `right` 没有时，结果是 `left.cache_read + 0`——即保留左侧的值。这是正确的：右侧没报不代表它是零，但「相加」这个操作的语义就是「左侧那份 + 右侧那份」，缺的当零。
- **两个分支的顺序是「先 int 后 dict」**。若一个键在一侧是 int 而另一侧是 dict，两个分支都不成立，落进 `else` 抛 `ValueError`。这是**类型不一致时的显式失败**——不尝试猜测，因为猜错会让用量数字出错。
- **`depth` / `max_depth=100`**：防无限递归。用量结构只有两层（顶层 + 明细），100 层纯属保险。
- **错误的 `types` 计算**写得很细：`[type(d[k]) for d in (left, right) if k in d]`——只列出真正有这个键的那几侧的类型。所以错误信息能说清「哪两侧的类型冲突」。

**`add_usage` 的第三个分支没有传 `default`，用默认的 `0`。** 这与 `_dict_int_op` 签名的默认值一致。所以「缺键当零」这条在加法里是隐式的。

而 `_dict_int_op` 的通用性（接受任意 `op`）解释了它为什么被抽到 `utils/usage.py` 而不是留在 `ai.py`：**同一套递归逻辑还要支持减法**。源码里减法用在 `max(le - ri, 0)`：

```python
**cast("UsageMetadata", _dict_int_op(cast("dict[str, Any]", left), cast("dict[str, Any]", right), (lambda le, ri: max(le - ri, 0)))
```

`max(le - ri, 0)` 是一个**夹到非负**的减法。它防止「减去一个更大的值」得到负数 token 数。这是必须的——用量不能为负，而减法在两份用量上很容易出现负数（例如拿「前一次累计」减「后一次累计」而顺序搞反时）。

**`UsageMetadataCallbackHandler` 是「跨多次调用累积」的入口，而它的键是模型名。**

```python
def on_llm_end(self, response: LLMResult, **kwargs: Any) -> None:
    try:
        generation = response.generations[0][0]
    except IndexError:
        generation = None

    usage_metadata = None
    model_name = None
    if isinstance(generation, ChatGeneration):
        try:
            message = generation.message
            if isinstance(message, AIMessage):
                usage_metadata = message.usage_metadata
                model_name = message.response_metadata.get("model_name")
        except AttributeError:
            pass

    if usage_metadata and model_name:
        with self._lock:
            if model_name not in self.usage_metadata:
                self.usage_metadata[model_name] = usage_metadata
            else:
                self.usage_metadata[model_name] = add_usage(self.usage_metadata[model_name], usage_metadata)
```

五处值得看：

1. **`response.generations[0][0]` 并 catch `IndexError`**。要拿「第一个候选的第一个生成」，但结果可能是空的。捕获后置 `None`，后续的 `isinstance` 检查会跳过。
2. **`if usage_metadata and model_name` 这个合取是关键**。两个条件必须同时成立：
   - 没有 `usage_metadata` → 这个供应商不报用量，记不了。
   - 没有 `model_name` → **不知道该记到哪个键下**，只能丢弃。

   第二点值得单想：这里选择了**丢弃而不记入未知桶**。理由是「按模型分桶」是这个 handler 的核心价值（用户要看「哪个模型花了多少」），记到一个 `"unknown"` 桶里对用户没用，还会污染统计。但这个选择的代价是「用量被静默丢失」——一份成本报告会少掉那些没报模型名的调用。
3. **`model_name` 取自 `response_metadata.get("model_name")`** 而不是消息的某个正式字段。这说明**模型名至今仍是「供应商特有元信息」而非标准字段**——它留在 b01 讲的 `response_metadata` 字典里。这个细节与 b01 的分工一致。
4. **`add_usage` 用在同一模型的多次调用之间**。所以 handler 的产出是「每个模型的累计用量」。这就是「明细可以相加」的实用前提——若明细不能相加，多次调用就无法合并，而这个 handler 的主要用途恰好是合并。
5. **`self._lock` 是 `threading.Lock`**。因为它可能被多个线程的回调同时调用。注意锁保护的是字典读改写，而 `add_usage` 本身是纯函数，无副作用。

**`__repr__` 返回 `str(self.usage_metadata)`**，所以 `print(cb)` 直接给出可读的用量表。这是一个小的可用性选择：让对象在打印时就展示它最重要的内容。

**`get_usage_metadata_callback` 用 `ContextVar` + `finally` 重置，而注释给了具体的事故编号。**

```python
@contextmanager
def get_usage_metadata_callback(name: str = "usage_metadata_callback") -> Generator[UsageMetadataCallbackHandler, None, None]:
    usage_metadata_callback_var: ContextVar[UsageMetadataCallbackHandler | None] = ContextVar(name, default=None)
    register_configure_hook(usage_metadata_callback_var, inheritable=True)
    cb = UsageMetadataCallbackHandler()
    token = usage_metadata_callback_var.set(cb)
    try:
        yield cb
    finally:
        usage_metadata_callback_var.reset(token)
```

四处：

- **`ContextVar` 而不是全局变量**。用量累积必须是「当前上下文的」，否则并发请求会互相污染。`ContextVar` 天然按任务/线程隔离。
- **`inheritable=True`**：让子任务（例如并行执行的分支）也继承这个回调。若不可继承，并行分支里的模型调用就统计不到——这会让用量偏低。
- **`ContextVar` 在函数内创建而不是模块级**。这是一个容易忽略的细节：每次调用 `get_usage_metadata_callback` 都新建一个 `ContextVar`，所以两个嵌套的 `with` 块互不干扰。若做成模块级单例，嵌套会覆盖外层的回调。
- **`finally` 里 `reset`，且注释点名了事故**：

  > Always clear the context var, including when the with-block raises. Without finally, post-block model calls keep accumulating into `cb` (see #38989).

  即若不重置，**`with` 块结束之后的模型调用仍会往这个 handler 里累积**。这是一个静默的错误：用户以为统计只覆盖块内，实际块外的调用也被记进去了。而这个问题只在异常路径或块后还有调用的场景下暴露——正是那种「测试不覆盖、线上偶发」的 bug。

`reset(token)` 而不是 `set(None)` 也是必要的：`token` 记录了设置前的原值，`reset` 能精确恢复（包括「原本就是 `None`」与其他回调共存的情形）。

## 关键取舍

**源码事实：** `UsageMetadata` 三个总量字段必填、两个明细字段 `NotRequired`；明细类型用 `total=False` 让所有键可选。

**源码事实：** 明细的三条契约明写在文档里：无需相加等于总量、无需齐全、可含供应商特有键。

**源码事实：** `InputTokenDetails` 分 `cache_creation`（未命中，写缓存）与 `cache_read`（命中，读缓存），两者单价不同；`cache_read` 的注释精确化为「读的是给这些 token 的模型状态」。

**源码事实：** `OutputTokenDetails` 的 `reasoning` 是「不返回给用户的思维链 token」，即它同时计入 `output_tokens` 又单独列出——这正是「明细不必等于总量」的实例。

**源码事实：** `add_usage` 三支：都无则返回全零三字段、仅一侧则原样返回不补齐、两侧则递归字典相加。

**源码事实：** 递归相加遍历两侧键的并集、缺键按 `default=0` 补齐、int 与 dict 类型冲突时抛 `ValueError` 而非猜测；递归有 `max_depth=100` 保护。

**源码事实：** 同一套递归函数以 `op` 参数复用于减法，且减法用 `max(le - ri, 0)` 夹到非负。

**源码事实：** `UsageMetadataCallbackHandler` 按 `model_name` 分桶，且只在 `usage_metadata` 与 `model_name` **同时存在**时才记录，否则丢弃。

**源码事实：** `get_usage_metadata_callback` 每次调用都新建 `ContextVar` 并设 `inheritable=True`，且在 `finally` 中 `reset(token)`；注释说明不重置会导致块外调用继续累积（#38989）。

**架构推论：** 这套结构的核心是**「尽力而为的明细 + 严格的总量」**。总量必须齐（因为成本估算的最低需求），明细可以缺（因为供应商不齐）。这个分层让「收到多少就记多少」成为一种合法状态，而不必伪造零值——伪造零值会让「缓存命中率」这类派生指标彻底失真（分母有了、分子是假的零）。

**架构推论：** `add_usage` 第二支「只有一侧就原样返回」是一条容易被忽视但很重要的选择。它保住了「未报告的键」与「报告为零的键」的区分。若在这里补齐成零，那么合并之后就无法回答「这个调用到底有没有报缓存明细」——而这决定了要不要把这个调用算进缓存命中率的分母。

**架构推论：** 类型冲突时抛错而不是猜测，体现了「用量数字不能猜」的立场。一个 int/dict 冲突的用法结构意味着适配器出错了，继续加下去会得到无意义的总数——而总数会被用来算钱。这类「错误必须暴露」的判定与 g01 里「明确失败才报错」相反，判据是**错误的后果是否会被下游当真**。

**架构推论：** `ContextVar` 在函数内创建这个细节值得单记。它使嵌套调用正确，但代价是**每次调用都注册一个新的 configure hook**（`register_configure_hook` 被重复调用）。若 `register_configure_hook` 内部把 hook 追加到全局列表，反复进入这个上下文管理器会让列表单调增长。这是一个在源码里能看出但注释未提及的潜在成本。

## 与主核 / AI 的关系

「总量严格、明细尽力」这个分层与主核里的**统计信息的精确度分级**同源。主核的 `pg_class.reltuples` 可能是精确值也可能是估算值，而 `pg_statistic` 里的直方图只覆盖被 `ANALYZE` 采样的列。规划器必须知道「这个数是不是精确的」，否则会基于估算做过度乐观的决策。本页的对应物是「明细能不能相加」这条契约——它决定了某个派生指标（缓存命中率）能不能被算出来而不失真。

「缺键与零值必须区分」这条与主核里**NULL 与 0 不可混淆**是同一条原则的会计版本。主核在聚合时对 NULL 的处理（跳过而非当零）直接决定平均值是否正确；本页在合并用量时对「未报告」的处理（不补齐）直接决定成本统计是否失真。

`ContextVar` 那种「按执行上下文隔离累积状态」的做法，在主核里对应的是**每个会话/事务私有的累加状态**（如本事务的 WAL 字节数），而不是全局计数器。判据相同——统计必须归属于产生它的那个执行单元，否则并发下必然错。

对 AI 工程的实际意义在于：token 用量是 agent 系统最直接的成本信号，而它的可用性完全取决于分档是否够细。这份实现给出的三条经验可直接用：**区分缓存写入与缓存读取**（两者单价可能差一个数量级，混在一起算不出账）、**把「未报告」与「报告为零」分开**（否则派生指标的分子会造假）、以及**上下文管理器必须在 `finally` 重置**（否则统计会静默地越界累积，而且只在异常与块后调用时暴露）。
