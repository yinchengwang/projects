# 内容块与工具调用块

## 一句话职责

用一组以 `type` 为判别位的 TypedDict 定义「一条消息的内容可以是什么」，把文本、推理、图片/视频/音频/文件、工具调用、服务端工具、以及「框架还不认识的东西」全部纳进同一个联合类型——这套划分决定了多模态消息能不能被无损表达。

## 机制是什么

这里要处理的是一个**开放世界**问题：模型返回的内容种类由供应商决定，而供应商在不断加新东西（推理块、服务端执行的工具、引用标注、refusal）。框架要么把它建模成完备的联合（然后就永远落后于供应商），要么留一个逃生舱。

依据源码里的划分，最终选择是**两者都要**：

```
ContentBlock = TextContentBlock
             | InvalidToolCall
             | ReasoningContentBlock
             | RefusalContentBlock
             | NonStandardContentBlock        ← 逃生舱
             | DataContentBlock                ← 多模态别名
             | ToolContentBlock                ← 工具别名
```

而两个别名展开后：

```
DataContentBlock = Image | Video | Audio | PlainText | File
ToolContentBlock = ToolCall | ToolCallChunk | ServerToolCall | ServerToolCallChunk | ServerToolResult
```

即 **15 个具体块类型**，覆盖文本、推理、拒答、四类多模态数据、五类工具相关、以及对未知的兜底。

这个联合的每一支都是 `TypedDict` 而非 dataclass 或 pydantic model。这个选择很关键：**块就是字典**，所以它可以无损地做「原样透传」——一个供应商块经过框架往返后仍然是同一份字典，不因序列化/反序列化而变形。

## 怎么实现的

**`type` 是唯一的判别位，而它是 `Literal` 单值。**

```python
class TextContentBlock(TypedDict):
    type: Literal["text"]
    text: str
    id: NotRequired[str]
    annotations: NotRequired[list[Annotation]]
    index: NotRequired[int | str]
    extras: NotRequired[dict[str, Any]]
```

`Literal["text"]` 保证「类型声明与值一致」。这对 TypedDict 尤其重要——TypedDict 在运行时不做校验，所以判别位的唯一保障是静态类型检查器。

**每个块都有一对可选的 `id` 与 `index`，两者用途完全不同。**

```python
id: NotRequired[str]
"""Unique identifier for this content block.
Either: — Generated by the provider — Generated by LangChain upon creation (`UUID4` prefixed with `'lc_'`))"""

index: NotRequired[int | str]
"""Index of block in aggregate response. Used during streaming."""
```

- **`id` 是块的稳定身份**。注释点名了 `'lc_'` 前缀，意为「LangChain 生成的 id」。工厂函数（`create_tool_call` / `create_text_block` 等）在 `id` 未提供时自动生成，这就是 `ensure_id` 的作用。段前缀让「框架生成的 id」与「供应商给的 id」在数据上可区分——排查时能一眼看出这个 id 是谁造的。
- **`index` 用于流式聚合**，类型是 `int | str` 而不是 `int`。为什么允许字符串？因为有的供应商用非数字的位置标识（如 Anthropic 的 content block 序号可能是字符串形态的其他键）。用 `int | str` 让两种都能被承载。

**`ToolCall`、`ToolCallChunk`、`InvalidToolCall` 三者的差异是流式架构的直接产物。**

| 类型 | `args` 类型 | `name` | 额外字段 | 何时用 |
|---|---|---|---|---|
| `ToolCall` | `dict[str, Any]` | `str` | — | 拼装完成 |
| `ToolCallChunk` | `str \| None` | `str \| None` | — | 流式中途 |
| `InvalidToolCall` | `str \| None` | `str \| None` | `error` | 解析失败 |

三处值得记：

1. **`ToolCallChunk.args` 是 `str`（JSON 子串）而不是 dict**。流式过程中模型逐 token 吐出参数，`'{"a":'` 后面接 `'1}'`，中途无法解析成 dict。所以碎片的 `args` 只能是字符串，拼接完成才 `parse_partial_json` 成 dict。
2. **`ToolCallChunk` 的所有身份字段都是 `str | None`**（`id`、`name`、`args` 都是 `Optional`）。因为一个碎片可能只带参数增量而不带名字——名字在第一块就齐了，后续块只有 args。这个 `None` 不是「字段可选」，而是「这一块没携带这个信息」。
3. **`InvalidToolCall` 的形状与 `ToolCallChunk` 几乎一样，只多一个 `error`**。它复用了「args 是字符串」的形态，因为畸形调用的 args 本来就是「解析失败的 JSON 字符串」——保留原文 + 错误信息，让上层能决定复现或修复。注释直接写「Allowance for errors made by LLM. Here we add an `error` key to surface errors made during generation (e.g., invalid JSON arguments.)」。

`ToolCallChunk` 的类文档把合并语义写成了可执行规格：

> When merging `ToolCallChunks` (e.g., via `AIMessageChunk.__add__`), all string attributes are concatenated. Chunks are only merged if their values of `index` are equal and not `None`.

即**合并两个条件**：字符串属性拼接、且 `index` 相等且非 `None`。这条规则解释了 `index` 为什么是 `NotRequired` 而不是必填——没有 `index` 的碎片**不参与合并**，它们是孤立的。这也解释了为什么 `index` 的类型是 `int | str`（不同供应商的编号方式不同，只要能比较相等即可）。

`ToolCallChunk` 的文档还给了一个逐字可验证的例子：

```python
left_chunks = [ToolCallChunk(name="foo", args='{"a":', index=0)]
right_chunks = [ToolCallChunk(name=None, args="1}", index=0)]
(left + right).tool_call_chunks == [ToolCallChunk(name="foo", args='{"a":1}', index=0)]
```

注意合并结果里 `name` 是 `"foo"` 而不是 `"foo" + None`——拼接逻辑必须对 `None` 做处理（取非 None 那侧）。这个例子把「拼接」的边界条件（其中一侧缺字段）固定住了。

**`ServerToolCall` / `ServerToolCallChunk` / `ServerToolResult` 是一组独立的三件套。**

```python
class ServerToolCall(TypedDict):
    type: Literal["server_tool_call"]
    id: str          # 注意：必填，不是 Optional
    name: str        # 必填
    args: dict[str, Any]

class ServerToolResult(TypedDict):
    type: Literal["server_tool_result"]
    id: NotRequired[str]
    tool_call_id: str           # 必填：指向对应的 server tool call
    status: Literal["success", "error"]
    output: NotRequired[Any]
```

这套东西存在的理由写在 `ServerToolCall` 的文档里：「Tool call that is executed server-side. For example: code execution, web search, etc.」

即**供应商在自己的服务器上执行的工具**（而非本地执行后回传结果）。它与 `ToolCall` 的结构差异很有信息量：

- **`ServerToolCall.id` 是必填 `str`**，而 `ToolCall.id` 是 `str | None`。因为服务端工具的调用与结果必须靠 id 配对（`ServerToolResult.tool_call_id`），所以 id 不可或缺；而本地工具调用即使没有 id 也能靠顺序处理。
- **`ServerToolResult` 用 `tool_call_id` 而不是复用 `id`** 指向对方。`id` 是结果自身的编号，`tool_call_id` 是「我在响应哪次调用」——两个不同语义的字段，用两个名字区分是正确的。
- **`status` 是 `Literal["success", "error"]` 而非布尔**。布尔只能表达成败，而字面量可以将来加第三个状态（如 `"pending"`）。

**多模态五件套的结构几乎一样，只有两处差异。**

`ImageContentBlock` / `VideoContentBlock` / `AudioContentBlock` / `FileContentBlock` 四者字段完全相同：

```
file_id / mime_type / url / base64 （全部 NotRequired）+ index / extras / id
```

即**四种承载方式**：外部文件存储的 id、URL、base64 数据、或不带数据（仅 mime_type）。这正是「图片可以怎么传到模型」的穷举。

差异只有两处：

1. **`PlainTextContentBlock` 多了 `text`、`title`、`context`**，且 `mime_type` 是 `Literal["text/plain"]`（唯一一个被收紧成字面量的 mime 类型）。因为纯文本可以直接内联而不必走 url/base64。
2. **`FileContentBlock` 的文档额外说明了「别用它装其他类型」**：注释说「If the file is an image, audio, or plaintext, you should use the corresponding content block type」。即 `file` 是兜底类别（PDF、Word 等），而分类的目的是让供应商适配层知道该用哪个字段（有些供应商对图片有专门的字段，对任意文件走另一条路）。

`PlainTextContentBlock` 里有一段特别值得读的警告，它把一次**破坏性改名**记录在案：

> A `PlainTextContentBlock` existed in `langchain-core<1.0.0`. Although the name has carried over, the structure has changed significantly. The only shared keys between the old and new versions are `type` and `text`, though the `type` value has changed from `'text'` to `'text-plain'.

即**同名但语义已变**，且判别位从 `"text"` 改成 `"text-plain"`。这个改名是必需的——否则新旧「纯文本块」在 `type` 上都叫 `"text"`，无法区分。而这也解释了 `TextContentBlock` 的 `type` 是 `"text"`（新式的对话文本），而文件型的纯文本是 `"text-plain"`（带连字符）。命名空间很紧：一个短横线就承担了两种语义的分界。

**`NonStandardContentBlock` 是逃生舱，而它的字段设计说明「逃生舱里不能再有逃生舱」。**

```python
class NonStandardContentBlock(TypedDict):
    type: Literal["non_standard"]
    id: NotRequired[str]
    value: dict[str, Any]
    index: NotRequired[int | str]
```

注释写得很明确：

> Has no `extras` field, as provider-specific data should be included in the `value` field.

即**唯一不设 `extras` 的块**。因为 `value` 已经是「原样的供应商负载」，若再加一个 `extras` 就会产生「到底该放哪个」的歧义。

还有一条更重要的职责划分：

> If a provider's non-standard output includes reasoning and tool calls, it should be the adapter's job to parse that payload and emit the corresponding standard `ReasoningContentBlock` and `ToolCalls`.

即**逃生舱是临时收容站，不是终态**。适配层的义务是把供应商负载里的推理与工具调用**拆出来变成标准块**，只把真正无法标准化的部分留在 `value` 里。这让 `non_standard` 的存在是「尚未适配」而不是「永不适配」。

**`KNOWN_BLOCK_TYPES` 是一个显式的「已知清单」，且它有意漏掉两项。**

```python
KNOWN_BLOCK_TYPES = {
    "text", "reasoning", "refusal",
    "tool_call", "invalid_tool_call", "tool_call_chunk",
    "image", "audio", "file", "text-plain", "video",
    "server_tool_call", "server_tool_call_chunk", "server_tool_result",
    "non_standard",
    # citation and non_standard_annotation intentionally omitted
}
```

注释说：「If a block has a type not in this set, it is considered to be provider-specific」。

有三处值得看：

1. **集合里没有 `"citation"` 与 `"non_standard_annotation"`**，注释直说「intentionally omitted」。理由可以从它们的类型上看出来：`Citation` 与 `NonStandardAnnotation` 是**标注**（被 `TextContentBlock.annotations` 引用），而不是独立的顶层块。把它们放进「块类型清单」会让「顶层块」与「子结构」混淆。
2. **`"non_standard"` 本身在集合里**。这看起来矛盾（未知才进 `non_standard`，而它在已知清单里），但实际是必要的：`content_blocks` 的解析流程会产生 `{"type": "non_standard", "value": item}`，若 `non_standard` 不在已知集合里，第二遍解析会再把它包一层 `non_standard`。
3. **集合里出现了 `tool_call_chunk` 与 `server_tool_call_chunk`**，即**流式碎片也被视为顶层块类型**。这让 `AIMessageChunk.content_blocks` 可以把碎片直接投影成内容块（b01 提到的那处重写）。

**`DataContentBlock` 的类型清单是运行时推导的，而不是手写常量。**

```python
def _get_data_content_block_types() -> tuple[str, ...]:
    data_block_types = []
    for block_type in get_args(DataContentBlock):
        hints = get_type_hints(block_type)
        if "type" in hints:
            type_annotation = hints["type"]
            if hasattr(type_annotation, "__args__"):
                literal_value = type_annotation.__args__[0]
                data_block_types.append(literal_value)
    return tuple(data_block_types)
```

即**从联合类型里反射出各成员的字面量**（`("image", "video", "audio", "text-plain", "file")`）。这样加一个新多模态块类型只要加进 `DataContentBlock` 联合，清单自动跟上——不需要在第二个地方同步。这是「用类型作为唯一真相来源」的做法。

而它的文档还点了一处历史包袱：

> Note that old style multimodal blocks type literals with new style blocks. Specifically, `"image"`, `"audio"`, and `"file"`.

即旧式的多模态块（带 `source_type` 字段的那套）与新式块**共用同样的 `type` 字面量**。所以仅凭 `type` 无法区分新旧，必须看 `source_type` 是否存在。

**`is_data_content_block` 是这套新旧兼容逻辑的落点，它的分支顺序很有讲究。**

```python
if block.get("type") not in _get_data_content_block_types():
    return False

if any(key in block for key in ("url", "base64", "file_id", "text")):
    if block["type"] == "text" and "source_type" not in block:
        return False
    return True

if "source_type" in block:
    source_type = block["source_type"]
    if (source_type == "url" and "url" in block) or (source_type == "base64" and "data" in block):
        return True
    if (source_type == "id" and "id" in block) or (source_type == "text" and "url" in block):
        return True

return False
```

四处：

1. **第一关是 `type` 白名单**。不在其中直接否。
2. **第二关是「有至少一个数据字段」**（`url`/`base64`/`file_id`/`text`）。如果只有 `type` 而没有任何数据，就不算数据块。
3. **那句 `if block["type"] == "text" and "source_type" not in block: return False` 是关键的消歧**。`"text"` 是 `TextContentBlock` 的类型（**不在** `DataContentBlock` 里），但旧式 `PlainTextContentBlock` 的 `type` 也是 `"text"`（且带 `source_type`）。所以：
   - `type == "text"` 且**无** `source_type` → 新式的对话文本块，不是数据块。
   - `type == "text"` 且**有** `source_type` → 旧式的文件型纯文本，是数据块。

   这一步让「同一个 type 字面量」在两个语义上被分开。注释还给了理由（源码行内注）：「`'text'` is checked to support v0 `PlainTextContentBlock` types. We must guard against new style `TextContentBlock` which also has `'text'` `type` by ensuring the presence of `source_type`」。
4. **第三关处理旧式的 `source_type` 形态**（四种子情形：`url`/`base64`/`id`/`text`），覆盖那些没有任何外露数据字段的旧块。

这套判断的实质是：**用「字段共现」而不是「类型原型」来识别旧式块**。这是因为旧式块没有独立的判别位，只能靠形状推断。

**工厂函数把「id 自动生成」这件事变成默认行为。**

```python
def create_tool_call(name: str, args: dict[str, Any], *, id: str | None = None, index: int | str | None = None, **kwargs: Any) -> ToolCall:
    block = ToolCall(type="tool_call", name=name, args=args, id=ensure_id(id))
    if index is not None:
        block["index"] = index
    extras = {k: v for k, v in kwargs.items() if v is not None}
    if extras:
        block["extras"] = extras
    return block
```

三处：

- **`id=ensure_id(id)`**：未提供就生成 `lc_` 前缀的 UUID4。这让「每次创建的调用都有稳定身份」，而上层不必每次记得传 id。
- **`index` 用 `is not None` 判断后写入**，而不是总写。因为 `index=None` 与「没有 index」在合并语义上等价（前文说过：`index` 为 `None` 的碎片不参与合并）。不写这个键省掉一次表示。
- **`extras` 用 `{k: v for k, v in kwargs.items() if v is not None}` 过滤掉 `None` 值**，且**只在非空时写入**。所以传 `extras={}` 与不传是同一个结果。

每个块的文档里都重复一段「Factory function」提示，说明 `create_*` 带来两个好处：「Automatic ID generation」与「Required arguments strictly validated at creation time」。即工厂函数是 **TypedDict 缺失的运行期校验的替代品**——TypedDict 本身不做校验，但工厂函数的签名会。

**`extras` 字段的注释措辞在多模态块里是统一的，且带一条禁令。**

```
extras: NotRequired[dict[str, Any]]
"""Provider-specific metadata. This shouldn't be used for the image data itself."""
```

「This shouldn't be used for the ... data itself」这条禁令防止一个具体的误用：把图片的 base64 塞进 `extras` 而不是 `base64` 字段。若这样做，块在静态类型上仍然「合法」，但所有下游适配器都拿不到数据。这是文档层面的约定，无法用类型强制——因为 `extras` 是任意字典。

## 关键取舍

**源码事实：** `ContentBlock` 是 15 个 TypedDict 的联合，按 `type` 字面量判别；全部是 TypedDict 而非 model 类，因此块「就是字典」，可无损往返。

**源码事实：** 每个块都有可选的 `id`（供应商或 `lc_` 前缀的框架 id）与 `index`（`int | str`，用于流式聚合）。

**源码事实：** `ToolCall.args` 是 `dict`，`ToolCallChunk.args` 与 `InvalidToolCall.args` 是 `str`——流式与失败两种情形下参数只能是 JSON 子串。

**源码事实：** `ToolCallChunk` 的合并规则是「字符串属性拼接、且 `index` 相等且非 `None`」；缺 `index` 的碎片不参与合并。

**源码事实：** `ServerToolCall.id` 与 `ServerToolResult.tool_call_id` 都是必填，而 `ToolCall.id` 可空——服务端工具的调用与结果必须靠 id 配对。

**源码事实：** `PlainTextContentBlock` 的 `type` 从旧的 `"text"` 改为 `"text-plain"`，因为新旧两个同名块共用 `"text"` 无法区分。

**源码事实：** `NonStandardContentBlock` 是唯一没有 `extras` 的块，且它的职责是「临时收容」——适配层有义务把其中的推理与工具调用拆成标准块。

**源码事实：** `KNOWN_BLOCK_TYPES` 有意不含 `citation` 与 `non_standard_annotation`（它们是嵌套标注而非顶层块），但**含** `non_standard`（否则解析时会被二次包裹）。

**源码事实：** `DataContentBlock` 的类型字面量由 `get_args` + `get_type_hints` 运行时推导，避免清单与联合定义漂移。

**源码事实：** `is_data_content_block` 用「`type` 白名单 + 数据字段共现 + `source_type` 消歧」三关判断，其中 `type == "text"` 且无 `source_type` 时判为非数据块。

**架构推论：** 这套划分的核心取舍是**「标准块尽可能细，剩余全进逃生舱」**。细的意义在于每类都能被适配器精确映射（图片走图片字段、文件走文件字段）；逃生舱的意义在于供应商加新东西时不必等框架发版。而 `non_standard` 的「临时性」定位（适配层义务拆分）是让逃生舱不被滥用、不被当成终态的关键——否则框架会逐渐退化成「什么都装进 value」。

**架构推论：** 用一个短横线区分 `"text"` 与 `"text-plain"`，是命名空间已经很紧时的典型取舍。更好的做法本来是用语义更远的名字（如 `"document"`），但那样会破坏旧代码里对 `PlainTextContentBlock` 的引用；沿用名字 + 改判别位是**牺牲可读性换取兼容性**。代价是任何读 `type` 的地方都必须记得这两个值的区别。

**架构推论：** `extras` 的「不得存放数据本身」这条禁令暴露了「任意字典字段」的固有风险。它无法用类型系统强制，只能靠文档 + 工厂函数的参数形状引导（`create_image_block` 有 `base64=` 参数，所以正常路径不会走到 `extras`）。这类「形状上合法、语义上错误」的误用在 TypedDict 体系里无解，只能靠约定。

## 源码落点

## 与主核 / AI 的关系

「用判别位联合表示开放世界的值类型」与主核里的**多模态值表示**是同一类问题。主核要存图像、向量、文本、JSON 这些异质值，做法是「一个类型标签 + 一个通用载荷」；本页的做法是「一个 `type` 字面量 + 一份 TypedDict」。差别在**类型标签的粒度**：主核的标签是几个大类，这里细到 15 类。更细的标签换来的是适配器可以精确映射，代价是每加一类就要动联合定义与已知清单。

`NonStandardContentBlock` 那种「临时收容 + 适配层义务拆分」的做法，与主核里的**未识别扩展字段**一致：主核把不认识的 `reloptions` 键原样保留，但要求相关插件自己解释它们。两者的共同纪律是**保留不等于解释**——保留是为了不丢数据，解释是别的层的责任。

`is_data_content_block` 用「字段共现」推断旧式块，与主核里的**按形状推断版本**同源：主核读一些旧版本的数据文件时没有版本头，只能靠「有没有某个魔数字段」判断。这类推断的代价相同——**形状判断永远可能被未来的新形状误伤**，所以分支顺序（先判 `type` 白名单、再判数据字段、再判 `source_type`）必须能解释清楚。

对 AI 工程的实际意义在于：多模态消息的表达能力直接决定「能不能把供应商的特有能力用上」。这份实现给出的三条经验可直接用：**流式碎片与完成态要用不同类型**（`args` 的 dict / str 差异就是这件事的实体）、**逃生舱要有明确的临时性定位**（否则会变成垃圾场）、以及**用类型做单一真相来源**（`DataContentBlock` 的字面量反射避免了清单漂移）。
