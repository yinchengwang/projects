## 四、WAL 与主库配对状态

| 配对情况 | 说明 |
|---|---|
| 有主库、有 WAL | 正常测试残留（如 `agg.db` + `agg.db-wal`） |
| 只有 WAL、无主库 | `smoke.db-wal`、`probe_idx.db-wal`、`probe_conc.db-wal`、`vec_bench.db-wal`（主库是同名但文件名不匹配的 `vec_bench.db`） |
| 只有主库、无 WAL | 多数测试库（测试结束 `remove()` 了 WAL） |
| `-clog` 存在 | 事务日志，与主库同生命周期 |

⚠️ **单独删除某个 `.db-wal` 会破坏对应库的可恢复性**。因此任何清理都必须按「主库 + WAL + CLG」成组进行，不能按扩展名批量删。

## 五、结论

1. **不存在需要迁移的用户数据。** 全部 575.4 MB 位于被 Git 忽略的测试目录，按文件名、页类型、mtime、以及「源码字面量 vs 未溯源」交叉比对，归属测试/基准/探针/手工调试产物。
2. **可重建性证据强度不一**：A 类（185.8 MB）可直接由源码路径宏重建；B 类（99.2 MB）可由 `vec_bench` 指定参数重建（注意其随机数是固定种子 `0x243F6A8885A308D3`，见 `bench/vec_bench_util.c:21`，因此可复现）；C 类（290.4 MB）多数**不可由当前源码重建**，因为它们来自已不存在的历史路径或一次性手工调试——删除即丢失，但丢失的内容本身无业务价值。
3. **这不构成删除授权。** 本报告只证明「没有业务数据」，不代表可以清理。清理 `test/tmp/` 是独立的破坏性动作，须用户单独批准，并在批准前决定是否需要先留一份文件清单/校验和存档。
