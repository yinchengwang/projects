# C5.3b-b：`PT_JSON_OVF` 页链所有权与 MVCC 生命周期设计

**日期**：2026-11-24
**状态**：待审阅
**关联计划**：`docs/superpowers/plans/2026-11-18-eight-modality-symmetry.md` 的 C5.3b-b
**内核位置**：`engine/db`
**前置**：`docs/superpowers/specs/2026-11-23-json-column-long-literal-design.md`（JSON 列长文档往返）

## 1. 为什么现在写这份设计

C5.3b-a 已经让 256–2048 字节的 JSON 文档能完整往返。但 **>2048 字节的 JSON 仍然被拒绝**，
错误是"文本无效或超过允许的长度"。

拒绝是当前的安全状态：超过 `JSON_INLINE_MAX`（2048）的文档没有合规的落盘位置。
`modalities/doc/json_ovf.c` 里有一套页链读写（`json_ovf_write/read/free`），但它**没有接入任何
生命周期**：

| 现状 | 位置 | 后果 |
|---|---|---|
| 页链写进 Pager 但**不写 WAL** | `json_ovf.c:93`（坑 M7-33） | 崩溃后"链写了一半"，读侧报 `E_CORRUPT` |
| 没有 tuple 持有链的引用 | `json_ovf.c` 全文 | 没人知道哪条链归哪个 tuple |
| abort / VACUUM 不碰链 | `txn/vacuum.c` 只处理 heap slot | 链页永远不回收，或被提前释放 |
| `json_ovf_read` 两趟 walk 无快照 | `json_ovf.h:165` | VACUUM 在两趟之间释放链 ⇒ 读到已释放页 |

**直接把 `json_ovf_write` 塞进 `val_to_record` 或 `heap_am_insert` 会制造静默数据损坏**：
链页泄漏、崩溃后半个文档、或者老快照读到已释放页。所以本步先定协议，不写代码。

### 1.1 已知会踩的坑（编号沿用 `MODALITIES.md`）

- **M7-33**：页链没有 WAL 钩子。
- **M7-34**：`JSON_INLINE_MAX`（2048）大于 `DbValue` 内联上限（255）——
  256..2048 的文档按阈值算"内联"，但值层 `s[]` 装不下。
  C5.3b-a 已经裁决：**256..2048 用运行时外部值中转**（不落页链），
  **>2048 才走页链**。本设计沿用这个裁决。

## 2. 范围

### 2.1 本设计覆盖

1. tuple 内 overflow tag、链首页号、长度的**持久化格式**。
2. 链的**发布顺序**与 INSERT / UPDATE / 索引失败后的**补偿**。
3. JSON 页链与 **WAL / redo / undo / abort** 的关系。
4. **VACUUM** 回收链的顺序与幂等性（不半释放、不 double-free）。
5. **两趟 detoast** 与并发 VACUUM 的互斥。
6. 启动时的**孤儿链发现**与 `DetoastFn` 的 `u16` 上限语义。

### 2.2 本设计不覆盖

- 路径索引（C5.8）—— 页链读路径要先支持"只读一段"，但那是独立一步。
- TEXT 列的长值落点 —— 另见 `2026-11-24-text-long-value-assessment.md`。
- 页链的**压缩**（页内去重）—— 一条链独占，不共享，不去重。

## 3. 已裁决的前提（用户确认，2026-11-24）

| 决策 | 结论 |
|---|---|
| 链的归属 | **每个 heap tuple 版本独占一条页链** |
| WAL 策略 | **页镜像**（`LOG_PAGEDATA`），复用现有 redo/undo 机制 |
| 释放时机 | **只在 VACUUM 物理删除 tuple 之后** |
| 两趟读取的并发 | **长度写在 tuple 里** + 读/释放互斥 |
| 长度上限 | **保留 `u16` 的 65535 字节** |
| 本轮产出 | **只写设计文档，不写代码** |

## 4. 持久化格式

### 4.1 tuple 里的溢出标记

JSON 变量长列在 record 里存的是 **JSONB 字节**（不是 JSON 文本）。
需要区分两种形态：

```
记录变长区（JSON 列）
├── 长度 ≤ JSON_INLINE_MAX(2048) ⇒ 直接存 JSONB 字节（当前 C5.3b-a 的做法）
└── 长度 > JSON_INLINE_MAX(2048) ⇒ 存**溢出标记**，不是 JSONB 字节
```

溢出标记的布局（12 字节，固定，紧跟在 JSONB 长度之后）：

```
偏移  大小  含义
0     4     tag：0x4A534F56（"JSOV"）
4     4     chain_head：页链首页页号（u32）
                  0 = PAGE_ID_NIL ⇒ 非法（空文档也有明确的链，见坑 M7-32）
8     4     chain_len：链里的 JSONB 字节数（u32，见 §4.2）
```

⚠️ **为什么标记要显式带 tag**：变长区里必须能区分"这是 JSONB 字节"和"这是溢出标记"——
两者的第一个字节都可能是任意值。隐式约定（"长度 > 2048 就是标记"）不可行：
`json_ovf_write` 写出的长度是**解码后**的 JSONB 长度，而 record 里存的也是 JSONB 长度，
所以"长度 > 2048 ⇒ 是标记"这条规则**成立**，但它依赖一个跨层的隐式契约。
显式 tag 更稳：读侧先看 tag，对不上就当 JSONB 字节处理。

⚠️ **溢出标记与 chain_len 的关系**：溢出标记固定 12 字节 ⇒ 读侧看到 tag 就知道
后面还有 8 字节的 chain_head 与 chain_len。**没有"变长标记"** ——
所有溢出标记一样长 ⇒ 偏移计算简单。


### 4.2 链的总长度：写在 tuple 的哪一处

**关键决策**：链的总长度（JSONB 字节数）**写在 tuple 的溢出标记之后**，即变长区里：

```
变长区布局（T_JSON 列，长度 > 2048）
┌──────────────┬──────────────┬──────────────┐
│ 溢出标记 8B  │ 长度 u32 4B  │ 预留 4B     │
│ tag + head   │ chain_len    │ （未来用）   │
└──────────────┴──────────────┴──────────────┘
```

**为什么长度必须持久化**（而不是每次读时 walk 一遍量）：
`json_ovf_read` 是两趟 walk（先问长度、再拷内容），**两趟之间如果 VACUUM 释放了链，
就会读到已释放页**。把长度持久化后：

- 读路径变成**一趟**：从 tuple 拿到长度 → 按长度分配缓冲 → 一次读完整条链。
- 不再需要在读路径上做任何"链级快照"。

**代价**：tuple 多占 4 字节。**收益**：读路径从两趟变一趟，且消除了一整类竞态。

⚠️ `DetoastFn` 的 `u16` 上限（65535）决定了 `chain_len` 的取值范围也是 65535。
超过就报错（见 §10）。

⚠️ **长度有两份存储**：tuple 里的 `chain_len`（持久化，权威）
与运行时 `DbValue.ext_off`（副本，传参用）。
**谁是权威见 §9.1b** —— 简单说：tuple 是权威，`ext_off` 只是副本。

⚠️ **溢出标记为什么是 12 字节而不是 8**：
`tag(4) + chain_head(4) + chain_len(4)` = 12 字节。
本文档前面画的图里"预留 4B"是早期草稿 —— **长度就放在那 4 字节里**，
不需要预留。最终布局：

```
变长区布局（T_JSON 列，JSONB 长度 > 2048）
┌───────────────┬───────────────┬───────────────┐
│ 溢出标记 4B   │ chain_head 4B │ chain_len 4B  │
│ tag           │ 链首页页号     │ 链的 JSONB 长度 │
└───────────────┴───────────────┴───────────────┘
共 12 字节
```


### 4.3 页链自身的页内布局

`json_ovf.h` 已定义（现状不变）：

```
JSON_OVF_HDR_OFF = 20        （页头之后）
JSON_OVF_NEXT_OFF = 20       u32 next：下一页页号；PAGE_ID_NIL = 末页
JSON_OVF_LEN_OFF  = 24       u32 payload_len：本页载荷字节数
JSON_OVF_DATA_OFF = 28       载荷起点
JSON_OVF_PAY_CAP  = 4068     每页容量
```

链的首页由 tuple 记着；链内的 `next` 串起后续页。

## 5. 发布顺序与补偿

### 5.1 INSERT 的顺序

```
1. 编码 JSON 文本 → JSONB 字节（doc 模态，超 2048 允许）
2. json_ovf_write(pager, jsonb, len, &chain_head)
   └─ 页链建好，但**还没人引用它**
3. 把溢出标记 + chain_len 写进 record
4. heap_am_insert（record 编码 + 写页 + WAL）
5. 成功 ⇒ 链归这个 tuple 版本所有
```

**关键**：步骤 2 在步骤 4 之前。所以**存在一个"链已建、tuple 还没写"的窗口**。

### 5.2 失败补偿

| 失败点 | 补偿 |
|---|---|
| 步骤 2 失败（`json_ovf_write` 内部） | `json_ovf_write` 自己回收已建的部分链（`json_ovf.h:149` 已承诺） |
| 步骤 3 失败（record 编码装不下） | `json_ovf_free(pager, chain_head)` |
| 步骤 4 失败（heap_am_insert 失败） | `json_ovf_free(pager, chain_head)` |

⚠️ **补偿必须幂等**：`json_ovf_free` 之后要把 `chain_head` 置 `PAGE_ID_NIL`，
避免二次释放。

⚠️ **补偿与 WAL 的交互**：如果链页已经写过 WAL（步骤 2 里写了），
而 tuple 没写成功，那么 WAL 里有一条"链存在"的记录但没有对应的 tuple。
→ 这正是 §8 的**孤儿链**，启动时必须能发现并回收。

### 5.3 UPDATE 的顺序

MVCC 更新是"打 xmax + 插新版本"（`heap_am.c` 的两段式）：

```
1. 编码新 JSONB
2. json_ovf_write → 新链（chain_head_new）
3. record 编码新版本（带新链的溢出标记）
4. heap_am.update → 旧版本打 xmax，新版本插入
5. 旧版本的链**不动**（老快照可能还在读它）
```

⚠️ **UPDATE 不释放旧链**。旧 tuple 版本在 VACUUM 物理删除它时才释放链（§6）。

### 5.4 索引失败

`heap_am_insert` 末尾会 `index_insert_row`（`heap_am.c:309`）。
索引失败时整个 insert 失败 ⇒ 走 §5.2 的补偿路径。

⚠️ **但索引已经写了怎么办**：索引项写了一半，链也补偿了。
索引项指向一个不存在的 RID —— 无害（扫描时 RID 不存在就被过滤掉），
且索引不写日志、重开会重建。

## 6. WAL / redo / undo / abort

### 6.1 WAL 策略：页镜像

**决策**：页链的每个页都用 `LOG_PAGEDATA`（整页镜像）写日志，
和元数据页一个待遇（`loghook.h:37`）。

**为什么不用逻辑记录**（FT tombstone 那套）：
逻辑记录需要新增 redo 与 undo 两条路径，而页镜像**完全复用**现有的
`recovery_run` 机制 —— 页镜像的 redo 是"把镜像盖回页里"，
undo 是"把前像盖回去"，都已经实现且被测过。

**代价**：日志体积。1MB 文档 = 256 页 = 256 条 4KB 镜像 = 1MB 日志。
**这是可接受的**：大文档本来就大，且页镜像是页边界的天然单位
（页是 WAL 的原子单位，不跨页）。

⚠️ **页镜像的前像问题**：`LOG_PAGEDATA` 的 before/after 都是整页。
链页是新分配的 ⇒ before 是"未初始化"（全 0），after 是写好的内容。
undo 时把 before 盖回去 ⇒ 页变回全 0 ⇒ **链被撤销**。

✅ **已核实：`pager_alloc` 会 `memset((*out)->data, 0, PAGE_SIZE)`**
（`storage/pager.c:520`）—— 即使是**复用**的空闲页也会被清零。
⇒ 链页的 before 镜像**确实是全 0**，undo 语义成立：
undo 链页 = 把页还原成"未初始化"，等价于撤销这条链。

⚠️ **但这只对"新建页"成立**：链页的 `next` 回填（§6.5）是对
**同一页的第二次修改**，那时它的 before 镜像是"载荷 + next=NIL"，
不是全 0 ⇒ undo 会把它还原成"载荷 + next=NIL"，
即**链的第一页存在但后面断了** —— 读侧会报 `E_CORRUPT`（不是错数据，但链废了）。

⇒ **这正是 §6.5 建议"先分配全部页再写内容"的原因**：
每页只写一次日志 ⇒ before 永远是全 0 ⇒ undo 语义干净。


### 6.2 redo（崩溃恢复）

页镜像 redo = 把镜像盖回页里。链页的页头（`PT_JSON_OVF`）和 `next` 指针都在镜像里
⇒ redo 后链完整。

⚠️ **redo 的幂等性**：靠页头的 `page_lsn` 判断（页 LSN ≤ 已落盘日志 LSN 则跳过）。
现有机制已经处理。

### 6.3 undo（回滚未提交事务）

undo 把前像（全 0）盖回页 ⇒ 链页变成"未初始化"。
但**页还在文件里**（页分配器不知道它该被释放）⇒ 变成孤儿页。

⚠️ **孤儿页的处理**：见 §8。

### 6.4 abort（运行时事务中止）

运行时 abort（用户按 Ctrl-C 或语句失败回滚）与崩溃 undo 不同：
运行时**知道**哪些链是本事务建的，可以主动释放。

**决策**：**运行时 abort 不主动释放链**。

理由：abort 时链页已经写进文件、也写了 WAL。若此时释放（把页还给分配器），
而 WAL 里还留着这些页的镜像 ⇒ 崩溃后 redo 会把镜像盖回一个**已被重新分配**的页
⇒ 破坏别人的数据。

⇒ **运行时 abort 也把链留成孤儿**，由 §8 的启动扫描回收。

**代价**：abort 过的链页要等到下次重启才被回收（空间浪费）。
**收益**：不用维护"本事务建了哪些链"的清单（那个清单本身在崩溃时会丢，
正是问题所在）。

⚠️ **这是一条重要的取舍**：选择"宁可浪费空间，不可破坏数据"。
替代方案（abort 时释放 + WAL 里记"页已释放"）需要 WAL 支持页释放记录，
且 undo 时要区分"页被释放"和"页被改写"—— 复杂度高得多。

### 6.5 谁来写 WAL

`json_ovf_write` 现在直接改 Pager 页（不写 WAL，坑 M7-33）。
本设计要求它**接受一个 `LogHookFn`**：

```c
int json_ovf_write(Pager *pg, LogHookFn log_hook, void *log_ctx,
                    u32 xid, const u8 *data, u32 len, u64 *ext_key_out);
```

⚠️ **分层问题**：`LogHookFn` 在 `common/loghook.h`（L0），`json_ovf.c` 在
`modalities/doc/`（L4）。L4 include L0 是允许的 ✓（只依赖 L0，不依赖 L1/L2/L3）。

⚠️ **xid 必须显式传**：`loghook.h:49` 明确警告过"xid 藏在共享对象里会串号"。
`json_ovf_write` 的 xid 由调用方（执行层）传进来。

⚠️ **写日志必须在改页之前**（`loghook.h:22` 的硬要求）：
`json_ovf_write` 现在是"分配页 → 填内容 → unpin"，要改成
"分配页 → **写日志** → 填内容 → 写页 LSN → unpin"。
先改页再写日志的话，崩溃后日志里缺这条记录、页上却已有内容 ⇒ 数据"没根"。

⚠️ **回填 `next` 的那一步也要写日志**：链页 i 的 `next` 字段是在页 i+1 分配之后
才回填的（`json_ovf.c:294`）。所以每个链页实际有**两次**内容变化：
1. 首次写入（载荷 + `next = PAGE_ID_NIL`）
2. 回填 `next`（改成下一页页号）

⇒ 两次都要写 WAL，否则 redo 后链会在第一页就断掉。

**简化建议**：改成"**先把整条链的页号算出来再写内容**"——
先分配全部页（拿到所有页号），再逐页写"载荷 + 最终 next"。
这样每页只写一次日志、只改一次。代价是要多记一份页号数组
（链最长 65535/4068 ≈ 17 页，一个 17 项的 u32 数组就够）。

⚠️ **与 heap 层的一致性**：`heap_insert` 自己写 slot 级的 WAL 记录
（`heap_am_insert` 调 `heap_insert`，后者内部调 `heap_wal_log`）。
页链的 WAL 由 `json_ovf_write` 自己写 —— 两者都写**不同的页**，
不冲突：WAL 规则只看"页 LSN ≤ 已落盘日志 LSN"，各页各管各的。

## 7. VACUUM 回收

### 7.1 顺序

`vacuum_table` 现在只做"标记 slot 删除 + 页内 compact"。本设计要求：

```
vacuum 一张表：
  for each 死版本（对所有活跃快照不可见）：
    1. 先读出该 tuple 的溢出标记（若有）
    2. 标记 slot 删除（page_delete）
    3. 把链页还给页分配器（json_ovf_free）
```

⚠️ **顺序很重要**：**先读标记，再删 slot，最后释放链**。
反过来（先删 slot 再读标记）就拿不到链首页了。

### 7.2 互斥：读 vs 释放

**决策**：**释放链时拿表级锁**，与读路径互斥。

理由：链的长度已经持久化在 tuple 里（§4.2），读路径是**一趟**读完整条链。
只要"释放"不会与"读"并发发生，就不需要链级引用计数。

⚠️ **具体机制**：heap 层已经有页 latch 机制。释放链时要确保
**没有读者正在读这条链的任何一页**。

⚠️ **这个约束必须落在哪一层**：不能只写在注释里。
`json_ovf_free` 的契约要写明"调用方必须确保没有读者"，并且
**执行层的 VACUUM 路径必须持有对应的锁**。

### 7.3 幂等性

**要求**：VACUUM 中途崩溃后重跑，不能半释放 / double-free。

**机制**：
- 释放是**逐页**的（`json_ovf_free` 走一遍链，把每页还给分配器）。
- 中途崩溃 ⇒ 部分页已还、部分页还在。
- 重跑时：链头已经在 tuple 里被标记删除（slot 是死的）⇒ 重跑会再走一遍
  `json_ovf_free` ⇒ **重复还页**。

⚠️ **这是一个真实的问题**。解决方式：
**把"链已释放"标记在 tuple 里** —— 释放成功后，把溢出标记的 tag 改成
`0x46524545`（"FREE"），重跑时看到 FREE 标记就跳过。

或者更简单：**先释放链、再删 slot**。这样崩溃后 slot 还活着 ⇒ 重跑会重来一遍 ⇒
但链已经被释放过一次 ⇒ 同样 double-free。

⇒ **结论：必须在 tuple 里留"已释放"标记。** 见 §7.4。

### 7.4 释放的状态机

tuple 的溢出标记（12 字节，见 §4.1）有三种状态：

| tag | 含义 | 动作 |
|---|---|---|
| `0x4A534F56`（JSOV） | 链活着，归这个 tuple 所有 | 读时走链；VACUUM 时释放并改 tag |
| `0x46524545`（FREE） | 链**已释放**（tuple 还没物理删掉） | 读时当作"空文档"；VACUUM 跳过 |
| 无溢出标记 | 普通内联 JSONB | 不适用 |

⚠️ **改 tag 会改 tuple ⇒ 必须写 WAL**。
释放链之后把 tag 从 JSOV 改成 FREE，这个修改本身要写进日志
（页镜像，tuple 所在的那个 heap 页），否则崩溃后重跑会看到旧 tag（JSOV）
⇒ 又释放一次 ⇒ double-free。

⇒ **释放链的顺序必须是**：
1. 释放链页（`json_ovf_free`）
2. 把 tuple 的 tag 改成 FREE（**写 WAL**）
3. 删除 slot

⚠️ **第 1 步和第 2 步之间崩溃**：链已释放但 tag 还是 JSOV
⇒ 重跑会再释放一次 ⇒ double-free。

⇒ **这说明"改 tag 再删 slot"也不够** —— 需要更强的幂等保证。

**最终方案**：把顺序改成
1. 释放链页（`json_ovf_free`）
2. 把 tag 改成 FREE（写 WAL）
3. 删除 slot

并且**接受第 1、2 步之间的窗口**，用**页分配器的幂等性**兜底：
`json_ovf_free` 释放页时，走一遍链把每页还给分配器；
如果链页已经被释放过（页头不再是 `PT_JSON_OVF`），`json_ovf_free` 要能识别并跳过。

⇒ **要求 `json_ovf_free` 本身幂等**：重复释放同一条链不崩、不重复还页。
判据：页头类型不是 `PT_JSON_OVF` ⇒ 说明这页已经释放过 ⇒ 跳过。

⚠️ **这个幂等性必须显式实现并测试**，不能靠"理论上不会重复调用"。
崩溃窗口是真实存在的（VACUUM 是个长事务，中途崩溃很常见）。

⚠️ **FREE 状态下的读**：这条 tuple 是死版本，正常查询不该读到它
（可见性过滤会挡掉）。但如果读到了（极端情况），
必须返回"文档不存在"而不是去读一条已被释放的链。


## 8. 启动时的孤儿链发现

崩溃可能留下三类孤儿：

| 类型 | 现象 | 回收方式 |
|---|---|---|
| A. 链建了、tuple 没写成（§5.2 窗口） | 链页在文件里，页头是 `PT_JSON_OVF`，但没有任何 tuple 引用它 | 启动扫描发现后释放 |
| B. abort 后留下的链（§6.4） | 同上 | 同上 |
| C. undo 后的链页（§6.3） | 页被前像（全 0）盖回，但页**已被分配器记为在用** | 同上（页头不是 `PT_JSON_OVF` 了，但类型字段仍是） |

**启动扫描算法**（`json_ovf` 提供，db 层在 catalog 打开后调用）：

```
1. 遍历所有页，找出页头类型 == PT_JSON_OVF 的页
2. 对每条链（首页 = 该页，且没有被另一条链的 next 指向），
   检查"有没有活跃 tuple 引用它的链首页"
3. 没有 ⇒ 孤儿 ⇒ json_ovf_free
```

⚠️ **步骤 2 的实现难点**：要知道"有没有 tuple 引用"，得扫所有表的所有 tuple。
这在启动时是可行的（catalog 已打开，表都在），但**成本**要评估：
O(页数 + tuple 数)。

⚠️ **一个更省的办法**：不扫 tuple，而是**扫页**。
链页的页头里有 `next` 指针 ⇒ 可以从所有 `PT_JSON_OVF` 页出发，
沿着 `next` 走一遍，标出"被到达过的页"。剩下的 `PT_JSON_OVF` 页就是孤儿。
但这只能发现**整条链都是孤儿**的情况，**发现不了"链的一部分是孤儿"**
（首页被引用、后续页是孤儿的混合情况）。

⇒ **决定：扫 tuple**（准确），接受启动时的 O(tuple 数) 开销。
这条路径只在启动时跑一次，且只在**有 JSON 页链的库**上跑
（没有 `PT_JSON_OVF` 页就直接跳过）。

⚠️ **回收孤儿必须是幂等的**：孤儿扫描可能与运行中的 VACUUM 撞上。
启动时只有一个连接，不会有并发 VACUUM ⇒ 幂等要求可以放宽到"启动时不做"。

## 9. 两趟 detoast 与并发

### 9.1 读路径的新形态

```
val_detoast(外部 JSON 值)
  └─ json_ovf_detoast(ctx, key, off, buf, cap, len_out)
       ├─ 第一趟（buf == NULL）：返回链总长度
       │    └─ 长度从哪来？**从 ext_off 拿，不走 walk**
       └─ 第二趟（buf != NULL）：按长度一次读完整条链
```

⚠️ **关键**：长度不再靠 walk 得到。但 `DetoastFn` 的契约是"两次调用，
第一次问长度"—— 所以 `json_ovf_detoast` 必须能拿到长度。

**决策**：外部 JSON 值的 `ext_off` 字段**存链的总长度**（而不是 0）。
`json_ovf_detoast` 收到 `off` 就是长度，不必 walk。

这与 blob/vector 的"off = 0"口径不同，但 `DetoastFn` 的契约本来就允许
off 带信息（`val_mem_detoast` 就把 off 当长度用）。

⇒ **不需要改 `DetoastFn` 契约**，只是 json 这一族用 off 的方式不同。
**必须写进 `json_ovf.h` 的契约注释**，否则后人会按 blob 的口径理解。

### 9.1b 长度的唯一权威：`ext_off` 还是 tuple 里的 `chain_len`

⚠️ **这两处存的是同一个数，必须定死谁是权威，否则会漂移。**

**决策**：**tuple 里的 `chain_len` 是权威**，`ext_off` 是它的**副本**。

理由：
- tuple 是**持久化**的 —— 崩溃后从磁盘读回来的 tuple 带着 `chain_len`，
  它是"这条链有多长"的事实来源。
- `ext_off` 只是**运行时** `DbValue` 里的一个字段，是从 tuple 读出来时
  顺手填的缓存。

⇒ **填充规则**：从 record 解出 JSON 外部值时，
`ext_off = tuple 里的 chain_len`，两者必须相等。

⚠️ **读侧不校验**：如果两者不等，说明有 bug。
但**不要在读路径上做校验并报错** —— 那是把一个内部 bug 变成用户可见的错误。
正确做法是：tuple 的 `chain_len` 是权威，读路径**只用它**，
`ext_off` 仅作为 `DetoastFn` 的传参通道。

⚠️ **写侧要校验**：写 tuple 时，`chain_len` 必须等于实际写进链的字节数。
不等就是 bug ⇒ 在写路径上断言（测试里断言，不在生产路径上做昂贵检查）。


### 9.2 并发读 vs VACUUM 释放

见 §7.2：**释放时拿表级锁，与读互斥**。

读路径拿到的是**已释放的页**时怎么办？
→ 释放前必须确保无读者；若有读者，释放必须等。
⇒ 这就是"读 vs 释放互斥"要保证的事。

⚠️ **具体怎么互斥**：heap 层的 latch 是**页级**的。
链跨多页 ⇒ 需要一次持有多个页的 latch，或者引入表级 latch。
**这一点需要在实施时定** —— 设计文档先记下约束。

## 10. `DetoastFn` 的 `u16` 上限语义

**决策**：**保留 65535 字节上限**，并把它变成公开契约。

- `chain_len` 是 u32（持久化在 tuple 里），但**超过 65535 直接拒绝**。
- 理由：读路径的 `len_out` 是 `u16`；两趟读取的长度必须装得下。
- 错误：`E_NOSPACE`，错误文本说明上限。

⇒ **一个 JSON 文档最大 65535 字节**（约 64KB）。
超过就是明确的错误，不是静默截断。

⚠️ **这是产品限制**，不是实现偷懒。64KB 的文档对绝大多数用例够用；
真要更大，需要改 `DetoastFn` 契约（u16 → u32），那会波及
blob / vector / FT / JSON 四个族 —— 另开一步。

## 11. 错误语义汇总

| 情形 | 返回 | 附加要求 |
|---|---|---|
| 文档 > 2048B（写入时） | 走页链，不报错 | ≤65535B |
| 文档 > 65535B | `E_NOSPACE` | 错误文本写明上限 |
| 链页分配失败 | `E_IO` | 已建的部分链由 `json_ovf_write` 回收 |
| tuple 写失败 | `E_IO` | 调用方 `json_ovf_free` 补偿 |
| 读到半个链（页内容损坏） | `E_CORRUPT` | 绝不返回半个文档 |
| 读到已释放的链 | `E_CORRUPT` | 绝不返回脏数据 |
| 孤儿链扫描失败 | 不阻塞开库 | 只是空间浪费，下次再扫 |

## 13. 未决与风险

1. **读/释放互斥的具体机制未定**（§9.2）。页级 latch 跨多页不够用，
   需要在实施时确定是"表级 latch"还是"一次锁住整条链的页"。
2. **孤儿扫描的成本**：O(页数 + tuple 数)。大库上启动会变慢。
   需要实测，必要时加"上次扫描水位"优化。
3. **页镜像的日志体积**：大文档产生大量 4KB 镜像。
   如果实测不可接受，退路是给页链设计专门的逻辑记录类型（更复杂）。
4. **页镜像的 before 语义已核实但有个前提**：`pager_alloc` 会清零整页
   （`pager.c:520`），所以"新建链页的 before = 全 0"成立。
   **但前提是每页只写一次日志** —— 一旦 `next` 回填造成第二次修改，
   before 就不是全 0 了（§6.1）。⇒ §6.5 的"先分配全部页再写内容"
   不是优化，是**正确性要求**。
5. **本设计未经实现验证**：所有页链交互的细节（尤其 §6 与 §7）都可能在实施时
   发现矛盾。实施计划应先做最小可跑路径（写链 + 读回 + 崩溃恢复），再补并发与回收。
