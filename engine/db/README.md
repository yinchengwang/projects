# db

一个用 C 从零写的多模数据库。目标不是替代谁，而是把八个模态的机制亲手实现一遍。

## 七条硬规则

**1. 依赖只能向上。** `make deps` 会跑检查脚本，越界直接报错。这条纪律比任何架构文档都管用——它在你手滑的那一刻拦住你。

**2. 头文件与实现同置，不放 `include/`。** 只有 `include/db.h` 是公共 API。把所有内部 `.h` 塞进 `include/` 会制造"这些都是公共接口"的假象，改一个内部结构就得动公共目录。

**3. 模态之间不许互相 include。** 这条决定三年后还能不能加第 9 个模态。模态之间只能通过 `spi/` 里的接口交互。

**4. 单文件不超过 800 行。** 超了就拆。⚠️ **v1.2 步骤 7 已拆完**：`btree.c` 1294 → 325 行（拆成页 / 搜索 / 插入 / 删除 / 游标 5 块），`catalog.c` 1036 → 538 行（拆成加载 / 写入 2 块）。✅ **v1.3 步骤 0 把剩下三处也拆了**：`src/storage/heap.c` 1081 → **614 行**、`src/storage/pager.c` 1002 → **609 行**、`src/db.c` 888 → **679 行**（拆成 `db.c` / `db_result.c` / `db_instance.c`）—— 超 800 行的欠账**已清零**。

**5. 任何"当前是谁"的信息都不能藏在共享对象里。** v0.7 加的这条，代价是所有写接口都带一个 `u32 xid` 参数 —— 但它挡掉的是**静默的数据损坏**。

```c
/* 错：xid 存在共享的 WAL 对象上 */
wal_set_xid(w, xid);            /* 已删除 */
/* 对：显式传 */
wal_append_xid(w, type, xid, page_id, ...);
heap_insert(h, xid, rec, len, &rid);
```

WAL / catalog / heap 都是实例级共享的（所有连接一个日志文件）。
两个连接各设一次 xid，后者会覆盖前者 → A 的日志带上 B 的 xid
→ 恢复时 **A 的未提交数据被判为已提交**。

推广：undo 链（`prev_lsn`）也是共享状态，所以按 xid 分槽维护。

**6. 模态各自管自己的元数据和页。** v0.8 加的这条，是第 3 条的落地。

blob 模态有自己的对象目录，**不复用关系模态的 catalog**。
反过来 catalog 也不该知道 blob 的存在。

同理，blob 的页**不进任何表的 freelist** ——
表的 freelist 回答"哪一页能放下 N 字节的行"，
blob 页是"一整页装一帧"，语义不同。混在一起会写坏数据。

**共享的只有底座**：pager（缓冲池）、WAL（崩溃安全）、页格式。

**7. 执行器不许知道模态。** v0.9 加的这条，是第 3 条的另一面。

执行器只认 `StorageAM` 接口。模态的知识（schema、可见性、
能不能写、能不能下推）全在 `spi/` 里。

```c
/* 对：执行器问接口 */
if (!tc->am->visible(tc->am, buf, len, &vis))
    continue;

/* 错：执行器里出现模态的名字 */
if (strcmp(st->table, "blob_frames") == 0) { ... }
```

验收方式是机械的：`grep blob src/query/exec*.c` 只能命中注释。

**为什么这条重要**：第 3 条防的是"模态之间互相依赖"，
这条防的是"执行器变成模态的堆积场"。
只有执行器真的模态无关，第 9 个模态才是"多写一个 .c 文件"。

**8. 每条入口路径都要加锁。** v0.10 加的这条。

实例级共享的状态（缓冲池、freelist、WAL、事务表、catalog、blob 目录）
**只有一个全局 latch** 保护 —— 锁画在语句边界上：

```c
db_exec(sql):
    latch_lock();
      解析 → 执行 → 结果构造
    latch_unlock();
```

**为什么是语句级大锁而不是更细的锁**：
当前的读接口返回**指向共享内存的指针**（`catalog_table_cols` 返回内部数组、
`pager_get` 返回缓冲池页），锁只能覆盖"取指针"那一刻，
取回去之后照样会被别人改 → 悬空指针。
要让细粒度锁成立，所有读接口都得改成返回**拷贝**（copy-out）——
那是另一个任务，不能和"引入锁"混在一起。

**每条入口路径都要自己加锁**，因为有的路径**不走 `db_exec`**：

```c
/* blob 的公开 API 有自己的入口 → 必须各自加锁 */
db_blob_create()  { latch_lock(); ... latch_unlock(); }
db_blob_write()   { latch_lock(); ... latch_unlock(); }
/* 8 个 API 全部如此 */
```

只锁 `db_exec` 等于**blob 裸奔**。
新增一条入口路径时，先问一句：**它加锁了吗？**

**只有一把锁 = 不可能死锁** —— 没有锁顺序问题。
细粒度化（多把锁）才会重新引入这个问题，那时才需要定顺序规则。

## 图模态（v0.11）

模态 2：**定长记录 + 双向邻接链**（对齐 Neo4j 的记录布局）。

### 一句话概括它证明了什么

blob 验证了 SPI 的"读 + 能力协商 + 虚拟表"路径；
图验证的是**另一半**：高频随机点查（`get` by RID）+ 定长写路径。

blob 一帧独占一页、对象不可变；图是**一页几十个节点、就地更新** ——
两种相反的访问形态。SPI 如果撑得住，设计才算真正站住。

**结论**：执行器一行没改（`grep -rn graph src/query/` 零命中）。
加第 2 个模态 = 多写一个适配器 + 多注册两条记录。

### 怎么用

```sql
-- 建图（属性 schema 是图自己的事，不进 catalog）
GRAPH CREATE id:INT4!, name:TEXT(16), score:INT8

-- 两张虚拟表
INSERT INTO graph_nodes VALUES (NULL, 1, 'alice', 100);   -- node_id 由存储层分配
INSERT INTO graph_edges VALUES (393216, 393217);          -- src / dst 是节点 id
SELECT * FROM graph_nodes WHERE score = 100;              -- 属性列自滤
SELECT * FROM graph_edges WHERE src = 393216;             -- 沿邻接链真下推

-- 遍历走 C API（SQL 表达不了递归）
GRAPH NODES / GRAPH EDGES / GRAPH HOP <rid> / GRAPH HOPIN <rid> / GRAPH STAT
```

公开 API（`include/db.h`）：`db_graph_create` / `add_node` / `add_edge` /
`remove_node` / `remove_edge` / `hop` / `hop_in` / `walk` / `get_node` /
`get_edge` / `list_nodes` / `list_edges` / `count` / `schema` / `reads`。

### 三个关键设计

| 决策 | 理由 |
|---|---|
| **定长槽页**（不是 slotted page） | 定长记录的位置纯算术可得，slot 数组纯属浪费一倍空间 |
| **属性 schema 落盘**（第三个 gstore） | 记录里没有"这一列多宽" —— 不落盘 = 重启后整张图读不出来 |
| **锁 + WAL，不做 MVCC** | 图记录可变、邻接链指针要稳定；`visible()` 恒真，写路径 xid 传 0 |

### 怎么证明"真下推"而不是"全扫 + 过滤"

这两种实现**返回的行集完全一样**，光看查询结果验不出来。

所以加了一个可观测量：`GStore.rec_reads`（累计取出的记录条数）。
真下推只读匹配链上的那几条（= 锚点的度数），全扫读了全表每一条。

实测：100 条边、hub 出度 30 → 下推读了 **30** 条，全表 **100** 条。

### 性能（10 万节点 / 100 万边）

| 指标 | 结果 | 目标 |
|---|---|---|
| 3 跳 p50 / p90 | 0.177 / 0.305 ms | — |
| **3 跳 p99** | **0.564 ms** | **< 10 ms** ✓ |
| 3 跳 max | 4.225 ms | — |
| 每次平均读 | 1104 条边 | PLAN 模型 1111 ✓ |

缓冲池的对照（1 万节点 / 10 万边）：

| 缓冲池 | 装载 | p99 |
|---|---|---|
| 256 帧（1MB，默认） | 121 s | 5.39 ms |
| 32768 帧（128MB） | 5.4 s | 0.14 ms |

差 37 倍 —— 不是图慢，是**工作集装不下**。

### pager 调试记录（值得回头看的三课）

- **哈希墓碑死循环**：开放定址 + 墓碑删除，墓碑不回收，写满 1 万页后探测序列遇不到 EMPTY，`hash_find` 挂死。修复：墓碑超容量 1/4 就从 frames 数组重建真值。
- **测试自己的未初始化内存**：`fill_page` 漏写 12..15 字节，写入路径是零、校验路径是栈垃圾，`memcmp` 必失败。定位方法：打印实际字节——16..31 完全一致立刻暴露问题在测试侧。
- **教训**：先隔离"写错还是读错"（绕过 pager 直接读文件），再改代码。

### WAL 调试记录（三个静默出错的 bug）

这三个 bug 的共同点：**都不报错，只是数据悄悄不对了**。

- **bootstrap 被当成未提交事务回滚**：catalog 建表时写的日志 xid=0，
  分析阶段找不到 COMMIT 就全回滚掉 → meta 页的 magic 归零 → `db_open` 报 `E_CORRUPT`。
  修法：xid=0 明确定义为"系统事务"，永远视为已提交。
  验证方式：**临时撤销这一行重跑**，`test_crash` 立刻 12 项失败 —— 证明测试不是假通过。

- **重放时重算 slot，撤销时用日志里的 slot**：重放算出的 slot 和日志记的不一致时，
  undo 会删错行，表现为"数据莫名少一条"。修法：重放必须用日志里的 slot 原地填回
  （新增 `page_insert_at`）。

- **事务号跨会话重置**：每次打开都从 xid=1 开始，上次未提交的 xid=1
  会被这次新的 xid=1 提交记录"连累"，判定成已提交 → 未提交的数据留在库里。
  修法：`wal_max_xid()` 从日志读出最大 xid，作为新会话的起点。

### 一条方法论

**反向验证是必须的。** 上面第一个 bug 我一度以为修好了但测试还是失败，
后来发现是"跑的是旧二进制"（`run.sh` 编译到 `build/test_crash`，
我手动跑的是另一个路径）。

教训：**改完代码先确认测试真的重新编译了**，
然后**故意撤销修复，确认测试会失败**。只有这样才能证明测试有效。

### MVCC 调试记录（四个静默出错的 bug）

v0.7 的 bug 有一个共同特点：**全都不报错，只是结果悄悄不对了**。
而且其中三个**单连接测试全绿** —— 只有多连接才暴露。

- **`in_txn` 双字段不同步**：`db.c` 的 `DB.in_txn` 和 `exec.h` 的 `Db.in_txn`
  是两个独立字段，一个设了另一个没设 → `COMMIT;` 永远报"不在事务中"。
  修法：删掉冗余字段，**同一个语义只能有一个存放处**。

- **WAL 的 xid 是共享状态**：WAL 是实例级共享的，
  `wal_set_xid(w, 5)` 会被另一个连接的 `wal_set_xid(w, 6)` 覆盖
  → A 的日志带上 B 的 xid → 恢复时 A 的未提交数据被判为已提交。
  修法：xid **显式传参**，删掉所有 `*_set_xid` API。
  推广成铁律：**任何"当前是谁"的信息都不能藏在共享对象里**。

- **可见性漏了「区间内但不在 xip」这个分支**：写方**自己都看不见刚提交的数据**。
  根因是我以为这个分支"理论上不该发生"，实际它是**主路径**
  （因为 `snap.xmin` 排除了 `my_xid`，区间把很多已提交事务圈了进去）。
  写成"保守地当作未提交" → **静默丢数据**。
  为什么单连接抓不到：单连接时 `xmin == xmax`，区间是空的。

- **vacuum 把自己算进活跃表**：vacuum 自己就跑在一个事务里，
  于是"还有活跃事务吗"永远是 yes → 死版本永远回收不掉 → vacuum 变成空转语句。
  修法：判断时**排除执行者自己**（`txn_has_active_except`）。
  教训：**"保守"和"失效"是两回事**。前者安全，后者是 bug。

### v0.7 的两条铁律

1. **xid 显式传，不能放共享对象里** —— 共享的对象（WAL / catalog / heap）
   必须让调用方传参。
2. **可见性判断的多连接场景必须专门构造** —— 单连接时快照区间是空的，
   很多分支永远走不到。

### blob 模态调试记录（一个方向性错误 + 两轮反向验证）

- **方案开头就理解错了方向**：我把 blob 理解成「关系模态的 TEXT 太大 → 外置」
  （TOAST 式），连 `storage/overflow.{h,c}` 的接口都写好了。
  读 DESIGN.md 时才发现三条线索都指向另一个答案：
  ① §7 的验收标准是「读 1GB **对象**第 3000 **帧**，IO 量 ≈ 4KB」——
  行外置模型里没有"对象的第 N 帧"这个概念；
  ② §10.4 最后一句明说「一行多个大字段正是 blob 模态要解决的场景，
  **不该让关系模态背这个包袱**」；
  ③ 项目目标是「把八个模态的机制亲手实现一遍」，blob 对标的是
  S3/GridFS/Parquet 的「对象 + 帧 + 随机访问」，不是数据库的大字段。
  **教训：动手写代码之前，先把 DESIGN.md 的验收标准读一遍**——
  验收标准是可测量的结果，比方案文档的措辞更可信。

- **blob_id = 页号 + 1，不是页号**：第一版直接用页号，
  结果首个对象的 id = 0，和「无效 id」无法区分。
  改后 `id = 0` 天然表示无效。
  **但这引出新问题**：页号空间是共享的（表页也占页号），
  所以 `blob_id = 1` 可能指向任何页。
  于是必须区分两种错误：
  「不是 blob 对象」→ `E_NOTFOUND`（正常情况），
  「是 blob 头页但内容坏了」→ `E_CORRUPT`（真损坏）。
  **报 CORRUPT 会把用户误用说成"库坏了"，把排查方向带偏。**

- **blob 不参与事务**：对象不可变（创建→写→定稿），
  没有"回滚到旧版本"，所以 WAL 的 xid 传 0（系统事务，永远视为已提交）。
  但它**写 WAL**，所以崩溃后数据不丢。

- **两轮反向验证**：
  ① 把「纯算术定位」改成「顺着页链逐页找」→ IO 量测试 2 项变红
  （含「浅访问与深访问 IO 相同」这条 —— 这才是 blob 存在的理由）。
  ② 把 blob 的 WAL 写日志去掉 → **崩溃恢复测试 6 条断言变红**。
  这一步最要紧：blob 复用 `WAL_PAGEDATA` 最容易出的错就是
  "页在盘上、日志里没有" → 崩溃后重放不出来 → **静默的数据丢失**，
  而这类 bug 只有模拟崩溃才抓得到。

- **又踩了"跑的是旧二进制"**：注入 bug 后编译报 unused-parameter 错误，
  `run.sh` 链接旧 `.o` → 测试结果完全不可信。
  这是 v0.7 记录过的坑，本轮又踩一次。
  修法：**注入的代码必须能编译通过**，否则就不是在测新代码。
  （`-Werror` 在这里帮了忙 —— 它把"注入没生效"暴露成编译错误，
  而不是让我拿着假结果继续。）

### v0.8 固化的两条纪律

1. **模态之间不许互相依赖** —— blob 有自己的对象目录，
   不复用关系模态的 catalog。反过来 catalog 也不该知道 blob 的存在。
2. **错误码要区分"用户误用"和"数据损坏"** ——
   前者 `E_NOTFOUND`，后者 `E_CORRUPT`。混淆会把排查方向带偏。

### v0.9 固化的三条纪律

1. **SPI 的草图一定会漏东西** —— 写接口的时候，
   脑子里想的是"这个模态要怎么存取数据"，不是"执行器需要什么"。
   对照执行器的实际需要逐条查：schema、解码、可见性、能力、xid。
   **接口不是照着"直觉"写的，是照着调用方的需要写的。**
2. **下推只能给超集，不能给子集** —— 执行器拿到下推的行之后
   仍然完整求值一遍 WHERE。所以下推错了最多是慢，不会是错（除非漏行）。
   **保守的优化是安全的，激进的优化是危险的。**
3. **大值不进值层** —— 塞不进去就换形态（外部引用），
   不要截断，也不要把值类型撑大。值撑大了不会让扫描变便宜，
   只会让每个值都变贵。

### 并发调试记录（一个 v0.8 的遗留 bug + 一个测试自己藏 bug 的例子）

- **★ v0.8 遗留的真 bug：blob_create 头页 pin 泄漏**
  `blob_create` 分配了三样带页的东西 —— 帧页（unpin 了）、
  索引块页（unpin 了）、**头页（忘了）**。
  `blob_alloc_page` 返回的是**被 pin 住的**帧，调用方负责 unpin。
  于是**每建一个对象就泄漏一个 pin** → 256 帧后缓冲池耗尽 →
  `db_blob_create` 报 `E_NOSPACE`。
  **为什么 v0.8 没发现**：单线程测试建的对象少（远少于 256），
  泄漏到测试结束都没撑爆缓冲池。**并发把创建次数放大 4 倍 × 320 次** → 爆了。
  修法：补一句 `pager_unpin(bs->pager, head_pid, true);`，
  加 `test_blob` t11 回归（建 400 个对象 + 断言 `pager_frames_used <= 64`）。
  **教训：资源泄漏在低负载下是不可见的。**

- **测试自己把 bug 藏起来了**：t2（xid 不串号）第一版用**标志**排序 ——
  A 插完 → 才让 B 开始。两个 `BEGIN` 被拉得很开 →
  **xid 分配根本不可能撞车** → 测试永远是绿的 → 什么也没测到。
  修法：改用**屏障**，让两个 `BEGIN` 真正同时发生。
  **教训：并发测试的价值完全取决于它有没有制造出真正的并发。**
  一个"顺序执行但用了线程"的测试比单线程测试更危险 ——
  它给人"已经测过并发了"的错觉。

- **无锁版本会让测试挂死**：缓冲池的哈希表被写坏 →
  `hash_find` 的探测序列永远遇不到 `EMPTY` → 死循环。
  加**看门狗**（120 秒超时 → 打印 FAIL 并 `exit(1)`）。
  看门狗报的"疑似死锁"和断言失败**是同等有效的失败信号**。

- **一轮反向验证暴露了盲区**：把可重入锁改成不可重入 → **没变红**。
  说明当前代码**没有嵌套加锁路径**，可重入性是靠设计保证的，不是靠测试。
  如实记入风险清单。

### v0.10 固化的三条纪律

1. **一把锁就不会死锁** —— 不是"锁得够细所以安全"，
   而是"只有一把锁所以不存在锁顺序"这个结构性保证。
   细粒度化会**重新引入**死锁问题。
2. **锁的边界要覆盖整条路径，不能只覆盖一半** ——
   blob 的 API 不走 `db_exec`，只锁 `db_exec` 等于 blob 裸奔。
   **每加一条新的入口路径，就要问一句：它加锁了吗？**
3. **测试必须真的并发** —— 用线程不等于并发。
   如果同步设计让两个关键操作"错开了"，测试就白写了。

### 图模态调试记录（三个静默出错的 bug + 基准测试抓到的瓶颈 + 两轮反向验证）

- **★ `gr_schema_read` 把游标结束的 `E_EOF` 原样返回**
  `graph_open` 拿到的不是 `E_NOTFOUND`，于是把"这个库还没建过图"
  当成错误 → **`db_open` 直接失败**，库都打不开。
  修法：`E_EOF` → `E_NOTFOUND`。
  **教训：错误码的语义要在产生它的地方就转好。**
  底层返回"流结束了"，上层要的是"没有这个东西" —— 两者不是一回事。

- **★ schema 记录从第 0 字节开始存**
  `gstore_alloc_with` 只拷**载荷区**（跳过 4 字节公共头），
  所以 version / ncols / node_size 这 4 个字节被**静默丢掉**了。
  写的时候不报错，读的时候才发现 version 不对 → 报"数据损坏"。
  修法：schema 的数据放在记录的 `GS_REC_HDR_SIZE` 之后。
  **教训：定长槽页的"载荷从第 4 字节开始"这个约定，
  写新模态的人如果没读那段，就会把它当成"整条记录"。**

- **REPL 的类型扫描没把 `\r` / `\n` 当结束符**
  最后一列的类型被读成 `"INT8\n"` → 建图永远失败。
  教训：解析**行输入**时，结束符不止是空格。

- **★ 基准测试找到了真正的瓶颈：CRC**
  `common/crc.c` 原来是逐位算的（每字节 8 次移位异或）。
  页校验和 4KB = 32768 次位运算，WAL 记录 8KB = 65536 次；
  而加一条边要改 4 个页 → 每条边约 26 万次位运算。
  crc.c 原来的注释写着"等 bench 显示它成为瓶颈再换成查表版" ——
  现在就是那个时候。**换成查表版，装载快 3 倍**（145µs/边 → 48µs/边）。

  换的时候**值一个都不能变**（页校验和在磁盘上，值变了老库全废）。
  所以新加了 `test/unit/test_crc.c`：里面保留一份**逐位参考实现**，
  逐字节比对两者的输出，再加标准检验向量
  （`"123456789"` → crc16 = 0x29B1、crc32 = 0xCBF43926）。
  **把"值不变"从"我相信没变"变成"测过没变"。**

- **两轮反向验证**：
  | 注入 | 变红的测试 |
  |---|---|
  | 摘链时漏改入链的 prev | `test_graph`（A1/A2 双向一致性） |
  | 下推的边枚举漏掉链尾 | `test_graph_am`（下推行数 == 全扫行数）、`test_graph_am_push`、`test_graph_it`（A4） |

  两次都**先确认编译通过再跑**（v0.7 起每次都踩"跑的是旧二进制"的坑），
  撤销后重跑 43 个测试文件全绿（当时；现状 58）。

- **基准跑在"模态层"（不挂 WAL）**：
  加一条边要改 4 个页 = 4 条 WAL 整页镜像 = 32KB 日志，
  100 万条边 ≈ **32GB**。那不是"慢一点"，是磁盘放不下。
  持久化路径由 `test_graph_crash.c` 单独验。
  **这个 32GB 已经记进风险清单** —— 方向是"槽级日志"
  （记 52 字节而不是 4KB）。

### v0.11 固化的三条纪律

1. **凡是"重启后要能解释数据"的东西，都必须落盘** ——
   图的属性 schema 只是"建图时的参数"，看起来像配置；
   但记录的长度由它决定，不落盘就等于图没了。
   **判断标准：重启后还需要它吗？**
2. **磁盘格式的定义只能有一处** ——
   schema 的字段布局写在 `graph_schema.c` 里，不写在调用方的结构体上。
   显式打包（而不是 memcpy 一个 struct）换来的是：
   改结构体不会影响磁盘格式。
3. **"看起来一样"不等于"就是一样"** ——
   `INT4 + INT4` 和 `INT8` 的记录总长一样，布局完全不同。
   比 schema 必须**逐列**比名字、类型、宽度、可空性。

#### 顺带撞出并修掉一个「静默少行」的既有 bug（索引）

10 万行、某列只有 1000 个取值，建索引后 `WHERE val = 900` 只返回 **99** 行（应为 100），
`WHERE val >= 900` 只返回 **9999** 行（应为 10000）—— **不报任何错**。

根因：索引 key 原来只编码**列值**不含 RID，同值多行共用一个 key；
叶子分裂时内部节点的「左子树严格小于 separator」不变式被打破，
查找就会跳过左子树里的同值行。

修法：**复合键「值部分 ‖ RID」**。键唯一后不变式恒成立，**B+tree 本体一行都不用改**。
另修掉「下界落在两棵子树缝隙里时直接返回空集」的第二层缺陷。

**为什么老验收没抓到**：老的索引测试只有 5 行、值全唯一 ——
一个叶子能装约 170 条，5 行**永远不会分裂**，不变式破不了。
**bug 在分裂路径上，不在查找路径上。** 新的回归测试插 2000 行、每值 100 行，
并做**反向验证**：临时退回旧编码 → 测试红 4 项 → 恢复 → 全绿。

#### 存储层三处前提修复（不动 SPI、不动执行器）

| 位置 | 问题 | 改法 |
|---|---|---|
| `storage/value.c` | 每个值都是 272 字节整结构 memset/memcpy（10 万行 ≈ 108 MB） | 只清有意义的小字段；`s[]` 只在文本类型下被读 |
| `storage/record.c` | 每行重算记录布局（O(ncols²)） | 布局提进 `RecLayout`，算一次用一辈子 |

#### 测出来的结论：3× 卡在 SPI 的逐行接口上

改完前提修复后，剩余时间 **81% 在 SPI 的逐行 `scan_next`（38%）+ 逐行 `decode`（43%）**。
证据：把同一行反复解码 10 万次（数据全在 L1）只要 3.1 ms，真扫一遍要 ~7 ms ——
差值是**记录数据的访存**，不是计算。

**=> 不改 SPI，A2 的 3× 不可达（比值上限约 1.2×）。**
按 PLAN §1.6 的 R2：记录数据，**SPI 批接口（批扫描 + 批解码）列入 v1.2**，
与"读接口 copy-out 重构"同一批做。两个批接口都走**能力协商**
（`caps` 位 + 函数指针为 NULL = 不支持），**blob / graph / vector 三个模态零改动**。

| **只把用得上的列放进批** | `SELECT id, grp … WHERE val >= 900` 只需 3 列，TEXT 列连数组都不分配 |
| **三态标记** | bool 装不下 NULL，所以 WHERE 的中间结果是"假/真/空"，AND/OR 查表 |
| **形状不支持就整条退回逐行** | 不做"批内降级" —— 同一份语义只有一处实现，不会分叉（两条路共用 `eval_expr`/`val_cmp`） |

**验收**：47 测试全绿；29 条对拍 SQL **逐格全等** ✓

**但只有 1.13×，不是 3×** —— 原因就是上面那条判定：
列式求值省的是"过滤时逐列 `val_copy`"，而那部分**已经被 `val_copy` 前提修复吃掉了**；
剩下 81% 在逐行 `decode` 的**物化**上（每行 4 个 272 字节的 `DbValue`）——
**向量化真正能省的是物化，而物化在 SPI 的 `decode` 里**。
→ SPI 批接口（不物化 `DbValue`，直接进列数组）已写进 **v1.2 步骤 0** + 验收 A9。

#### 步骤 3（聚合 + GROUP BY）已完成

消化 v0.4 与 v0.3.5 的两个顺延项。新增 `src/query/exec_agg.c`（聚合执行器）与
`src/query/exec_group.{c,h}`（组键编码 + hash 组表），建在列批之上。

| 设计 | 说明 |
|---|---|
| **组键 = 类型字节 ‖ 值** | 类型字节让 INT 1 与 TEXT "1" 不混组；文本加转义 + 终止符（否则 "a" 与 "ab" 会同组） |
| **编码的字节序 == 值的序** | 输出按键排序 → 这条是硬要求；两个独立实现（生产 + 参照）对拍时顺序必须一致 |
| **hash 组表，75% 负载翻倍** | 扩容会换槽位 → 累加器住在组里，跟着组一起搬家 |
| **组数上限 4096，超限明确报错** | 不 spill（另一个数量级的工程）；**静默截断 = 看起来对其实错** |
| **WHERE 两条走法** | 列式能求值就列式；不能就逐行（进批前滤掉）—— 语义只有一处实现 |

**语义对齐 SQLite 3.49.1**：`COUNT/SUM/AVG/MIN/MAX` + GROUP BY；
`AVG` 恒为浮点；`SUM` 全 NULL 出 NULL；无 GROUP BY 恒 1 行；有 GROUP BY 每组 1 行。
**整数求和溢出 → 报错**（SQLite 报 "integer overflow"，PG 报 "bigint out of range"）——
转浮点是**静默丢精度**（…807 + 2 = …809，转 double 变成 …808）。

**验收**：
- 11 项单元测试（内嵌手算期望值，含组数超限 A4）
- **25 条聚合 SQL 与 SQLite 逐格全等**（`test/integration/test_agg_sqlite.c`）
- **25 条聚合 SQL 与逐行参照实现逐格全等**（`bench/exec_agg_ref.c`）
  —— 冻结的火山副本诞生于聚合之前，跑不了聚合查询，所以另立一份参照实现：
  不同的扫描方式（列批 vs 逐行）、不同的分组方式（hash vs 线性）、
  不同的输出排序（编码键字节序 vs `val_cmp` 值序）

#### 步骤 3 顺带撞出并修掉五个既有缺陷（都是"静默给出错结果"）

|---|---|---|

#### 步骤 4（规则 CBO + EXPLAIN）已完成

动手前先发现一个更基础的问题：`sys_table` 的 `nrows_est` 列**从来没被写过**
（写的是 NULL，读出来恒 0）—— 代价模型拿 0 就等于没有代价。

| 设计 | 说明 |
|---|---|
| **统计从哪来** | 写路径增量（INSERT +n / DELETE -n，O(1) 改内存）+ VACUUM 校准并落盘 |
| **为什么不在每次写时落盘** | 每插一行多一次元数据页写 + WAL —— 给"统计"付比业务更高的代价 |
| **为什么原地重写** | `sys_table` 扫描不做可见性过滤，插新版本会让同一张表被登记两次 |
| **代价公式** | `cost_seq = nrows`；`cost_idx = 树高 + sel × nrows × 1.2`；等值 `sel = 1/nrows`，范围 `1/3` |
| **小表规则** | `nrows < 64` 恒全扫（索引的固定开销超过顺序读 64 行） |
| **两层决策** | 门槛 `can_push`（能力）+ 排序 `cost`（代价），缺一不可 |
| **谓词选择** | 从"找到第一个就推"改成"挑选择率最小的"（`a = 1 AND b > 900` 推 `a` 而不是 `b`） |
| **虚拟表不参与** | 模态表没有 catalog 行 → 没有估算 → 不替模态算账，退回老行为 |

**EXPLAIN 与执行共用 `plan_push()`** —— 一份实现两个调用方。
分开写的话迟早分叉，那时 EXPLAIN 说"走索引"、实际走了全扫，用户就再也不信它了。

```
Index Scan on big  (列 val)
  rows_est = 200
  Index Cond: (val = 20)
  Cost: seq = 200.00   idx = 3.20   sel = 0.0050
  Decision: index scan   (cost_idx < cost_seq)
```

**行为变化**：小表不再走索引 → `test_index` 里"用返回顺序证明走索引"的 9 项断言失效。
改成"集合语义用排序比较 + 另建 200 行大表验顺序"。**这是正确的新行为，不是 bug。**

#### 步骤 5（性能验收）：A2 不达标，如实记录

| 指标 | 改造前 | 现在 | 比值 | 目标 |
|---|---|---|---|---|
| 完整查询（10 万行，选择性 10%） | 10.085 ms | 9.099 ms | **1.11×** | ≥ 3× |

**差 2.7 倍。** 分解：`scan 38% / decode 42% / filter 18%` ——
81% 在 SPI 的逐行 `scan_next` + 逐行 `decode` 上，**每行仍要物化 4 个 272 字节的 DbValue**。
向量化与聚合都碰不到这部分。SPI 批接口已列入 v1.2 步骤 0 + 验收 A9。

**1.11× 就是 1.11×，不注水。**

#### 步骤 6（反向验证）：一次"注入不红"的收获

注入 1 是把列式 AND 真值表里的 `(真, 空)` 改成 `假` —— 预期 NULL 语义测试红，**结果不红**。

两层原因：
1. 顶层 WHERE 里"空"和"假"**都是不匹配**，只有 `NOT (...)` 或 `(...) IS NULL` 能区分；
2. 补了 `NOT (id > 0 AND name = 'zzz')` 后**仍不红** —— `name` 是 TEXT，列式不支持文本比较，
   整条退回**逐行路径**；而注入点在**列式路径**。**三值逻辑有两份实现，只测了一份。**

补了三条用例（两条逐行 + 一条列式，`tri` 表带数值 NULL）后注入才红。
**反向验证的价值不是"证明测试有效"，而是暴露盲区。**

### 向量模态（v1.0）

#### 一句话概括它证明了什么

**列式存储 + 图索引能在同一个内核里成立，而且执行器一行不改。**

向量是第三个模态，比前两个多要一样东西：**一个 ANN 索引**（HNSW）——
也就是 Index AM 的第二个实现。

#### 怎么用

```sql
-- 虚拟表：元数据与向量本体分离
SELECT row_id, label FROM vec_items;    -- 一个向量页都不读（向量是外部值）
```

```c
db_vec_create(db, dim, m, efc);
db_vec_insert(db, vec, label, &row_id);
db_vec_knn(db, q, k, ef, hits, &n);                    /* ANN */
db_vec_knn_exact(db, q, k, hits, &n);                 /* 暴力扫 = ground truth */
db_vec_knn_filtered(db, q, k, ef, label, hits, &n);   /* 过滤 + ANN */
```

REPL：`VEC CREATE 128` / `VEC INSERT <v...>` / `VEC KNN <q...> 10` / `VEC STAT`。

#### 三个关键设计
1. **列式** —— 一页 7 个 128 维向量连续排列，寻址是纯算术
   （`row_id / 7` = 第几个数据页，`row_id % 7` = 页内第几个）。
2. **向量是外部值** —— `vec_items` 的一行只有 12 字节
   （`row_id` + `label`），向量本体不进值层。所以查元数据不读向量页。
3. **过滤 + ANN 给超集** —— 候选池扩到 ≥ 4k 再过滤、截断到 k、
   如实报告实际数量（可能 < k）。

#### 性能（10 万 × 128 维，ef=64）

| 数据形态 | 我们 | hnswlib（同一批数据、同样参数） |
|---|---|---|
| 聚簇（接近真实 embedding） | **0.993** | 0.977 |
| 均匀随机（已知最坏情况） | **0.390** | 0.338 |

逐档 ef=16/32/64/128/256/512 对比，**我们每一档都不低于 hnswlib**。

| 项 | 值 |
|---|---|
| ANN 查询页读 | 0（索引常驻内存） |
| 暴力扫一次 | 14286 页（= 10 万 ÷ 每页 7 个） |
| 索引常驻内存 | 93.3 MB（向量副本 48.8 + 图结构上界 44.4） |
| 公开 API 装载 | 1753 条/秒，WAL **19.5 KB/向量** |

#### 两条被数据教育过的判断

**① 均匀随机数据上的 recall 低，是数据性质，不是实现问题。**
PLAN 原来的验收线是"随机向量 recall@10 ≥ 0.95"。实测 0.390，
但 **hnswlib 在同一批数据上只有 0.338** —— 高维均匀向量近乎等距，
"近邻"本身没有明确结构，是图索引的已知最坏情况。这条验收标准因此被修订
（详见 `docs/PLAN-v1.0.md` §3 步骤 6）。

**② 上层导航在 10 万点以内几乎不产生收益。**
实测 5 万 × 128 维，走上层与不走上层的 recall 几乎一样
（ef=64：0.506 / 0.504），工作量只差 0.5%；论文里的 10~100 倍加速
要到更大规模、更小 ef 才显现。所以测试断言的是"**机制在不在**"
（起点有没有被上层挪过），而不是"收益有多大"。


**为什么必须先下沉**（已做）：硬规则 3 禁止模态之间互相 include。
向量模态也要用定长槽页（HNSW 的邻接表节点是定长的 `2 + 2M 个 u32`），
如果 gstore 住在 `modalities/graph/`，向量模态就不能用它 ——
要么复制一份（两份实现必然漂移），要么破例 include。

下沉是**纯搬家**：`gstore` 只依赖 `common/` + `storage/pager`，搬到 `storage/` 后依赖方向不变。
搬完立刻跑 v0.11 全部 43 个测试文件当回归门 —— 全绿（当时；现状 58）。

**执行 v1.0 之前要读的三份**：
1. `docs/PLAN-v1.0.md` — 分步执行计划 + 验收标准
2. `docs/MODALITIES.md` §5 — 向量模态的机制全貌与坑清单
3. 工作区根目录 `向量模态实现规格.html` — 字节级施工图纸

> **记一笔**：v0.11 量到的 WAL 写放大（加一条边 = 32KB 日志，100 万边 ≈ 32GB）
> 同样会卡住向量模态的批量装载。v1.0 开工前应该先决定
> "槽级日志"做不做 —— 不做的话，批量写入永远是图和向量共同的短板。
> **v1.0 步骤 1 的实际做法**：先按原计划把 gstore 下沉（纯搬家，零风险），
> 槽级日志单独排期 —— 两件事不该混在一次改动里。

### 内核收尾（v1.2）

#### 步骤 0（SPI 批接口）已完成：A9 达标，扫描+过滤 5.52×

v1.1 的 A2 只拿到 1.11×，原因量得很清楚：**81% 的时间在 SPI 的逐行接口上**
（逐行 `scan_next` 38% + 逐行 `decode` 的 `DbValue` 物化 43%）。
向量化求值与聚合都碰不到这部分 —— **不改 SPI，3× 不可达**。
所以 v1.2 第一步就把 SPI 的批接口做出来。

| 落地的东西 | 说明 |
|---|---|
| `src/storage/batch.{h,c}` | 批契约：`AmRowRef`（指针+长度+RID）/ `AmBatchCol`（列数组）/ `AmBatch`；`val_batch_decode` 把记录字节**直接解进列数组**，不物化 `DbValue` |
| `src/spi/storage_am.h` | 两个**可选**能力位 `AM_CAP_BATCH_SCAN` / `AM_CAP_BATCH_DECODE` + 两个可选函数指针 |
| `src/spi/heap_am_batch.c` | heap 的批扫描 + 批解码（`heap_am_internal.h` 存私有扫描状态，批路径与逐行路径**共用一份取行逻辑**） |
| `src/storage/heap.c` | **零拷贝**批扫描 `heap_scan_page_batch`：行指针直接指向页内 |
| `src/query/exec_batch.c` | 执行器侧：攒批从"逐行转置"改成"AM 直接给列批"；列式求值与投影**不动** |
| blob / graph / vector | 两个指针置 NULL，**一行逻辑不改** |

#### 三个设计决定

**① 全表扫走零拷贝（不拷行字节）。**

堆表的行**内联在页里**，所以"取一行"本来不需要拷贝 ——
逐行路径的 memcpy 纯粹是接口逼出来的。实测三种取法：

| 取法 | 完整查询 |
|---|---|
| 页 → 竞技场（一次 memcpy） | 2.13 ms |
| 页 → 4 KB 中转 → 竞技场（两次 memcpy） | 2.88 ms |
| **零拷贝** | **2.10 ms** |

中转反而更慢：**4K 别名**。页缓冲（4 KB）和竞技场（256 KB）低 12 位常常相同，
"从页里读、向竞技场写"撞上 store-to-load forwarding 误判，内存消歧器每次多等一拍。
不拷就没有这个依赖。

代价是**行字节的有效期 = 页的 pin 期**，所以契约写死一条：
**行字节的有效期到下一次 `batch_scan` 调用为止**。
⚠️ 原来靠全局 latch 兜着；**v1.2 步骤 4c 已落地** ——
frame 域给每一帧配了内容锁，`pager_get` → `pager_unpin` 全程持有，
解码窗口落在内容锁的保护期内（见下"步骤 4c"一节）。
⚠️ **v1.2 步骤 4d 之后**：关系型语句**不再取全局 latch**，
这条零拷贝边界**完全依赖 frame 域的内容锁**。

**② 批能力是可选加速，不是正确性前提。**

`caps` 位 + 指针为 NULL = 不支持，执行器自动退回逐行路径。
没实现的模态**一行都不用改** —— 这正是 v1.1 §1.2 担心的"那条底线"，
能力协商本身就是项目自有的机制。

**③ 批解码与逐行解码必须逐格一致。**

三个易错点：NULL 位图的位号、文本截断到 `VAL_TEXT_MAX-1`、INT4 符号扩展成 i64。
守卫是**对拍**（批式 vs 冻结的火山执行器，逐格全等）。

#### 实测（10 万行、选择性 10%、重复 10 次取最小）

| 阶段 | 火山（逐行） | 批式 | 倍数 |
|---|---|---|---|
| 扫描 | 1.010 ms | 0.141 ms | 7.2× |
| + 解码 | 4.146 ms | 0.763 ms | 5.4× |
| **+ 过滤（A9 口径）** | **5.097 ms** | **0.924 ms** | **5.52×** ✓ |
| 完整查询（含结果物化） | 6.09 ms | 2.161 ms | 2.82× |

#### 顺带撞出并修掉的两件事

**① 缓冲池 1 MB → 16 MB（默认值）+ `DB_BP_FRAMES` 环境变量。**

原来默认 256 帧 = 1 MB，装不下 4 MB 的表，每次扫表都把整张表从磁盘读一遍
（pager 用 `setvbuf(_IONBF)` + 每页一次 `fread`）。
实测扫描阶段：**1 MB 池 4.0–5.0 ms → 16 MB 池 0.60–0.72 ms，差 7 倍**。

**v1.1 那个 1.11–1.13×，是在一个不断换页的池上量的** —— 它测到的主要是磁盘。
基准现在自己按数据集大小设池（两条路径共用同一个池，比值仍然公平）。

**② 批路径的"静默丢数据"截断 bug。**

批路径一次取一页，一页里的行可能恰好**全都不可见**（另一个事务插了还没提交）。
原来的写法是"本批 0 行 → 收工" —— 第 1 页全不可见时，后面页里的可见行**全被丢掉**，
不报错，只是结果少了。改成靠 `eof` 判断收工。

回归测试（`test/integration/test_batch_scan.c`）：写方先插 200 行不提交（占掉第 1、2 页），
读方再插 10 行提交（落在第 3 页），读方查表必须看到那 10 行。
**已做反向验证：把修复回退，这个测试立刻变红。**

#### 如实记录

- **完整查询的比值只有 2.82×，比 A9 的 5.52× 低。**
  结果物化（`b_push` → `char **` + 每格 `snprintf`/`malloc`）两条路径**共有**，
  约 1.0–1.1 ms/查询。A9 的口径是"扫描 + 过滤"，按定义不含物化 ——
  这不是挑口径，物化是 v1.1 就存在的固定成本，两边一样。
- **扫描阶段的绝对值已经很小（0.141 ms）。** 再往上优化的空间在**解码**（0.62 ms），不在扫描。
- **零拷贝的安全性原来依赖全局 latch**；v1.2 步骤 4c 已把解码窗口放进**页内容锁**
  （`pager_get` → `pager_unpin` 全程持有），这条债已经还掉；
  步骤 4d 退役大锁后，这条边界**只剩内容锁**在护着。

#### 步骤 1（copy-out 重构）已完成：三个读接口改成拷贝出参

v0.10 说"读接口返回共享指针，所以锁只能画粗"。这一版先把前置条件还上。

**审计结果：计划里点的两个接口，一个不用改，另一个要改的还不止它。**

| 接口 | 原来返回 | 判决 |
|---|---|---|
| `catalog_table_meta` | `&e->meta`（`e` 在 `cat->t` 数组里） | **真悬空** —— 建表时 `cat->t` 被 realloc，整个数组搬家 |
| `catalog_table_indexes` | `e->idxs` | **真悬空** —— 建索引时 `te->idxs` 被 realloc |
| `catalog_table_cols` | `e->cols` | **恰好稳定**（每表一份 malloc，只有关库才 free）—— 改它的理由是**契约统一**，不是修 bug |

#### 步骤 2（latch 框架）已完成：域编号 + 获取全序 + 断言

从"一把大锁"走向"编号的一组小锁"的第一步：**先把纪律立起来，再一把一把地换**。

| 域 | 序号 | 保护什么 | 类型 |
|---|---|---|---|
| `LATCH_CATALOG` | 1 | 表 / 列 / 索引元数据缓存 | 读写锁 |
| `LATCH_TXN` | 2 | `next_xid`、clog、活跃表 | 独占（很短） |
| `LATCH_BTREE` | 3 | B+tree 的结构与页内容 | 独占（中） |
| `LATCH_FRAME` | 4 | 单页数据 + `pin_count` | 每帧一把（极短） |
| `LATCH_WAL` | 5 | 日志缓冲、LSN 计数、append | 独占 |
| `LATCH_FREELIST` | 6 | 空闲页链 | 独占（很短） |

**获取全序**：`catalog → txn → btree → frame → wal → freelist`

⚠️ **上表是当前的编号**（⚠️ 勘误过两次）：
步骤 2 当初写的是 `catalog → txn → wal → freelist → frame`，
步骤 4c 改成 `catalog → txn → frame → wal → freelist`，
步骤 4d 又补上了 btree 域，并把 btree 放在 frame 之前
（B+tree 插入是"先改树结构、再写页"，页在树结构之内）。

**本步骤只做"记账 + 断言"，不加真实互斥** —— 真实互斥在步骤 3/4 接线，
那时才改调用点。所以这一步对现有行为是**零变化**：现有代码一行都不用动。

**全序检查规则**：获取序号 r 的域之前，已持有的所有域的序号必须 `< r`。
- 同域重复获取（可重入）不算逆序。
- **被拦下的获取不记账** —— 否则持锁集合会记录一把"其实没拿到"的锁。
- **crabbing**（B+tree 分裂的锁降级）是显式例外，且只允许**同域内**；
  跨域用它就是普通违规。

**断言默认 abort，而且一直开**（没有"调试版才开"这回事）——
一个能抓到逆序的断言，不该在发布版里消失。开销是每域 5 次整数比较。

**默认行为真的是 abort**（子进程实撞，退出码 3）。

> 第 6 项特意让子进程先打印一个标记 ——
> 否则"命令没找到"也是非 0 退出码，测试会**假通过**。

> **框架目前没有接入任何真实锁** —— 它的价值现在还只是"纪律 + 测试"，
> 真正起作用要等步骤 3/4。这不是"做了一半"，是计划里就定好的顺序
> （"一次只动一件事"）。

#### 步骤 3（catalog 读写锁）已完成：第一个真正接上线的域

细粒度化的**第一个域**。catalog 是实例级共享的元数据，读多写少
（只有建表 / 建索引 / 改统计才写）→ 用**读写锁**，读读不互斥。

**锁画在哪一层**：**公开 API 自己拿锁**（`src/catalog/catalog_lock.c`），
内部实现一律走 `_locked` 版本：

```c
int catalog_table_cols(Catalog *cat, u32 table_id, ColDesc *buf, int cap, int *ncols)
{
    catalog_read_lock(cat);
    int rc = catalog_table_cols_locked(cat, table_id, buf, cap, ncols);
    catalog_read_unlock(cat);
    return rc;
}
```

这么拆有两个硬理由：

- 每个公开 API 只有**一个出口** → 加锁/解锁不会漏路径（多一个 `return` 就漏一次解锁）；
- 内部函数互调**不会递归取锁**（POSIX：重复取读锁是未定义行为，有写者在等时会死锁）。

调用方**不要**自己拿锁 —— 拿两次就是递归取读写锁。

**三条使用纪律**（违反 → 打印 + `abort()`）：

| 纪律 | 原因 |
|---|---|
| 读锁**可重入** | 同线程重复取读锁 → 计数 +1，不重复碰底层 rwlock（POSIX 禁止重复取读锁） |
| 写锁**不可重入** | 重复取写锁 = 自锁 |
| **不许升级 / 降级** | 读写锁的升级没有正确实现（读者一多就死锁） |

**验收**（`test/unit/test_catalog_lock.c`，7 项）：读锁可重入（用**写者当探针**：
放一层仍挡、放两层才进）/ 读读不互斥 / 写锁排他 / 升级被拒 / 降级被拒 /
写锁不可重入 / **默认行为真 abort**（子进程实撞 + 标记文件防假通过）。

#### 步骤 4a（txn 域）已完成：写路径持锁，读路径走原子

txn 域保护三样东西：`next_xid`、`clog`、活跃表。

| 路径 | 手段 | 为什么 |
|---|---|---|
| **写**（xid 分配 / 活跃表增删 / clog 写入） | 域内互斥锁 | 分配 xid 要"找空槽 + 占住它"，两个线程可能看上同一个槽 |
| **读**（clog 状态 / 活跃表查询） | **原子读，一把锁都不取** | 可见性判断**每读一行就要查一次 clog** —— 最热的读路径；每次取锁会让 10 万行的扫描多花几毫秒，A9 门槛会破 |

**clog 从"2bit 打包"改成"一 xid 一字节"**（1 KB → 4 KB）：
不是为了内存（只多 3 KB），是为了**并发** ——
2bit 打包时写入是"读-改-写一个字节"，两个线程改同一字节里**不同的 xid**
会互相覆盖 → 提交状态丢失 → "已提交的数据读不出来"。
一 xid 一字节之后写入变成纯 store，原子操作不会丢更新。

**发布顺序**：分配 xid 时**先**重置 clog 槽位（环形窗口会复用槽位，
里面可能留着老事务的"已提交"），**再**发布 `next_xid` —— 反过来就是脏读。

**锁的粒度**：域锁是**进程级**的一把锁（不是每实例一把）——
一个进程同时开两个库的情况极少，而进程级锁换来
"不需要 init/destroy、不需要改任何调用点"（`TxnTable` 在测试里是栈上对象）。

**验收**（`test/unit/test_txn_domain.c`，4 项）：并发 xid 唯一（1600 个，0 重复）/
槽位复用不产生脏读 / 并发读 20 万次无脏读 / 活跃表上限。
**这个测试是真的会红的**：把域锁临时去掉，第 1 项立刻报"xid 重复 6 个"。

**验证性缩小实验**（去掉 `db_exec` 大锁）：`test_concurrent` 的失败项与步骤 3 **完全一样**
（并发插入 / 缓冲池压力 / 崩溃恢复 / 并发读写）→ 竞态在 **heap / pager / WAL** 域，
是步骤 4b / 4c 的活。**大锁仍然不能退役**，但 txn 域已经能独立站住。

#### 步骤 4b（wal 域）已完成：它保护的不是内存，是**日志文件本身**

wal 域保护：LSN 计数、undo 链（按 xid 分槽）、日志文件本身、扫描游标。

`wal_append_xid` 里这三步必须是一个整体：

```
    lsn = last_lsn + 1;      ← 取号
    FSEEK(f, 0, SEEK_END);   ← 定位到文件尾
    fwrite(b, 1, n, f);      ← 写一条记录
```

两个线程同时进来 → 取到**同一个 LSN**（恢复时日志顺序错乱）；
更糟的是各自 fseek 到尾再 fwrite → **字节交错** →
文件里出现半条 A、半条 B → CRC 失败 → 恢复**截断** →
截断点之后的**所有**记录作废。也就是说，**一次并发写日志的竞态能废掉整段日志**，
而且没有报错、没有崩溃 —— 只是"数据不见了"。

| 路径 | 手段 | 为什么 |
|---|---|---|
| **写**（append / fsync / reset） | wal 域的互斥锁 | 取号 → 定位 → 写必须独占；同一 `FILE*` 不能并发 fsync |
| **扫描**（scan / read_payload） | **同一把**域锁 | 扫描与 append 争同一个 `FILE*` 和同一个 `scratch` 缓冲，不加锁会读到"写了一半"的记录 |
| **读**（last_lsn / nrecords / max_xid / flushed_lsn） | **原子读，一把锁都不取** | 热路径（每条语句结束都查 `flushed_lsn`） |

**锁的粒度**：**每实例一把**（`struct Wal` 里的 `pthread_mutex_t mu`）——
与 txn 域不同：WAL 是实例级资源（一个库一个日志文件），不同库之间没有共享状态；
`Wal` 的生命周期由 `wal_open`/`wal_close` 管住 → 不需要改任何调用点。

**发布顺序**：`last_lsn` 在 `fwrite` 成功**之后**才发布 ——
反过来读者会看到"已分配但没落盘"的 LSN，刷页时会误判"日志已落盘"。

**验收**（`test/unit/test_wal_domain.c`，4 项）：并发 append 的 LSN 唯一且连续
（2400 条，0 重复 0 断号）/ 并发写出的日志一条不差地扫回来（2400/2400）/
append 与 fsync 混跑时计数器单调不减 / undo 链按 xid 独立。
**这个测试是真的会红的**：拿上一步的 `wal.c` 跑同一个测试，
立刻报"LSN 重复 2087 个、2400 条只扫回 125 条"。

**验证性缩小实验**（去掉 `db_exec` 大锁）：`test_concurrent` 的失败项与步骤 4a **完全一样**
（同批行号），`test_mvcc_it` / `test_copyout` 全绿 →
竞态仍在 **heap / pager / frame** 域。**大锁仍然不能退役**，
但 wal 域已经能独立站住（新测试不经过 `db_exec`，直接压 `wal_append_xid`）。

⚠️ **给步骤 4c 的约束（已作废）**：原文写"刷页前要调 WAL flush 钩子，
那时若已握着 frame 域的锁，就是 frame(5) → wal(3) **逆序** → 断言 abort；
刷页路径必须**先落日志、再取 frame 锁**"。
**作废理由**：真实的嵌套边是 **frame → wal**（钩子就是在页被捏住时调的），
持 frame 锁调 WAL 钩子**恰恰是对的** —— WAL 规则要求"日志先落盘、页后落盘"，
钩子必须在刷页那一刻被调。要避免的是**反过来**（持 wal 锁去取 frame 锁）。

#### 步骤 4c（freelist + frame 域）已完成：两个"派生数据"域

| 域 | 保护的 | 手段 |
|---|---|---|
| **freelist** | 每页的剩余空间档位 + 每档多少页 | 实例级一把锁；**读路径也持锁**（`levels` 是 `realloc` 出来的 → 悬空指针） |
| **frame** | 一帧的**页内容** + 池子的账本 | **池级锁**（哈希表 / Clock 手 / pin_count / npages）+ **每帧一把内容锁**（递归） |

**内容锁覆盖 get → unpin 的整个借用期**：
从 `pager_get` 拿到帧到 `pager_unpin` 归还，页的内容是**借给调用方**的。
这段时间里如果另一线程把这一帧逐出并载入别的页，
调用方手里的指针就指向了**别的页的内容** —— 写进去的数据张冠李戴，且无报错。

**内容锁必须是递归的**：同一线程可能对同一页 `get` 两次
（B+tree 先取父页再取子页，中间又回头看一眼父页）。

**公开 API 一个字没改**（`pager_get` / `pager_unpin` 签名与语义全变），
所以 242 处调用点零改动 —— 锁画在模块内部的红利。

**死锁怎么排除：一条不变式** —— **持有内容锁 ⇒ 该帧 `pin_count` ≥ 1**。
由它推出：逐出路径只挑 `pin_count == 0` 的帧 ⇒ 那一帧的内容锁一定是空的
⇒ 逐出（持池级锁 → 取受害者内容锁）**不会阻塞**，没有环。

| **新增 btree 域** | 每棵 B+tree 一把锁；公开入口统一持锁；**游标把锁带在身上**，`btree_cursor_close` 才放 |
| **全序第二次勘误** | `catalog(1) → txn(2) → **btree(3)** → frame(4) → wal(5) → freelist(6)` |
| **堆插入修竞态** | freelist 的 **「find → use」窗口**：`heap_insert` 加有界重试（`E_NOSPACE` 就 unpin 重找） |
| **修掉一条真实逆序边** | `heap_am_reindex` 跨 `heap_scan_next` 捏着堆页 → `frame → btree` 逆序，**被断言当场 abort**；新增 `heap_scan_release_page()` |

**为什么 btree 排在 frame 之前**：B+tree 插入是"先改树结构、再写页"，
页在树结构之内。

**两个被大锁长期掩盖的缺陷**（拆掉大锁才露出来）：

| 缺陷 | 现象 | 修法 |
|---|---|---|
| 堆的 freelist「find → use」 | 4 线程 × 500 行并发插入，**500 次全部失败**（`E_NOSPACE`） | `heap_insert` 有界重试（`HEAP_INSERT_MAX_RETRY 64`） |
| **B+tree 一把锁都没有** | 4 线程 × 300 行写带索引的表，堆里 1200 行全在，**点查漏掉 213 / 7 / 178 个** —— 静默的数据不一致 | 新增 btree 域，每棵树一把锁 |

**验收**：`test/unit/test_heap_insert_domain.c`（3 项）+
`test/unit/test_btree_domain.c`（3 项）。
**RED 证据**：

| 测试 | 修好后 | 修坏后 |
|---|---|---|
| 堆并发插入 | `errors=0` | **500/500 失败** |

| `test_concurrent` | 6 项全过（5/5 次） | **失败 14~15 项断言**（5/5 次） |

**如实记录**：
- **btree 域是"每棵树一把粗锁"** —— 一棵树的并发写被完全串行化。
  它解决的是**正确性**，不是**并发度**；⚠️ **步骤 7 只做了拆文件，没做 crabbing / 页级 latch** ——
  拆文件是 A8 的要求（`btree.c` < 800 行），crabbing 留给 v1.3。

  改的是撞车之后的反应。

#### 步骤 5（页内 compact + WAL 双镜像）已完成：A5 全表碎片率 < 20%

`page_compact()` 这个函数 **v0.1 就在了，但从来没有人调用它** ——
步骤 5 把它接进了 VACUUM，并保证这个动作可回滚、可重放。

| 变更 | 内容 |
|---|---|
| **堆表新增 compact 接口** | `heap_compact_page` / `heap_compact_table` / `heap_compact_frag_pct` |
| **VACUUM 增加第三遍** | 删除之后做页内 compact（**空洞是删除造出来的**，不删就没有空洞可整理） |
| **WAL 双镜像** | 一条 `LOG_PAGEDATA` 记录里同时带 before / after 两份整页（各 4096B）：重放盖 after、回滚盖 before |
| **在副本上整理** | 日志写好之后才盖回真页 —— 满足"先日志后数据" |
| **RID 不变** | 只挪物理位置，**slot 号不动** → 索引项和游标都不受影响 |
| **freelist 档位同步更新** | 不更新的话，这一页在 freelist 里还挂旧档位 → 空间空着却用不上 |
| **VACUUM 输出 3 列 → 6 列** | `scanned / removed / kept / compacted_pages / freed_bytes / frag_pct` |

⚠️ **两处勘误（计划写错了）**：

| 计划写的 | 实际做的 | 为什么 |
|---|---|---|
| "> 50% 碎片的页进 compact 队列" | **阈值 0**（只要有空洞就整理） | 逐页 50% 保证不了"**全表** < 20%"—— 一堆 40% 的页摊在一起，全表就是 40% |
| "compact 前后**各写一次**整页镜像" | **一条**记录带两份镜像 | 日志里的信息是**原子的**，不会出现"只有前半截"的半整理页 |

**A5 的证据**（`test/integration/test_vacuum_compact.c`）：

```
第一次 VACUUM：scanned=2250 removed=750 kept=1500 compacted=22 freed=29583 frag=36%
第二次 VACUUM：scanned=1500 removed=0   kept=1500 compacted=0  freed=0     frag=0%   ← A5 达成
```

**为什么"第二次 VACUUM 报 frag=0"才是证据**：第一次报 36% 说的是
"我收拾的是多碎的一张表"，不是"我没收拾干净"。
如果第一次没整理干净，第二次还会看到碎片。

⚠️ **规模偏离**：计划写"10 万次随机增删"，实际 2000 行 + 750 次改删 ——
每条 SQL 都是独立事务、提交要 fsync 一次，10 万条要几分钟。
⚠️ **步骤 7 的吞吐基准也没做到 10 万级** —— A3 的负载是每表 500–20000 行、
每线程 20–500 轮；而且 ⚠️ **A3 本身未达标**（0.78× – 1.01×），
所以「10 万级压测」这条路整体顺延到 v1.3（连同池级锁一起改）。

#### 顺带撞出并修掉一个既有缺陷：恢复阶段 xid 状态表的 256 项上限

**不是步骤 5 引入的** —— 去掉 VACUUM 一样复现。

```
300 次插入 + 150 次删除 = 450 个事务
  关闭前 COUNT(*) = 150
  重启后 COUNT(*) = 255      ← 删掉的 105 行又"活"了
```

**为什么**：删除不是物理删除，是给记录打 xmax 标记。
"这行删了没有"记在 xmax 的那个 xid 上，而那个 xid 的提交状态被丢了
→ clog 说"进行中" → 可见性判断认为这行还活着。
（老测试全绿是因为它们的事务数都在 256 以内。）

**修法**：固定 256 项的数组 → **按需增长的开放寻址哈希表**。
回归测试 `test/integration/test_recovery_xids.c`（600 个事务）。

| 测试 | 修复前 | 修复后 |
|---|---|---|
| `test_recovery_xids` | **3 项失败**（重启后 255 行、已删的 id=0 还能读到） | 全过 |
| `test_vacuum_compact` | **2 项失败**（重启后行数不对） | 全过 |

**遗留**：clog 本身是 4096 槽的环形窗口，xid 跨度超 4096 后老状态会被覆盖 ——
那是 **v1.2 步骤 6**（checkpoint + clog 落盘）的范围。**已在步骤 6 解决**（见下）。

#### 步骤 6（checkpoint + 日志截断）已完成：A6 恢复时间解耦

**要解决的问题**：恢复阶段本来要把**整个日志**从头扫一遍。
库跑得越久，日志越大，重启越慢 —— 而且慢得没有上限。

| 变更 | 内容 |
|---|---|
| **`CHECKPOINT` 语句 + `db_checkpoint()` API** | 手动触发；另有阈值触发（环境变量 `DB_CKPT_BYTES`，默认 16MB） |
| **meta 页记重放点** | `M_CKPT_LSN`（`catalog.h` 公开）—— "这个 LSN 之前的记录都已在数据文件里了" |
| **ARIES 式的 `rec_lsn`** | `PageFrame.rec_lsn` = 一页"自上次刷盘以来的第一次改动"的 LSN；`pager_min_dirty_lsn()` 取脏页里的最小值 = 重放点的上界 |
| **日志可截断** | `wal_truncate()`：保留后缀整体前移到文件头 + 截短文件 |
| **clog 分块 + 落盘** | 按 xid 高位分块（65536/块，≈6700 万 xid），读路径无锁；落盘到 `<db>-clog`（一字节一 xid） |
| **恢复起点** | `recovery_run()` 多一个 `checkpoint_lsn` 参数 |

**A6 的证据**（`test/integration/test_ckpt_recovery_time.c`，20000 行主负载）：

| 用例 | 恢复耗时 | 日志大小 |
|---|---|---|
| 不 checkpoint | **824 ms** | 1 247 467 字节 |
| checkpoint 后断电 | **16 ms** | 8 224 字节 |
| checkpoint 后**再写 100 行** | **16 ms** | 8 224 字节 |

**第三行才是重点**：checkpoint 之后又写了 100 行，恢复时间**一点没变** ——
恢复时间只取决于 checkpoint 之后的日志量，与这个库一共写了多少无关。

⚠️ **三处勘误（计划写错了）+ 两个设计补充**：

| 计划写的 | 实际做的 | 为什么 |
|---|---|---|
| 阈值"进 config.h" | **环境变量 `DB_CKPT_BYTES`** | `db_open` 只有 path 一个参数，没有配置文件机制 |
| 过程"① 拿全序锁（catalog→txn→wal）" | **一把锁都不取** | 要防的是"刷页时有人在改页"，那个由 frame 域锁逐帧解决；取全序锁反而造成计划担心的全局停顿 |
| "恢复从 `checkpoint_lsn` 开始重放" | **重放按它过滤，回滚不按它过滤** | 未提交事务的记录可能**横跨** checkpoint 点，回滚要的是前像，哪怕 `lsn <= ckpt_lsn` 也必须留着 |
| （计划里没有） | 新记录类型 **`WAL_ABORT_DONE`** | 崩溃时开着的事务在日志里永远显示"没结束" → **日志永远截不掉** → 步骤 6 的目的落空。恢复回滚完补一条"已回滚完" |
| （计划里没有） | **clog 必须先落盘再截日志** | 提交状态只记在 clog 文件里，不在日志里。顺序反了 = 已提交的数据全部不可见（静默丢数据） |

**两者的区别不能混**：`WAL_ABORT`（运行时事务失败，**回滚还没做** —— 本内核的删除是物理删除）
与 `WAL_ABORT_DONE`（恢复阶段**已回滚完**，前像可以扔）。
混为一谈 = 把"没回滚的"当成"回滚完了" → 数据错。

**20 轮「写 → checkpoint → 断电 → 恢复」**（`test/integration/test_checkpoint.c`）：
每轮写 20 行 → checkpoint → 断电（`db_abandon`，脏页全丢、clog 不落盘）→ 重开 → 校验。
**日志大小不随轮数增长**：第 1 轮 8224 字节，第 20 轮还是 8224 字节
（截断没生效的话会线性增长）。

⚠️ **如实记录**：A6 的规模是 20000 行（约 1MB 库），不是计划写的 100MB ——
重放量相同、趋势一致，但绝对耗时不可与 100MB 对比。

##### ② A3 吞吐基准：❌ 未达标

⚠️ **先勘误计划的前提**：A3 那行写的是「基线 v1.1 已存档」——**这个前提是错的**。
v1.1 存档的是**执行器火山副本**，仓库里从来没有大锁版本的二进制。
基线是**当场重建**的：同一份源码 + 编译期开关 `-DDB_BIGLOCK_BASELINE=1`
（`src/db_stmt.c` 里把步骤 4d 退役的那把全局大锁原样放回去），两个二进制**逐字同源**。

| 每表行数 | 轮数 | 线程 | 细粒度（条语句/秒） | 大锁基线 | **比值** |
|---|---|---|---|---|---|
| 500 | 500 | 4 | 21902.6 | 22155.6 | **0.99×** |
| 2000 | 200 | 4 | 13714.3 | 15485.8 | **0.89×** |
| 20000 | 20 | 4 | 2200.6 | 2677.0 | **0.82×** |
| 2000 | 200 | 1 | 17902.9 | 17691.0 | **1.01×** |

**两个版本都不随线程数扩展**：读阶段耗时（各线程累加）
1 线程 45 ms → 2 线程 178 ms → 3 线程 566 ms → 4 线程 1455 ms（**放大 ~8×**）。
单线程下两者完全打平（1.01×）—— 细粒度 latch **既没带来开销，也没带来收益**。

**瓶颈是怎么查出来的（证据链，不是猜测）**：

| # | 手段 | 结果 |
|---|---|---|
| 1 | gdb `thread apply all bt`（4 线程运行中采样） | **4 个工作线程里 3 个堵在 `pool_lock`（`src/storage/pager.c:120`）** |
| 2 | 运行时读缓冲池状态 | `hand=105, npages=105` → **无逐出 churn** |
| 3 | `DB_BP_FRAMES=200000` 巨池重跑 | 曲线不变 → **池容量/逐出不是原因** |
| 4 | 分配器探针（4 线程 × 16000 × 12 次 malloc/free） | 共 **4.6 ms** → **分配器没有争用** |
| 5 | 互斥量探针 | 交接成本**亚微秒级** → 放大是真的，但绝对值不足以解释 8× |

> **关键性质**：语句级大锁挡住的是「**所有语句**互斥」，池级锁挡住的是「**所有页访问**互斥」。
> 后者粒度更细，但**仍然是全局串行点**。
> 把语句级大锁拆掉，只是把排队点从「语句入口」挪到了「页入口」——**并发特性上等于没动**。
> 而且两个版本的放大**性质不同**：大锁是**排队**，细粒度是**争用**，
> 结果细粒度版本在墙钟时间上**还慢 28%**。

**教训比结论更重要**：**细粒度化必须一路挖到底。**
v1.2 把 catalog / txn / wal / freelist / frame / btree 六个域都拆开了，
唯独缓冲池的池级锁没人动 —— 因为它长得像「实现细节」而不是「设计」。
**六个域的细粒度化，收益全被一把池级锁吃掉了。**

**v1.3 步骤 0 收口（详见 `docs/PLAN-v1.3.md` §3 步骤 0）** ——
根因其实是**三层**，一层比一层隐蔽：

| # | 根因 | 修法 |
|---|---|---|
| 1 | winpthreads 的 `pthread_rwlock_t` **不允许并发读者**（"读写锁"实际是互斥量） | 自研 `DbRwLock`（`src/common/rwlock.h`），4 线程比 pthread_rwlock 快 **8.9×** |
| 2 | 堆表扫描**遍历整个页空间**（每个 SELECT 走 ≈79 页，本表只有 ≈17 页） | 每表**页号表** → 帧内容锁真实争用 **12,713 → 0** |
| 3 | COMMIT 的 fsync **持着 WAL 域锁** | fsync 移出域锁（fflush 仍在锁内），`wal_bytes()` 改原子读 |

收口后的实测（基准**默认配置**：5 万行/表、30 轮、4 线程）：

| 轮次 | 细粒度（条语句/秒） | 大锁基线 | **比值** |
|---|---|---|---|
| 1 | 5117.3 | 1535.1 | **3.33×** |
| 2 | 4653.1 | 1506.2 | **3.09×** |
| 3 | 5081.6 | 1601.6 | **3.17×** |

线程扩展性（细粒度）：1 线程 1710 → 2 线程 3289 → 4 线程 ≈5080（**2.97×**）；
大锁基线 4 线程 1535 ≈ 1 线程水平（**完全不扩展**）。

⚠️ **读轻配置（2000 行/表）只有 1.57× – 1.84×**：墙钟里磁盘 fsync 占了 ~220 ms
（80 次提交 × ≈2.75 ms），**两个版本受同一个磁盘限制** ——
判据口径取基准的默认配置（`bench/latch_bench.c` 的设计说明：「读必须重到 fsync 可以忽略」）。

##### ④ 两条附带发现

- **M8-1 · 被拒绝的获取不记账** → 配对的释放会报「释放未持有的域」。
  想让「只记录不中止」的 handler 跑下去就得补记账，
  而补记账**只修好了账本，真实锁的归属没变** —— 账本说「txn 域没被持有」，
  真实上**锁已经被取到了**。所以「记录型 handler」在语义上是骗自己。
- **M8-2 · 全序断言是「事后检查」，挡不住 AB-BA 死锁** ——
  `latch_order_acquire` 跑在**真实加锁之后**。
  它能抓住「**已经完成**的逆序」（当场 abort），但**不能预防**死锁：
  两个线程会先各自拿到自己那把真实锁，**死锁已经形成**。
  ⚠️ 因此「断言 = 唯一防线」必须限定：
  **断言是发现逆序的探测器，不是预防死锁的护栏**；
  真正的防线仍然是「**按全序获取**」这条纪律本身。
