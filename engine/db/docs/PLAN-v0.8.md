# v0.8 执行方案与计划 · blob 模态（独立大对象存储）

> 前提：v0.7（MVCC + vacuum）已完成并全绿（124 项验收）。
> 本版目标：打开多模态路径的第一条 —— **blob 模态**：独立的大对象存储，支持帧级随机访问。

---

## 一、方案

### 1.0 先纠正一个方向性错误

初稿我按「关系模态的 TEXT 太大 → 外置到 overflow 页」来设计（TOAST 式）。
**这是错的**，理由有三：

1. **DESIGN.md §7 的验收标准就说不通**：
   「读 1GB 对象第 3000 帧，IO 量 ≈ 4KB」——
   1GB 是一个**对象**，3000 是它的**帧号**，4KB 是**一帧的 IO 量**。
   行外置模型里没有"对象的第 N 帧"这个概念。

2. **DESIGN.md §10.4 最后一句明确划了界**：
   > 一行 3 个 TEXT 各 1KB（总 3KB）时整行外置要读 2 页，列级只需外置 1 列。
   > 但"一行多个大字段"**正是 blob 模态要解决的场景，不该让关系模态背这个包袱**。

   也就是说：**blob 模态不是关系模态的大字段类型**，
   它是独立的一层，专门解决"多个大对象"。

3. **这违背了项目的立项目标**：
   目标是「把八个模态的机制亲手实现一遍」。
   blob 模态对标业界的是 **S3/MinIO 的对象存储**、
   **MongoDB GridFS**、**Parquet/Lance 的分块文件**——
   它们的共同机制是**对象 + 帧 + 帧索引**，
   而不是"数据库里的大字段"。

所以本版做的是**独立的大对象存储引擎**。

### 1.1 范围

**做**：

1. **`storage/blob.{h,c}`**：blob 对象存储。
   - 对象（object）：一个大的字节序列，逻辑上切成**等长帧**。
   - 帧（frame）：固定大小（默认 4KB），是 IO 的最小单位。
   - **帧索引**：帧号 → 物理页号的映射，支持 O(1) 随机访问。
   - 对象的元数据：帧数、总长度、每帧大小。
2. **帧索引的两级结构**：一级索引放不下 1GB 对象的帧数，所以索引本身也要分块。
3. **`blob_read_frame(obj, frame_no)`**：读第 N 帧，IO 量 ≈ 一帧（4KB）。
4. **WAL 支持**：blob 页也要写日志，崩溃后大对象不能丢。
5. **公开 API**：`db_blob_create` / `db_blob_write` / `db_blob_read_frame` 等。

**不做**（明确划掉）：

- **全局 latch**（v0.7 顺延的）：并发模型改动波及全代码库，与本版新机制叠加，
  出错时分不清是谁的锅。**顺延 v0.9。**
- **对象的多版本 / 事务性**：blob 对象是**不可变的**（写完就定稿）。
  这是对象存储的标准模型（S3 的对象一旦 PUT 完就是不可变的）。
- **分块上传 / 断点续传**。
- **范围查询**（读第 100-200 帧）：先做单帧读，范围读是自然的扩展。
- **压缩 / 加密**。
- **对象的删除与空间回收**：v0.8 只增不减。

### 1.2 五个决定

#### A · 帧定长，不做变长帧

**决定**：一个对象的所有帧大小相同（`BLOB_FRAME_SIZE`，默认 4096）。

**为什么**：
- 定长 → 帧号 → 页号的映射是**算术**，不需要查表。
- 定长 → 读第 N 帧的 IO 量恒定（这正是验收标准要保证的）。
- 变长帧 → 每帧要存自己的长度，帧索引从"算术"变成"查表"，
  索引本身还要分块，随机访问多一次 IO。

**代价**：对象末尾那一帧可能没写满（浪费 ≤ 4KB）。
1GB 对象浪费 4KB —— 可忽略。

#### B · 帧索引用「页号 = 基址 + 帧号」的直接映射 + 一层间接

**决定**：一个对象占**一段连续的页**。第 N 帧在第 `base_page + N` 页。

**为什么能连续**：对象是**一次写完**的（不可变对象），
写的时候页是连续分配的（`pager_alloc` 顺序分配）。

**为什么还要一级间接**：1GB / 4KB = 262144 帧。
一个 u32 的页号数组要 1MB —— 放不进一页。
所以索引必须能"索引自己"：**索引分块存放**，
第一块索引记录"每个索引块覆盖哪些帧、放在哪一页"。

**结构**：

```
┌─────────────┬──────────────────────────────────────┐
│ 对象头页     │  帧数据页（连续的 N 页）               │
│ (base+0)    │  base+1, base+2, ... base+nframes    │
├─────────────┼──────────────────────────────────────┤
│ 索引块 0     │  索引块 1, ... 索引块 m               │
│ (base+n+1)  │  （覆盖帧号 → 页号的映射）             │
└─────────────┴──────────────────────────────────────┘
```

每个索引块覆盖 `FRAMES_PER_INDEX` 帧（比如 1024 帧 = 4KB / 4B 每项）。
索引块 0 的头部存"索引块 m 存在哪一页"（m 个 u32，m 很小）。

**读第 N 帧的路径**：
1. 算 N 在哪个索引块：`blk = N / FRAMES_PER_INDEX`
2. 从对象头页拿到索引块表的第 blk 项 → 那个索引块的页号
3. 读索引块 → 拿到第 N 帧的页号
4. 读那一帧的数据页

**IO 量**：4 次页读（头页 + 索引块表 + 索引块 + 数据页）≈ 16KB。
但**头页和索引块表可以常驻缓存**（它们很小），
热路径上就是 2 次页读 ≈ 8KB。

> **验收标准说「IO 量 ≈ 4KB」**。要达到这个数，
> 得让索引块表也在头页里（头页扩到能放更多条目），
> 或者接受"数据页 4KB + 索引 4KB ≈ 8KB"。
> v0.8 的做法：**把索引块表放进对象头页**（头页可以有大空间），
> 让热路径 = 读索引块 + 读数据页 = 2 页。
> 再进一步：把「帧号 → 页号」做成纯算术（对象头页记 `base_page`，
> 数据页连续），那索引块都不用读 —— **1 次页读 = 4KB** ✓
>
> **最终决定**：既然数据页是连续的，帧号→页号就是纯算术！
> **索引只需要用来支持"不连续"的情况**（比如未来支持增量写）。
> v0.8 的对象一次写完 → 页连续 → **纯算术，零索引 IO**。
> 但帧索引的数据结构照样要建（这是"支持随机访问"的通用机制），
> 只是 v0.8 的快路径恰好能绕开它。

**这是本版最重要的设计点**：先想清楚"什么情况下索引是必需的"，
再决定要不要为它付 IO 代价。

#### C · 对象的页不登记到任何表的 freelist

**决定**：blob 的页由 blob 模块自己管理，**不进表的 freelist**。

**为什么**：表的 freelist 回答的是"哪一页能放下 N 字节的行"。
blob 页是"一整页装一帧数据"，语义完全不同。
混在一起 → `freelist_find` 把 blob 页当行页用 → **写坏数据**。

这和 v0.7 的「overflow 页不进表 freelist」是同一个道理。

#### D · blob 页用独立页类型 `PT_BLOB`

**决定**：新增页类型 `PT_BLOB = 0x06`。

**为什么不用 PT_OVERFLOW**：
- `PT_OVERFLOW` 语义是"关系模态的一行的溢出部分"，
  它的页头布局和 blob 帧页不同（blob 帧页不需要 slot 数组）。
- 混用会导致关系模态的行扫描撞上 blob 页。

**blob 帧页的布局**：

```
┌──────────┬────────────────────────────────────────┐
│ 页头 20B │  帧数据 BLOB_FRAME_DATA 字节            │
│ H_TYPE=  │                                       │
│ PT_BLOB  │                                       │
└──────────┴────────────────────────────────────────┘
```

**对象头页**（第 0 页）多存一点：

```
┌──────────┬────────────────────────────────────────┐
│ 页头 20B │  对象头（变长）                          │
│          │  magic | nframes | frame_size | ...    │
└──────────┴────────────────────────────────────────┘
```

#### E · WAL 用整页镜像（复用 WAL_PAGEDATA）

**决定**：blob 页写日志时，用 `WAL_PAGEDATA`（before/after 各 4KB）。

**为什么复用**：
`WAL_PAGEDATA` 的语义是"这一页变成了这样"，
正好是 blob 页需要的。重放时 `memcpy` 整页即可，**恢复逻辑零改动**。

**代价**：日志膨胀一倍（8KB 日志 / 4KB 数据）。
PG 用「页首次修改时记全页，之后只记增量」避免这个问题。
v0.8 接受 —— 因为 blob 对象是不可变的，
**每个页只写一次**，不存在"增量修改"的场景。

> **这是不可变对象带来的额外好处**：
> 不可变 ⇒ 每页只写一次 ⇒ 日志不需要区分首次/后续 ⇒ 逻辑大幅简化。

### 1.3 blob 模态与关系模态的关系

**它们是并列的两个存储引擎，不是父子。**

```
关系模态（heap + catalog）        blob 模态
├─ 行存放在表页里                ├─ 对象存放在 blob 页里
├─ tuple 有 xmin/xmax            ├─ 对象不可变，没有版本号
├─ MVCC 可见性判断               ├─ 没有可见性问题（要么存在要么不存在）
├─ 表的 freelist 管行页          ├─ blob 模块自己管 blob 页
└─ DELETE 打 xmax + vacuum 回收  └─ 只增不减（v0.8）
```

**共同的底座**：pager（缓冲池 + 页读）、WAL（崩溃安全）、页格式（页头 + 校验和）。

**这是 SPI 存在的意义** —— 模态是并列的，各自有自己的物理组织，
但共享底座。v0.8 做的 blob 就是第一个真正的模态实现。

### 1.4 公开 API

```c
/* 创建对象：分配 nframes 帧的空间 */
db_err db_blob_create(DB *db, u64 nframes, u32 frame_size, u64 *blob_id_out);

/* 写整个对象（一次写完，不可变） */
db_err db_blob_write(DB *db, u64 blob_id, const u8 *data, u64 len);

/* 读第 N 帧 —— 核心操作 */
db_err db_blob_read_frame(DB *db, u64 blob_id, u64 frame_no,
                           u8 *buf, u32 cap, u32 *len_out);

/* 读整个对象 */
db_err db_blob_read(DB *db, u64 blob_id, u8 *buf, u64 cap, u64 *len_out);

/* 对象元信息 */
db_err db_blob_stat(DB *db, u64 blob_id, u64 *nframes, u32 *frame_size);
```

**blob_id 是什么**：页号。对象头页的页号就是 blob_id。
这样 blob_id → base_page 是 O(1)，不需要再查目录。

**对象目录**：v0.8 只支持一个"当前对象"？
不 —— 用 blob_id（页号）就能定位，不需要全局目录表。
新建对象 = `pager_alloc` 分配页，返回第一个页号作为 blob_id。

> **这样就不需要 catalog 表** —— blob 对象不进关系模态的 catalog。
> 这是"模态独立"的直接体现。

### 1.5 验收

**单元测试 `test/unit/test_blob.c`**（10 项）：

1. 创建对象 → 分配了 nframes 页，页类型是 PT_BLOB。
2. 写整个对象 → 读回来逐字节相同。
3. 读第 N 帧 → 内容与源数据的对应区间相同。
4. 读第 0 帧 / 中间帧 / 最后一帧 → 都正确（边界）。
5. **IO 量**：读第 3000 帧的页读次数 ≤ 2（头页 + 数据页）。
6. 跨对象隔离：两个对象的数据不串。
7. 不完整对象（最后一帧没写满）→ 读出来长度正确。
8. 越界读（frame_no ≥ nframes）→ 报错，不返回垃圾。
9. WAL：写对象产生 PAGEDATA 日志记录。
10. 崩溃恢复：对象写一半崩溃 → 重启后要么完整要么不存在（不能是半截数据）。

**集成测试**（4 项）：

1. 写 1MB 对象 → 读回一致（跨 256 帧）。
2. 重启后读回一致（持久化）。
3. 崩溃恢复后读回一致。
4. blob 与关系模态共存：表的数据和对象的数据都完好（页不串）。

### 1.6 风险清单

| 风险 | 影响 | 对策 |
|---|---|---|
| blob 页被表扫描撞上 | 读到垃圾 | 独立页类型 `PT_BLOB`；heap 扫描只认 `PT_HEAP` |
| blob 页被表的 freelist 误用 | 写坏数据 | blob 页不进任何表的 freelist |
| 帧号算错页号 | 读到别的数据 | 帧数据页里存自己的帧号，读时校验 |
| 对象头损坏 | 整个对象不可用 | 头页带 magic + crc |
| WAL 没覆盖 blob 页 | 崩溃后对象丢 | 复用 WAL_PAGEDATA，恢复逻辑零改动 |
| 帧大小写死 | 换页大小后失效 | 帧大小存在对象头里，读时校验与当前页大小一致 |

### 3.3 五个设计决定（正文 §1.2）

正文已详述，这里记**实现时才感受到的**部分：

#### 帧号 → 页号用纯算术，索引块成了「为扩展留的接口」

设计上有两个选择：
- **查索引表**（帧号 → 页号的映射表）
- **纯算术**（`base_page + N`，因为对象一次写完、页连续分配）

纯算术的读第 N 帧是 **1 次页读**（头页 + 帧页 = 2 次，头页可缓存），
正好命中验收标准的「IO 量 ≈ 4KB」。

但索引块的数据结构照样建了 —— 因为"页连续"是**当前实现恰好成立**，
不是本质约束。一旦支持增量写，页就不连续了。

**这是"为扩展留好接口，但不提前付代价"**：
索引块在 v0.8 完全用不上（快路径绕开了），但它已经把
「1GB 对象 = 262144 帧 = 256 个索引块」这个规模问题算清楚了。

#### blob_id = 页号 + 1

第一版直接用页号当 id，结果**首个对象的 id = 0**，
和「无效 id」无法区分。

改成 `blob_id = 页号 + 1`，`id = 0` 天然表示无效。
API 的常见用法是"先查有没有，有才用"，让 0 表示无效能省掉一堆特判。

**但这引出一个新问题**：页号空间是**共享**的 —— 关系模态的表页、
catalog 页也占页号。所以 `blob_id = 1` 可能指向**任何页**。

这带来一个必须区分的错误码：

| 情况 | 错误码 | 为什么 |
|---|---|---|
| id 指向的页不是 blob 头页 | `E_NOTFOUND` | 「这不是一个 blob 对象」是正常情况（用户传了无效 id） |
| 是 blob 头页但 magic/crc 不对 | `E_CORRUPT` | 真的是数据坏了 |

**返回 CORRUPT 会把用户误用说成"库坏了"，把排查方向带偏。**
这个区分是实现过程中才想清楚的 —— 单元测试里专门加了断言锁住它。

#### blob 有自己的目录，不依赖 catalog

`catalog` 是关系模态的元数据。blob 依赖它 = **模态之间互相依赖**，
这正是 SPI 明确禁止的（"模态之间不许互相 include"）。

所以 blob 自己维护对象目录，重启时**扫全文件**重建
（找 `PT_BLOB` 且带"头页标志"的页）。

**为什么不用持久化的目录页**：目录页和实际对象可能对不上（一致性问题）。
扫全文件的代价和关系模态"恢复后重建 freelist"是同一个量级，
但没有一致性风险。

**页头标志**：blob 头页和 blob 帧页的页类型都是 `PT_BLOB`，
用 `H_FLAGS` 的 bit3 区分（`BLOB_FLAG_HEAD`）。
这个标志同时用于两件事：目录重建时找头页、读对象时判断"这是不是一个 blob"。

#### blob 页不写进任何表的 freelist

表的 freelist 回答"哪一页能放下 N 字节的行"。
blob 页是"一整页装一帧"，语义不同。
混在一起 → `freelist_find` 把 blob 页当行页用 → **写坏数据**。

这和 v0.7 的「overflow 页不进表 freelist」是同一个道理。

#### WAL 用整页镜像（复用 WAL_PAGEDATA）

`WAL_PAGEDATA` 的语义是"这一页变成了这样"，正好是 blob 页需要的。
**恢复逻辑零改动** —— 这是复用已有机制的最大好处。

代价是日志膨胀一倍（8KB 日志 / 4KB 数据）。
PG 用「页首次修改时记全页，之后只记增量」避免这个问题，
但 **blob 对象不可变、每页只写一次** ⇒ 不存在"增量修改"的场景
⇒ 直接记全页即可。

**不可变对象带来的额外好处**：省掉了 WAL 的首次/后续区分逻辑。

### 3.4 一个真实的 bug：blob 的事务语义

**问题**：blob 的 API 该不该参与事务？

第一版我写了 `db_blob_write(db, id, data, len)`，但心里一直不安：
blob 页要写 WAL，日志里的 xid 是多少？

**结论**：**blob 不参与事务，xid 传 0（系统事务）**。

理由：
- 对象**不可变**（创建 → 写 → 定稿），没有"回滚到旧版本"这回事。
- 没有并发写同一对象的问题（写完就定稿）。
- 但它**写 WAL**，所以崩溃后数据不丢。

xid=0 在恢复时被视为"永远已提交" —— 这正是我们要的：
blob 页在写完的瞬间就是最终状态，不存在"属于一个未提交事务"的情况。

**如果将来 blob 要支持"多段上传、最后合并"**，
那时就需要给它真正的 xid，让未完成的对象在恢复时被清理。
这个"将来"我写在了代码注释里。

### 3.5 两个反向验证

#### 验证一：IO 量测试能抓到「深访问变慢」

把「纯算术定位」改成「顺着页链逐页找」：

```
FAIL test/unit/test_blob.c:292: reads <= 2
FAIL test/unit/test_blob.c:299: reads == reads2
```

两项都变红。特别是第二个 —— **浅访问和深访问的 IO 量必须相同**，
这才是 blob 模态存在的理由。

#### 验证二：blob 不写 WAL → 崩溃恢复测试变红

```
FAIL test/integration/test_blob_it.c:176: db_blob_read(db2, id, dst, len, &got) == DB_OK
FAIL test/integration/test_blob_it.c:177: got == len
FAIL test/integration/test_blob_it.c:178: memcmp(src, dst, (size_t)len) == 0
（t3 崩溃恢复 + t5 双模态崩溃，共 6 条断言失败）
```

**这一步特别重要**：blob 复用 WAL_PAGEDATA 最容易出的错就是
"页在盘上、日志里没有" → 崩溃后重放不出来 → **静默的数据丢失**。
而这类 bug 只有"模拟崩溃"才抓得到 —— 功能测试全绿。

#### 踩到的坑：反向验证时编译失败，跑的是旧二进制

第一次注入「blob 不写 WAL」时，编译报 unused-parameter 错误 →
`run.sh` 链接的是旧 `.o` → 测试结果**完全不可信**。

这是 v0.7 就记录过的坑，本轮又踩了一次。
修法：**注入的代码必须能编译通过**，否则就不是在测新代码。

（`-Werror` 在这里帮了忙 —— 它把"注入没生效"暴露成了编译错误，
而不是让我拿着一个假绿/假红的结果继续。）

### 3.6 blob 与关系模态的对照

这是 v0.8 最重要的产出 —— **第一个真正的模态**，
它让"模态"这个抽象从文档变成了代码。

| | 关系模态（heap + catalog） | blob 模态 |
|---|---|---|
| 寻址 | RID (page, slot) | blob_id（页号 + 1） |
| 页类型 | `PT_HEAP` | `PT_BLOB` |
| 页归属 | 表的 freelist | blob 模块自己管 |
| 版本 | xmin / xmax | **无**（对象不可变） |
| 可见性 | MVCC 快照判断 | **无**（要么存在要么不存在） |
| 删除 | 打 xmax + vacuum 回收 | v0.8 只增不减 |
| 生命周期 | insert/update/delete | 创建 → 写 → 定稿 |
| WAL | 行级日志（slot 镜像） | 整页镜像（`WAL_PAGEDATA`） |
| 目录 | catalog（4 张系统表） | blob 自己的目录（扫全文件重建） |

**共享的底座**：pager（缓冲池 + 页读）、WAL（崩溃安全）、
页格式（20B 页头 + crc16 校验）、`LOG_PAGEDATA` 日志类型。

**这正是 SPI 存在的意义**：模态是并列的，各自有自己的物理组织，
但共享底座。v0.8 做的 blob 就是第一个模态实现。

### 3.7 顺手做对的两件事

#### blob 的 REPL 命令

blob 有自己的 API（不是 SQL），所以 REPL 里给它单独的命令前缀：

```
BLOB CREATE <帧数> [内容]    创建（可同时写入）
BLOB WRITE <id> <内容>       写入
BLOB READ <id> <帧号>        读一帧
BLOB STAT <id>               元信息
BLOB LIST                    列出所有对象
```

**为什么不加成 SQL 语句**（`CREATE BLOB` / `SELECT FROM BLOB`）：
blob 模态还没接入 SQL 层（没有 SPI 的执行器接线）。
加 SQL 语句就要让 query 层认识 blob —— 那是 v0.9 SPI 接线时该做的事。
模态之间不许互相依赖，先给一个直接可用的命令入口。

#### 帧页的自校验

每个 blob 帧页在 `H_NEXT` 里存着自己的帧号。
读的时候校验 —— 帧号对不上立刻报错。

**为什么**：万一页号算错（映射的前提不成立），
会读到**别的帧**甚至**别的对象**的数据。
帧号对不上 → 立刻报错，而不是把错误数据返回给用户。

blob 页不用 `H_NEXT`（不用链），正好拿来存帧号。

### 3.8 还没做的

| 项 | 说明 |
|---|---|
| **全局 latch** | 方案里顺延过来的。仍是单线程。v0.9 |
| **SPI 接线** | blob 还没进 SQL 层。`spi/{storage_am,index_am,pushdown}.h` 三个接口待定稿 |
| **对象的删除与空间回收** | v0.8 只增不减。页回收需要"哪些对象没人引用了"的判据 |
| **分块上传 / 断点续传** | 对象的写入是一次性的 |
| **范围读** | 读第 100-200 帧。blob_read 已经支持整读，单帧读也有，加个循环即可 |
| **对象内的局部更新** | 不可变对象的设定，不做 |
| **页目录的持久化** | 现在靠扫全文件重建。对象极多时启动会慢 |

### 3.9 下一步（v0.9）
