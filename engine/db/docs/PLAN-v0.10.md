## 一、方案

### 1.0 这一版要证明什么

DESIGN.md D4 的原话：

> | v0.1–v0.7 | 单线程 | 先把正确性做对，排除并发干扰 |
> | v0.8 | 全局 latch（一把大锁） | 引入临界区概念，跑通多线程不出错 |
> | v0.9+ | 细粒度 latch + lock manager | crabbing、锁升级、死锁检测 |

（编号已修正为 v0.10 / v0.11+）

**这一版的目标是"不出错"，不是"更快"。**

判据只有一条：

> 多个线程同时用同一个库（多个连接），**数据不能错**：
> 不能丢行、不能串 xid、不能读到半写的行、崩溃后不能丢已提交的数据。

**明确不做的事**：吞吐优化、细粒度锁、锁管理器、死锁检测。
**一把大锁的代价（吞吐下降）本版只测量、不优化** —— 先要正确，再谈快。

### 1.1 范围

**做：**

1. `src/common/latch.{h,c}` —— 全局可重入互斥量（L0 基础设施）。
2. 所有**实例级共享状态**的访问纳入临界区。
3. 并发测试：多线程 × 多连接 × 混合读写 + 崩溃恢复。
4. 记录"大锁的代价"（吞吐基线），作为将来细粒度化的对照。

**不做：**

| 项 | 为什么 |
|---|---|
| 细粒度 latch | 细粒度化要求"临界区边界画在数据结构内部"，而当前的读接口返回**指向共享内存的指针**（见 §1.4）—— 这是下一版要解决的大问题 |
| lock manager / 死锁检测 | 只有一把锁时不存在死锁 |
| 无锁结构 / 原子操作 | 优化，不是这一版的目标 |
| RC/RR 的语义改动 | v0.7 已经把语义钉死了，这版只验证它在并发下仍然成立 |

### 1.2 竞态清单：哪些地方会出事

逐个模块列出**实例级共享的可变状态**，以及不保护会怎样：

| # | 模块 | 共享状态 | 不保护的后果 | 严重度 |
|---|---|---|---|---|
| 1 | **事务表** | `next_xid` | **两个线程拿到同一个 xid** → 一个回滚，另一个的提交被判为回滚 → **已提交的数据消失** | **致命** |
| 2 | **事务表** | `clog[]`、`active[]` | 提交/回滚状态互相覆盖 → 可见性判断错 | **致命** |
| 3 | **WAL** | `fd`、记录缓冲、LSN 计数 | 两个线程的日志记录**交错写** → 恢复时记录错乱 → **静默的数据损坏** | **致命** |
| 4 | **缓冲池** | `frames[]`、哈希表、`pin_count`、`hand` | 同一个页被分给两个线程 → 读到**半写的行**；或页被逐出而别人还拿着指针 → **野指针** | **致命** |
| 5 | **freelist** | 空闲页链表 | 同一个页分给两个表 → 两个表写同一页 → 数据互相覆盖 | **致命** |
| 6 | **catalog** | 表目录、列定义缓存、索引句柄 | 目录链表损坏 / 返回的列定义指针悬空 | 高 |
| 7 | **blob 目录** | `ids[]` | 数组扩容时另一个线程在读 → 读到半个对象 id | 高 |

第 1 条是最危险的：**xid 串号会让已提交的数据"消失"**，
而它只在特定的时序下发生 —— 单线程测试永远测不出来。

### 1.3 关键决定：锁的粒度选在哪

三个候选：

| 候选 | 做法 | 判决 |
|---|---|---|
| (a) 模块级临界区 | 在 pager / wal / txn / catalog 的公开入口各加一次锁 | **否决**（见下） |
| (b) **语句级大锁** | `db_exec` 全程持锁；`db_blob_*` 各自持锁 | **采纳** |
| (c) 只锁最热的两三处 | 只锁 xid 分配和 WAL append | **否决** —— 竞态有 7 处，漏一处就出事 |

#### 为什么否决 (a) 模块级临界区

方案里本来打算选 (a)（更接近"引入临界区概念"的教学目标）。
写方案时逐个模块推演，发现了一个**绕不过去的问题**：

**当前的读接口返回的是"指向共享内存的指针"，不是拷贝。**

```c
/* catalog.h */
int catalog_table_cols(Catalog *cat, u32 table_id, const ColDesc **cols, int *ncols);
/* 返回的指针指向 catalog 内部的缓存 */
```

如果锁只覆盖 `catalog_table_cols` 这个函数本身，
那么函数返回后锁就放了 —— 另一个线程这时 `CREATE TABLE`，
catalog 扩容了列定义数组 → **调用方手里的指针悬空** → 野指针。

同理还有：
- `pager_get` 返回 `PageFrame *`（指向缓冲池里的页）
- `heap_scan_begin` 返回一个跨多次调用的游标
- `blob_id_at` 返回目录数组里的元素

**要让模块级锁成立，所有读接口都得改成"拷出来"**（copy-out），
这是接口层面的重构 —— 值得做，但**不该和"引入锁"这件事混在一起**
（两个不确定叠加，调试成本会吃掉全部学习收益 —— 这正是 D4 的教训）。

所以本版选 (b)，并把"读接口要改成 copy-out"记成下一版的任务。

#### 语句级大锁的边界

```
db_exec(sql):
    latch_lock()
      解析 → 执行 → 结果构造
    latch_unlock()
```

- **锁覆盖整个语句** → 语句内的所有共享状态访问都被保护，
  不可能漏（漏的只可能是"某个共享状态没被任何语句碰到"）。
- **不在语句之间持锁** → 显式事务的多个语句之间不持锁，
  MVCC 照常工作（RR 的快照在事务开始时定，RC 每语句刷新）✓。
- 事务控制语句（BEGIN/COMMIT/ROLLBACK）也走 db_exec → 也持锁 ✓。

### 1.4 记一笔：细粒度化的前置条件

本版顺带确认了细粒度化的**真正难点**，记进 DESIGN.md：

> **要让锁画在数据结构内部，所有读接口必须从"返回共享指针"改成"返回拷贝"。**
> 否则锁只能覆盖"取指针"这一刻，取回去之后照样会被别人改。

这是 PG 用 "MVCC + 每连接缓冲" 回避问题的原因 ——
它的读路径本来就不共享页内存。

### 1.5 latch 原语的设计

```c
/* src/common/latch.h */

/*
 * 全局 latch —— 一把进程级的可重入互斥量。
 *
 * 【为什么可重入】
 * 语句级大锁会在**嵌套**中用到：语句执行 → pager 刷页 → WAL 钩子 → wal_fsync。
 * 不可重入的锁在这里会自己把自己锁死。
 *
 * 【为什么只有一把】
 * 一把锁 = 不可能有锁顺序问题 = 不可能死锁。
 * 细粒度化（多把锁）才需要定顺序 —— 那是下一版的事。
 */

/* 初始化（幂等，可以多处调用） */
void latch_init(void);

/* 加锁 / 解锁（可重入） */
void latch_lock(void);
void latch_unlock(void);

/*
 * 当前线程的持锁深度（调试用）。
 *
 * 用**线程本地**存储 —— 不是共享状态（硬规则 5 的精神：
 * "当前是谁"的信息不能放在共享对象里）。
 *
 * 用途：unlock 时如果深度 <= 0，说明解锁配对错了 —— 立刻报错，
 * 而不是等到莫名其妙死锁。
 */
int latch_depth(void);
```

**深度计数的价值**：它是"忘了解锁"的**即时**探测器。
没有它，忘了解锁的表现是"程序卡住"，排查要靠猜。

### 3.3 latch 原语的三个设计

#### 可重入

语句级大锁会在**嵌套**中用到：

```
db_exec → pager 刷页 → WAL 钩子 → wal_fsync
```

不可重入的锁在这里会自己把自己锁死。
用 `PTHREAD_MUTEX_RECURSIVE` 属性解决。

**反向验证第 2 轮的结果**：把锁改成不可重入 → **没有触发死锁**。
这暴露了一个测试盲区：**当前代码没有嵌套加锁路径**。
（也就是说，可重入性目前是靠"设计上不会嵌套"保证的，不是靠测试保证的。
这是本版的一个已知薄弱点，如实记录。）

#### 深度计数是线程本地的

```c
static _Thread_local int t_depth;
```

"当前持锁深度"是**每个线程各自的状态**，不是共享状态。
放进共享对象就变成"连接 A 的深度影响连接 B" —— 正是硬规则 5 说的那类错误。

`latch_unlock` 时如果 `t_depth <= 0` → **当场报错退出**（`abort`）。
理由：忘了解锁的典型症状是死锁（程序卡住），排查要靠猜；
当场抓住，成本差一个数量级。

#### 用 pthread 而不是 Windows API

MinGW-w64 的 winpthreads 提供 pthread 接口，Linux 上 pthread 是标准。
Windows 原生的 `CRITICAL_SECTION` 要写两套代码 ——
那会让"线程"这件事在代码里变得比它应该有的更复杂。

> **交叉验证**：4 线程 400 万次自增，
> 有锁版本**零丢失**，无锁版本**丢 290 万**。
> 这直接证明了临界区真的起作用了（不是"反正有锁肯定对"）。

### 3.4 加锁点：三个文件，12 处

| 文件 | 位置 | 数量 |
|---|---|---|
| `src/db_stmt.c` | `db_exec` 整个语句（含 BEGIN/COMMIT/ROLLBACK） | 1 |
| `src/db_blob.c` | `db_blob_create` / `write` / `read_frame` / `read` / `stat` / `count` / `id_at` / `page_reads` | 8 |
| `src/db.c` | `db_connect` / `db_close` / `db_abandon` | 3 |

**为什么 blob 的 8 个 API 要各自加锁而不是只锁 `db_exec`**：
blob 的公开 API **不走 `db_exec`** —— 它有自己的入口。
如果只在 `db_exec` 加锁，blob 这条路径就完全裸奔了。
这正是并发测试拆分后显式化的那条路径。

**`db_connect` / `db_close` / `db_abandon` 为什么要加锁**：
它们操作**实例的引用计数**和实例的销毁。
两个线程同时 `db_close` 同一个实例 → 一个把实例析构了，另一个还在用 → 野指针。
现在 `db_close` 是引用计数，最后一个引用才销毁。

### 3.5 挖出一个 v0.8 遗留的真 bug：blob_create 头页 pin 泄漏

这是本版最有价值的产出 —— **不是新写的代码有 bug，是老代码里的 bug 被并发测试照了出来**。

#### 现象

并发 blob 测试报 `db_blob_create` 失败，`E_NOSPACE`。

#### 追查路径

```
db_blob_create 失败 (E_NOSPACE)
  → pager_alloc 返回 E_NOSPACE
    → 缓冲池 256 帧耗尽
      → 但磁盘上明明还有空间
        → 说明帧被"占着"却没人用
          → pin_count 没归零
            → 谁漏了 unpin？
```

顺着 `blob_create` 的分配流程看：
分配了**三样**带页的东西 ——
帧页（unpin 了）、索引块页（unpin 了）、**头页（忘了）**。

```c
/* 立刻 unpin 头页（v0.10 修的真 bug）。
 * blob_alloc_page 返回的帧是**被 pin 住**的（调用方负责 unpin）。
 * 帧页和索引块页都 unpin 了，唯独头页漏了 ——
 * 于是**每建一个对象就泄漏一个 pin**。 */
pager_unpin(bs->pager, head_pid, true);
```

**为什么 v0.8 没发现**：单线程测试建的对象少（远少于 256），
泄漏到测试结束都没把缓冲池撑爆。
**并发把创建次数放大了 4 倍 × 320 次 = 1280 个对象** → 远超 256 帧 → 撑爆。

#### 回归测试

`test/unit/test_blob.c` 的 t11：

```c
/* 建 400 个对象（远超 256 帧）→ 断言全部成功 + 缓冲池占用没涨 */
CHECK(created == 400);
CHECK(pager_frames_used(pg) <= 64);
```

**反向验证**（第三轮）：移除那句 `pager_unpin` →

```
FAIL test/unit/test_blob.c:578: created == 400
  1 项失败 [FAIL]
```

恢复后全绿。**证明测试真的在测这件事。**

#### 教训

> **资源泄漏在低负载下是不可见的。**
> 单线程 + 小规模是最容易让人以为"没问题"的组合。
> 引入并发（或者只是把规模提上去）会把这类 bug 从"看不见"变成"立刻爆"。
>
> 另一条教训：**pin 的所有权必须写清楚**。
> `blob_alloc_page` 返回的是**被 pin 住的**帧 —— 这个约定只写在函数注释里，
> 调用方漏了就是漏了。更好的做法是让 API 自己管（比如返回时同时给出 unpin 的责任说明，
> 或者提供 `blob_alloc_page_unpinned`）。本版没改接口，但把约定写进了注释。

### 3.6 三轮反向验证

| # | 注入什么 | 结果 | 结论 |
|---|---|---|---|
| 1 | `latch_lock` 变成空操作 | 测试红 + **挂死**（被看门狗抓到） | ✓ 测试真的在测并发正确性 |
| 2 | 锁改成**不可重入** | **没变红** | ✗ 暴露盲区：当前没有嵌套加锁路径 |
| 3 | 移除 blob 头页的 `unpin` | `test_blob` t11 变红 | ✓ 回归测试有效 |

**第 1 轮的挂死**：去掉锁后缓冲池的哈希表被写坏 → `hash_find` 的探测序列
永远遇不到 `EMPTY` → 死循环。**如果没有看门狗，整个测试套件会卡住。**
这直接证明了看门狗的必要性。

**第 2 轮是个诚实但不舒服的结果**：它说明可重入性目前是"设计上保证"的，
不是"测试保证"的。如实记入风险清单。

**第 3 轮挖出了真 bug**（见 §3.5）。

### 3.7 踩到的坑

#### 坑 1：测试自己把 bug 藏起来了

第一版的 t2（xid 串号）用**标志**来排序：
A 插完 → 才让 B 开始。

结果是两个 `BEGIN` 被拉得很开 → **xid 分配根本不可能撞车** →
测试永远是绿的 → 什么也没测到。

**修法**：改用**屏障**，让两个 `BEGIN` 真正同时发生。

> **教训**：并发测试的价值完全取决于**它有没有制造出真正的并发**。
> 一个"顺序执行但用了线程"的测试，比单线程测试更危险 ——
> 因为它给人"已经测过并发了"的错觉。

#### 坑 2：t7 对 blob 的竞态不敏感

去掉 blob API 的锁之后，t7 仍然绿。
提高到 300 次只创建 + 20 次写读校验，**仍然绿**。

**原因**：blob 的操作 I/O 密集，线程之间的窗口被 I/O 拉开了。

**如实记录**：这一项**对数据竞态不敏感**。
但它测到了另一类问题 —— **页/pin 泄漏**（§3.5 的真 bug 就是它抓到的）。
所以它的定位应该改成：**并发路径上唯一能稳定抓到资源泄漏的探针**。

#### 坑 3：并发测试挂死比失败更糟

无锁版本会让哈希表坏掉 → 死循环 → 整个测试套件卡住。
加了**看门狗**（120 秒超时 → 打印 FAIL 并 `exit(1)`）。

> 看门狗报的"疑似死锁"和断言失败**是同等有效的失败信号** —— 它不是掩盖问题。

#### 坑 4：Makefile 的 pthread 链接

MinGW-w64 的 winpthreads 在默认库里（不需要 `-lpthread`），
Linux 需要。`Makefile` 和 `test/run.sh` 都要处理：
用 `uname -s` 判断（`MINGW*` / `MSYS*` / `CYGWIN*` → 空，其他 → `-lpthread`）。

#### 坑 5：统计误报

`mingw32-make | grep -cE 'error|warning'` 把命令行里的 `-Werror` 也计进去了。
改用 `grep -E 'error:|warning:'` 精确匹配。

### 3.8 还没做的

| 项 | 为什么 |
|---|---|
| **细粒度 latch + lock manager** | 本版只做"不出错"。前置条件（读接口 copy-out 重构）见 §1.4 |
| **读接口 copy-out 重构** | `catalog_table_cols` / `pager_get` / `blob_id_at` 仍返回共享内存指针 |
| **吞吐基线测量** | 方案 §1.1 提到要记录大锁的吞吐代价，本版**没做**（顺延） |
| **嵌套加锁路径的测试** | 反向验证第 2 轮暴露的盲区 |
| **hint bits** | v0.9 起一直顺延 |
| **页内 compact / B+tree 物理日志 / 日志截断 / group commit** | 历史顺延项 |
| **`btree.c`(1038) / `catalog.c`(927) 超 800 行** | 历史遗留。本版碰过的文件全部合规 |

### 3.9 固化的三条纪律

1. **一把锁就不会死锁** —— 不是"锁得够细所以安全"，
   而是"只有一把锁所以不存在锁顺序"这个结构性保证。
   细粒度化会**重新引入**死锁问题，那时要先定顺序规则。

2. **锁的边界要覆盖整条路径，不能只覆盖一半** ——
   blob 的 API 不走 `db_exec`，只锁 `db_exec` 就等于 blob 裸奔。
   **每加一条新的入口路径，就要问一句：它加锁了吗？**

3. **测试必须真的并发** —— 用线程不等于并发。
   如果同步设计让两个关键操作"错开了"，测试就白写了。
   **屏障**是让两个 `BEGIN` 真正撞在一起的唯一办法。

### 3.10 下一步（v0.11）

**模态 2：图**（原计划的 v0.10）。

图模态对标 Neo4j 的定长记录模型，天然满足 `slot = 记录序号`，
RID 不用像 blob 那样妥协成 `(base_page + frame_no, slot=0)`。

验收目标：10 万节点 / 100 万边 / 3 跳 p99 < 10ms。

前置条件已就位：
- SPI 定稿（v0.9）→ 图模态只需写一个 `StorageAM` 适配 + 一套定长记录存储
- 全局 latch（v0.10）→ 读写路径的并发安全已有基础
- 执行器模态无关（v0.9）→ 图接进 SQL 不需要改执行器

**先决的一步**：图模态的行模型设计 ——
节点的"行"是什么？边的"行"是什么？
（blob 的教训：一行 = 一帧。图的对应物大概是**一行 = 一个节点记录**，边另算。）

## 四、这一版的一句话总结

> 并发的第一步不是"加锁"，是**决定锁画在哪**。
> 画错了（画在数据结构内部），前提是要先把所有读接口改成返回拷贝；
> 画粗了（语句级大锁），代价是吞吐，但正确性有保证。
> **先要正确，再谈快** —— 这和 D4 当初"并发分三步走"的判断完全一致。
