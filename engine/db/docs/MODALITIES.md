# 八模态实现方案

> **这份文档是什么**：按**模态**组织的实现方案总文档 —— 每个模态一节，
> 讲清它的定位、行模型、物理布局、事务语义、SPI 三件套（虚拟表 · 能力位 · 下推）、
> 索引与外部值、与执行器的关系、本版范围与明确不做项。
>
> **它不是什么**：不是版本计划。版本计划回答「什么时候做、按什么顺序做、验收怎么测」，
> 见 `PLAN-v*.md`；本文档回答「每个模态的机制长什么样、判决是什么、为什么这么判」。
>
> **怎么用**：要执行某一版 → 读对应的 `PLAN-vX.Y.md`；
> 要理解某一模态的设计全貌、或者要给第 9 个模态做参考 → 读本文档对应节。

一个实测出来的缺口：`DESIGN.md` §5 SPI 是「多模的唯一扩展点」，

本文档把散落的判决**按模态收拢成一处**，同时不重复 PLAN 已经在做的事：

### 1.1 一屏看完

这是八模态里唯一的例外，其余七个各有独立存储。

### 1.2 三个"为什么不是关系模态的类型"的对照

八模态不是"八张表"，而是**八套物理组织**。判据只有一条：
**它的访问模式与关系模态的 tuple 模型不相容，就必须是独立模态。**

| 模态 | 与关系模态冲突的地方 | 冲突性质 |
|---|---|---|
| blob | 一行 = 一帧（4076B 定长），一帧独占一页，页不是"装 N 字节的行" | **寻址单位**不同 → RID 语义不同 |
| graph | 一页几十个定长记录，位置纯算术；边是**指针**不是值 | **记录结构**不同 → slotted page 的 slot 数组纯属浪费 |
| vector | 128 维 fp32 = 512B，按行存则相邻向量分散在页各处 | **布局**不同 → 列式才可扫 |
| ft | segment **写完即不可变**，删除只打标记 | **生命周期**不同 → 与 MVCC 版本链正交 |
| geo | 键不是一维全序，是"相交 / 包含 / mindist" | **比较关系**不同 → `index_key` 装不下 |
| ts | 同一分区内按时间追加、几乎不更新、旧数据变冷 | **生命周期**不同 → 行式 vs 列式的格式转换时机 |
| json | 自描述，schema-less，值表示与索引是难点 | **值表示**不同 → 路径值映射成通用标量才进得了 SQL |

### 1.3 三条贯穿线索

八模态的设计不是八次独立发明，是**三个思想各重复四次**：

**线索一：不变文件 + 后台合并（×4）**

| 出现处 | "不可变的东西" | "合并/压缩" |
|---|---|---|
| blob | 对象（写完定稿） | 无合并（对象级不可分） |
| 全文 | segment（写完不可变） | Tiered 合并：字典多路归并 + tombstone 物理丢弃 |
| 向量 | 向量数据页（只追加） | 无合并；索引层做增量插入 |
| 时序 | 封窗后的分区（不可变） | 封窗压缩 = 行式 → 列式的格式转换 |

**线索二：外部值 + 惰性物化（×3）**

| 出现处 | 值层里放什么 | 内容在哪 |
|---|---|---|
| blob | `ext_key = blob_id`，`ext_off = frame_no` | 帧页（读第 N 帧 = 1 次页读） |
| 向量 | `ext_key = row_id`，`ext_off = 序号` | 向量数据页（只查元数据不读向量） |
| 大 JSON | `ext_key = 首页页号`，`ext_off = 偏移` | `PT_JSON_OVF` 页链（沿链读） |

三条纪律（v0.9 定，逐字适用于三者）：
**只在输出路径物化 / 比较时必须物化（要么对要么报错，不许近似比较）/ 物化失败要报错不能给空。**

**线索三：下推只能给超集（×7）**

除 blob 外的每个模态都要面对下推。统一判据是：

> **执行器能不能独立重判？**
> 能 → 进 SQL 谓词（下推是优化，执行器复核）；
> 不能 → 走专用 API（下推不成立，只能是主路径）。

| 模态 | 谓词 | 执行器能独立重判吗 | 判决 |
|---|---|---|---|
| 关系 | `col op const` | 能 | 进 SQL |
| blob | 按属性过滤 | 能（属性在行内） | 进 SQL |
| 图 | `src = RID` / 属性列 | 能 | 进 SQL |
| 向量 | 标量属性（label） | 能 | 进 SQL；**距离排序不进** |
| 全文 | `match(col, 'term')` | **不能**（相关性依赖全局统计 idf/avgdl） | **专用 API** |
| 空间 | 窗口 / KNN | **不能**（几何语义） | **专用 API** |
| 时序 | 时间范围 | 能（分区裁剪只是少读） | 进 SQL |
| 文档 | `json_match(doc, '$.a.b = 5')` | **能**（路径值 → 通用标量） | 进 SQL |

一进一不进的判据是同一条，**不是"这个模态特殊"**。这条边界在 v1.4 结束后写进 `DESIGN.md` 复盘。

### 1.4 事务语义三足鼎立

八模态的可见性语义收敛成**三种**，没有第四种：

| 语义 | 用在 | 可见性怎么答 | 提交粒度 | WAL |
|---|---|---|---|---|
| **MVCC 版本链** | heap（+ JSON 列） | `am->visible()` 查快照三元组 + clog（`DESIGN.md` §7.5） | 显式事务（RC / RR） | 行级日志 |
| **不可变对象** | blob | `visible()` **恒真** | 无事务（写完即最终态） | 整页镜像，xid 传 0 |
| **锁 + WAL** | graph / vector / ft / ts | `visible()` **恒真**（记录要么在用要么空闲） | 语句级（每条语句一个隐式事务） | 整页镜像，xid 传 0 |

**为什么 graph/vector/ft/ts 不能上 MVCC**：
图的邻接链是指针，版本化意味着指针要跟着版本走（Neo4j 不这么做的原因）；
ft 的 segment 不可变，版本链无处可挂；
时序的行不可变是建模前提（唯一删除路径是 TTL 整分区）；
向量的 HNSW 图是指针结构，删点要重建（v1.0 明确只支持插入）。

**三种语义到执行器的接口是同一个** —— 因为可见性判断本来就在 `am->visible()` 里。
执行器不关心差别，这是 SPI 设计的回报。

**代价必须记下来**（`DESIGN.md` §8 风险清单的延续）：

| 代价 | 后果 | 缓解 |
|---|---|---|
| graph 无版本链 + 空闲记录立即复用 | 读游标跨语句可能看到记录被复用 | 图游标只在单语句内有效（文档写死） |
| ft / vector / ts 语句级提交 | 不参与 BEGIN/COMMIT 的多语句事务 | 文档写死；跨模态事务（v1.7+）另议 |
| blob xid=0 | 将来多段上传需要真 xid 清理未完成对象 | 记在案，届时改 |

## 2 · 模态 0：关系（heap）—— 一切的基础

> 已落地（v0.1–v0.7）。本节是**参照系**：后面七个模态都拿它做对照。
> 详细设计见 `DESIGN.md` §3（数据模型）、§7.5（可见性规则）、§10.1（SQL 子集）、§10.2（类型系统）。

### 2.1 定位与对标

PostgreSQL 的 heap、SQLite 的 b-tree 表、MySQL 的 InnoDB clustered index。
本项目的 heap 是**纯堆表**：无主键、无聚簇、无行存表。
（B+tree 是独立的索引结构，见 `DESIGN.md` §3.2 / §9。）

### 2.2 行模型与 RID

- **一行 = 一个 tuple**（变长记录，`storage/record.{h,c}` 编码）
- **RID = (page_id, slot)**，slot 是页内 slot 数组的下标
- tuple 头含 `xmin` / `xmax` 两个事务字段 → **这是 MVCC 版本链的载体**

### 2.3 物理布局

slotted page（`storage/page.{h,c}`）：20B 页头 + 变长记录区 + 4B slot 数组
（`offset:u16 + length:u16`）。页类型 `PT_HEAP`。

### 2.4 事务语义

**MVCC 版本链**（RC / RR）。快照三元组 `(xmin, xmax, xip[])`，
插入者/删除者的可见性规则见 `DESIGN.md` §7.5（那一节标注了"必须能背出来"）。

关键分支：「区间内但不在 `xip` 里」**必须查 clog**，不能"保守地当作未提交"——
写错的代价是**已提交的数据读不出来**（静默丢数据）。

### 2.5 SPI 落地三件

| 项 | 内容 |
|---|---|
| **虚拟表** | 不用 —— 关系表在 catalog 里（持久化元数据），**不走注册表** |
| **能力位** | `AM_CAP_SCAN \| INSERT \| UPDATE \| REMOVE \| PUSHDOWN \| VACUUM \| INDEX`（全给）+ `AM_CAP_BATCH_SCAN \| AM_CAP_BATCH_DECODE`（v1.2 步骤 0，见 §10.2.1） |
| **下推** | `col op const` 全支持（值在 tuple 内，AM 逐行自滤 → 超集语义） |

### 2.6 与执行器的关系

`spi/heap_am.{h,c}` 是唯一的适配层。执行器（`query/exec*.c`）**不认 heap** ——
它只拿 `StorageAM*`。验收方式是机械的：`grep blob src/query/exec*.c` 只能命中注释。

### 2.7 本版范围与不做项

已覆盖：建表 / 插入 / 更新 / 删除 / 扫描 / 聚合 / 索引 / MVCC / vacuum / 崩溃恢复。

**不做**（`DESIGN.md` §10.1 的 SQL 子集决定）：JOIN、递归 CTE、复合类型。
（本模态是「参照系」，其余七节的对标对象都是它。）

### 2.8 关键坑

**坑 M0-1 · RID 空间是表内的**
每张表有自己的 RID 空间，`blob_frames` 与 `blob_objects` 的 RID 互不相干，
**也不该互相比较**。跨表比较 RID 是没有意义的。

**坑 M0-2 · 单连接测不出可见性 bug**
单连接时 `xmin == xmax`，区间是空的，永远走不到那个分支。
**必须专门构造多连接场景**（有长事务占着区间）才暴露。已踩过。

**坑 M0-3 · xid 不能藏在共享对象里**
`wal_set_xid(w, xid)` 这种写法在多连接下会让 A 的日志带上 B 的 xid →
恢复时 **A 的未提交数据被判为已提交**。铁律：所有写接口显式传 `u32 xid`。

## 3 · 模态 1：blob —— 第一个模态，也是 SPI 的样板

> 已落地（v0.8 实现，v0.9 接进 SQL）。本节是**唯一的"已落地样板"**，
> 后面六个模态的实现方案都拿它当模板。
> 字节级施工图纸见工作区根目录 `blob模态实现规格.html`。

### 3.1 定位与业界对标

S3 / MinIO 的对象存储、MongoDB GridFS、Parquet / Lance 的分块文件。
共同点：**把大字节流切成定长块，随机访问的 IO 量与对象大小无关。**

### 3.2 为什么它是独立模态，不是关系模态的大字段类型

| | 关系模态 | blob 模态 |
|---|---|---|
| 寻址 | RID (page, slot) | blob_id（**页号 + 1**） |
| 页类型 | `PT_HEAP` | `PT_BLOB` = `0x06` |
| 页归属 | 表的 freelist | blob 模块自己管 |
| 版本 | xmin / xmax | **无**（对象不可变） |
| 可见性 | MVCC 快照判断 | **无**（恒可见） |
| 删除 | 打 xmax + vacuum 回收 | v0.8 只增不减 |
| WAL | 行级日志 | 整页镜像（复用 `WAL_PAGEDATA`） |
| 目录 | catalog（4 张系统表） | **blob 自己的目录**（扫全文件重建） |
| 写能力 | 可写 | **只读**（对象不可变，SQL 侧返回 `E_NOTSUP`） |

**共享的底座**：pager（缓冲池）、WAL（崩溃安全）、页格式（20B 页头 + crc16）、`WAL_PAGEDATA` 日志类型。

### 3.3 行模型：帧才是行

| 候选 | 判决 |
|---|---|
| (a) 一行 = 一个对象 | 只看得到元信息；对象内部的帧**无法被寻址**（RID 指不到具体内容） |
| (b) **一行 = 一帧** | **采纳**：帧是 blob 唯一的可寻址单位；粒度也和别的模态对齐 |
| (c) 一行 = 一段变长字节 | 行没有稳定身份 → **RID 表达不了**，SPI 的核心约束直接崩 |

**为什么"帧"是对的**：帧是 blob 唯一的可寻址单位（RID 要能定位到最小可读单位）；
粒度对齐（图的一行 = 一个节点，向量的一行 = 一个向量，blob 的一行 = 一帧 ——
三个模态的行粒度都是**该模态的最小可寻址单元**，这是 SPI 要求的统一，
而不是"都长得像关系表"）；帧行带着 blob_id，就能定位回对象。

**RID 怎么定**：

```
blob_frames 的 RID = (页号 = base_page + frame_no, slot = 0)
blob_objects 的 RID = (头页页号 = blob_id - 1, slot = 0)
```

`slot` 恒为 0：一帧独占一页，一页一行。

**已知限制**：RID → 行的反解靠遍历 blob 自己的对象目录（O(对象数)）。
将来的修法是 blob 自己维护一张"页号 → 对象"的反查表。
注意这里用的是 **blob 自己的目录**，不是 catalog —— 模态之间不许互相依赖。

### 3.4 物理布局

**帧号 → 页号用纯算术**：对象一次写完（不可变），页连续分配，
所以 `第 N 帧 → 页号 base_page + N`。读一帧 = 1 次页读（+ 头页，可缓存）。

索引块的数据结构照样建了（为"页不连续"的未来留接口），但快路径绕开了它 ——
**为扩展留好接口，但不提前付代价**。

关键常量（全部来自 `src/storage/blob.h` / `blob_hdr.h`）：

| 常量 | 值 | 出处 |
|---|---|---|
| `BLOB_FRAME_SIZE` | `PAGE_SIZE − HDR_SIZE` = **4076** | 一帧可用字节 |
| `BLOB_FRAMES_PER_INDEX` | 1024 | 索引块覆盖的帧数 |
| `PT_BLOB` | `0x06` | 页类型 |
| `BLOB_MAGIC` | `0x424C4F42` | 对象头 magic |
| `BLOB_HDR_FIXED_SIZE` | 44 | 头页固定部分 |
| `blob_id` | **页号 + 1** | 让 `id = 0` 天然表示无效 |

对象头字段偏移（`blob_hdr.h`）：

```
BH_MAGIC = 0    BH_VERSION = 4    BH_NFRAMES = 8   BH_FRAME_SIZE = 16
BH_TOTAL_LEN = 20   BH_BASE_PAGE = 28   BH_N_INDEX_BLK = 32   BH_INDEX_BLK = 36
```

**blob 页不进任何表的 freelist**：表的 freelist 回答"哪一页能放下 N 字节的行"；
blob 页是"一整页装一帧"。语义不同，混用会写坏数据。

**blob 有自己的目录，不依赖 catalog**：catalog 是关系模态的元数据，
blob 依赖它 = **模态之间互相依赖**，这正是 SPI 明确禁止的（硬规则 6）。

### 3.5 事务语义

**不参与事务，WAL 的 xid 传 0（系统事务）。**

对象不可变（创建 → 写 → 定稿）⇒ 没有"回滚到旧版本"，没有并发写同一对象的问题。
但它**写 WAL**，所以崩溃后数据不丢。xid=0 在恢复时视为"永远已提交" ——
正是我们要的：blob 页写完的瞬间就是最终状态。

> 将来若支持"多段上传、最后合并"，就需要给它真正的 xid，
> 让未完成的对象在恢复时被清理。这条记在案。

### 3.6 SPI 落地三件

**虚拟表：两张，不是一张**

| 表 | 一行 = | 列 |
|---|---|---|
| `blob_frames` | 一帧 | blob_id / frame_no / data_len / data_off / data |
| `blob_objects` | 一个对象 | blob_id / nframes / frame_size / total_len |

为什么两张：对象级元信息（帧数 / 帧大小 / 总长）放在帧表里是**每行冗余一遍**。
一张表要么冗余要么缺。两张表各自语义干净，还顺带证明了一件事：
**一个模态可以提供多张表**。

`data_off` = 这一帧在数据文件里的字节偏移 = `页号 × 4096 + 20`。
它就是业界说的**外部引用**（Parquet 的 column chunk offset、
ClickHouse 的外部字符串引用都是这个形态）：拿到 offset + length，任何人都能直接去文件里定位。

**能力位**：`AM_CAP_SCAN | AM_CAP_EXTERNAL`（只读；`INSERT/UPDATE/REMOVE` 不给 →
SQL 侧返回 `E_NOTSUP`）。

**下推**：按帧内属性过滤可下推（超集语义）；但 v0.8 阶段 blob 无属性列，
实际可下推的谓词为空 —— 能力位上 `AM_CAP_PUSHDOWN` 不给。

### 3.7 外部值：blob 是第 1 个用户

一帧 4076 字节；`DbValue` 的文本上限是 255 字节。三条路：

| 路 | 做法 | 判决 |
|---|---|---|
| 1. 截断 | 只留前 255 字节 | **否决**。SQL 返回的值和实际内容不符 = 静默的数据错误，比报错更坏 |
| 2. 加大值类型 | `DbValue.s` 改成 4KB | **否决**。每值 4KB、每行 16 列 = 64KB；而且**值变大并不会让扫描变便宜** —— 扫描时把每帧内容读出来，1GB 对象就要读 1GB。而"只查帧号和长度"本该只读对象头 |
| 3. **外部值** | 值里存"句柄 + 取回方法"，内容**被需要时**才读 | **采纳** |

外部值的结构在 `storage/value.h`：`ext_key`（模态内部对象标识）+ `ext_off`（模态内位置）+
`ext_fn`（取回函数）+ `ext_ctx`（模态上下文）。

**三条纪律**：

1. **外部值只在输出路径物化**。过滤、投影的中间过程**不**物化。
   这正是"扫描 blob_frames 不读帧页"的实现方式 —— 不是靠优化器，是靠值的形态。
2. **比较时必须物化**（`val_cmp` 遇外部值先物化再比）。要么对，要么报错，**不能"近似比较"**。
3. **物化失败要报错，不能给空**。空的 TEXT 和"内容是空串"是两回事。

**外部值不持有堆内存** —— 它只持句柄和函数指针。
物化出来的缓冲由结果集自己管（`b_push` 里 free）。
这样 `DbValue` 依然可以按值随意拷贝，不会出现"谁负责 free"的问题。

### 3.8 一个容易搞错的错误码

页号空间是**共享**的 —— 关系模态的页也占页号。
而 `blob_id = 页号 + 1`，所以 `blob_id = 1` 可能指向**任何页**。

| 情况 | 错误码 | 为什么 |
|---|---|---|
| id 指向的页不是 blob 头页 | `E_NOTFOUND` | 「这不是 blob 对象」是正常情况 |
| 是 blob 头页但 magic/crc 不对 | `E_CORRUPT` | 真的是数据坏了 |

**返回 CORRUPT 会把用户误用说成"库坏了"，把排查方向带偏。**

### 3.9 本版范围与不做项

**做**（v0.8 已落地）：对象 → 帧 → 页的分块存储、帧号 → 页号的纯算术映射、
blob 自管目录（扫全文件重建）、WAL 整页镜像、`blob_frames` / `blob_objects` 两张虚拟表、
外部值（第 1 个用户）。

| 不做 | 为什么 |
|---|---|
| **对象的删除与空间回收** | v0.8 **只增不减** —— 删除要配套"哪些帧可回收"的目录改造，留待后续 |
| 多段上传 / 断点续传 | 需要真正的 xid 让未完成对象在恢复时被清理（见 §3.5 的记案） |
| 范围查询（读第 100–200 帧） | 读单帧是自然的扩展；范围读是 IO 批次的优化，不改机制 |
| 压缩 / 加密 | 帧是定长原始字节，压缩会让"帧号 → 页号"的算术映射失效 |
| blob 属性的下推 | v0.8 阶段 blob 无属性列，`AM_CAP_PUSHDOWN` 不给 |

### 3.10 关键坑

**坑 M1-1 · `blob_id = 页号 + 1` 让首对象 id = 0**
`id = 0` 必须是"无效"，所以 id 从 1 起。**任何地方都不能把 id 0 当有效对象**，
包括"id 为 0 表示全集"这类约定 —— 那会和无效值撞车。

**坑 M1-2 · 末帧填充 0 与真实数据无法区分**
对象总长不是帧长的整数倍时，末帧要填 0 补齐。
但**填充的 0 和真实数据里的 0x00 一模一样** —— 必须**单独存 `total_len`**
（`BH_TOTAL_LEN`），靠它算出末帧的有效长度。少存这一个字段 = 读多出垃圾字节。

**坑 M1-3 · 帧号 → 页号算错会静默读到别人的数据**
`base_page + N` 算错**不报错**，只会读到相邻页的内容 —— 读出来是别的对象的数据。
帧号→页号的换算必须与页分配顺序**同一个不变量**；写页读页都要走同一个函数。

**坑 M1-4 · 页语义不是"行" → 不进表 freelist**
表 freelist 的语义是"哪页能放下 N 字节的行"；blob 页是"一整页装一帧"。
混用会写坏数据（把半帧写进被当成行槽的页）。

**坑 M1-5 · 反向验证跑旧二进制**
注入 bug 后必须**先确认编译通过再跑**（v0.7 起每次都踩）。
`make` 没报错不代表跑的是新二进制 —— 老规矩：**先看编译输出**。

## 4 · 模态 2：图 —— 定长记录 + 指针链

> 计划：`PLAN-v0.11.md`（已定稿）。字节级施工图纸见工作区根目录 `图模态实现规格.html`。

### 4.1 定位与业界对标

Neo4j / NebulaGraph / TigerGraph。核心机制是**邻接链**：定长记录里存指针，
指针跳转 = 一次 `get(am, rid)` 直接命中，没有任何间接层。

### 4.2 为什么它是独立模态

三个候选（`PLAN-v0.11.md` §1.2）：

| 候选 | 判决 |
|---|---|
| (a) 边内联在节点记录里 | **否决** —— 内联数组让记录变长，"定长"这个前提就没了 |
| (b) 边存普通堆表，图只管节点 | **否决** —— 3 跳 = 沿边链跳，边记录若藏在 B+tree/slotted page 里，跳一次 = 一次页内 slot 查找 + 可能在任意页；定长记录的直接算术定位正是本版的理由 |
| (c) **节点和边都是定长记录，边挂双向邻接链** | **采纳** |

**为什么边要两条链（出链 + 入链）**：3 跳查询走的是**有向**遍历（沿出边）；
但"谁指向我"的反向查询（入边）在图应用里同样高频（Neo4j 两种都维护）。
没有入边链，反向查询 = 全表扫边 —— 100 万边的全扫每次几毫秒，p99 必炸。

### 4.3 行模型与 RID

**图的行 = 一个节点或一条边。**

| | RID |
|---|---|
| `graph_nodes` | 节点记录的 `(page, slot)` |
| `graph_edges` | 边记录的 `(page, slot)` |

**边记录里存的 src/dst 就是节点 RID** —— 指针跳转 = `am->get(am, rid, ...)` 直接命中。
定长记录送的礼物：blob 需要纯算术换算（`base_page + frame_no`），图连换算都不用。

**记录布局**（对齐 Neo4j，逐字段注明用途）：

```
节点记录（定长 GR_NODE_SIZE，预估 ~40B）：
  in_use        1B    在用标记（0 = 空闲，挂在空闲链上）
  next_free     4B    空闲链：下一个空闲节点（in_use=0 时有效）
  first_out     8B    第一条出边的 (page,slot)   ← 邻接链的头
  first_in      8B    第一条入边的 (page,slot)   ← 反向链的头
  prop[...]     定长  本版固定列的属性

边记录（定长 GR_EDGE_SIZE，预估 ~48B）：
  in_use        1B
  next_free     4B
  src           8B    起点节点 (page,slot)
  dst           8B    终点节点 (page,slot)
  out_prev      8B    起点出边链的 .prev   ← 双向链：删除 O(1)
  out_next      8B    起点出边链的 .next
  in_prev       8B    终点入边链的 .prev
  in_next       8B    终点入边链的 .next
```

**属性怎么办（本版的最简裁决）**：节点属性用**固定列 schema**（建图时声明列，复用 `ColDesc`），
属性内联在节点记录的 prop 区。**列类型限 INT / FLOAT / TEXT(定长)**。
理由：本版要验证的是**拓扑机制**，不是属性系统 ——
属性系统的真实复杂度（变长、嵌套、索引）值得单独一版。

**schema 必须落盘（v0.11 步骤 4 补）**：节点记录是**定长**的，
长度 = 公共头 + NULL 位图 + 各列宽度之和 ——
记录里**没有**"这一列多宽"的信息，宽度只存在于 schema 里。
所以 schema 不落盘 = 重启后整张图变成一堆看不懂的字节
（连节点数都数不出来：`gstore_recover` 会先因为 `rec_size` 对不上而 E_CORRUPT）。

落盘方式：**第三个 gstore**（页类型 `PT_GRAPH_SCHEMA`）。
排除掉的两条路：塞进节点记录（每条存一份 = 纯浪费，且改 schema 会改所有记录长度）、
塞进 catalog（硬规则 6：catalog 不知道任何模态）。

**schema 是图的身份，一经确定不可更改**：磁盘上已有 schema 且与传入的
**逐列相同** → 接管这张图；不同 → E_INVAL。
只比记录总长是不够的 —— `INT4+INT4` 和 `INT8` 长度一样，布局完全不同。

### 4.4 物理布局：定长槽页，不用 slotted page

现有 `page.c` 是 slotted page（变长记录 + slot 数组）。图的记录是定长的，
用 slotted page 是自缚手脚：

| 候选 | 判决 |
|---|---|
| (a) 复用 slotted page，每记录一个 slot | **否决** —— slot 数组是给变长记录定位用的；定长记录的位置纯算术可得，slot 数组纯属浪费一倍空间 |
| (b) **定长槽页**：一页 = 固定 N 个槽，`slot i` 的位置 = `页头 + i × rec_size` | **采纳** |

```
图页头（16B）：
  magic/type    页类型（PT_GRAPH_NODE / PT_GRAPH_EDGE）
  rec_size      记录大小（节点页 / 边页各自固定）
  nslots        本页槽数 = (4096 - 16) / rec_size
  free_head     本页空闲链头（slot 序号，-1 = 无）
```

**RID = (page_id, slot)。记录物理位置 = 页内偏移，纯算术，零查找。**

**删除**：`in_use = 0`，`next_free` 指向页空闲链头，页头 `free_head` 指向它。
**分配**：先看页空闲链，再开新页。空闲记录**立即复用**（Neo4j 同款）——
代价见 §4.5。

**页类型**：新增 `PT_GRAPH_NODE` / `PT_GRAPH_EDGE`，**不进任何表的 freelist**
（对齐 v0.8 硬规则 6：模态各自管自己的页）。

### 4.5 事务语义：锁 + WAL，不做 MVCC

这是本模态**最重要的设计判决**，因为图记录是**可变**的（blob 对象不可变），
SPI 的 `visible()` 回调必须有人回答"图行怎么判可见"。

| 候选 | 判决 |
|---|---|
| (a) 图也上版本链（UPDATE = 插新版本） | **否决** —— 邻接链里的指针全要跟版本走（Neo4j 不这么做的原因就是指针稳定性），复杂度爆炸 |
| (b) **就地更新 + 恒可见 + 语句级提交** | **采纳** |
| (c) 图模态只读 | **否决** —— 图的写路径（边链双端维护）正是本版要练的东西 |

判决 (b) 的完整语义（**对齐 Neo4j 的真实选择 —— 它也是锁 + WAL，不做 MVCC**）：

| 方面 | 语义 |
|---|---|
| 可见性 | `visible()` **恒真**（记录要么在用要么空闲，没有中间态给读者看） |
| 隔离 | **写者互斥**（全局 latch 保证）+ **读不加锁**。并发读写一个节点：读到旧值或新值，不会读到半写的值（WAL 整页镜像 + 8B 对齐写） |
| 提交 | 语句级（每条语句一个隐式事务）；图操作不参与 BEGIN/COMMIT 的多语句事务 |
| WAL | 每次改页 → `WAL_PAGEDATA` 整页镜像（blob 先例，恢复零改动）；**xid 传 0**（系统事务，永远视为已提交）—— SPI 的写接口强制带 xid，图模态传 0 是**合法值**而非绕过 |
| 崩溃 | 已写的图操作全保留（页镜像重放），不存在"未提交图数据要回滚"的问题（语句级粒度） |

**必须记录的代价**（进 `DESIGN.md` 风险清单）：
空闲记录立即复用 + 无版本链 = **读游标跨语句使用时可能看到记录被复用**
（旧游标拿着 RID，记录被删又建）。缓解：图游标只在单语句内有效（文档写死）。

### 4.6 遍历 API：3 跳怎么查

SQL 表达不了递归（`DESIGN.md` §10.1 决定不做递归 CTE）。遍历走 C API，
**原语只有一个**：

```c
/* 沿出边走一步：给节点 RID，返回它的出边邻居 RID 数组 */
int db_graph_hop(DB *conn, db_graph_rid node,
                 db_graph_rid **out, uint32_t *n_out);

/* 反向：入边邻居（复用同一条链机制，方向参数区分） */
int db_graph_hop_in(DB *conn, db_graph_rid node,
                    db_graph_rid **out, uint32_t *n_out);
```

- 内部实现：读节点记录 → 沿 `first_out` 的边链逐个 `next` →
  每跳一次 = **1 次节点页读 + K 次边页读**（K = 出度，边记录命中同一页时免费）。
- 加锁：`db_graph_*` 是新入口路径 → **必须 latch**（硬规则 8）。
- 性能模型：3 跳 = 3 轮 hop。100 万边 / 10 万节点 = 平均出度 10 →
  3 跳最坏 1 + 10 + 100 + 1000 = 1111 次页读 ≈ 全部命中缓冲池（热点子图）→
  **p99 < 10ms 可达**。但冷启动（缓冲池全 miss）单跳就是毫秒级 ——
  基准必须**先"预热遍历一遍"再测 p99**（写进验收方法）。

### 4.7 SPI 落地三件

| 项 | 内容 |
|---|---|
| **虚拟表** | `graph_nodes` / `graph_edges`（两张，照 blob 的模式注册） |
| **能力位** | `AM_CAP_SCAN \| INSERT \| UPDATE \| REMOVE \| PUSHDOWN \| INDEX`（可写） |
| **下推** | `graph_nodes`：按属性列下推（列值在记录里，AM 逐行自滤 → 超集语义）。`graph_edges`：按 `src` / `dst` 等值下推（**真下推**：只枚举匹配的边链，不是全扫） |

**遍历本身不下推** —— 递归语义进不了标量谓词系统（同 v1.3 / v1.4 的边界）。

### 4.8 本版范围与不做项

**做**：图存储（定长记录 + 双向邻接链）、`StorageAM` 适配、两张虚拟表、
遍历 C API、崩溃安全（`WAL_PAGEDATA`）、性能验收（10 万节点 / 100 万边 / 3 跳 p99 < 10ms）。

| 不做 | 为什么 |
|---|---|
| 变长属性存储（Neo4j 的 PropertyRecord） | 属性系统是独立的第三个子系统；本版用固定列 schema 表达节点属性，验证的是图拓扑机制 |
| 图算法（最短路、PageRank…） | 遍历原语（邻接跳转）是它们的地基，原语没验收之前算法都是空中楼阁 |
| MVCC 版本链 | 见 §4.5 的判决 —— 对齐 Neo4j 的真实选择 |
| Cypher / 图查询语言 | SQL 虚拟表 + 遍历 API 已够验收 |
| 细粒度 latch | 全局 latch 覆盖图的所有入口（硬规则 8） |

### 4.9 关键坑

**坑 M2-1 · 双向链维护漏改一边**
摘链时 prev/next 指针漏改一边 → 链断或成环，而且**不一定立刻崩**（可能只是少一条边）。
防线：每次增删后断言"沿出链走的集合 == 沿入链走的集合"。

**坑 M2-2 · 页内槽算术错**
`rec_size` 对齐错、页头大小算错 → 越界写。防线：页头大小进 `config.h` 单点定义；ASan 全程开。

**坑 M2-3 · `visible()` 恒真被滥用**
把"还没写完的记录"放出去 → 读者看到半条记录。
防线：分配记录时先 `in_use=1` + 全字段写完才挂链；WAL 先写后改页。

**坑 M2-4 · 3 跳 p99 不达标**
出度方差大，长尾节点邻居上千。防线：预热 + 缓冲池命中是前提；
不达标先查 IO 计数再谈优化。

**坑 M2-5 · gstore 下沉到 `storage/gstore` 是前置重构**
HNSW 的邻接表节点也是定长的，图模态刚把"定长记录 + 空闲链"写对并测透，
向量模态想复用 —— 但**硬规则 3 禁止模态之间互相 include**。
正确做法：把定长槽页**下沉到 `storage/`（L1）**，图和向量都依赖它。
**下沉是纯搬家（不改逻辑）；搬完立刻跑 v0.11 全部测试作为回归门。**

**坑 M2-6 · 定长槽页的"载荷从第 4 字节开始"（v0.11 步骤 4 踩）**
gstore 的槽布局是 `[in_use(1)][保留(1)][next_free(2)][载荷…]`，
`gstore_alloc_with` **只拷载荷区**（从 init 的第 4 字节起）—— 公共头归 gstore 自己管。
所以新的定长记录（比如 schema）必须把数据放在 `GS_REC_HDR_SIZE` 之后。
踩了的后果：前 4 字节被**静默丢掉**，写的时候不报错，读的时候才发现 version 不对。
防线：格式定义和它的偏移写在同一处（`graph.h`）；测试要覆盖"写进去再读回来"。

**坑 M2-7 · WAL 整页镜像的写放大（v0.11 步骤 6 量到）**
加一条边要改 4 个页（边记录 / 原链头 / src / dst），
每改一个页就是一条 `WAL_PAGEDATA` 整页镜像 = 8KB 日志 → **每条边 32KB**。
100 万条边 ≈ **32GB** —— 不是"慢一点"，是磁盘放不下。
所以性能基准必须跑在**不挂 WAL 钩子**的模态层，持久化路径单独用崩溃测试验。
根治方向：**槽级日志**（记 52 字节而不是 4KB）—— 图和向量共同受益，v1.0 前该定。

## 5 · 模态 3：向量 —— 列式 + HNSW

> 计划：`PLAN-v1.0.md`（已定稿）。字节级施工图纸见工作区根目录 `向量模态实现规格.html`。

### 5.1 定位与业界对标

Milvus / Qdrant / Weaviate / Lance。核心机制两条：**列式布局**（对齐 Lance / Parquet）
+ **HNSW 图索引**（Malkov & Yashunin 2016，对齐 hnswlib）。

### 5.2 为什么它是独立模态

这是第三个模态、**第三种布局** —— blob 是"对象→帧→页"，图是"定长槽页"，向量是**列式**。

| 候选 | 判决 |
|---|---|
| (a) 向量塞进 slotted page 当一行 | **否决** —— 128 维 fp32 = 512B，一页只能放 7 个向量；且按行存，相邻向量分散在页的各处，扫描/训练/量化都要跳读 |
| (b) **列式向量页**：一页连续放 K 个 fp32 向量，`向量 i` 的位置 = `页头 + i × dim × 4B`，页间顺序衔接 | **采纳** |

### 5.3 行模型与 RID

- **一行 = 一个向量**
- **RID = `(data_page_of(row_id), row_id % K)`** —— 纯算术（对齐 blob 的先例）
- **列对齐是列式的灵魂**：第 `i` 个向量和第 `i` 行标量属性靠**序号**对应，不需要指针。
  过滤标量列命中的 row_id 集合 → 直接换算出向量位置 ——
  这是"过滤 + ANN"和将来"量化训练"的地基。

```
向量页（PT_VEC_DATA）：
  页头 20B（页类型 + 向量计数）
  数据区：(4096-20) / (dim × 4) 个向量连续排列

标量页（PT_VEC_META 系列，普通定长槽页，同 gstore）：
  每行 = (row_id, label, ...) —— 向量的标量属性
  row_id = 全局序号，第 i 个向量 == 标量表第 i 行（列对齐）
```

**页头为什么是 20B 而不是 8B**：8B 会**静默压坏两个公共字段** ——
`H_LSN`（偏移 12，重放幂等判断读它）与 `H_CKSUM`（偏移 16，校验和固定写在这里）
是**所有页类型共用**的，不归某个页类型自己支配。页头取 8B 的话，
第 0 个向量从偏移 8 开始，前 10 个字节正好被 LSN 和校验和覆盖 ——
**只坏每页的第一个向量，而且不报错**。
所以页头取 20B（= `HDR_SIZE`），与 slotted page、定长槽页保持同一约定。
代价：K 从 7.98 变成 7.96，对 128 维没有影响（都是 7）。
完整论证见 `PLAN-v1.0.md` §3 步骤 2 的「① 规格里的"页头 8B"是错的，改成 20B」。

### 5.4 HNSW 实现要点

| 要素 | 决定 | 理由 |
|---|---|---|
| 距离 | L2 与内积两种（构建时指定） | 应用最广的两种；cosine 用归一化内积实现 |
| M（每层邻居数） | 16 | hnswlib 默认 |
| ef_construction | 200 | hnswlib 默认 |
| ef_search | 由查询方传（默认 64） | 召回/延迟的旋钮，不写死 |
| 层级分配 | `level = floor(-ln(uniform) × mL)`，`mL = 1/ln(M)` | 论文原式（`mL ≈ 0.3607`） |
| 邻居修剪 | 启发式（保留方向多样的邻居，e0/e1/e2 判据） | 论文 Algorithm 4；hnswlib 同款 |
| 入口点 | 单一 entry point，记录最高层 | 标准做法 |

**落盘格式**（`PT_VEC_INDEX` 页系列）：

```
索引头页：dim / count / M / entry_point / max_level / 数据页链头
邻接页：  定长槽页（同 gstore 复用！每槽 = 一个节点的邻居数组，
          M + M×2 双数组：上层 M 个、第 0 层 2M 个）
```

**复用 gstore 的定长槽页**是本版的一个结构决定，但**不能模态之间互相 include**
（硬规则 3）→ 定长槽页已**下沉到 `storage/gstore`**
（`src/modalities/graph/gstore.{h,c}` → `src/storage/gstore.{h,c}`，纯搬家，
v1.0 步骤 1 已执行并跑过 v0.11 全量回归），图和向量都依赖它（见坑 M2-5）。

**增量插入**：HNSW 天然支持（逐点插入 + 贪心搜近邻 + 修剪）。
插入并发：全局 latch 已覆盖（硬规则 8）。

### 5.5 事务语义

**锁 + WAL（语句级）**，与 graph / ft / ts 同族。理由：
HNSW 索引是指针结构，增量删除极难做对 → v1.0 只支持插入；
不插入就不存在"回滚到旧版本"的需求 → 无版本链。

向量**数据页**本身是只追加的（写了不改正），这一点与 blob 类似；
但**索引页**会被增量插入改写，所以整体走"锁 + WAL + 整页镜像"。

### 5.6 SPI 落地三件

**虚拟表**：`vec_items`（一行 = 一个向量，列含 row_id / label / 向量本身）。

**能力位**：`AM_CAP_SCAN | AM_CAP_EXTERNAL | AM_CAP_PUSHDOWN`；
本版**只读**（装载走专用 API），`INSERT/UPDATE/REMOVE` 不给 → SQL 侧 `E_NOTSUP`。

**下推**：
- 标量谓词（label 等值）→ 下推（只扫匹配的 row_id），**进 SQL**
- **距离排序不进 SQL** —— 排序键是计算出来的，不是列值；
  进 SQL 需要新的算子类型，违反"下推结果是行源"的同构性。
  这是**有意的范围收缩，不是遗漏**。

**`knn` 是 `IndexAM` 的第一个真实现**（B+tree 返回 `E_NOTSUP`）：
优化器看到 `E_NOTSUP` 就退回全表扫描 —— **能力协商靠返回值，不靠类型判断**。

```c
/* B+tree 的实现返回 E_NOTSUP，向量模态是第一个真实现 */
int (*knn)(IndexAM *am, const void *query, u32 k,
           AmKnnResult *out);   /* out: row_id 数组 + 距离数组 */
```

### 5.7 过滤 + ANN：给超集，不给子集

| 候选 | 做法 | 判决 |
|---|---|---|
| (a) 先 ANN 取 top-k，再过滤 | 召回不足：如果 top-k 都不满足过滤条件，结果**少于 k 且不可补** —— **静默丢数据** | **否决** —— 违反"下推只能给超集"铁律 |
| (b) 先过滤标量，再对幸存者暴力扫 | 正确但 O(N)，索引白建 | **否决**（作为默认路径） |
| (c) **ANN 扩大候选池（ef_search 拉高，候选 ef ≥ 4k）再过滤** | ANN 给超集候选，过滤后可能仍少于 k → **如实报告实际数量** | **采纳** |

判决 (c) 的语义必须写死在 API 文档里：

> `db_vec_knn` 返回的是"满足过滤条件的、ANN 能找到的最相似向量"，
> **不保证恰好 k 个**（可能少于 k）。这是 ANN 的固有性质（近似），不是 bug。
> 需要精确结果请用 `db_vec_knn_exact`（暴力扫，供回归对照）。

### 5.8 IO 可证

复用 v0.9 的 `db_blob_page_reads` 模式 —— `db_vec_page_reads()` 前后对比：
ANN 的页读数必须 **≪** 暴力扫描（10 万向量 = 14286 页）。
验收标准：**暴力扫一次 14286 页（10 万 ÷ 每页 7 个）vs ANN 查询 0 页**。
分母为 0 时比值无意义，写成"1/999999"是自欺欺人；真实代价写在别处 ——
**索引常驻约 93.3 MB**（向量副本 48.8 + 图结构上界 44.4）。

### 5.9 本版范围与不做项

**做**：列式向量存储、HNSW（内存构建 + 落盘 + 增量插入）、
`modalities/vector/vector_am.{h,c}` + `index_am` 的 `knn`、`vec_items` 虚拟表、
过滤 + ANN 配合策略、recall 验收框架（暴力扫 GT + hnswlib 双重对照）。

> **脚注**：AM 适配器住在 `modalities/vector/` 而不是 `spi/` ——
> 分层规则（`spi/` 是 L3、`modalities/` 是 L4，L4 不得反向被依赖）逼得
> 适配器必须住在 `modalities/vector/`；决策记录见 `PLAN-v1.0.md` §3 步骤 5 的判决①。

| 不做 | 为什么 |
|---|---|
| 量化（PQ / SQ / binary） | 量化是为了省内存省 IO；先做精确 fp32 把 HNSW 本身做对，量化是它的正交优化 |
| 过滤吸收进 HNSW（filtered-HNSW） | 本版用"ANN 给超集 + 执行器过滤"，保守安全；吸收进图是激进优化 |
| 多向量 / 稀疏向量 | 单模态单类型，混合检索是应用层的事 |
| 增量删除（HNSW 的删除很难做对） | 标记删除 + 重建（v1.2 的 vacuum/rebuild 一起处理）；本版只支持插入 |
| IVF / 其他索引 | 只做 HNSW，做深不做多 |

### 5.10 关键坑

**坑 M3-1 · `(4096 − 8) / 512 = 7.98` 取下界**
K = `(PAGE_SIZE − 页头) / (dim × 4)`。128 维 fp32 = 512B → `4088 / 512 = 7.98`。
**必须取下界 7**，取 7.98 会在页尾越界写 0.98 个向量。
防线：K 的计算用整数除法，且写路径断言 `offset + dim*4 ≤ PAGE_SIZE`。

**坑 M3-2 · 列对齐被破坏**
向量页的向量序号与标量页的 row_id 序号必须严格一一对应。
一旦错位（比如插入时跳过了一个 row_id、或回收时复用了序号），
过滤结果与向量内容就**错配** —— 而且不报错，只是查出来的向量是错的。
防线：row_id 全局单调、不复用；断言 `row_id ↔ 序号` 双向一致。

**坑 M3-3 · 启发式修剪判据写错 → recall 静默下降**
e0/e1/e2 判据抄错 → 邻居集合质量差 → recall@10 从 0.95 掉到 0.6，
但**接口照样返回结果**，没有任何报错。
防线：recall 硬指标（与暴力扫 GT 逐条 diff）；召回异常先 diff 邻居表再怀疑参数。

**坑 M3-4 · 先 ANN 后过滤 = 静默丢数据**
见 §5.7 的候选 (a)。这正是"下推只能给超集"铁律要防的那一类。

**坑 M3-5 · 过滤与 ANN 的顺序反了**
先过滤后 ANN：过滤把候选池缩到很小，HNSW 的图结构被绕过，索引白建；
且若实现上退化成"过滤后暴力扫"，性能全丢。顺序必须与 §5.7 判决 (c) 一致。

**坑 M3-6 · 崩溃后向量页与索引页不一致**
数据页写了、索引页没写（或反过来）→ 索引与数据对不上。
防线：崩溃恢复走 `reindex` 路径重建索引（索引不写日志，崩溃后重建 ——
v0.6 的既定原则）。

## 6 · 模态 4：全文检索 —— 不可变 segment + 后台合并

> 计划：`PLAN-v1.3.md`（已定稿）。字节级施工图纸见工作区根目录 `全文检索模态实现规格.html`。

### 6.1 定位与业界对标

Elasticsearch / Lucene。核心机制：**不变文件 + 后台合并** ——
索引 segment 写完就不可变；删除只打标记；后台把小 segment 合并成大的
（合并时才物理丢弃被删文档）。

这是"不变文件"思想的**第二次**出现（第一次是 blob 对象，第三次是时序封窗分区）。

### 6.2 为什么它是独立模态

segment 的**生命周期**与关系模态的 MVCC 版本链正交：
一个 segment 一旦写完就永远不变，删除靠 tombstone 标记，物理丢弃推迟到合并时。
把 segment 做成"关系表 + 版本链"是拿一套机制模拟另一套机制。

### 6.3 关键判决：检索语义走专用 API，不进 SQL 谓词

**这是本模态最重要的边界判决**（对齐 v1.0 的"距离排序不进 SQL"先例）：

| 路径 | 内容 | 判决 |
|---|---|---|
| `db_ft_search(conn, term, top_k)` | 专用 API：返回 `(doc_id, score)` 按 BM25 排序 | **主路径** |
| `ft_docs` 虚拟表 | `(doc_id, doc_len, nterms, sealed)` —— 标量列，`doc_id` 等值/范围下推 | 元数据路径 |
| `match(col, 'term')` 进 SQL 谓词 | 需要 `PD_MATCH`、相关性排序键、执行器拥有全局统计（idf/avgdl） | **否决** |

**否决的理由**（写清楚，防止将来心血来潮去改）：

1. `pushdown.h` 的 `Predicate` 是 `(col_idx, op, DbValue)` —— 单值标量比较。
   相关性评分依赖**全局统计**（idf 随语料变、avgdl 随 segment 合并变），
   执行器根本无法独立重求值 —— **"下推给超集、执行器重判"的契约无法成立**。
2. 为单一模态改三个已验收模态共用的公共契约，违反 v0.9 的教训
   （接口是照着调用方的需要写的 —— 执行器不需要）。
3. 同性质先例已有三个：graph 遍历、vector knn、geo 窗口。
   **模态特有语义不进标量谓词系统**。

### 6.4 行模型与 RID

- **一行 = 一个文档**（但 `ft_docs` 虚拟表暴露的是**文档的元数据**，不是正文）
- **RID = (段号, 段内 doc 序号)** —— 文档正文在 segment 的 posting 链里，
  虚拟表的行只是元数据视图
- **正文按 term 定位，不按 RID 定位** —— 这是全文模态与其它模态最大的不同：
  其它模态的 RID 指向"数据本身"，全文的 RID 指向"文档的一个索引条目"，
  真正的内容要靠 posting list 找到

**为什么这样切**：段是不可变的，文档在段内没有稳定物理位置
（同一文档的多个 term 分散在多个 posting list 里）。
把 RID 定义成"元数据视图的行"是唯一自洽的做法 —— 与 blob 的
"`blob_frames` 的行是帧、`blob_objects` 的行是对象"是同款思路：
**一个模态可以提供多张表，各自语义干净**。

### 6.5 segment 的物理形态

```
一个 segment = 三种页的区间（写完不可变）：

PT_FT_HEAD（段头页，1 页）：
  seg_id / doc_count / 创建 LSN / avgdl / 段内 max doc_id
  dict_page_start / dict_page_count / post_page_start / post_page_count

PT_FT_DICT（字典页，若干）：
  term 有序数组：[term_len, term_bytes, df, post_ptr]
  跨页二分查找（页内有序 + 页间有序）

PT_FT_POST（posting 页，若干）：
  (doc_id_delta, tf) 有序对数组，doc_id 用 delta 编码
  一个 term 的 posting 可能跨页链（页头带 next）
```

**为什么 term 用有序数组而不是哈希**：检索要"按字典序批量扫"（前缀查询的将来），
且**合并 = 多路归并**（有序对有序，天然归并）—— 哈希两头都不占。

### 6.6 事务语义

**锁 + WAL（语句级）**。segment 不可变 → 写操作只有"追加新 segment"和"追加 tombstone"，
两者都不需要版本链。

**tombstone（删除标记）**：按 `seg_id` 组织的 doc_id 位图；
内存持有 + WAL 逐条追加（`WAL_FT_TOMB` **新记录类型**，内容仅 `seg_id + doc_id`）；
重启时重放重建。**查询时过滤，合并时物理丢弃**。

`WAL_FT_TOMB` 是本项目第一条**模态专用的 WAL 记录类型** —— 之前的 blob / graph 都复用
`WAL_PAGEDATA` 整页镜像。全文模态第一次需要"只记一条逻辑删除、不记整页"。

### 6.7 评分：BM25

```
idf(t)   = ln(1 + (N - df + 0.5) / (df + 0.5))     ← Lucene 式，非教科书式
score    = Σ_t idf(t) · tf·(k1+1) / (tf + k1·(1 - b + b·dl/avgdl))
```
k1 = 1.2，b = 0.75。

**为什么选 Lucene 式 idf**：教科书式的 idf 在 df=0 时为负、单文档语料时除零；
Lucene 式恒正且平滑 —— **抄业界实现，不抄教科书**（本项目的既定方针）。
TF-IDF 作为对照实现保留（验收用：两种评分对同一语料的排序差异要**可解释** ——
主要来自 BM25 的文档长度归一）。

**跨 segment 的统计合并**：`N`（总文档数）和 `avgdl` 是全局量 ——
检索时实时聚合各段头（段数 ≤ 阈值 8，聚合代价可忽略）。
**这正是合并的动机之一**：段越少，聚合越便宜。

### 6.8 合并：Tiered

```
段数 > 8 时：挑"文档数之和最小"的相邻若干段合并成一个
  合并 = 字典多路归并（term 对齐）+ posting 拼接（重算 delta）+
         tombstone 过滤（被删文档物理丢弃）+ 重建段头
旧段页 → 回收（freelist，页号空间共享）
```

**合并的代价是可解释的**：10 万文档分批插入，合并总 IO 呈 `O(N × log_f N)` 量级（f = 合并因子）。

### 6.9 SPI 落地三件

| 项 | 内容 |
|---|---|
| **虚拟表** | `ft_docs`（一行 = 一个文档的元数据） |
| **能力位** | `AM_CAP_SCAN \| PUSHDOWN`；本版文档写入走专用 API，`INSERT/UPDATE` 不给 → `E_NOTSUP` |
| **下推** | `doc_id` 等值/范围 → 下推（元数据路径）。**`match` 不下推**（见 §6.3） |

**IO 可证**：单 term 检索页读 = 字典二分页数 + 该 term 的 posting 页数
（**与总文档量无关**）—— `db_ft_page_reads()`。

### 6.10 本版范围与不做项

**做**：英文分词器（小写化 + 非字母数字切分）、倒排索引（有序 term 字典 + delta 编码 posting）、
BM25 评分（+ TF-IDF 对照）、segment 物理格式 + Tiered 合并 + tombstone 删除、
`ft_docs` 虚拟表 + `db_ft_search`、WAL 保护（`WAL_PAGEDATA` + `WAL_FT_TOMB`）。

| 不做 | 为什么 |
|---|---|
| 中文分词 | 分词器是独立工程（词典/统计模型），对理解倒排零增量 |
| FST / 前缀压缩的 term 字典 | 字典压缩是内存优化；有序数组 + 二分已能学 posting 机制 |
| 位置索引 / 短语查询 / 高亮 | 预留接口（posting 项留 pos 字段位），机制不做 |
| 近实时搜索（NRT / 内存 segment） | Lucene 的 NRT 是工程甜点，不是核心机制 |
| 多字段加权 schema | 单字段已覆盖全部评分机制 |

### 6.11 关键坑

**坑 M4-1 · 字典项变长，不能用定长槽页**
term 长度可变 → 不能用图模态的定长槽页（那个要求 `rec_size` 固定）。
**取舍**：统一哈希 + 8B 指纹，牺牲一部分有序性换布局统一。
（term 字典有序数组是主路径，8B 指纹是定长槽页方案下的退路。）

**坑 M4-2 · 合并时 delta 没重算**
posting 的 doc_id 是 delta 编码的。合并两条 posting 时若只是**拼接**而不重算 delta，
解出来的 doc_id 全错 —— 而且**不报错**（delta 单调递增，解出来还是"合法"的 doc_id）。
防线：合并后必须全量重解 + 与合并前的集合做 diff。

**坑 M4-3 · 聚合写成"最后一段 avgdl"**
跨 segment 聚合时，若取"最后一个段的 avgdl"当全局 avgdl，
BM25 的长度归一项全错 → 排序结果偏斜。**必须按文档数加权聚合**。

**坑 M4-4 · tombstone 只在内存 → 已删文档复活**
删除标记没落 WAL → 崩溃恢复后 segment 重放，文档复活。
防线：`WAL_FT_TOMB` 逐条追加 + 重启重放重建位图。

**坑 M4-5 · 合并的原子切换点**
合并 = 写新段 + 回收旧段。崩溃在中间会怎样？
**原子切换点 = 新段落盘**（旧段回收是幂等的，回收两次无害）。
这是 blob 定稿、时序 `sealed_lsn` 的同款手法：**新东西落盘即成功，旧东西清理可重试**。

## 7 · 模态 5：地理空间 —— 多维数据进树

> 计划：`PLAN-v1.4.md`（已定稿）。字节级施工图纸见工作区根目录 `地理空间模态实现规格.html`。

### 7.1 定位与业界对标

PostGIS（GiST / SP-GiST）、MongoDB 2dsphere、MySQL Spatial。
核心机制：**多维数据怎么进树** —— R-tree 用最小包围矩形（MBR）嵌套
把"二维邻近"变成"树内聚集"。窗口查询 = 子树剪枝；KNN = mindist 优先队列。

### 7.2 为什么它是独立模态

B+tree 的键是**一维全序**；空间数据没有全序。
判据落在**比较关系**上：R-tree 的"比较"是相交 / 包含 / mindist，不是全序比较 ——
`index_key`（列值 → 一维可比字节串）装不下它。

### 7.3 关键判决

#### 判决 1：真 R-tree，不做 Z-order 一维编码塞 B+tree

| 候选 | 判决 |
|---|---|
| (a) 点 → Morton 码 → 塞进现有 B+tree | **否决（作为主路径）** —— 复用 B+tree 学习增量是零；窗口查询要拆成多个 Z 区间（BigMin 算法），逻辑绕 |
| (b) **真 R-tree**（节点存 MBR 数组） | **采纳（主路径）** —— 要学的就是多维树自己的分裂与剪枝 |
| (a′) Z-order 作为**对照实现** | **采纳（bench 路径）** —— 与 R-tree 比 IO，结论可解释 |

**学习增量论**（写进 `DESIGN.md` 复盘）：复用已有结构的工作量小，
但本项目的目标是"把机制亲手实现一遍" —— Z-order 塞 B+tree 学的是 Morton 编码，
真 R-tree 学的是多维树。对照实验把两者的真实代价差摆出来，这比单独做任何一个都完整。

#### 判决 2：R-tree 的键不走 `index_key`

```c
/* R-tree 的键就是 MBR 结构体，直接存进树页条目： */
typedef struct { float minx, miny, maxx, maxy; } Mbr;

/* 树页条目（PT_RTREE 页）：
   内部节点：[child_page, Mbr] 数组（Mbr 概括整棵子树）
   叶子节点：[row_id,    Mbr] 数组（点 → 退化 MBR） */
```

**IndexAM 的接口够用吗**：`knn(am, query, k, out)` 的 query 是 `void*`（传 MBR/点），
范围扫描的语义换成"窗口"—— `IndexAM` 是模态级契约，
R-tree 作为它的第三个实现（btree → hnsw → rtree），**接口零改动**。

#### 判决 3：KNN 是精确的（与 v1.0 形成对照）

HNSW 的 KNN 是**近似**（ef 换召回）；R-tree 的 mindist 优先队列是**精确**算法：

```
优先队列（按 mindist(节点MBR, 查询点) 最小堆）：
  弹出 → 若是叶子条目：入结果集（真实距离）
        → 若是内部节点：把子条目按 mindist 压栈
  结果集满 k 个且堆顶 mindist ≥ 第 k 近的真实距离 → 提前终止
```

**两版对照是设计教育点**：近似的代价是召回、收益是跳过大部分树；
精确的代价是必须展开所有"可能更近"的子树、收益是结果无懈可击。
验收里两边的对照方法不同（recall vs 全等），这个差异本身要写进文档。

#### 判决 4：并列距离的稳定顺序

浮点距离并列时（网格点、对称分布），KNN 的第 k 名可能不唯一：
**tie-break 定死为 row_id 升序**。暴力对照实现用同一规则 ——
否则"全等"验收会被浮点噪声随机击穿。

### 7.4 行模型与 RID

- **一行 = 一个几何对象**（`POINT(x,y)` 或 `RECT(minx,miny,maxx,maxy)`）
- **RID = (树页号, 叶子槽号)** —— 与图模态同构（定长槽页），
  条目内容是 `(row_id, Mbr)`
- 树高 = O(log N)，根节点必须能分（否则树高失控 —— 见坑 M5-2）

### 7.5 MBR 的三个纯函数

```c
bool mbr_intersects(const Mbr *a, const Mbr *b);   /* 相交 */
bool mbr_contains(const Mbr *a, const Mbr *b);     /* 包含 */
float mbr_mindist(const Mbr *a, float x, float y); /* mindist（下界） */
```

**mindist 是下界** —— 它是精确 KNN 的剪枝依据：
子树里任何点到查询点的距离 ≥ mindist(子树 MBR, 查询点)，
所以堆顶 mindist ≥ 第 k 近的真实距离时可以提前终止。

**三个纯函数**（相交/包含/mindist）是纯几何，不依赖存储 —— 可独立单测、对照手算。

### 7.6 事务语义

**锁 + WAL（语句级）**。R-tree 内部节点在分裂时被重写（新的 MBR 数组），
叶子条目在插入/删除时被改 —— 都是就地更新，与图模态同类。

**删除 = 标记死条目**（不 rebalance，对齐 B+tree 的先例）+ `reindex` 重建。
死条目留在树上但被跳过 —— 见坑 M5-5。

### 7.7 SPI 落地三件

| 项 | 内容 |
|---|---|
| **虚拟表** | `geo_points`（一行 = 一个几何对象，列含 row_id / x / y / minx / miny / maxx / maxy） |
| **能力位** | `AM_CAP_SCAN \| PUSHDOWN \| INDEX`；删除走专用 API，`REMOVE` 不给 → `E_NOTSUP` |
| **下推** | 标量列（x / y / minx …）等值与范围 → 下推（超集语义）。**窗口与 KNN 不下推**（见下） |

**窗口与 KNN 走专用 API**：`db_geo_window(conn, rect)` / `db_geo_knn(conn, x, y, k)`。
理由同 v1.3 §1.2 —— 几何语义不进标量谓词系统。

### 7.8 本版范围与不做项

**做**：`geometry` 二进制列（`POINT` / `RECT`）、
R-tree（Guttman 1984 原始版：插入 / ChooseSubtree / 二次分裂 / 窗口查询 / mindist KNN）、
Z-order 对照实现（点 → Morton 码 → B+tree，窗口 = 区间分解）、
`geo_points` 虚拟表 + 专用 API、删除 = 死条目 + `reindex`、WAL + 崩溃恢复。

| 不做 | 为什么 |
|---|---|
| 多边形 / 线串 | 点/矩形已覆盖 R-tree 全部机制（分裂/剪枝/mindist）；多边形只加求交代码量 |
| R*-tree / STR 批量加载 | 重插入与批量打包是插入质量的优化；先学原始启发式 |
| 空间 JOIN / 距离 JOIN | 需要 JOIN（§10.1 维持不做） |
| 坐标系 / 投影 / 测地距离 | 假定平面直角坐标（PostGIS 的 geography 模式明确不做） |
| 空间谓词进 SQL（ST_ 函数族） | 同 v1.3 §1.2 的边界：几何语义不进标量谓词系统（专用 API） |

### 7.9 IO 可证与对照结论

- **剪枝可证**：1% 选择率的窗口查询页读数 < 全扫的 1/10（`db_geo_page_reads()`）
- **Z-order 对照**：均匀分布 / 聚簇分布 / 高斯基组，三组 IO 对比 + 每组一句解释
- **如实记录**：R-tree 的剪枝收益**随插入顺序变化** —— 随机插入约 4.5×，
  聚簇/有序插入可达约 100×。这个数字必须写进 bench 结论，
  否则"剪枝无效"的结论会在有序数据上被推翻。

### 7.10 关键坑

**坑 M5-1 · 浮点噪声随机击穿全等**
窗口/KNN 的"全等"验收用浮点比较，边界点（恰在窗口边上）会因计算顺序不同
得到不同的 `<` / `>` 判定 → 随机失败。
防线：暴力对照实现与 R-tree **用同一套比较函数**（同源计算，无舍入路径差）；
边界用例（恰在边界、共边、负坐标）进专门的边界用例表。

**坑 M5-2 · 根节点必须能分，否则树高失控**
Guttman 二次分裂：如果根节点分裂后无法把子树分到两侧（所有条目都挤在一边），
树会退化成链，剪枝完全失效。
防线：分裂后断言两侧都非空；根分裂时建新根。

**坑 M5-3 · 只测随机分布就宣布剪枝无效**
均匀随机点下 R-tree 相对全扫的收益只有 ~4.5×；如果只看这一组就下结论，
会低估聚簇数据上的收益（~100×）。两种分布都要测。

**坑 M5-4 · mindist 提前终止条件写错**
条件写成 `>` 而不是 `>=`（或反了）→ 漏展开子树 → **结果少一条但测试可能碰巧过**。
防线：KNN 全等验收兜底；终止条件附论文伪代码对照注释。

**坑 M5-5 · 死条目还在树上**
删除只打标记不改树 → 死条目仍占叶子槽、仍参与 MBR 计算 → 树越来越"胖"，
剪枝效率下降。防线：`reindex` 重建路径 + 验收断言"删除后窗口/KNN 不返回死点"。

## 8 · 模态 6：时序 —— 写入优化 + 封窗压缩 + 整分区丢弃

> 计划：`PLAN-v1.5.md`（已定稿）。字节级施工图纸见工作区根目录 `时序模态实现规格.html`。

### 8.1 定位与业界对标

InfluxDB / TimescaleDB / TDengine / Gorilla（Facebook 2015 论文）。
核心机制：**为写入优化的布局 + 封窗压缩 + 整分区丢弃**。

时序数据的三特点（按时间有序追加 / 几乎不更新 / 旧数据变冷）决定了它的存储形态。
这是"分区封闭后不可变"思想的**第三次**出现（第一次 blob，第二次 Lucene segment）。

### 8.2 为什么它是独立模态

**生命周期**不同：同一分区内按时间追加、几乎不更新、旧数据变冷。
行式布局对写入友好但对读取不友好；列式反过来。
时序的答案是**两种布局共存，用"封窗"作为格式转换的时机** ——
这是关系模态的单一 tuple 模型给不了的。

### 8.3 关键判决

#### 判决 1（修正总览预判）：分区元数据自管，不进 catalog

总览（`PLAN-modality-expansion.md` §3）预判"分区元数据进 catalog（sys_partition 新系统表）"。
**细化时被推翻**，理由记录如下：

| 路径 | 分析 |
|---|---|
| 进 catalog（sys_partition） | 前提是"要被通用查询裁剪就得让执行器看得见" —— **这个前提不成立**：裁剪发生在 AM 的 `push` 里（拿到时间谓词后查自己的分区表），执行器从头到尾不需要知道分区存在 |
| **自管目录 + `ts_partitions` 虚拟表** | ① `blob_id` 下推的同款先例（blob 自管对象目录，下推时自己查）；② 硬规则 6 的一致性更强：**catalog 不知道任何模态**（blob/graph/vector/ft 都没进 catalog，时序凭什么进）；③ 用户可见性由虚拟表解决（`SELECT * FROM ts_partitions`），不需要系统表 |

> **这正好是"总览 → 独立 PLAN 细化"环节的价值证明**：预判阶段看起来必须共享的结构，
> 对照既有先例逐条过堂后，发现自管更一致。执行记录里保留这次修正。

#### 判决 2：封窗（seal）的时机与原子性

```
活跃分区（裸写）── 满/超时 ──→ 封窗压缩（不可逆）──→ 封闭分区（只读）
   slotted page                    列式压缩页                PT_TS_COL
```

- **触发**：分区行数 ≥ 阈值（`config.h`）或时间窗滑过（封窗 = 最后一次写之后）。
- **原子性**：压缩 = 新写一组 `PT_TS_COL` 页 → 段头记 `sealed_lsn` → 旧 slotted 页回收。
  崩溃窗口（新页写完、旧页未回收）由恢复逻辑收敛：重放后发现新旧并存 → 用新页、旧页进 freelist。
  （**判定规则：`sealed_lsn` 落盘即封窗成功** —— 对齐 v0.6 的"meta 页是根指针"手法。）

#### 判决 3：压缩三件套（逐列选型）

| 列 | 编码 | 出处 |
|---|---|---|
| 时间戳 | **delta-of-delta**（变长 zigzag：常间隔 → 0x0 一个 bit） | Gorilla 论文（Facebook 2015） |
| 整数（tag id 等） | **delta + RLE**（重复值游程） | 通用时序实践 |
| 浮点（value） | **Gorilla XOR**（与前值异或 → 前导零/尾零计数 + 有效位） | Gorilla 论文 |

**封窗分区是列式的**（对齐 v1.0 向量列式页的先例）：
每列一段连续页，行号 → 列内偏移有页级换算。**活跃分区是行式的**（slotted page）——
两种布局在同一个模态里共存，"封窗"就是格式转换的时机。这也是学习点：
**列式不是 everywhere 的，是"冷数据"的**（Lance / ClickHouse 的现实约束同构）。

#### 判决 4：TTL 的页回收

`db_ts_retention(conn, seconds)` → 过期分区整块回收：

```
分区页区间 → freelist（页号空间共享，回收的页可被任何结构用）
分区目录项 → 标记 dropped（虚拟表仍可见历史，标 state）
```

**回收进 freelist 的合法性**（对照 v0.8"blob 页不进表 freelist"）：
那条规定说的是"**表的** freelist"（每表独立、语义是"哪页能放下 N 字节的行"）；
时序回收走的是**全局页分配器的空闲回收**，与 blob 新分配页同一条路
（`pager_alloc` 的对侧）。这两者是不同的东西，不要混为一谈。

### 8.4 行模型与 RID

- **一行 = 一个数据点**（time, tag, value）
- 活跃分区：RID = (页号, slot)（slotted page）
- 封窗分区：行号 → 列内偏移有页级换算（RID 映射在封窗时重建）

### 8.5 事务语义

**锁 + WAL（语句级）**。时序不可变是建模前提 ——
唯一的删除路径是 TTL 的整分区，不需要版本链。

**WAL**：活跃分区整页镜像；封窗重写前后镜像。
封窗的原子性由 `sealed_lsn` 保证（见判决 2）。

### 8.6 SPI 落地三件

| 项 | 内容 |
|---|---|
| **虚拟表** | `ts_partitions`（一行 = 一个分区，列含分区号 / 起止时间 / 行数 / 状态 / 压缩比） |
| **能力位** | `AM_CAP_SCAN \| PUSHDOWN \| EXTERNAL`；`INSERT` 走专用写入路径 |
| **下推** | 时间谓词 → **分区裁剪**（无时间谓词 = 裁剪退化为全分区，**超集安全**） |

**裁剪只能少读，不能少给** —— 无谓词 / 不可解析谓词（OR / 函数）时**必须读全分区**，
两条路径的结果都要全等。

### 8.7 本版范围与不做项

**做**：时间分区（默认 1 天，可配）+ 自管目录 + `ts_partitions` 虚拟表、
活跃分区 slotted page 追加写、封窗压缩（`PT_TS_COL` 列式压缩页）、
时间谓词下推 → 分区裁剪、TTL / 保留策略、WAL。

| 不做 | 为什么 |
|---|---|
| 乱序写缓冲（OOO buffer） | 写路径按时间戳路由到正确分区即可；乱序让压缩率下降是**如实记录的代价**，不是要修的 bug |
| 降采样 / 连续查询 | 查询层特性，与存储内核无关 |
| 多指标宽表（一行多列指标） | 单指标模型（time, tag, value）已覆盖全部存储机制；宽表是 schema 糖 |
| 块级倒排（时间范围 → 列块索引） | 页级统计（min/max）进页头即可，独立的块索引是优化 |
| 更新 / 删除单行 | 时序不可变是建模前提；唯一的删除路径是 TTL 的整分区 |

### 8.8 关键坑

**坑 M6-1 · 变长位流读写不对称**
delta-of-delta 与 Gorilla 都是变长位流。读写的位序不对称（一边 MSB-first 一边 LSB-first）
→ 读出来全是垃圾，但**长度校验可能刚好通过**。
防线：位流读写器独立成文件、纯函数化；随机往返全等 + fuzz（随机长度 / 极值 / 负数 / NaN）。

**坑 M6-2 · Gorilla 全同值 / 全异值边界**
全同值时前导零 = 64，尾零 = 0；全异值时有效位 = 64。两种极端都要走对。
**NaN 特别小心**：NaN 的 XOR 结果与普通浮点不同，且 NaN != NaN 会破坏比较。
防线：论文伪代码逐行对照注释 + 极值用例（含 ±0.0、±Inf、NaN）。

**坑 M6-3 · 乱序时间戳路由错分区**
写入时算错时间窗 → 数据落进错误的分区 → 查询时按分区裁剪就**漏数据**。
防线：写路径断言 `part_start ≤ t < part_end`；负例进测试。

**坑 M6-4 · 封窗中途崩溃 → 新旧页并存**
见判决 2 的收敛规则：**`sealed_lsn` 落盘即封窗成功**。
重放后发现新旧并存 → 用新页、旧页进 freelist。

**坑 M6-5 · 为裁剪率猜谓词范围 → 静默漏数据**
"我觉得这个谓词大概只涉及最近 3 个分区" —— 猜错了就是静默漏数据。
**裁剪只能少读不能少给**：谓词不可解析时一律全分区。

## 9 · 模态 7：文档 / JSON —— 寄生模态

> 计划：`PLAN-v1.6.md`（已定稿）。字节级施工图纸见工作区根目录 `文档JSON模态实现规格.html`。

### 9.1 定位与业界对标

MongoDB（BSON）、PostgreSQL JSONB、SQLite JSON1、CouchDB。
核心机制：**schema-less 的难点不在存储，在值表示与索引** ——
自描述文档怎么变成可寻址、可索引、可比较的数据。

### 9.2 为什么它是寄生模态（唯一的例外）

**文档模态是八模态里唯一一个不建存储的** —— 它是关系模态上的列类型。

其他七个模态各有独立存储（自己的页类型、自己的目录、自己的事务语义）；
文档没有 —— 文档就是 heap 行里的一个 `JSON` 列值。

**这不是偷懒，是判决**：文档的难点在**值表示（JSONB）与索引（路径索引）**，
不在物理存储。做一个独立的文档存储 = 重新实现一遍 heap（页、freelist、MVCC），
却没有增加任何关于文档的知识。

### 9.3 行模型与 RID

- **一行 = 一个文档**（= heap 行）
- **RID = heap 行的 RID**（完全继承）
- 事务语义 = **继承 heap 的 MVCC**（整文档替换走 UPDATE 两段式）

### 9.4 关键判决

#### 判决 1（本版核心）：路径提取值映射为通用标量 —— 超集契约的闭环

**问题**：下推契约（v0.9）要求"AM 给候选行，执行器重新求值 WHERE"。
但 WHERE 里的 `json_match(doc, '$.a.b = 5')` 要求执行器能**独立**判断文档。

**判决**：

```
JSONB 整体      → 不进通用类型系统（blob 同款：字节串 / 外部值）
路径提取值      → 映射为通用标量：
    string  → DbValue(TEXT)
    number  → DbValue(INT 或 REAL)
    true/false → DbValue(INT 1/0)
    null / 路径不存在 / 类型不匹配 → DbValue(NULL)
    object/array（非标量路径）→ NULL（语义写死）
```

于是超集契约完整成立：**索引按提取值建的键，执行器用同一套提取规则重判** ——
两边的映射函数是同一个（`json_extract_scalar`），不可能语义分叉。

v1.3 §1.2 说过"相关性评分执行器无法重求值"（所以 match 不进 SQL）——
**JSON 路径值可以**，所以 json_match 进 SQL 是合法的。
一进一不进，判据是同一条：**执行器能不能独立重判**。

#### 判决 2（修正总览预判）：路径索引写入时同步维护，不存在"快照过期"

总览（`PLAN-modality-expansion.md` §4）预判"索引存标量快照、可能过期（文档更新了但索引项未删），
执行器重求值兜底"。**细化时被推翻**：

| 路径 | 分析 |
|---|---|
| 快照过期 + 重判兜底 | 过期意味着**索引里躺着死键**：没人删它，越积越多 —— 那不是"保守的超集"，是**泄漏** |
| **写时同步维护**（采纳） | 文档更新 = 整替换（已定）→ 写路径删旧键、插新键 —— **v0.5 的写路径维护索引原样适用**，B+tree 既有能力，零新机制 |

执行器重判**仍然保留**（它是超集契约的一半，防的是索引实现 bug 而非过期快照），
但"过期"这个设计借口不存在了。

#### 判决 3：JSONB 格式

```
JSONB = 长度前缀树形序列化（PG JSONB / MongoDB BSON 同思路）：

  [tag][payload]：
    tag ∈ { null, true, false, int32, float64, string, array, object }
    string  ：[len][utf-8 bytes]
    array   ：[count][element]×count          （顺序即语义）
    object  ：[count][[klen][key][element]]×count  （键按长度+字典序存放 → 二分可查）

  小文档（≤ 行内限）→ 内联 heap 行的列值
  大文档            → 外部值：PT_JSON_OVF 页链（ext_key = 首页号，ext_fn 沿链读）
```

**键排序**是 JSONB 相对裸文本的真实收益之一：对象键二分查找，
路径 `$.a.b` 的访问是"两次二分"，不是全文扫描。

#### 判决 4：事务语义 —— 三足鼎立的收官

| 模态 | 事务语义 | 出处 |
|---|---|---|
| heap（+ 本版 JSON 列） | **MVCC 版本链**（RC/RR） | v0.7 |
| blob | 不可变对象 | v0.8 |
| graph / vector / ft / ts | 锁 + WAL（语句级） | v0.10–v1.5 |

文档是 heap 行 → **继承 MVCC**：整文档替换走 UPDATE 两段式（旧版本打 xmax + 插新版本），
RR 快照下读到的文档**不撕裂**。三种语义到齐。

### 9.5 SPI 落地三件

| 项 | 内容 |
|---|---|
| **虚拟表** | 无独立虚拟表 —— 文档是 heap 表的一个列类型，用户自己 `CREATE TABLE t (doc JSON)` |
| **能力位** | 由 heap AM 承载；JSON 列的 `INSERT/UPDATE` 走标准写路径 |
| **下推** | `json_match(doc, '$.a.b = 5')` **能**进 SQL（执行器可独立重判）。路径索引给候选行 → 执行器重判 |

### 9.6 外部值：大 JSON 是第 3 个用户

一帧 4076 字节；`DbValue` 文本上限 255 字节。**大 JSON 文档走 `PT_JSON_OVF` 页链外置**。

这是外部值机制的第 3 个用户（前两个：blob 帧 → 向量），
也是 v0.9 设计 foresight 的收官考试：
**`ext_fn` 从"按帧读"换成"按页链读"，契约一行不改。**

IO 可证：**只取路径字段时不读全文** —— 页读计数对比（v0.9 IO 断言模式的第 3 次应用）。

### 9.7 执行器改动审计（先定义后实现）

**寄生模态注定要碰执行器** —— 路径求值发生在执行器。
所以改动的边界必须**事先定义、事后审计**。

**允许的落点只有两个**：
1. 通用值层的路径变体（`json_extract_scalar` 落在值层）
2. `json_match` 的求值入口

**零容忍**：`if (strcmp(col_type, "json"))` 这类**模态名硬编码**。
验收是机械的：`grep -i json src/query/` 的命中**限于**上述两处，
改动清单在执行记录里逐行列出。

> 这是硬规则 7（执行器不许知道模态）的第一次"有正当理由的例外" ——
> 所以它必须被**限定范围**地写死，而不是"原则上允许"。

### 9.8 本版范围与不做项

**做**：JSON parser（递归下降）+ JSONB 二进制格式、`JSON` 列类型
（小文档内联 / 大文档外置）、路径表达式（`$.a.b[0].c`）+ 提取 → 通用标量映射、
路径索引（`CREATE INDEX ON t (json '$.a.b')`）、`json_match(doc, '$.a.b = 5')` 求值、
`db_json_*` API + 对照 SQLite JSON1 全等测试。

| 不做 | 为什么 |
|---|---|
| JSON Schema 校验 | 应用层职责 |
| 多值索引（数组展开成多键） | 只索引标量路径；数组路径提取返回 **NULL**（语义写死） |
| 部分更新（`$set` 语义） | 只做整文档替换（MongoDB 的文档级替换同款起点） |
| JSON 聚合 / 生成函数（json_group_array…） | 查询层糖 |
| MongoDB 查询语法（find 的操作符族） | SQL 谓词 + json_match 已覆盖机制 |
| 键字典 / 重复键压缩 | Lucene FST 同类的内存优化，不做 |

### 9.9 关键坑

**坑 M7-1 · 外置页链断裂 → 读到半个文档**
大文档跨页，崩溃窗口可能留下断链。
防线：页链 WAL 整页镜像 + 崩溃恢复专项测试；
恢复时**发现页链不完整就报错**，不能返回半个文档（半个文档比报错更危险 ——
它看起来是合法的 JSON）。

**坑 M7-2 · 索引建键与执行器重判的映射语义分叉 → 静默漏数据**
如果建索引时"数字 5"编码成一种标量，而执行器重判时"数字 5"映射成另一种
（比如 INT vs REAL 的边界），则索引给出的候选行在重判时被全部否掉 →
**该匹配的行一条都不返回**。
防线：两处调用**同一个** `json_extract_scalar` 函数（不是两份实现）；
单测断言两者输出全等。

**坑 M7-3 · 索引项泄漏**
索引项只增不减（没删旧键）→ 索引越来越大，且旧键指向已不存在的行。
防线：**写时同步维护**（判决 2）；验收断言"索引项计数 == 活跃文档命中数"（对账）。

## 10 · SPI 三件套：八模态逐格对照

> 这一节是**给第 9 个模态的模板**。加新模态时照着这张表填，
> 填不满说明有哪个 SPI 契约还没想清楚。

### 10.1 虚拟表对照

| 模态 | 虚拟表 | 一行 = | 是否走注册表 |
|---|---|---|---|
| 关系 | （catalog 里的真表） | 一个 tuple | **不走**（持久化元数据） |
| blob | `blob_frames` / `blob_objects` | 一帧 / 一个对象 | 走 |
| 图 | `graph_nodes` / `graph_edges` | 一个节点 / 一条边 | 走 |
| 向量 | `vec_items` | 一个向量 | 走 |
| 全文 | `ft_docs` | 一个文档的元数据 | 走 |
| 空间 | `geo_points` | 一个几何对象 | 走 |
| 时序 | `ts_partitions` | 一个分区 | 走 |
| 文档 | （无 —— heap 表的 JSON 列） | 一个文档 | 不适用 |

**解析顺序**（`DESIGN.md` §5.7）：catalog（用户建的表，赢）→ 注册表（模态的虚拟表）→ 都没有 → 表不存在。
注册表**不知道 blob 是什么** —— 它只知道"名字 → 一个 `StorageAM`"。
第 9 个模态接进来，只是多注册两条记录，执行器一行不改。

**一个模态可以提供多张表** —— blob（帧表 + 对象表）、图（节点表 + 边表）都是两张。

### 10.2 能力位对照

| 模态 | SCAN | INSERT | UPDATE | REMOVE | EXTERNAL | PUSHDOWN | VACUUM | INDEX |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| 关系 heap | ✅ | ✅ | ✅ | ✅ | | ✅ | ✅ | ✅ |
| blob | ✅ | | | | ✅ | | | |
| 图 | ✅ | ✅ | ✅ | ✅ | | ✅ | | ✅ |
| 向量 | ✅ | | | | ✅ | ✅ | | ✅ |
| 全文 | ✅ | | | | | ✅ | | ✅ |
| 空间 | ✅ | | | | | ✅ | | ✅ |
| 时序 | ✅ | | | | ✅ | ✅ | | |
| 文档 JSON | （走 heap） | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

**规律**：
- **只读模态**（blob / 向量 / 全文 / 空间）不给写能力位 → SQL 侧返回 `E_NOTSUP`
  （**明确报错，不是崩溃**，也不是"静默成功"）
- **带外部值的模态**（blob / 向量 / 时序 / 文档）给 `AM_CAP_EXTERNAL`
- **可写但语句级提交的模态**（图）给全套写能力位，但 `visible()` 恒真
- `VACUUM` 只有真正有版本链的给（关系 + 文档）
- `INDEX` 指的是"模态自带的加速结构"（btree 不算 —— 它是通用索引，另走 `IndexAM`）

### 10.2.1 批能力（v1.2 步骤 0 新增）：可选加速，不是正确性前提

| 模态 | `AM_CAP_BATCH_SCAN` | `AM_CAP_BATCH_DECODE` |
|---|:-:|:-:|
| 关系 heap | ✅ | ✅ |
| blob | | |
| 图 | | |
| 向量 | | |
| 全文 / 空间 / 时序 / 文档 | | （文档走 heap，随 heap） |

**规律**：

1. 批能力是**另一根轴**，与 §10.2 的表正交：
   那张表管"这个模态支持什么**操作**"，批能力管"这个模态支持什么**访问形状**"。
2. **指针为 NULL = 不支持**，执行器自动退回逐行路径 ——
   所以没实现的模态**一行都不用改**（blob / graph / vector 各加两行 `= NULL`）。
   这正是 v1.1 §1.2 担心被打脸的"那条底线"：能力协商本身是项目自有的机制。
3. **heap 先做的理由**：它有 `RecLayout`（记录布局），批量解码不用每行重算布局；
   其它模态的行格式各不相同，收益/复杂度比不划算。
4. **契约**（`src/storage/batch.h`）：
   - `batch_scan` 给一批原始行（`AmRowRef`：指针 + 长度 + RID）
   - `batch_decode` 把一批行直接解进列数组（`AmBatchCol`），**不物化 `DbValue`**
   - **行字节的有效期到下一次 `batch_scan` 调用为止** ——
     heap 的批扫描是**零拷贝**的（行指针直接指向页内，页保持 pin），
     换页时才释放上一页
5. **零拷贝的安全边界**：目前靠全局 latch 兜着（整条语句期间不换页）。
   v1.2 步骤 4 引入细粒度 latch 后，**解码窗口必须被页 latch 覆盖**，
   否则页被换出就是悬空指针。这条已写进 `PLAN-v1.2.md` 步骤 4 的前置条件。

### 10.3 下推对照

| 模态 | 什么能下推 | 什么**不能**下推 | 理由 |
|---|---|---|---|
| 关系 | `col op const` 全支持 | — | 值在 tuple 内，执行器可独立重判 |
| blob | （v0.8 无属性列，实际为空） | — | — |
| 图 | 属性列；`src`/`dst` 等值（**真下推**：只枚举匹配的链） | 遍历（递归语义） | 递归进不了标量谓词系统 |
| 向量 | 标量属性（label 等值） | **距离排序** | 排序键是计算出来的，不是列值 |
| 全文 | `doc_id` 等值/范围 | **`match(col,'term')`** | 相关性依赖全局统计（idf/avgdl），执行器无法独立重求值 |
| 空间 | 标量列（x/y/minx…） | **窗口 / KNN** | 几何语义 |
| 时序 | 时间谓词 → 分区裁剪 | — | 裁剪只是少读，结果仍全等 |
| 文档 | `json_match(doc, '$.a.b = 5')` | — | 路径值映射成通用标量，执行器可独立重判 |

**唯一判据**（出现三次，一次比一次明确）：

> **执行器能不能独立重判？**
> 能 → 进 SQL 谓词；不能 → 走专用 API。

这条判据在 v1.3 §1.2 写下，在 v1.4 结束时被确认为跨模态边界，
在 v1.6 §1.2 判决 1 用来判定 `json_match` **可以**进 SQL —— 一进一不进，判据是同一条。

### 10.4 下推的三条铁律

1. **下推的结果是一个行源，和全表扫描同构** ——
   都是"给我下一行的 (rid, 字节串)"。于是执行器只有一种取行路径，
   **不需要为下推新增算子类型**。
2. **下推不改变正确性** —— 执行器拿到行之后**仍然完整求值一遍 WHERE**。
   下推只是"少读一些行"，不是"替你判断"。
   于是下推实现错了**最多是慢，不会是错** —— 除非它漏行。
   所以下推的实现必须**保守**：宁可多给行，不能少给。
3. **超集是安全的，子集是危险的** ——
   范围扫描返回候选行而非精确结果（B+tree 只支持闭区间，开区间由适配层返回超集）。
   超集安全（调用方重新过滤），子集危险（**静默丢数据**）。

## 11 · 八模态验收清单（统一口径）

> 各模态的详细验收项在各自的 `PLAN-vX.Y.md` §1.5/§1.6。这里是**跨模态的统一口径** ——
> 每个模态的实现完成时，除了自己的验收项，还要过这四条。

| # | 统一验收 | 怎么验 | 为什么 |
|---|---|---|---|
| U1 | **执行器零改动** | `grep <模态> src/query/` 零命中（只允许命中注释） | SPI 白设了；加第 9 个模态要改执行器就是失败 |
| U2 | **依赖方向正确** | `make deps` 无越界 | 硬规则 1 |
| U3 | **新文件 < 800 行** | `wc -l` 检查 | 硬规则 4 |
| U4 | **旧验收全绿** | `make test` | 新模态不能破坏既有语义 |

### 11.1 每个模态额外要过的三条

| # | 验收 | 覆盖的模态 |
|---|---|---|
| M1 | **崩溃恢复**：装载数据后模拟断电 → 恢复后数据完整、语义正确 | 全部 |
| M2 | **IO 可证**：该模态的核心查询页读数**远小于**全扫（用 `db_*_page_reads()` 前后对比） | blob / 向量 / 全文 / 空间 / 时序 |
| M3 | **能力协商**：不支持的操作返回明确 `E_NOTSUP`，**不是崩溃、不是静默成功** | 全部 |

### 11.2 模态特有的对照验收（每个模态的"对照组"）

每个模态都有**一个暴力/线性对照实现** —— 这是本项目一贯的方法：

| 模态 | 对照组 | 对照的是什么 |
|---|---|---|
| blob | 读整个对象比对 | 帧的随机访问等价于顺序读 |
| 图 | 全边表扫 | 3 跳结果集全等 |
| 向量 | **暴力扫**（GT） | 均匀随机分布：不低于 hnswlib 参照实现；聚簇分布：recall@10 ≥ 0.95；且不比 hnswlib 差 2 点以上 |
| 全文 | 线性扫描 BM25 | top-k 结果与分数**全等** |
| 空间 | 暴力扫 | 窗口 / KNN 结果**全等**（含边界点） |
| 时序 | 未压缩数据 | 压缩解压**全等** + fuzz |
| 文档 | **SQLite JSON1** | 逐条全等（SQLite 当语法裁判） |

**为什么坚持对照**：`DESIGN.md` §8 的风险清单里第一条就是
"B+tree 合并 bug 只在特定 key 分布下暴露，功能测试抓不到" ——
所以每个模态都要有一个**独立的、简单的、慢但一定对**的参考实现做 diff。

## 12 · 跨模态的公共约定

> 这些约定在实现中反复出现，写在一起免得每次重新推导。

### 12.1 六条通用约定

| # | 约定 | 含义 |
|---|---|---|
| 1 | **行 = 该模态的最小可寻址单元** | blob 一帧 / 图一个节点 / 向量一个向量 / 全文一篇文档 / 空间一个对象 / 时序一个数据点 / 文档一个 heap 行 |
| 2 | **RID = (page_id, slot)，slot 是表内局部** | 不同模态的 RID 空间互不相干，**不该互相比较** |
| 3 | **模态自管目录与页** | 不进 catalog；页不进别的结构的 freelist |
| 4 | **能力协商靠返回值，不靠类型判断** | `E_NOTSUP` → 调用方退回全扫 |
| 5 | **下推只给超集** | 宁可多给行，不能少给 |
| 6 | **新入口路径必须自己加锁** | 有的路径不走 `db_exec`（硬规则 8） |

### 12.2 "不变文件"在四个模态里的形态

| 模态 | 不可变的东西 | 谁来合并/压缩 | 原子切换点 |
|---|---|---|---|
| blob | 对象（创建 → 写 → 定稿） | —（对象级不可分） | 对象定稿 |
| 全文 | segment | Tiered 合并 | **新段落盘** |
| 向量 | 向量数据页（只追加） | 索引层增量插入 | 索引页落盘 + `reindex` 兜底 |
| 时序 | 封窗后的分区 | 封窗压缩（行式 → 列式） | **`sealed_lsn` 落盘** |

**共同的手法**：新东西落盘即成功，旧东西的清理可重试、可幂等。
（blob 定稿、ft 新段、ts `sealed_lsn` 是同一个判据的三次出现。）

### 12.3 三种事务语义的适配点

| 语义 | `visible()` 怎么答 | 写路径的 xid | WAL 类型 |
|---|---|---|---|
| MVCC | 查快照三元组 + clog（`DESIGN.md` §7.5） | 真实 xid | 行级日志 |
| 不可变 | **恒真** | **0**（系统事务） | `WAL_PAGEDATA` 整页镜像 |
| 锁 + WAL | **恒真** | **0**（系统事务） | `WAL_PAGEDATA` 整页镜像 |

**注意**：图 / 向量 / 全文 / 时序 虽然语义是"锁 + WAL"，
但 blob 是"不可变对象" —— 两者的 `visible()` 都是恒真、WAL 都是整页镜像、
xid 都传 0。区别在于**前者可变**（图的就地更新、段的合并、分区的压缩），
后者不可变。

### 12.4 外部值的三个用户

| 模态 | `ext_key` | `ext_off` | `ext_fn` 做什么 |
|---|---|---|---|
| blob | blob_id | frame_no | 按帧号读帧页 |
| 向量 | row_id | 序号 | 按序号读向量数据页 |
| 文档 JSON | 首页页号 | 偏移 | 沿 `PT_JSON_OVF` 页链读 |

**契约一行不改** —— `ext_fn` 的签名不变，换的是实现。
这是 v0.9 设计 foresight 的收官考试。

### 12.5 五条"静默出错"的高发区（重点盯）

从 `DESIGN.md` §8 的风险清单与各模态的坑清单汇总：

| # | 高发区 | 共同特征 | 防线 |
|---|---|---|---|
| 1 | **可见性 / 快照** | 单连接测不出（`xmin==xmax`，区间为空） | 必须构造多连接场景 |
| 2 | **合并 / 归并的 delta 重算** | 解出来的值"看起来合法" | 与参考实现全量 diff |
| 3 | **共享状态串号**（xid 等） | 并发下才暴露 | 所有"当前是谁"显式传参 |
| 4 | **提前终止 / 剪枝条件写错** | 少一条结果但测试可能碰巧过 | 全等验收兜底 |
| 5 | **下推漏行** | 少给行 = 静默丢数据 | 下推后仍完整求值 WHERE |

**共同特征**：这些 bug **不会让程序崩溃**，只会让结果悄悄少一点或多一点。
所以每个模态都必须有**暴力对照实现**做 diff（§11.2）。

### 13.3 本文档的维护规则

   体积大、迭代快；`db/docs/` 放的是**判决与稳定结论**。
