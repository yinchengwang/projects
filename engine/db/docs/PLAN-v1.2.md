## 一、方案

### 1.0 这一版要证明什么

DESIGN.md D4「并发三步走」的**第三步**（前两步已走完）：

> | v0.10 | 全局 latch（一把大锁） | ✅ 跑通多线程不出错 |
> | **v1.2** | **细粒度 latch + lock manager** | crabbing、锁升级、死锁检测 |

顺延项总表（PLAN-v1.1 §四）把这一版定位为「内核收尾」：
**这是还债版** —— v0.10 明确记下的那笔账（读接口返回共享指针，锁只能画粗）到本版偿还。

判据三条：

1. **并发正确性不回退**：v0.10 的全部并发测试原样跑绿（一把锁换成多把锁，
   第一受损的就是正确性）。
2. **吞吐真的变好**：读多写少场景（8:2）的并发吞吐 ≥ 语句级大锁的 **2 倍**
   （对照基线在 v1.1 的 bench 里已经存档）。
3. **每个决定可解释**：latch 获取全序写死、compact 触发条件写死、
   checkpoint 代价公式写死 —— 收尾版的本质是**把散落的决定收拢成文档**。

### 1.1 范围

**做：**

1. **copy-out 重构**：无 pin 保护的内部结构指针全部改为返回拷贝。
2. **细粒度 latch 分域**：缓冲池 per-frame、WAL、事务表、catalog 各自独立 latch。
3. **latch 获取全序** + 调试构建的顺序断言（死锁的结构性规避）。
4. **页内 compact**：slotted page 碎片整理，vacuum 联动触发。
5. **checkpoint + 日志截断**：恢复时间与全日志量解耦。
6. **拆超限文件**：`btree.c`(1105) / `catalog.c`(927)。
7. **SPI 批接口**（v1.1 实测所迫，见下）。

### 1.1.1 SPI 批接口：v1.1 的 A2 为什么没达标

v1.1 把执行器这一侧该做的都做完了（列批、选择向量、三值逻辑、投影批式化），
但 A2 的 3× 只拿到 **1.13×**。原因实测得很清楚：

| | 占整条查询 | 为什么向量化碰不到 |
|---|---|---|
| 逐行 `scan_next` | ~38% | 执行器只能一行一行攒批（PLAN-v1.1 §1.2 的判决） |
| 逐行 `decode`（物化 272 字节/值的 `DbValue`） | ~43% | `DbValue` 是 SPI 的值契约，**每行都要物化** |

**=> 瓶颈是"每行一次的 SPI 调用"和"每行一次的物化"。**
列式求值省的是"过滤时逐列 `val_copy`"，而那部分已经被 v1.1 的
`val_copy` 前提修复吃掉了（过滤阶段 3.6 → 1.1 ms）——
**向量化用错了地方：要省的是物化，而物化在 SPI 的 `decode` 里。**

**=> 本版加两个 SPI 能力（都走能力协商，`caps` 位 + 指针为 NULL = 不支持）**

| 能力 | 内容 | 预期收益 |
|---|---|---|
| `AM_CAP_BATCH_SCAN` | 一次给一批原始行 | 扫描阶段 38% → 约 10% |
| `AM_CAP_BATCH_DECODE` | 一次解一批，**直接进列数组，不物化 `DbValue`** | 解码阶段 43% → 约 15% |

**三个已验收的模态（blob / graph / vector）一行都不用改** ✓ ——
指针为 NULL 就是不支持，执行器自动退回逐行路径。
这正是 v1.1 §1.2 担心被打破的那条底线，而能力协商本来就是项目自己的机制。

**做完之后重新验收 v1.1 的 A2**（3× 是 v1.1 的对外承诺，不能只记在文档里）。

**不做（明确划掉）：**

| 项 | 为什么 |
|---|---|
| 死锁**检测**（等待图） | 全序获取**规避**了死锁，检测器没有存在必要（PG 的 LWLock 同款思路）。加检测器是给不存在的问题写代码 |
| lock manager（行级锁） | MVCC 已经让读写互不阻塞；行级锁解决的是写-写冲突，当前写路径被 latch 串行化，没有行级锁的用武之地 |
| 并行执行单语句 | 依赖本版的 latch 分域，但不属于"收尾"；有需求再立项 |
| 增量 / 分组 checkpoint | 全量 checkpoint 的代价可测可控；增量化是运维级优化 |
| hint bits | 总表已标"不排期"，维持 |

### 1.2 copy-out 的边界：不是"所有指针都拷"

v0.10 的判断是"读接口返回共享指针，所以锁只能画粗"。
但**不能矫枉过正把所有指针都拷** —— 逐个接口过堂：

| 接口 | 处置 | 理由 |
|---|---|---|
| `catalog_table_cols`（返回内部数组指针） | **改 copy-out** | 列定义是小结构，拷贝便宜。⚠️ 步骤 1 实测：它**恰好**稳定（每表一份 malloc），改它是为了契约统一 |
| `catalog_table_meta`（返回内部元素地址） | **改 copy-out** | ⚠️ 步骤 1 实测补上：`&e->meta` 在 `cat->t` 数组里，建表 realloc → **真悬空** |
| `catalog_table_indexes`（返回内部数组指针） | **改 copy-out** | ⚠️ 步骤 1 实测补上：建索引 realloc `te->idxs` → **真悬空** |
| `db_blob_id_at`（计划里写"返回目录元素"） | **不用改** | ⚠️ 步骤 1 实测推翻：它**按值返回** `BlobId`，本来就是拷贝 |
| `pager_get`（返回缓冲池页） | **不改，靠 pin** | 页帧被 pin 住就不会被逐出 —— **pin 本身就是"逻辑引用"**，这是缓冲池设计的本意（PG 的 buffer pin 同款）。拷 4KB 页是灾难 |
| heap/graph 游标（跨多次调用持有状态） | **不改语义**，游标持的页靠 pin 保护 | "游标只在语句内有效"的既有约束维持 |

**关键洞察（写进 DESIGN.md D4.2 的勘误）**：
v0.10 说"所有读接口都得改成拷出来" —— **说宽了**。
准确的规则是：**copy-out 只针对没有 pin 保护的内部结构指针**；
页数据有 pin 机制，本来就不需要拷。
细粒度化的真正工作量在"把 catalog/blob 目录这类小结构改成拷贝语义"，
而**不是**把缓冲池的访问模式推倒重来。

> 步骤 1 执行后，这条边界表已经按**实测审计**更新过一遍
> （三个 ⚠️ 标记处）—— 计划阶段的判断和实际代码对不上的地方，以实际为准。

### 1.3 latch 分域与获取全序

| # | latch | 保护 | 类型 | 临界区特征 |
|---|---|---|---|---|
| L1 | `catalog_latch` | 表/列/索引元数据缓存 | **读写锁** | 读多写少（建表/建索引才写） |
| L2 | `txn_latch` | `next_xid`、clog、活跃表 | 独占（短） | xid 分配 ~纳秒级 |
| L3 | `btree_latch`（**每棵树一把**） | B+tree 的结构与页内容 | 独占（中） | 插入 / 删除 / 查找 / 扫描 |
| L4 | `frame_latch`（**每帧一把**） | 单页数据 + pin_count | 独占（极短） | 页读改写 |
| L5 | `wal_latch` | 日志缓冲、LSN 计数、append | 独占 | append + 偶发 fsync |
| L6 | `freelist_latch` | 空闲页链 | 独占（短） | 分配/回收 |

**获取全序（绝不逆序）**：

```
catalog(1) → txn(2) → btree(3) → frame(4) → wal(5) → freelist(6)
```

⚠️ **v1.2 步骤 4d 勘误：全序里多了一个 btree 域。**

4c 定下的顺序是 `catalog → txn → frame → wal → freelist`，
步骤 4d 真正退役大锁之后才发现：**B+tree 原来一把锁都没有**，
必须补一个域（详见 §3 步骤 4d）。补进来的位置是 **frame 之前** ——
因为 B+tree 插入要**先改树结构、再写页**，页在树结构之内。

⚠️ **v1.2 步骤 4c 勘误：计划里写的全序是错的。**

计划原本写的是 `catalog → txn → wal → freelist → frame`，
理由是"写路径先 wal 后页"。**但真实代码不是这样嵌套的**：

| 真实的嵌套边 | 代码位置 |
|---|---|
| **frame → wal** | `heap.c` 的 `wal_log` 是在**页还捏在手里**的时候调的；`pager.c` 的 `flush_page` 钩子同理 |
| **frame → freelist** | `heap.c` / `btree.c` 的 `freelist_set(fl, pid, page_free_bytes(f->data))` 要读页内容算剩余空间，页还捏在手里 |

也就是说：**页比日志"更外层"**，不是相反。
计划那句"先 wal 后页"说的是**语义顺序**（日志必须先落盘才能刷页），
把它当成**锁的获取顺序**就错了 ——
语义顺序靠 WAL 规则保证（WAL 钩子 + page_lsn），不靠锁顺序。

反过来没有一条边：wal 锁里不会去碰页，freelist 锁里也不会去碰页
（`freelist_find` 先返回、`freelist_grow` 在页被捏住之后才调）。

**实现按"获取序号"编号**（= 全序位置）：

```
LATCH_CATALOG = 1   LATCH_TXN = 2   LATCH_BTREE = 3
LATCH_FRAME  = 4    LATCH_WAL  = 5   LATCH_FREELIST = 6
```

编号变了，`test_latch.c` 的"按全序获取 N 个域"也跟着改
（步骤 4c 改成 5 个域，步骤 4d 改成 6 个域）。

> **状态（步骤 3 后）**：L1 `catalog_latch` **已落地** —— 读写锁，
> 公开 API 自己拿锁（`src/catalog/catalog_lock.c`），内部走 `_locked` 版本。
> L2–L5 尚未接线（步骤 4）。步骤 3 同时向 latch 框架记账，
> 于是"catalog 排在最前"这条纪律从此刻起是**机器检查**的。

> **状态（步骤 4a 后）**：L2 `txn_latch` **已落地** —— 写路径互斥、
> 读路径走原子（clog 一 xid 一字节），见 §3 步骤 4a。
> L3–L5 仍未接线。

> **状态（步骤 4b 后）**：L3 `wal_latch` **已落地** —— **每实例一把**域锁
> （`src/wal/wal.c` 里 `struct Wal` 的 `pthread_mutex_t mu`），
> 写路径（append / fsync / reset）与扫描路径（scan / read_payload）持锁，
> 读路径（`wal_last_lsn` 等）走原子，见 §3 步骤 4b。
> L4–L5（freelist / frame）仍未接线。
> ⚠️ **步骤 4b 当时给 4c 留的约束是错的**（原文："刷页前要调 WAL flush 钩子，
> 那时若已握着 frame 域的锁就是 frame(5) → wal(3) **逆序** → 断言 abort；
> 刷页路径必须**先落日志、再取 frame 锁**"）。
> 勘误：**持 frame 锁调 WAL 钩子恰恰是对的**（frame(3) → wal(4) 符合全序），
> 因为 WAL 规则要求"日志先落盘、页后落盘"，钩子必须在刷页那一刻被调。
> 真正要避免的是**反过来**（持 wal 锁去取 frame 锁）。见 §3 步骤 4c。

> **状态（步骤 4c 后）**：L4 `frame_latch` 与 L5 `freelist_latch` **都已落地** ——
> frame 域是"池级锁（哈希表 / Clock 手 / pin_count / npages）+
> **每帧一把内容锁**"；freelist 域是一把实例级锁，
> **读路径也持锁**（`levels` 是 `realloc` 出来的，不持锁就是悬空指针）。
> 全序同步改成 `catalog → txn → frame → wal → freelist`（见上面的勘误）。
> ⚠️ **当时写的"去掉 `db_exec` 大锁后全套测试 58 PASS / 0 FAIL"是错的** ——
> 步骤 4d 复核时重跑 5 次，`test_concurrent` **每次都失败 14~15 项断言**。
> 那次全绿是撞运气的偶然，不是"两个域落地就够"的证据。见 §3 步骤 4c / 步骤 4d。

> **状态（步骤 4d 后）**：**新增 L3 `btree_latch`** —— 每棵 B+tree 一把锁，
> 公开入口（insert / delete / search / scan / reset / stats / height…）统一持锁，
> 游标把锁带在身上、`btree_cursor_close` 才放。
> 全序再勘误一次：`catalog → txn → **btree** → frame → wal → freelist`。
> **`db_exec` 大锁已退役**（关系型语句不再取全局 latch；模态语句仍取，
> 因为模态内部还没有域锁）。见 §3 步骤 4d。

**调试构建的顺序断言**：每个 latch 带编号，
`latch_lock(L4)` 时若当前线程已持有更小编号的锁之外的组合 → **abort**。
这是"死锁不可能发生"的**机器证明**（测试只是抽样，断言是全量）。

**crabbing（锁降级）**：B+tree 分裂时的"先锁子再锁父"路径（v0.3 注释里留过）
在本版实现 —— 父页锁住确认不分裂 → 放父锁 → 锁子页操作。
**这是全序里的合法例外**（页与页之间的获取序按树高从大到小），单独记入全序表。

### 1.4 页内 compact

v0.1 的测试记录：10 万次增删后**峰值碎片 100%**（页内有空洞但 slot 目录不动）。
vacuum 只删死版本，不整理页内碎片 —— 长期写负载下页利用率会塌。

| 决定 | 内容 |
|---|---|
| 触发 | vacuum 扫描时顺带统计每页碎片率（空洞字节 / 页大小）；**> 50% 的页**进入 compact 队列 ⚠️ **勘误（步骤 5 已落地）**：VACUUM 路径实际取阈值 **0**（只要有空洞就整理）—— 逐页 50% 保证不了 A5 的"全表 < 20%"（一堆 40% 碎片的页摊在一起，全表就是 40%）。详见 §3 步骤 5 |
| 做法 | 页内 slot 重排：存活记录前移、slot 目录压缩、free space 合并 |
| 崩溃安全 | compact 前后各写一次 `WAL_PAGEDATA` 整页镜像（重放最后一张即最终态） ⚠️ **勘误（步骤 5 已落地）**：实际是**一条** `WAL_PAGEDATA` 记录里同时带 before / after 两份整页镜像 —— 原子性更好，不会出现"日志里只有前半截"的状态。详见 §3 步骤 5 |
| 并发 | compact 在页 frame latch **内**完成（页级操作，不跨页）—— 这正是细粒度 latch 的第一个受益者：大锁下 compact 会卡住整库 |
| RID 稳定性 | **slot 序号不变**（重排的是物理位置和 slot 目录的顺序，RID = (page, slot) 不变）→ 索引和游标不受影响 |

**RID 不变是整个设计的锚**：compact 若改 slot 号，所有索引项全部失效 ——
那就不是 compact 而是重表。所以 compact 的自由度只有"页内物理布局"，
代价是 slot 目录要带一个"slot 序号 → 物理偏移"的重排（本来就有的间接层，只是变密了）。

### 1.5 checkpoint 与日志截断

现状：WAL 无限增长；恢复 = 重放**全部**日志 —— 跑得越久，崩溃后恢复越慢。

| 决定 | 内容 |
|---|---|
| 触发 | 手动 `CHECKPOINT` 语句 + 日志量阈值（`wal_bytes_since_ckpt > 16MB`，进 config.h） |
| 过程 | ① 拿全序锁（catalog→txn→wal）② 刷全部脏页 ③ 把 `checkpoint_lsn` 写进 meta 页（整页镜像日志）④ **截断**：`checkpoint_lsn` 之前的日志文件区间丢弃 |
| 恢复 | 从 `checkpoint_lsn` 开始重放（之前的页已在盘上）→ **恢复时间 = O(checkpoint 之后的日志量)**，与库的历史长度无关 |
| 与 blob/graph/vector 的关系 | 三模态的页同样走 `WAL_PAGEDATA` → checkpoint 一并覆盖，无需模态各自实现 |

**代价（如实记录）**：checkpoint 期间持全序锁 → 写请求阻塞一次刷盘的时间。
缓解：阈值调高、或 v1.2 之后的"增量 checkpoint"（不排期池）。

**⚠️ 勘误（步骤 6 执行后回填）**：

| 计划写的 | 实际做的 | 为什么 |
|---|---|---|
| 触发阈值"进 config.h" | **环境变量 `DB_CKPT_BYTES`**（默认 16MB） | `db_open` 只有 path 一个参数，没有配置文件机制；环境变量是不破坏现有 API 的唯一办法 |
| 过程①"拿全序锁（catalog→txn→wal）" | **不取任何锁** | checkpoint 要做的事（刷页、写 meta、落 clog、截日志）本身不需要跨域临界区；真正需要防的是"刷页的同时有人在改页"，那个由 **frame 域锁**逐帧解决（`pager_flush_all` 逐帧取内容锁，不持池级锁）。取全序锁反而会把 checkpoint 变成一次全局停顿 |
| 恢复"从 `checkpoint_lsn` 开始重放" | **重放按 `checkpoint_lsn` 过滤，回滚不按它过滤** | 未提交事务的记录可能横跨 checkpoint 点（事务在 checkpoint 时还开着），回滚要的是前像，哪怕 `lsn <= checkpoint_lsn` 也必须留着 |
| （计划里没有） | **新增 `WAL_ABORT_DONE` 记录类型** | 崩溃时开着的事务在日志里永远显示"没结束" → 日志永远截不掉 → 步骤 6 的目的落空。恢复把它回滚完之后补一条"已回滚完"的记录，截断才放行 |
| （计划里没有） | **clog 必须先落盘再截日志** | 提交状态只记在 clog 文件里，不在日志里。日志一截，这条信息就只剩 clog 文件 —— 顺序反了 = 已提交的数据全部不可见（静默丢数据） |

#### 三个设计决定

**① 全表扫走零拷贝：行指针直接指向页内，不拷。**

堆表的行是**内联在页里**的，所以"取一行"本来不需要拷贝 ——
逐行路径的 memcpy 纯粹是接口逼出来的。

实测三种取法（同一台机器、同一份数据、缓冲池预热）：

| 取法 | 完整查询耗时 |
|---|---|
| 页 → 竞技场（一次 memcpy） | 2.13 ms |
| 页 → 4 KB 中转 → 竞技场（两次 memcpy） | 2.88 ms |
| **零拷贝（不拷）** | **2.10 ms** |

中转反而更慢，原因是 **4K 别名**：页缓冲（4 KB）和竞技场（256 KB）都是大块对齐的分配，
低 12 位常常相同，于是"从页里读、向竞技场写"撞上 store-to-load forwarding 误判 ——
内存消歧器每次都要多等一拍。不拷就没有这个依赖。

零拷贝的代价是**行字节的有效期 = 页的 pin 期**，
所以契约里写死了一条：**行字节的有效期到下一次 `batch_scan` 调用为止**。
这与 PLAN-v1.2 §1.2 的"pin 本身就是逻辑引用"一致。
⚠️ **步骤 4（细粒度 latch）落地时，解码窗口必须被页 latch 覆盖** ——
现在靠全局 latch 兜着（整条语句期间不换页），拆完锁这句话就不成立了。

**② 批解码不物化 `DbValue`。**

`DbValue` 一个 272 字节，一行四列 = 1088 字节。
逐行路径每行要 memset 一遍 `Value[]` 再把每个值拷成一个 `DbValue` ——
这正是 v1.1 定位到的 43%。批解码直接写进列数组（INT 列每行 8 字节），这一步整个省掉。

三个必须与逐行路径**逐格一致**的点（写在 `storage/batch.c` 的注释里）：
NULL 位图的位号、文本截断到 `VAL_TEXT_MAX-1`、INT4 符号扩展成 i64。
对拍（批式 vs 火山，逐格全等）就是这三点的守卫。

**③ 批能力是可选加速，不是正确性前提。**

`caps` 位 + 函数指针为 NULL = 不支持，执行器自动退回逐行路径。
blob / graph / vector 三个指针置 NULL，**一行逻辑都不用改**。

#### 实测（10 万行、选择性 10%、重复 10 次取最小）

| 阶段 | 火山（逐行） | 批式 | 倍数 |
|---|---|---|---|
| 扫描 | 1.010 ms | 0.141 ms | 7.2× |
| + 解码 | 4.146 ms | 0.763 ms | 5.4× |
| **+ 过滤（A9 口径：扫描 + 过滤）** | **5.097 ms** | **0.924 ms** | **5.52×** ✓ |
| 完整查询（含结果物化） | 6.09 ms | 2.161 ms | 2.82× |

对拍：批式 vs 冻结的火山执行器，**逐格全等**（38 条 SQL + 聚合 25 条 + 索引一致性 10 条探针）。

#### 顺带发现并修掉的两个问题

**① 缓冲池 1 MB → 16 MB（默认值），另加 `DB_BP_FRAMES` 环境变量。**

这一条直接决定上面的数字是不是在量执行器。

原来默认 256 帧 = **1 MB**，装不下 4 MB 的表（≈1064 页），
于是每次扫表都把整张表从磁盘读一遍（pager 用 `setvbuf(_IONBF)` + 每页一次 `fread` 系统调用）。
实测扫描阶段：**1 MB 池 4.0–5.0 ms → 16 MB 池 0.60–0.72 ms，差 7 倍**。

**v1.1 那个 1.11–1.13×，是在一个不断换页的池上量的** —— 它测到的主要是磁盘。
现在默认 4096 帧（16 MB），并且可以用 `DB_BP_FRAMES` 调；
基准自己按数据集大小设池（`bench/exec_bench.c`），保证量的是执行器。

**② 批路径的截断 bug（静默丢数据）。**

批路径一次取一页，一页里的行可能恰好**全都不可见**（另一个事务插了还没提交）。
原来的写法是"本批 0 行 → 收工"，于是第 1 页全不可见时，
后面页里的可见行**全被丢掉** —— 不报错，只是结果少了。

改成靠 `eof` 判断收工，不靠 `nrows`。
回归测试在 `test/integration/test_batch_scan.c`：
写方先插 200 行不提交（占掉第 1、2 页），读方再插 10 行提交（落在第 3 页），
读方查表必须看到那 10 行。**已验证：把修复回退，这个测试立刻变红。**

#### 审计结果：哪些接口真的需要改

计划里只点了 `catalog_table_cols` 和 `db_blob_id_at` 两个名字。逐个过堂之后，
**其中一个不用改，另一个要改的还不止它**：

| 接口 | 原来返回 | 判决 |
|---|---|---|
| `catalog_table_meta` | `&e->meta`（`e` 在 `cat->t` 数组里） | **真悬空** —— 建表时 `cat->t` 被 realloc，整个数组搬家 |
| `catalog_table_indexes` | `e->idxs` | **真悬空** —— 建索引时 `te->idxs` 被 realloc |
| `catalog_table_cols` | `e->cols` | **恰好稳定**（每表一份 malloc，只有关库才 free）—— 但那是隐含前提，不是保证。统一改掉，契约才没有例外 |

| `db_graph_schema` / `list_*` / `hop*` | 调用方缓冲 / 调用方 free | **不用改** —— 本来就是拷贝出参 |
| SPI `am->columns` | 模态的静态常量数组 | **不用改** —— 但执行器现在也会拷进自己的缓冲区，规则统一 |

这条勘误写进了 DESIGN.md 的 D4.2.1：
**v0.10 说的"所有读接口都得拷"太宽了**，准确规则是
"copy-out 只针对没有 pin 保护、且会随 catalog 变更而失效的内部结构指针"。

#### 两个设计决定

**① 拷贝用"两段式"，不用"函数分配内存"。**

```c
int n = 0;
catalog_table_cols(cat, tid, NULL, 0, &n);      /* 先问要多少 */
ColDesc buf[16];
rc = catalog_table_cols(cat, tid, buf, 16, &n);  /* 再拷贝 */
```

理由：调用方给缓冲区 → **谁分配谁释放**的规则不用新增，
执行器的 `TableCtx` 是栈上结构，不用引入一套 `free` 纪律。
缓冲区不够 → `E_NOSPACE`，且 `*ncols` 仍然报出实际需要的个数（不静默截断）。

**② 副本放在 `TableCtx` 里，随语句的生命周期走。**

`TableCtx` 本来就是"一张表的执行期上下文"，加两个固定数组（16 × `ColDesc` + 16 × `IndexInfo`，
约 2.2 KB 栈空间）就够了 —— 不用 malloc，也就不用担心释放。
于是 `tc->cols` 有一条**没有例外**的规则：**永远指向 `TableCtx` 自己的缓冲区**。

代价：每张表最多 16 个索引（超过就在建索引时明确报错，不再让它在查询时炸）。
一张表最多 16 列（parser 层已卡），所以这个上限和列数同阶，不算苛刻。

`test/integration/test_copyout.c`：

   三份副本**一字不差**；同时重新取一次，索引数确实变成 1 ——
   证明 DDL 生效了，只是没影响旧副本。

### 步骤 2 · latch 框架（2026-11-04）

**结论：完成。框架就位，调用点一行未改，零行为变化。**

#### 落地的东西

| 文件 | 作用 |
|---|---|
| `src/common/latch.h` | 域编号 `LatchId`（catalog / txn / wal / freelist / frame）+ 全序表 + 框架 API + 违规处理钩子 |
| `src/common/latch.c` | 线程本地持锁集合、全序断言、crabbing 例外、违规默认 abort |
| `test/unit/test_latch.c` | 框架验收（6 项） |

#### 三个设计决定

**① 编号 = 获取序号，不沿用计划的 L 编号。**

计划（§1.3）里 frame 记作 L4、freelist 记作 L5，但**全序**是
`catalog → txn → wal → freelist → frame` —— freelist 在 frame 之前。
两个编号打架会让人拿错顺序，所以实现按**获取序号**编号
（= 全序位置），对应关系写进头文件：

```
L1 catalog → 1    L2 txn → 2    L3 wal → 3
L5 freelist → 4   L4 frame → 5
```

**② 步骤 2 只做"记账 + 断言"，不加真实互斥。**

真实互斥在步骤 3/4 接线（那时才改调用点）。
好处是这一步对现有行为**零变化** —— 现有代码一行都不用动，
可以先让纪律立起来，再一把一把地换。
记账是**线程本地**的（和 `t_depth` 同一个道理）：
"当前持有哪些域的锁"是每个线程各自的状态，不是共享状态。

**③ 断言默认 abort，而且一直开。**

没有"调试版才开"这回事 —— 一个能抓到逆序的断言，
不该在发布版里消失。开销是每个域 5 次整数比较，可以忽略。
测试可以装自己的处理函数，这样"确实被拦住了"能被断言到，
而不必杀死测试进程。

#### 全序检查的规则

```
获取序号 r 的域之前，已持有的所有域的序号必须 < r
```

- **同域重复获取**（可重入）不算逆序 —— 那是嵌套调用同一把锁。
- **被拦下的获取不记账** —— 否则持锁集合会记录一把"其实没拿到"的锁，
  后面所有判断都建立在假状态上。这条有专门的测试项。
- **crabbing**（B+tree 分裂的锁降级）是显式例外：
  `latch_order_acquire_crabbing(id)` 只允许**同域内**（手里握的已经是这个域的锁），
  跨域使用它就是普通违规。域级别本来就管不到同域内部的顺序，
  所以它的价值是**在代码里留下显式标记** ——
  让读代码的人知道这条路径是经过论证的例外。
  页与页之间的树高顺序，由步骤 4 的 per-frame 检查真正管。

#### 验收（6 项，`test/unit/test_latch.c`）

1. 按全序获取 5 个域 → 全 OK，记账正确，逆序释放后归零。
2. **逆序被拦**：先 frame 再 txn → 被拒、违规计数 +1、**且没记账**；
   释放 frame 后再取 txn → 正常。
3. 可重入：同域两次 → 计数 2，域个数仍是 1。
4. crabbing：同域允许；跨域**拒绝**。
5. **持锁集合是线程本地的**：主线程持 catalog，另一个线程取 txn 互不影响。
6. **默认行为真的是 abort**：用 `system()` 另起一个子进程去撞逆序，
   检查退出码非 0（实测 3 = abort）。
   并且子进程先打印一个标记 —— 否则"命令没找到"也是非 0，
   测试会**假通过**。

#### 如实记录（不注水）

- **第 6 项的 `system()` 依赖测试二进制的路径**（`build/test_latch.exe`）。
  `test/run.sh` 正是从那里跑它，所以路径是成立的；
  但如果有人改了测试的输出目录，这一项会**假通过**（命令找不到 → 非 0）。
  标记检查就是为了堵这个洞 —— 命令找不到时输出文件里没有标记。

- **框架目前没有接入任何真实锁。**
  它的价值现在还只是"纪律 + 测试"；真正起作用要等步骤 3/4。
  这不是"做了一半"，是计划里就定好的顺序（"一次只动一件事"）。

- **断言只查"域"这一层。**
  同一域里不同帧的顺序（树高序）现在**查不出来** ——
  那是步骤 4 的 per-frame latch 才有的检查。

### 步骤 3 · 分域 ①：catalog 读写锁（2026-11-04）

**结论：完成。catalog 域换成读写锁，大锁仍在。
验证性缩小实验证明：catalog 域已经能独立站住；剩下的是 txn / 页 / WAL 域（步骤 4 的活）。**

#### 落地的东西

| 文件 | 作用 |
|---|---|
| `src/catalog/catalog_lock.c`（新） | 4 个锁原语（read/write lock/unlock）+ 15 个公开 API 的包装层 + 违规处理钩子 |
| `src/catalog/catalog.h` | 锁 API 声明 + `CatalogViolationFn`（测试用） |
| `src/catalog/catalog_priv.h` | `struct Catalog` 增加 `pthread_rwlock_t rw`；声明 15 个 `_locked` 内部版本 |
| `src/catalog/catalog.c` | 11 个公开实现改名为 `_locked`；`catalog_open` 初始化 rwlock、`catalog_close` 销毁 |
| `src/catalog/catalog_stats.c` | 4 个公开实现改名为 `_locked` |
| `test/unit/test_catalog_lock.c`（新） | 验收 7 项 |

#### 三个设计决定

**① 锁画在"公开 API"这一层，内部一律走 `_locked`。**

```c
/* src/catalog/catalog_lock.c */
int catalog_table_cols(Catalog *cat, u32 table_id, ColDesc *buf, int cap, int *ncols)
{
    catalog_read_lock(cat);
    int rc = catalog_table_cols_locked(cat, table_id, buf, cap, ncols);
    catalog_read_unlock(cat);
    return rc;
}
```

两个硬理由：

- 每个公开 API 只有**一个出口** → 加锁/解锁不会漏路径
  （把 lock/unlock 写在函数体内的话，多一个 `return` 就漏一次解锁）；
- 内部函数互调**不会递归取锁** —— POSIX 规定"重复取读锁"是未定义行为，
  有写者在等时会死锁；重复取写锁直接自锁。

调用方**不要**自己拿锁（拿两次 = 递归取读写锁）。
`catalog_create_table_locked` 内部要查重名，走的也是 `catalog_find_table_locked`。

**② 读锁可重入，写锁不可重入，不许升级/降级。**

| 纪律 | 实现 |
|---|---|
| 读锁可重入 | 线程本地计数 +1，**只有第一次**才碰底层 rwlock |
| 写锁不可重入 | 第二次取写锁 → 违规 |
| 升级（读→写）/ 降级（写→读） | 都违规 —— 读写锁的升级没有正确实现（读者一多就死锁） |

违规默认**打印 + `abort()`**（"不可能发生"要有机器证明），
测试可以装 `catalog_set_violation_handler` 换成"记一笔"。

持锁状态是**线程本地**的（`_Thread_local` 槽位表）——
"我持有什么锁"是当前线程的属性，不是共享状态。
槽位会**回收**（释放后可以给别的 catalog 实例用），
否则一个线程先后开 4 个库就再也拿不到槽位了
（这个洞第一版就踩了：测试跑到一半报"锁槽位已满"）。

**③ 锁与 latch 框架记账同时做。**

取锁的同时向 latch 框架**记账**（`LATCH_CATALOG`，序号 1 = 全序最前）。
这样步骤 4 换 txn / wal / freelist / frame 时，
"catalog 必须排在它们之前"这条纪律是**机器检查**的，不是口头约定。

#### 验收（7 项，`test/unit/test_catalog_lock.c`）

1. **读锁可重入** —— 用**写者当探针**：主线程取两层读锁，
   写者线程必须被挡住；放一层仍挡（说明还剩一层），全放才进。
   （"读者还剩几层"能从外面看出来，才算真的测到了重入语义。）
2. **读读不互斥** —— 两个线程同时持读锁都能进。
3. **写锁排他** —— 持写锁时读者进不来；放锁后立刻进。
4. **升级被拒** —— 持读锁取写锁 → 违规计数 +1，消息含"升级"。
5. **降级被拒** —— 持写锁取读锁 → 违规计数 +1，消息含"降级"。
6. **写锁不可重入** —— 违规计数 +1。
7. **默认行为真 abort** —— `system()` 另起子进程去撞升级，
   检查退出码非 0；并且子进程先写一个标记文件 ——
   否则"命令没找到"也是非 0，测试会**假通过**。

计划要求："把 `db_exec` 大锁临时去掉 → 并发测试应暴露 catalog 竞态 → 恢复大锁"。

| `test_concurrent`（并发插入 / xid 不串号 / 缓冲池压力 / 崩溃恢复 / 并发读写） | **13 项断言失败**（插入报错、行数不对、恢复后行数不对） | 竞态在 **txn / heap / pager / WAL** 域 —— 步骤 4 的活 |

#### 如实记录（不注水）

- **大锁保留期间，catalog 锁是"备而不用"的。**
  所有 catalog 访问都在 `db_exec` 的大锁里面，锁与锁之间不会真的并发争用。

### 步骤 4a · 分域 ②：txn 域（2026-11-04）

**结论：完成。txn 域（next_xid / clog / 活跃表）已自带保护，
但 `db_exec` 大锁**仍然不能退役** —— 剩下的竞态在 heap / pager / WAL 域。**

#### 落地的东西

| 文件 | 作用 |
|---|---|
| `src/txn/txn.h` | `TxnTable` 的共享字段改成原子（`next_xid` / `clog[]` / `active[]` / `n_active`）；clog 改成**一 xid 一字节** |
| `src/txn/txn.c` | txn 域的锁（进程级互斥）+ 写路径持锁、读路径无锁 |
| `test/unit/test_txn_domain.c`（新） | 验收 4 项 |

#### 三个设计决定

**① 写路径持域锁，读路径完全无锁（原子读）。**

txn 域的读路径是**整个内核最热的路径**：可见性判断每读一行就要查一次 clog。
如果每次查 clog 都取一次 rwlock，10 万行的扫描会多花几毫秒 ——
A9 的门槛（扫描 + 过滤 ≥ 3×）会直接破。所以：

| 路径 | 手段 |
|---|---|
| 写（xid 分配 / 活跃表增删 / clog 写入） | txn 域的互斥锁（进程级，txn.c 里的静态锁） |
| 读（clog 状态 / 活跃表查询） | **原子读，一把锁都不取** |

域锁是**进程级**的一把锁，不是每实例一把：一个进程里同时开两个库的情况极少，
而进程级锁换来的是"不需要 init/destroy、不需要改任何调用点"的干净实现
（`TxnTable` 在测试里是栈上对象，20 多处 `txn_table_init` 一行都不用动）。

**② clog 从"2bit 打包"改成"一 xid 一字节"。**

原来一个字节存 4 个 xid 的状态（省内存）。改成每个 xid 一字节（4096 字节），
原因不是内存，而是**并发**：

- 2bit 打包时，clog 的写入是"读-改-写"一个字节 ——
  两个线程改**同一字节里不同的 xid** 会互相覆盖 → 提交状态丢失 →
  "已提交的数据读不出来"。
- 一 xid 一字节之后，每个 xid 的状态独占一个字节 → 只存不读改，
  原子读写不会丢更新。代价只有 3 KB 内存。

**③ 发布顺序：先 clog，再 next_xid。**

分配 xid 时必须**先**把 `clog[xid % SLOTS]` 重置成"进行中"，**再**发布 `next_xid`。
因为 clog 是环形窗口：那个槽位可能留着 4096 个事务之前的老 xid 的"已提交"，
不重置就发布 → 读者会读到陈旧的"已提交" → **脏读**。

（`next_xid` 的发布与 `active[]` 的登记之间也有窗口，但那个窗口是**安全**的：
事务还没进活跃表 → 不在快照的 xip 里 → 可见性判断回落到 clog → "进行中" → 不可见。）

#### 验收（4 项，`test/unit/test_txn_domain.c`）

1. **xid 唯一性**：8 线程 × 200 轮并发开事务 → 1600 个 xid 两两不同，
   且每个都已提交、活跃表不漏项。
2. **槽位复用**：把 clog 窗口填满"已提交"，再开一个新事务（复用槽位）→
   它**还没提交**时必须读成"进行中"（不是槽位里残留的"已提交"）。
3. **并发无脏读**：写者持有一个事务不放，读者连读 20 万次 → 状态必须一直是"进行中"。
4. **活跃表上限**：128 个线程并发开事务 → 满了明确报 `E_NOSPACE`，不越界，收尾后活跃表为空。

**这个测试是真的会红的**：把 `txn_begin` 的域锁临时去掉（模拟步骤 4 之前的状态），

### 步骤 4b · 分域 ③：wal 域（2026-11-04）

**结论：完成。wal 域（LSN 计数 / undo 链 / 日志文件本身 / 扫描游标）已自带保护，

#### 落地的东西

| 文件 | 作用 |
|---|---|
| `src/wal/wal.c` | wal 域的锁（**每实例一把**）+ 计数器改原子 + 扫描路径走同一把锁 |
| `test/unit/test_wal_domain.c`（新） | 验收 4 项 |

#### 这一域的特殊性：它保护的不是内存，是**日志文件本身**

catalog 域保护的是元数据，txn 域保护的是事务表 —— 出了错是"读到脏数据"。
wal 域不一样：`wal_append_xid` 里这三步必须是一个整体：

```
    lsn = last_lsn + 1;      ← 取号
    FSEEK(f, 0, SEEK_END);   ← 定位到文件尾
    fwrite(b, 1, n, f);      ← 写一条记录
```

两个线程同时进来会怎样？

| 后果 | 后果的严重性 |
|---|---|
| 两个线程取到**同一个 LSN** | 恢复时日志顺序错乱（LSN 是 page_lsn / undo 链的排序依据） |
| 两个线程各自 fseek 到尾再 fwrite → **字节交错** | 文件里出现半条 A、半条 B → CRC 失败 → 恢复**截断** → 截断点之后**所有**记录作废 |

第二条尤其致命：**一次并发写日志的竞态能废掉整段日志**，
而且没有报错、没有崩溃 —— 只是"数据不见了"。

#### 三个设计决定

**① 每实例一把锁，不是进程级（与 txn 域不同）。**

txn 域用的是进程级互斥量（`txn.c` 里的 `g_txn_lock`），wal 域不是：

- WAL 是**实例级**资源 —— 一个库一个日志文件。不同库之间没有任何共享状态，
  用进程级锁会让不相关的库互相阻塞。
- `Wal` 的生命周期完全由 `wal_open` / `wal_close` 管住，加锁**不需要改任何调用点**
  （不像 `txn_table_init` 有 20 多处调用点）。
- `wal_reset` 会**重开文件**（关掉再以 `"wb"` 打开）——
  进程级锁下这个"重开"会牵扯到别的实例，语义反而更糊。

**② 写路径与扫描路径持锁，读路径完全无锁（原子读）。**

| 路径 | 手段 | 为什么 |
|---|---|---|
| 写（append / fsync / reset） | wal 域的互斥锁（每实例一把） | 取号 → 定位 → 写必须独占 |
| 扫描（scan_begin / scan_next / scan_end / read_payload） | **同一把**域锁 | 扫描与 append 争同一个 `FILE*` 和同一个 `scratch` 缓冲 |
| 读（last_lsn / nrecords / max_xid / flushed_lsn） | **原子读，一把锁都不取** | 热路径（每条语句结束都查 `flushed_lsn`），取锁会拖慢语句吞吐 |

**③ 发布顺序：先写文件，后发布 LSN。**

`last_lsn` 必须在 `fwrite` 成功**之后**才发布。反过来的话，
读者会看到一个"已经分配但还没落盘"的 LSN ——
刷页时按 `page_lsn <= flushed_lsn` 判断，会以为日志已经落盘了。

#### 验收（4 项，`test/unit/test_wal_domain.c`）

1. **LSN 唯一且连续**：8 线程 × 300 轮并发 append → 2400 个 LSN 两两不同，
   且合起来正好是 1..2400（既不重复，也不断号）。
2. **日志文件本身完整**：并发写出来的日志，2400 条**一条不差**地扫回来
   （`wal_scan_next` 内部校验 CRC，扫不回来就说明文件里有撕裂的记录）。
3. **append 与 fsync 混跑**：读线程不停读三个计数器 → 只许变大、不许倒退。
4. **undo 链按 xid 独立**：xid=7 的三条串成一条链，xid=8 自成一条（不接 xid=7）。

**这个测试是真的会红的**：拿步骤 4b 之前的 `wal.c` 跑同一个测试，立刻报
**"LSN 重复 2087 个、断号 2399 个、2400 条只扫回 125 条"** —— 已实测验证。
（那 125 条就是交错写入之后**恰好 CRC 通过**的幸存者。）

#### ⚠️ 勘误一：获取全序写错了（计划里的顺序是错的）

计划（§1.3）写的全序是 `catalog → txn → wal → freelist → frame`，
理由"写路径先 wal 后页"。

**真实代码不是这样嵌套的** —— 两条边都在**页还捏在手里**的时候发生：

| 真实的嵌套边 | 代码位置 |
|---|---|
| **frame → wal** | `heap.c` 的 `wal_log`（在 pin 住的页上写日志）、`pager.c` 的 `flush_page` 钩子 |
| **frame → freelist** | `heap.c` / `btree.c` 的 `freelist_set(fl, pid, page_free_bytes(f->data))`（要读页内容算剩余空间） |

**页比日志更外层**，不是相反。计划那句"先 wal 后页"说的是**语义顺序**
（日志必须先落盘才能刷页），把它当成**锁的获取顺序**就错了 ——
语义顺序靠 WAL 规则（WAL 钩子 + page_lsn）保证，不靠锁顺序。

反过来没有一条边：wal 锁里不会去碰页，freelist 锁里也不会去碰页。

**新全序**：`catalog(1) → txn(2) → frame(3) → wal(4) → freelist(5)`，
枚举值按**获取序号**重编号（`src/common/latch.h`）。

**顺带作废步骤 4b 留给 4c 的那条约束**（原文说"持 frame 锁调 WAL 钩子是逆序"）：
持 frame 锁调 WAL 钩子**恰恰是对的**（frame(3) → wal(4) 符合全序）——
WAL 规则要求"日志先落盘、页后落盘"，钩子必须在刷页那一刻被调。
要避免的是**反过来**（持 wal 锁去取 frame 锁）。

#### ⚠️ 勘误二：freelist 的读路径也必须持锁

原以为 freelist 只有写路径有竞态（桶计数的读-改-写）。
实测**读路径同样要锁**，原因是 `freelist_grow` 用 `realloc` 扩 `levels[]` ——
**指针会变**。读者缓存了旧指针，扩容之后就是**悬空指针**。

所以 freelist 域的**所有**公开函数（含 `level` / `find` / `npages` / `count_at`）都持锁。

#### 三个设计决定

**① freelist 域：桶计数与实际档位必须一起改，且一起持锁。**

`freelist_set` 做的是两个共享计数器的"读-改-写"：

```
    if (bucket[old]) bucket[old]--;
    bucket[new]++;
    levels[page_id] = new;
```

两个线程改的是**不同的页**，但很可能命中**同一个桶**（桶按档位分，不按页分）。
没有锁时两次 `bucket[old]--` 互相覆盖 → 桶里的计数比实际档位少 →
**`find` 会返回已经被别人占满的页**。

后果不是"多占一点空间"：调用方拿到一页就往里塞数据，
而那一页可能已经满了 → `page_insert` 失败，或者**页内 slot 目录被并发写坏**。

**② frame 域：两把锁，各管各的。**

| 锁 | 管什么 | 特点 |
|---|---|---|
| 池级锁 `pg->mu` | 哈希表（page_id → 帧下标）、Clock 手、`pin_count`、`npages` | 普通互斥量 |
| 内容锁 `pg->latches[i]` | **一帧的页内容** | **递归**互斥量 |

**内容锁覆盖 get → unpin 的整个借用期**：
从 `pager_get` 拿到帧，到 `pager_unpin` 归还，
这期间页的内容是**借给调用方**的。
这段时间里如果另一线程把这一帧逐出并载入别的页，
调用方手里的指针就指向了**别的页的内容** —— 写进去的数据张冠李戴，且无报错。

**内容锁必须是递归的**：同一线程可能对同一页 `get` 两次
（B+tree 先取父页再取子页，中间又回头看一眼父页）——
不可重入的锁会自己把自己锁死。

**③ 死锁怎么排除：一条不变式。**

> **持有内容锁 ⇒ 该帧的 `pin_count` ≥ 1**

由它推出两条：

1. `pin_count == 0` 的帧，**内容锁一定是空的**
   → 逐出路径（持池级锁 → 取受害者内容锁）**不会阻塞**在内容锁上
   → 不存在"池级锁等内容锁、内容锁持有者等池级锁"的环
2. 逐出路径只挑 `pin_count == 0` 的帧（Clock 的规矩），
   所以内容锁的持有者不可能是"正在被逐出的那一帧"

配套的顺序纪律：**任何等待池级锁的路径都不持有内容锁**。
唯一的例外是 `unpin`，它的顺序是
"查表（池级锁）→ **放内容锁** → 减 pin_count（池级锁）"——
它在等池级锁时**还没持有内容锁** ✓。

#### 一、大锁怎么退的

`db_exec` 不再无条件 `latch_lock()`。改成**按语句类型判定**：

```c
bool modality = (st.table[0] != '\0' &&
                 spi_registry_find(db->inst->reg, st.table) != NULL);
if (modality) latch_lock();
rc = exec_stmt(&db->db, &st, &qr, db->errmsg, (int)sizeof(db->errmsg));
if (modality) latch_unlock();
```

**为什么模态语句还留着大锁**：blob / graph / vector 的内部
（blob 的 `BlobId *ids` 是 `realloc` 出来的、graph 是纯内存、
vector 的 store/index 直接用 pager 的 get/unpin）
**一个域锁都还没有**。大锁现在是它们的**唯一**保护，
在给模态补域之前先撤掉等于直接放血。

**为什么撤掉是安全的**：关系型语句的每一条路径
（catalog → txn → btree → frame → wal → freelist）现在都有域锁，
**且每条路径都遵守全序** —— 由 `latch.c` 的断言**机器检查**。

#### 二、⚠️ 勘误一：全序里多了一个 btree 域

4c 定下的顺序是 `catalog → txn → frame → wal → freelist`。
步骤 4d 真正拆大锁之后才发现：**B+tree 原来一把锁都没有**
（见下面缺陷二），必须补一个域。

**补进来的位置是 frame 之前** —— 因为 B+tree 插入要
**先改树结构（根分裂 / 页分裂 / 分隔键）、再写页**，页在树结构之内。
所以新全序：

```
catalog(1) → txn(2) → btree(3) → frame(4) → wal(5) → freelist(6)
```

`src/common/latch.h` 的枚举同步重编号，`latch.c` 的域名表补上 `"btree"`，
**逆序报错信息也改了**：现在会指出**具体是哪个域逆序**
（原来只说"已持有更高序号的域"），排查时能直接定位。

#### 三、缺陷一：堆的 freelist「find → use」窗口

**现象**：4 线程并发往一张表插 500 行，全部失败。

```
thread 0: errors=500   thread 1: errors=500
thread 2: errors=454   错误码 E_NOSPACE
```

**根因**：`freelist_find` 按**档位**挑页，
但**档位是在插入之后才更新**的 —— 于是：

1. 线程 A `find` 到页 P（档位看起来够）
2. 线程 B `find` 到**同一页** P（A 还没插、档位还没更新）
3. A 插满 P 并更新档位；B 插 P → `page_insert` 报 `E_NOSPACE`

**这不是"槽位丢失"或"页内容损坏"**，是一处**典型的 find→use 竞态**。

**修法**：`heap_insert` 加**有界重试**
（`HEAP_INSERT_MAX_RETRY 64`）—— `E_NOSPACE` 就 unpin、重新 find。

**为什么能收敛**：填页的那一方是**持着内容锁**更新档位的，
而 `level < need_level ⟹ free < need ⟹ find` 不会再挑中它。
所以重试次数很少，实测 `errors=0`。

顺带把堆的 `npages` / `wal_calls` 改成 C11 `_Atomic`
（`atomic_fetch_add` / `atomic_load`）——它们是被无锁读的统计量。

#### 四、缺陷二：B+tree 原来一把锁都没有

**现象**：4 线程并发往**带索引**的表插 300 行（共 1200 行），
堆里 1200 行全在，**点查却能漏掉两百多个**：

```
点查: 缺失=213 / 7 / 178
```

这是**静默的数据不一致** —— 行在，索引找不到。

**根因**：`btree.c` 里没有任何锁。
B+tree 的树结构本身就是**共享可变状态**：

- `root` / `height`：根分裂要换根，根降高要换根；
- `scratch[]`：**compact 用的整页暂存区** —— 两个线程同时用它
  就是两个人往同一块内存里搬数据；
- **分裂本身不是原子的**：`insert_rec` 先在孩子页插，再回父亲页插分隔键，
  这两步之间如果另一个线程也在分裂，父亲页的条目就可能重复或丢失。

**修法**：新增 **btree 域** —— 每棵树一把 `pthread_mutex_t`，
`bt_lock()` / `bt_unlock()` 走 `latch_order_acquire(LATCH_BTREE)`。
公开入口统一持锁：

| 入口 | 说明 |
|---|---|
| `btree_insert` / `btree_delete` | 写路径 |
| `btree_search` | 点查 |
| `btree_scan` | **锁转交游标**，`btree_cursor_close` 才放 |
| `btree_reset` / `btree_stats` | 统计与重置 |
| `btree_height` / `btree_npages` / `btree_root` | 读接口（`bt_mut()` 去 const） |
| `btree_format_ok` | 格式校验 |

`btree_cursor_next` **不取锁** —— 游标已经持有那把锁。

**修完之后**：点查 `缺失=0 多行=0 值错=0`。

#### 五、顺带修掉一条真实的逆序边（断言逮到的）

`heap_am_reindex`（`src/spi/heap_am.c`）跨 `heap_scan_next` 一直
**捏着堆页不放**，等行拷出来之后才去调 `btree_insert` ——
于是形成 **frame(4) → btree(3)** 的真实逆序边，
被 `latch.c` 的顺序断言当场 abort：

```
latch: 违反获取全序: 获取 btree（序号 3）时已持有更高序号的域 frame（序号 4）
```

**修法**：行数据已经拷进 `recbuf` 了，插索引前先把页放掉 ——

在 `heap_am_reindex` 里插索引前调它。

**这条边是断言逮到的，不是人肉看出来的** —— 这是全序断言的价值。

```
记录从页尾往下长（slot 号越大，地址越低）。
假设按顺序插了 R0 / R1 / R2（各 100 字节），后来 R1 被删了：

整理前（页头 ← 空闲区 → R2 → 空洞 → R0）：
  [ 空闲 ][ R2 ][  洞  ][ R0 ]     ← 洞就是被删掉的 R1 留下的 100 字节
整理后（空洞抹平，空闲区合并到页头一侧）：
  [      空闲      ][ R2 ][ R0 ]
```

整理后每条记录的**地址变了**（R2 从 3800 挪到 3896，R0 从 4000 挪到 3996），
但它们的**相对顺序不变**，而且 **slot 号没变** —— RID 因此不变。

关键：**slot 编号不变**（`slot_set(pg, i, dst, l)` 只改物理偏移，
不改 slot 号）。这是整个设计能成立的前提，见 §五。

#### 二、⚠️ 勘误一：阈值不是 50%，是 0

计划（§1.4）写的是"**> 50% 的页**进入 compact 队列"。

那是**插入路径**的取舍标准（插入时顺手整理一下，碎片率不到一半
就不值得为它写一条整页日志）。但 **VACUUM 是显式的维护操作** ——
用户就是要"把表收拾干净"，而验收 A5 要的是"**全表**碎片率 < 20%"。

逐页 50% 的阈值**保证不了**这个结果：一堆 40% 碎片的页摊在一起，
全表就是 40%。

所以 VACUUM 路径取阈值 **0**：只要有空洞就整理。
代价是每个整理过的页写一条 8KB 的日志记录（before + after 两份整页）——
WAL 增长换空间回收，这个取舍交给步骤 6 的 checkpoint 去兜（日志会被截断）。

`heap_compact_page` 的阈值参数保留（`frag_threshold_pct`），
插入路径将来要用；VACUUM 现在传 0。

#### 三、整理必须在**副本**上做（log before data）

崩溃安全的铁律是"**先日志，后数据**"：页的内容变之前，
对应的日志必须已经写好。

如果直接就地整理（先 `page_compact(真页)` 再写日志），
中间崩溃就会留下"页变了、日志里没有"的窗口 —— 重放之后这页回不来。

所以做法是：

```c
u8 before[PAGE_SIZE];   /* 整理前 */
u8 after[PAGE_SIZE];    /* 整理后（在副本上整理出来） */
memcpy(before, f->data, PAGE_SIZE);
memcpy(after,  f->data, PAGE_SIZE);
page_compact(after);               /* 只动副本 */

/* 先写日志 */
wal_log(h, xid, LOG_PAGEDATA, page_id, 0, LOG_NO_SLOT_OFF,
        before, PAGE_SIZE, after, PAGE_SIZE, &lsn);

/* 日志写好了，才把整理结果落到真页上 */
memcpy(f->data, after, PAGE_SIZE);
```

`test/unit/test_compact.c` 的第 2 项专门盯这条：日志钩子捕获
`LOG_PAGEDATA`，断言**恰好一条**、before/after 各 4096 字节，
而且 `spy.frag_before == pc.frag_before`（日志里的 before 就是真页的 before）。

#### 四、⚠️ 勘误二：一条日志记录带两份整页，不是"前后各一条"

计划写的是"compact 前后**各写一次** `WAL_PAGEDATA` 整页镜像
（重放最后一张即最终态）"。

实际实现是**一条**记录里同时带 before 和 after：

```
┌──────────── WAL 记录 ────────────┐
│ header │ before[4096] │ after[4096] │ crc │
└────────────────────────────────────┘
```

- **重放（redo）**：盖 after → 最终态
- **回滚（undo）**：盖回 before → 整理被撤销

比"前后各一条"好的地方：日志里的信息是**原子的**，
不会出现"日志里只有前半截"的状态（后半截丢失 → 恢复出来的页是半整理的）。

代价：一条记录 4096 + 4096 = **8192 字节**，
正好等于 `WAL_MAX_PAYLOAD`（判据是 `>`，所以放得下）。

#### 五、RID 不变是整个设计的锚

`RID = (page, slot)`。compact 只改**物理偏移**，不改 **slot 号**：

- 索引项指向的 RID 不变 → 索引不需要重建，也不需要失效
- 游标每次 `scan_next` 重新过 latch 拿偏移（本来就该如此）

这一步顺带**纠正了 v0.7 的一处旧注释**：当时写的是
"compact 会移动记录位置 → RID 变化 → 索引失效"，
并以此为理由**没有**在 VACUUM 里调用 compact。

实测（`test/unit/test_compact.c` 第 1 项）：整理前后
12 行的**字节内容逐字节相同**，RID 不变，扫描行数不变。

#### 六、freelist 档位必须跟着更新

页里的空间回收了，`freelist` 里这一页挂的档位（可用字节数）也得更新：

```c
freelist_set(h->fl, page_id, page_free_bytes(f->data));
```

不更新的后果：这一页在 freelist 里还挂着**旧的（更小的）档位**，
找页的时候会被当成"塞不下"而跳过 —— 空间明明空着却用不上。

实测（单元第 3 项）：档位 68 → 158（回收 1440 字节）。

#### 七、VACUUM 输出变成六列

```
scanned | removed | kept | compacted_pages | freed_bytes | frag_pct
```

前 3 列是老的；后 3 列是步骤 5 加的 —— 页内 compact 干了多少活，
得能看见，否则"VACUUM 说成功"和"空间真回收了"分不开。

`frag_pct` 是**整理之前**这张表的碎片率：它回答的是
"这次 VACUUM 收拾的是多碎的一张表"。
整理之后再来一次 VACUUM，`frag_pct` 应该是 0 —— 这正是 A5 的判据。

`test/integration/test_mvcc_it.c` 和 `test_spi_it.c` 里
"`db_result_cols(r) == 3`" 的断言同步改成 6。

#### 八、A5 的证据

`test/integration/test_vacuum_compact.c`（集成，3 个阶段）：

```
造数据：2000 行插入 + 750 次删改（2750 个事务，20 多页）
        索引建在整理之前 —— 这样"整理后索引点查还准"才真的在验 RID 不变

阶段 A（回收 + A5）：
  第一次 VACUUM：scanned=2250 removed=750 kept=1500
                 compacted=22 freed=29583 frag=36%
  第二次 VACUUM：scanned=1500 removed=0   kept=1500
                 compacted=0  freed=0     frag=0%      ← A5 达成

阶段 B（数据没被改坏）：
  活着的行数 = 1500（应为 1500）
  逐行抽查 val：全部正确
  已删除的行：读不到
  索引点查：值正确（RID 没变）

阶段 C（还能用 + 落盘了）：
  整理后插入 / 点查：正常
  关库 → 重开：行数一致、值一致
  重开后再 VACUUM：frag=0%、compacted=0
```

**为什么"第二次 VACUUM 报 frag=0"就是 A5 的证据**：
第一次报 36% 说的是"我收拾的是多碎的一张表"，不是"我没收拾干净"。
真正说明结果的是第二次 —— 如果第一次没整理干净，
第二次还会看到碎片（frag > 0、compacted > 0）。

⚠️ **规模偏离（如实记录）**：计划 A5 写的是"10 万次随机增删"，
实际是 2000 行 + 750 次改删。原因：每条 SQL 语句都是独立事务，
提交时要 fsync 一次日志 —— 10 万条语句光 fsync 就要几分钟，
集成测试不能这么跑。10 万级的压测留给步骤 7 的吞吐基准。

#### 九、附带修掉一个**既有缺陷**：恢复阶段 xid 状态表的 256 项上限

这是步骤 5 的集成测试撞出来的，**不是步骤 5 引入的** ——
它跟页内 compact 没关系，去掉 VACUUM 一样复现。

**缺陷**：`src/wal/recovery.c` 收集 xid 提交状态用的是**固定 256 项**的数组：

```c
#define REC_MAX_XIDS 256
typedef struct {
    int         n;
    RecoveredXid xids[REC_MAX_XIDS];   /* 固定 256 项 */
} RecoveredState;
```

扫日志时表满了就 `continue` —— 后面的 xid **既没记"已提交"也没记"已中止"**。

**后果是静默的数据错误**（不崩溃，数据悄悄变错）：

```
300 次插入 + 150 次删除 = 450 个事务
  关闭前 COUNT(*) = 150
  重启后 COUNT(*) = 255      ← 删掉的 105 行又"活"了
```

为什么是"活"而不是"死"：删除**不是物理删除**，是给记录打 xmax 标记。
"这行删了没有"这件事记在 xmax 的那个 xid 上，而那个 xid 的提交状态被丢了
→ clog 说"进行中" → 可见性判断认为这行还活着。

**边界在哪**：事务数 ≤ 256 时一切正常（这也是为什么老测试全绿 ——
它们的数据量都太小）。实测：

| 事务数 | 修复前：关闭前 → 重启后 | 修复后 |
|---|---|---|
| 15 | 5 → 5 ✓ | 5 → 5 ✓ |
| 150 | 50 → 50 ✓ | 50 → 50 ✓ |
| 300 | 100 → **145** ✗ | 100 → 100 ✓ |
| 450 | 150 → **255** ✗ | 150 → 150 ✓ |

**修复**：把固定数组换成**按需增长的开放寻址哈希表**
（`recovery.c` 的 `rec_put` / `rec_grow` / `rec_hash`）：
事务多少都不会丢状态，查找也从 O(n) 变成 O(1)。

**RED 证据**（把三个文件回退到修复前、重编、重跑）：

| 测试 | 修复前 | 修复后 |
|---|---|---|
| `test_recovery_xids`（600 事务） | **3 项失败**：重启后 255 行（应为 200）、id=297 的值读不到、已删的 id=0 还能读到 | 1 项全过 |
| `test_vacuum_compact` | **2 项失败**：重启后行数不对、整理后插的那行读不到 | 3 项全过 |

**遗留**：clog 本身是个 4096 槽的**环形窗口**（`txn.h`），
xid 跨度超过 4096 之后老事务的提交状态会被覆盖。
那是 **v1.2 步骤 6**（checkpoint + clog 落盘）要解决的事，不在步骤 5 范围内。
（本步骤的集成测试因此把事务数控制在 4096 以内。）

#### 十、如实记录（不注水）

- **WAL 增长**：每整理一个页写 8KB 日志。20 多页的表一次 VACUUM 就是几百 KB。
  这是"WAL 增长换空间回收"的自觉取舍，步骤 6 的日志截断来兜底。
- **只整理堆表**：blob / graph / vector 的页**不参与**页内 compact ——
  它们不是 slotted page（blob 是定长帧链，graph 是定长槽页，vector 是列式），
  物理布局不一样，整理逻辑不通用。
- **compact 是页级操作，在 frame 域内完成**：不跨页 ⇒ 不引入新的锁序风险
  （"frame → wal"是合法方向）。
- **`frag_pct` 是"整理前"的碎片率**：它是**这次 VACUUM 的工作量指标**，
  不是"当前表的碎片率"。想知道当前表的碎片率，要再 VACUUM 一次
  （第二次会报 0，因为第一次已经整理干净了）。
- **`heap_compact_table` 逐页独立**：一页整理失败不影响别的页 ——
  维护操作不该因为"某一页有点怪"就整体失败。
- **步骤 5 没有碰并发路径**：compact 在 VACUUM 里跑，
  而 VACUUM 是单连接维护操作；页内整理没有新的锁，
  靠的是 pager 已有的 frame 域锁。
- **恢复阶段 xid 表换成了哈希表**：这是**行为变更**（以前超 256 就丢），
  但只是把"静默丢状态"改成"不丢"，没有新的失败模式。
  哈希表在极端 xid 稀疏时会有一次 rehash 的开销（摊销 O(1)）。

#### 一、checkpoint 的 8 步顺序（顺序本身就是设计）

```
1. wal_fsync                       日志先落盘（WAL 规则：页刷盘前日志必须已落盘）
2. L = wal_last_lsn()              记下日志末尾 —— 必须在刷页**之前**读
3. pager_flush_all()               刷所有脏页
4. d = pager_min_dirty_lsn()       脏页里的最小 recLSN
   ckpt_lsn = d ? d-1 : L          重放点
5. catalog_set_checkpoint_lsn()    重放点写进 meta 页（整页镜像进日志）
6. wal_fsync + pager_flush_all     meta 页的日志先落盘，页再落盘
7. txn_clog_sync()                 提交状态落盘 ← 必须在截日志之前
8. wal_truncate(ckpt_lsn)          截日志（前提：日志里的事务都结束了）
```

**第 2 步为什么必须在第 3 步之前**：
"日志末尾"和"页在盘上"这两件事之间可能又冒出新记录。
先读 L 再刷页，重放点才足以覆盖"所有已落盘的效果"。

**第 7 步为什么必须在第 8 步之前**：
提交状态只记在 clog 文件里，**不在日志里**。日志一截，
"哪些事务提交过"就只剩 clog 文件了。顺序反了 = 静默丢数据
（重启后所有历史事务都被当成"进行中" → 已提交的数据全部不可见）。

#### 二、ARIES 式的 recLSN

`PageFrame.rec_lsn` = "这一页自上次刷盘以来的**第一次**改动的 LSN"。

- 写入时（`pager_unpin`）：页本来是干净的 → `rec_lsn = page_lsn(页)`；
  页已经是脏的且 `rec_lsn != 0` → 保持不动（第一次改动的 LSN 不能被后面的改动顶掉）。
- 刷盘后（`pager_flush_all`）：`rec_lsn = 0` —— 下一轮改动重新记。
- 帧被复用（淘汰后装入别的页）：`rec_lsn = 0` —— 不能继承上一任主人的值。

`pager_min_dirty_lsn()` 取所有脏页里最小的 `rec_lsn`：
- `rec_lsn == 0` 的页被**跳过** —— 那是"故意不写日志"的页（向量索引），
  日志里没有它们的记录，它们不约束重放点。
- 反过来，如果某个**本该写日志**的页 `rec_lsn` 也是 0，
  说明写它的时候漏了 `page_set_lsn` —— 那是 bug，
  后果是"那一页的重做信息丢了"，checkpoint 救不回来（所以不在这里停下整个 checkpoint）。

#### 三、⚠️ 勘误一：阈值走环境变量，不是 config.h

计划写"`wal_bytes_since_ckpt > 16MB`，进 config.h"。
`db_open` 只有 path 一个参数 —— 根本没有配置文件机制。
改成环境变量 `DB_CKPT_BYTES`（默认 16MB，钳在 4KB..1GB）。
这是唯一不破坏现有 API 的办法。

#### 四、⚠️ 勘误二：checkpoint **不取全序锁**

计划写"① 拿全序锁（catalog→txn→wal）"。实际**一把锁都不取**。

理由：checkpoint 要做的事（刷页、写 meta、落 clog、截日志）本身
不需要一个跨域的临界区。真正要防的是"刷页的同时有人在改页"，
那个由 **frame 域锁**逐帧解决 —— `pager_flush_all` 逐帧取内容锁、
**不持池级锁**（持池级锁去等别人的内容锁 = 死锁）。

取全序锁反而会把 checkpoint 变成一次全局停顿，
而计划里"代价（如实记录）"担心的正是这个。

**并发下的保守性**：如果有人在 checkpoint 刷页的同时改了页，
那一页会重新变脏并带上新的 `rec_lsn` → `pager_min_dirty_lsn()`
会把它算进去 → 重放点被压低 → **多重放，不漏重放**。
方向是安全的（宁可多放，不丢数据）。

#### 五、⚠️ 勘误三：回滚**不**按 `checkpoint_lsn` 过滤

计划只说"恢复从 `checkpoint_lsn` 开始重放"。但如果**回滚**也按它过滤，
就会丢数据：

> 事务 T 在 checkpoint 时还开着。它的日志记录一部分在 checkpoint 点**之前**、
> 一部分在**之后**。回滚要的是**前像**（before image）——
> 哪怕 `lsn <= checkpoint_lsn`，那条记录也必须留着、必须回滚。

所以：**重放按 `checkpoint_lsn` 过滤，回滚遍历全部记录**。
这一条是本步最容易写错的地方 —— 写错了就是"物理删掉的行永久消失"。

#### 六、⚠️ 设计补充：新的记录类型 `WAL_ABORT_DONE`

**问题**：崩溃时开着的事务，在日志里只有 BEGIN + 数据记录，没有 COMMIT。
恢复把它回滚了 —— 但**日志里看不出它已经回滚完了**。

**后果**：截断的前提是"日志里的事务都结束了"，而这个事务永远显示"没结束"
→ **日志永远截不掉** → 步骤 6 想要的性质（恢复时间与历史长度无关）直接落空。
而且这个状态是**永久性**的：一次崩溃之后，这个库就再也不能截日志了。

**解法**：新增 `WAL_ABORT_DONE` 记录类型，恢复阶段回滚完一个事务就补一条。

**为什么不用 `WAL_ABORT`**：两者语义不同，不能混：

| 记录 | 什么时候写 | 回滚做了吗 | 前像还能扔吗 |
|---|---|---|---|
| `WAL_ABORT` | 运行时事务失败 | **没做**（本内核的删除是物理删除，运行时不做 undo） | **不能** |
| `WAL_ABORT_DONE` | 恢复阶段回滚完 | 做了 | 能 |

把两者混为一谈 = 把"没回滚的"当成"回滚完了" → 数据错。

**配套**：截断的前提判据从"全是 COMMITTED"改成
"全是 COMMITTED **或** ABORT_DONE"。

#### 七、⚠️ 设计补充：clog 落盘是截断的**硬前提**

clog 是 v0.7 的 4096 槽环形窗口，**只在内存里**。
步骤 5 的执行记录里就写了："xid 跨度超过 4096 时老状态会被覆盖，
那是 v1.2 步骤 6（日志截断 + clog 落盘）要解决的事"。

步骤 6 把它一起解决了：

1. **分块**：按 xid 高位切块，一块 65536 个 xid，块指针表 1024 项
   （覆盖约 6700 万 xid）。老 xid 的状态**不再被覆盖**。
   块是按需分配的（`calloc` 出来的默认值正好是"进行中"）。
   读路径**无锁**（原子读块指针）—— 可见性判断是最热的读路径，不能加锁。
2. **落盘**：`<db>-clog` 文件，第 xid 个字节就是它的状态。
   开库时整个读进内存的块里。

**为什么必须整个读进来**：恢复阶段要判断"这个 xid 提交了没有"。
日志被截断之后，提交记录已经不在日志里了 —— 唯一的依据就是 clog 文件。
只记个文件偏移是不够的（查询是随机的）。

**陈旧 clog 的处置**（和陈旧日志一个思路）：
数据文件不存在（全新库）→ 同名 clog 一定是上一个同名库的孤儿 → 删掉。
反过来（数据文件存在但 clog 不存在）→ 那是"老版本建的库"，从日志重建就行。

**xid 必须跨会话接续**：日志被截断之后，日志里的最大 xid 会变小，
真正"用过的最大 xid"记在 clog 文件里。开库时两边取大
（`txn_table_bump_xid`）—— 否则新会话会**重用**旧 xid
→ 旧事务的提交状态被覆盖 → 可见性判断错乱（静默的数据错误）。

#### 八、日志截断的实现

`wal_truncate(keep_lsn)`：LSN 在文件里是递增的，所以"要保留的记录"
就是文件的一个**后缀**。把后缀整体前移到文件头，再把文件截短。

- 前移用固定 64KB 缓冲流式做 —— 不把整个日志读进内存。
- **一条都留不住时保留最后一条** —— LSN 不能倒退。
  日志被截空之后重开库，`last_lsn` 会算成 0，新记录的 LSN 从 1 重新开始，
  而 `checkpoint_lsn` 可能是 5000 → 新记录全部落在 `checkpoint_lsn` 之下
  → 恢复时被跳过 → **数据丢**。
- 截断后重算 `last_lsn / nrecords / max_xid / flushed_lsn`，
  **只统计保留部分**（否则 `nrecords` 会带着已经扔掉的记录，重开库时 xid 从虚高的值往下走）。

#### 九、关库 / 断电的顺序

**关库**（`instance_close`）：
```
checkpoint（刷页 + 写重放点 + 落 clog + 截日志）
  → db_vec_close（向量索引落盘）
  → pager_close（刷剩余脏页）
  → 写 WAL_CHECKPOINT 标记（**只有日志里的事务都结束了才写**）
  → wal_close
  → txn_clog_close（关之前再 sync 一次）
```

**断电**（`db_abandon`）：不刷脏页、**clog 不落盘**、直接关。
同步落盘会让"断电模拟"变得太温柔，把本该暴露的问题藏起来。

**WAL_CHECKPOINT 标记**：含义是"上次是干净关闭，不用重放"。
如果还有没提交的事务却写了标记，恢复阶段会跳过重放**和回滚**
→ 那个事务物理删掉的行就永久消失了。所以只在安全时写。

#### 十、A6 的实测（三组对照）

`test/integration/test_ckpt_recovery_time.c`，规模 20000 行 + 100 行：

| 用例 | 恢复耗时 | 日志大小（断电时 / checkpoint 后） |
|---|---|---|
| A 不 checkpoint | **824 ms** | 1 247 467 字节 |
| B checkpoint 后断电 | **16 ms** | 8 224 字节 |
| C checkpoint 后再写 100 行 | **16 ms** | 8 224 字节 |

**C 这一行才是 A6 的正题**：checkpoint 之后又写了 100 行，
恢复时间**一点没变**（16 ms）—— 恢复时间只取决于 checkpoint 之后的日志量，
与这个库一共写了多少无关。

这正是要测的东西；100MB 对**趋势**没有额外信息，只是把测试时间拉长一个量级。
绝对耗时（824 ms）**不可**与 100MB 的预期对比。

**计时口径**：`clock()`（进程 CPU 时间）。恢复是 CPU 密集的（逐条重放），
CPU 时间比墙钟时间稳，不受机器负载干扰。

#### 十二、如实记录（不注水）

- **A6 的规模偏离**（20000 行 vs 计划的 100MB）—— 见 §十。
- **阈值触发的自动 checkpoint 没有专门的测试**：
  阈值走环境变量，集成测试里改环境变量会污染同进程的其他用例。
  自动路径与手动路径走的是**同一个** `db_checkpoint_internal()`，
  差别只有"谁触发的"。手动路径有测试覆盖。
- **clog 文件是每个库多一个文件**（`<db>-clog`）。
  开库时整个读进内存 —— 一个跑了 6700 万 xid 的库，
  clog 文件会占 64MB 内存（按需分配的块，只有用到的块才占）。
- **运行时中止的事务不做物理回滚**（本内核的删除是物理删除）。
  这类事务的日志记录**不能被截断** —— 它的前像还得留着，
  万一再崩一次还要回滚。所以截断的前提判据把 `WAL_ABORT`（未回滚）
  和 `WAL_ABORT_DONE`（已回滚）分开。代价：发生过运行时中止的库，
  日志会一直涨。这是**继承下来的老问题**（v0.7 的设计），
  不在步骤 6 的范围内，如实记录。
- **checkpoint 不取全序锁**（见 §四）—— 与计划不同，
  理由是取锁反而会造成计划里担心的全局停顿。
  并发下的保守性靠 `rec_lsn` 保证（宁可多放，不漏重放）。
- **步骤 6 没有碰并发路径**：新代码（分块 clog、截断、recLSN）
  都在已有的域锁保护之下，没有新增锁。
  `txn_clog_sync` 取的是 txn 域锁；`wal_truncate` 取的是 wal 域锁；
  `pager_min_dirty_lsn` 逐帧取内容锁、不持池级锁。

#### ② A3 吞吐基准：❌ 未达标

**⚠️ 先勘误计划的前提**：A3 那一行写的是「基线 v1.1 已存档」——
**这个前提是错的**。v1.1 存档的是**执行器火山副本**（PLAN-v1.1 §3），
仓库里从来**没有**存过大锁版本的二进制。

所以基线是**当场重建**的：同一份源码 + 一个编译期开关
`-DDB_BIGLOCK_BASELINE=1`（`src/db_stmt.c` 里把步骤 4d 退役的那把全局 latch 原样放回去），
两个二进制**逐字同源**，只差这一个宏 —— 这样对照才公平。

**实测结果（同一台机器、同一个负载，逐个删库重跑）：**

| 每表行数 | 轮数 | 线程 | 细粒度（条语句/秒） | 大锁基线 | **比值** |
|---|---|---|---|---|---|
| 500 | 500 | 4 | 21902.6 | 22155.6 | **0.99×** |
| 2000 | 200 | 4 | 13714.3 | 15485.8 | **0.89×** |
| 20000 | 20 | 4 | 2200.6 | 2677.0 | **0.82×** |
| 2000 | 200 | 1 | 17902.9 | 17691.0 | **1.01×** |

**比值区间 0.78× – 1.01×，判据是 ≥ 2×，差了一个数量级。A3 不达标。**

两个额外事实，一并如实记下：

- **单线程下两者完全打平（1.01×）** —— 说明细粒度 latch **没有引入额外开销**，
  也没有带来任何收益。
- **两个版本都不随线程数扩展。** 读阶段耗时（各线程累加）：
  1 线程 45 ms → 2 线程 178 ms → 3 线程 566 ms → 4 线程 1455 ms，
  **4 线程下放大约 8×**。大锁基线也放大（110 → 2475 ms）。
  细粒度版本在**墙钟时间**上比大锁还慢约 28%。

**负载设计（避免自造瓶颈）：** 4 线程 × N 轮 ×（8 SELECT + 2 INSERT）= 8:2 混合；
**每个线程一张自己的表**（`lb_t0..lb_t3`），线程之间不抢同一批页；
读是全表扫（`SELECT id FROM lb_tK WHERE grp = g`，1% 选择性）；
每 10 轮提交一次（摊薄 fsync）；1 轮预热不计时。

**瓶颈定位（证据链，不是猜测）：**

| # | 手段 | 结果 | 排除了什么 |
|---|---|---|---|
| 1 | gdb `thread apply all bt`（4 线程运行中采样） | **4 个工作线程里 3 个堵在 `pool_lock`（`src/storage/pager.c:120`）**，调用点分别是 `pager_unpin`（pager.c:642）和 `fetch_frame`（pager.c:389） | —— |
| 2 | 运行时读缓冲池状态 | `nframes=4096, hand=105, hash_cap=8192, hash_tombs=0, npages=105` | **没有逐出 churn**（hand 是缺页计数器，只涨了 105 次）→ 逐出不是原因 |
| 3 | `DB_BP_FRAMES=200000` 巨池重跑 | 曲线**不变** | 池容量/逐出不是原因 |
| 4 | `malloc_probe`（4 线程 × 16000 × 12 次 malloc/free） | 总共 **4.6 ms** | **分配器没有争用** |
| 5 | `mutex_probe2`（临界区里放真实计算） | 1 线程 0.026 µs / 4 线程 0.253 µs（20 次加法）；200 次加法时 1 线程 0.179 µs / 4 线程 1.739 µs | 互斥量**交接**成本是亚微秒级，放大是真的，但绝对值不足以解释 8× |

**结论（这是 A3 真正的产出）：**

> 细粒度 latch 把「语句级大锁」拆掉了，但**下面还压着一把全局锁**——
> 缓冲池的池级互斥量 `pg->mu`（`src/storage/pager.c:120`）。
> 语句级大锁挡住的是「所有语句互斥」，池级锁挡住的是「所有页访问互斥」；
> 后者粒度更细，但**仍然是全局串行点**。所以「拆锁」没有换来吞吐。
>
> 更要命的是：**两个版本都不扩展**。大锁基线的放大是**排队**（等锁），
> 细粒度版本的放大是**争用**（同一把池级锁上排队 + 排队效应）。
> 换句话说，v1.2 把「一把大锁」换成了「一把更隐蔽的小锁」，
> **并发特性上等于没动**。

**下一步（未做，留给 v1.3）**：把池级锁做成分段/分桶锁（按页号 hash 到 N 把锁），
或改成「锁外读页内数据」的乐观并发（读路径拿快照引用，不持池锁）。
这一步是**结构性**改动，不该混在「拆文件」这一步里做。

#### ④ 两条附带发现：M8-1 / M8-2

**M8-1：被拒绝的获取不记账 → 匹配释放会报「释放未持有的域」。**

`latch_order_acquire` 判定逆序并 abort 时，**不会**给这个域记账；
于是匹配的 `latch_order_release` 会因为「这个域没被持有」而报错。
反向验证第 3 项为了让流程继续，只补了**记账**，没有动真实锁的归属 ——
所以现在能同时看到两件事：真实 txn 锁被取到了（逆序被执行），
而记账层面却认为「txn 域没被持有」。

**M8-2（重要）：全序断言是「事后检查」，挡不住 AB-BA 死锁。**

`latch_order_acquire` 跑在**真实的 `pthread_mutex_lock` / rwlock 获取之后**。
这意味着：

- 它能抓住「**已经完成**的逆序」—— 断言触发、事务 abort，这是 A7 第 1/2 项验证的；
- 它**不能预防** AB-BA 死锁 —— 两个线程会先各自拿到自己那把**真实**锁，
  然后才在断言里发现顺序不对，但此时真实锁已经握在手里，**死锁已经形成**。

第 4 项验证的正是这一点：断言全关时真的死锁了；断言开时它会在**其中一侧**
abort 掉 —— 但那是「事后发现 + 牺牲一个线程」，**不是「避免」**。

> ⚠️ 因此 DESIGN.md 里「断言 = 唯一防线」这句话必须限定：
> 断言是**发现**逆序的探测器，不是**预防**死锁的护栏。
> 真正的防线仍然是「全序获取」这条纪律本身（先取低序号，再取高序号），
> 断言只是把违反纪律的代码**当场抓出来**。
