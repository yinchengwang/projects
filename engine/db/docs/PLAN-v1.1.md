## 一、方案

### 1.0 这一版要证明什么

DESIGN.md §7 路线图的原话：

> **v1.1** | 向量化执行 + 规则 CBO | 扫描+过滤比火山模型快 ≥ 3 倍

前 10 个版本在验证"**对**"——存储、事务、恢复、模态。
这一版开始验证"**快**"，但有一条铁律不变：

> **先有正确的基准，再谈快**。所有性能数字必须和改造前的同一工作负载对照，
> 对照结果全部保留（不能只报新数字）。

这一版要证明的两件事：

1. **向量化是真的**：同一查询，批式执行 ≥ 3 倍于逐行火山模型（有基准为证），
   且**结果集逐行全等**（快不能以错为代价）。
2. **CBO 是真的**：代价模型能选出正确的扫描方式（索引 vs 全扫），
   且选错的场景能被**规则+统计**解释（不是碰运气）。

### 1.1 范围

**做：**

1. 执行器批式化：火山 `next()` 逐行 → 批（`VEC_BATCH = 1024`）。
2. 表达式向量化：SELECT 投影与 WHERE 求值改为**列式批求值**。
3. **聚合 + GROUP BY**（消化 v0.4 / v0.3.5 的顺延项）—— 向量化对聚合收益最大，
   且 hash 聚合天然是批算子，一并做掉。
4. 规则 CBO：基于 `nrows_est`（catalog 已有）的代价公式 + 规则表。
5. 基准框架 `bench/exec_bench.c`：前后对照。

**不做（明确划掉）：**

| 项 | 为什么 |
|---|---|
| JOIN | §10.1 的决定维持：连接顺序是 CBO 的活，但**没有 JOIN 就不需要连接顺序** —— JOIN 放到有真实多表需求时再议 |
| 动态统计 / ANALYZE 直方图 | 规则 CBO 只用 `nrows_est`；直方图是 CBO 的第二阶段 |
| SIMD intrinsics 手写内核 | 编译器 -O2 自动向量化先行；不够了再手写（和 v1.0 R4 同一原则） |
| 并行执行 | 全局 latch 是语句级大锁，多线程执行同一语句会自己锁死自己 —— 并行执行要等细粒度 latch |
| JIT / LLVM | 对理解"为什么列式快"没有增量价值 |

### 1.2 向量化执行：改哪里、不改哪里

当前执行器（v0.9 重写后）的结构是火山模型：

```
每行：scan_next() → 求值 WHERE → 求值 SELECT → 塞进结果集
```

改造为批式：

```
每批：scan_next_batch(1024) → 列式求值 WHERE（选择向量）→ 投影 → 批进结果集
```

| 项 | 决定 | 理由 |
|---|---|---|
| 批大小 | 1024 | 经验值；Neumann 的论文与 DuckDB/ClickHouse 同量级 |
| 改造范围 | **只改 scan → filter → project → aggregate 这条热路径**；写路径（INSERT/UPDATE/DELETE）不动 | 写路径是低频操作，向量化收益趋零，改动只添风险 |
| StorageAM 接口 | **不改**。批 = 循环调 `scan_next` 攒够 1024 行（**攒批在执行器内部**） | SPI 的逐行接口是模态契约，为向量化改 SPI 会把三个已验收的模态全部重新打开 —— 违背"接口是照着调用方需要写的"的反面教训。攒批的开销（memcpy）实测后如果占大头，v1.2 再议 SPI 加批接口 |
| 值表示 | 批内**列式**：`DbValueBatch { DbValue vals[1024]; bool null[1024]; int n; }`（SoA） | 列式求值的前提；SoA 让 WHERE 循环对分支预测和缓存都友好 |
| 求值 | 表达式树编译成**批求值器**：每个算子（=, <, AND, +…）一次处理一列 1024 个值 | 这是"向量化"的本体 |
| 外部值 | 批内保持惰性（外部值不物化，除非输出路径命中） | v0.9 的机制不能破坏 —— IO 回归测试（页读计数）继续跑 |

**结果集逐行全等**是本版的正确性主线：
同一批 SQL 在新旧执行器上各跑一遍，结果集**逐字节相同**（含行序——
行序由 scan 的物理顺序决定，攒批不改变顺序）。

### 1.3 聚合 + GROUP BY（顺延项的消化）

| 项 | 设计 | 理由 |
|---|---|---|
| 无 GROUP BY 聚合（COUNT/SUM/AVG/MIN/MAX） | 单累加器数组，批内循环累加 | v0.4 顺延项；批式下天然向量化 |
| GROUP BY（hash 分组） | 批内：算 key → hash 表查/建组 → 组内累加器累加；**组数超限不 spill**（内存 hash，组数上限写进错误信息） | v0.3.5 顺延项；spill 是另一个数量级的工程，本版不做并明确报错 |
| 聚合下推 | 不做 | blob/图模态 `AM_CAP_SCAN` 不含聚合；聚合是执行器的算子，不是 AM 的能力 |

**正确性对照**：聚合结果对照**手工计算**（测试内嵌期望值）+ 对照 SQLite
（v0.4 的对照方法复用——同一批 SQL 两边跑，结果全等）。

### 1.4 规则 CBO：代价公式与规则表

v0.9 把索引选择**下沉到了 AM**（`can_push` / `push`）——
那当时是正确的（blob 必须能拒绝）。但 CBO 的意思是：**不只是"能不能"，
还有"值不值"**。

现状的问题：有索引就走索引，哪怕表只有 10 行（全扫更快）。

| 决定 | 内容 |
|---|---|
| 统计来源 | **只用 `nrows_est`**（catalog 已有，analyze/vacuum 更新）—— §10.3 的既定约定 |
| 索引扫描代价 | `cost_idx = 树高(实测缓存) + sel × nrows_est × 回表代价(1.2)` |
| 全表扫描代价 | `cost_seq = nrows_est × 1.0` |
| 选择率 sel | 等值 `1/max(nrows_est,1)`；范围 `1/3`（无直方图的教科书默认值）；多个 AND 谓词取最小 sel |
| 决策规则 | `cost_idx < cost_seq` 才走索引；`nrows_est < 64` 恒全扫（小表索引必亏）；下推能力（`can_push`）是**门槛**，代价是**排序** —— 两层都要过 |
| 汇报 | `EXPLAIN`（新增）：打印选中的路径与两个代价 —— CBO 不做黑盒，每个决定可解释 |

**为什么是"规则 CBO"而不是"真 CBO"**：一个 `nrows_est` 撑不起真正的代价模型
（没有列统计、没有相关性、没有页数）。
本版的目标是**把"代价"这个概念引进决策**，公式是可替换的骨架 ——
将来加统计信息时，只换公式，不动决策框架。

## 三、执行记录

### 步骤 1 · 基准先行（改造前的数字）

**产出**

| 文件 | 作用 |
|---|---|
| `bench/exec_bench.c` | 基准 + 相位分解 + 对拍框架 + 索引一致性门禁 |
| `bench/exec_volcano.c` | v1.1 开工前 `exec_select` 的**冻结副本**（只链进 bench，不进主二进制） |
| `Makefile` | 新增 `EXEC_BENCH_EXE`（`make bench` 一并构建；`LIB_OBJS` 不含 bench 对象，旧路径天然不进 db.exe） |

**为什么对拍必须在同一个进程里**

项目没有 git（`fatal: not a git repository`），所以 PLAN 里的"留底一个 tag"
只能用源码副本实现。对拍如果拆成两个二进制各跑一遍再比输出文件，
中间隔着两次进程启动、两次 WAL 恢复、两次页缓存冷启动 ——
任何一处不确定都会变成假阳性。同进程比对只有"两条路径结果是否相同"这一个变量。

**计时口径**

不走 `db_exec`：它一圈下来含 `wal_fsync`（毫秒级），而执行器开销是毫秒以下的量级 ——
用 `db_exec` 量等于在针尖上垫机床。基准直接调内核入口 `exec_stmt(Db*, Stmt*, ...)`，
事务在装载阶段一次性做完，解析在计时之外，计时区间里只剩执行器本身。
before/after 用同一个口径，对比才公平。

**改造前的数字（before）**

口径：10 万行（`bench_t`：`id/grp/val/name` 四列），`val` 取值 0..999 均匀分布，
查询 `SELECT id, grp FROM bench_t WHERE val >= 900`（命中 10%），
**无索引全扫**。每项取 5 次里的最好成绩，连跑 3 遍取稳定区间。

| 阶段 | 耗时 | 占比 |
|---|---|---|
| [1] scan（`scan_next`：pager_get + memcpy 记录） | 3.3 ~ 3.4 ms | 24% |
| [2] + visible + decode（`val_from_record`） | 10.1 ~ 10.6 ms（净增 6.8 ~ 7.2） | 49% |
| [3] + WHERE 求值（`eval_expr`） | 12.7 ~ 13.1 ms（净增 2.2 ~ 2.7） | 16% |
| [4] 完整查询（含结果物化 `b_push`） | **14.0 ~ 14.4 ms** | 100% |

**A2 的达标线**：批式 ≤ 4.8 ms（14.3 ÷ 3）。

**R2 的分解结论：热点是 decode（49%），不是 memcpy**

R2 说"攒批 memcpy 占大头就记录数据、别中途改 SPI"。实测**不是 memcpy**：
`scan_next` 的 memcpy 只占 24%，`val_from_record` 独占 49%。

原因在 `DbValue` 有 **272 字节**（`VAL_TEXT_MAX=256` + 若干字段），
而 `val_int` / `val_text` 是**整结构 memset**，`val_copy` 是整结构 memcpy：

- 每行 4 列 × 272 字节 memset = 1088 字节/行 → 10 万行 = **约 108 MB 的内存清零**
- 过滤时每行再 `val_copy` 一列 = 272 字节/行 → **约 27 MB 的拷贝**

合计约 135 MB 的内存流量，和实测的 7 ms + 2.5 ms 对得上。

**=> 步骤 2 的靶子很明确：不是"少调 scan_next"，而是"别再逐值 memset/memcpy 整个 DbValue"。**
列式批求值天然解决这件事：批里存紧凑的列数组（i64 / f64 / 变长文本指针），
只有真正要投影出去的值才物化成 `DbValue`。

### 步骤 1 顺带撞出并修掉的既有缺陷：索引在重复列值上丢行

**这是既有 bug，不是 v1.1 引入的** —— 但 v1.1 的基准第一次跑就撞上了，
而且 A2/A5 都建立在索引扫描之上，不修就不能往下走。

**症状**

10 万行、`val` 取值 0..999（每个值 100 行），建索引后：

| 查询 | 全扫 | 走索引（修前） | 走索引（修后） |
|---|---|---|---|
| `val = 900` | 100 | **99** | 100 |
| `val >= 900` | 10000 | **9999** | 10000 |
| `val >= 899` | 10100 | 10100 | 10100 |

**静默少行，不报任何错。** 索引路径比全扫少结果，而少的那一行去哪了没人知道。

**根因（三层）**

1. `index_key_encode` 只编码**列值**，不含 RID —— 同一列值的所有行共用一个 key。
2. 叶子分裂时提升的 separator = `key[mid]`，左页保留 `key[0..mid-1]`。
   内部节点的不变式是「左子树所有 key **严格小于** separator」，
   而值重复时左页里可能有 `key[mid-1] == key[mid]` —— **不变式破了**。
3. 查找时 `descend` 用 `upper_bound`（第一个 sep > key），
   `K == sep` 会走到**右**子树，左页里那些同值行**再也够不着**。

另外还挖出第二层缺陷：`btree_scan` 在「下界落在两棵子树的缝隙里」时
直接 `c->done = true` 放弃扫描 —— 应当是往后翻叶子。
（复合键的下界是「值 + 最小 RID」，比树里的分隔符「值 + 实际最小 RID」小，
descend 必然落到左子树，答案在右子树。）

**为什么前面的验收没抓到**

`test/unit/test_index.c` 只有 5 行、值全唯一 —— 一个叶子能放约 170 条，
5 行永远不会分裂，不变式破不了。**bug 在分裂路径上，不在查找路径上。**

**修法**

| 改动 | 说明 |
|---|---|
| `index_key.c/.h` | key 改成**复合键「值部分 ‖ RID(8 字节大端)」**。键唯一后 separator 严格落在左右两页之间，不变式恒成立 —— **B+tree 本体一行都不用改**。TEXT 值部分加 `0x00` 转义 + `0x00 0x00` 终止符，保证值部分互不为前缀（否则复合键比较会跑进 RID 部分）。 |
| `heap_am.c` | 插入/删除/重建索引都带上 RID；下推边界改成「值部分 ‖ RID 极值」（lo=00×8，hi=FF×8），等值查询的闭区间正好覆盖该值的所有行。 |
| `btree.c` | 游标换叶子时**重新定位下界**（`reseek`），修掉"下界落在缝隙里就返回空集"。页头 `BT_FLAGS` 字节存索引 key 的**格式版本**。 |
| `btree.h` | `BT_MAX_KEY` 256 → 288（值部分最长 255+2，加 RID 8 = 265）。 |
| `exec_write.c` / `exec.h` / `db.c` | `exec_rebuild_indexes(db, force)`：崩溃恢复时全量重建；正常开库只重建**格式过期**的索引（索引是派生物，重建没有语义风险，也就不需要写版本迁移代码）。 |

**反向验证（新测试是真的门禁，不是摆设）**

`test/unit/test_index.c` 加了第 10、11 项：2000 行、每个值 100 行
（分裂点必然落在重复值组内部），建索引前后逐条比对行数。

- 旧编码下：**红 4 项**（建索引前后行数不一致 + 三个 TEXT 查询计数错）
- 新编码下：**全绿**

### 步骤 2 开工前先做的三处「存储层前提修复」

相位分解把 14 ms 的查询拆开后，发现**大头不在执行器里**：
`DbValue` 有 272 字节而每个值都是**整结构 memset**；
记录布局每行重算一遍；扫描每行两次哈希查找。
这三样都在 SPI 之下，改它们**不动 SPI、也不动执行器** ——
但不改，向量化能拿到的收益会被压到只剩执行器自己那点。

| # | 位置 | 问题 | 改法 | 效果 |
|---|---|---|---|---|
| 1 | `storage/value.c` | `val_int`/`val_text`/`val_null`/`val_copy` 都是 272 字节整结构 memset/memcpy。10 万行 × 4 列 ≈ **108 MB 内存清零** | 只清"有意义的小字段"。`s[]` 那 256 字节只在 `type == T_TEXT` 时被读，而文本值本来就要 memcpy 进去 | 过滤阶段 3.6 → 1.1 ms |
| 2 | `storage/record.c` | `rec_decode` **每行重算记录布局**（`layout_of` + 每列一次 `fixed_off_of`/`var_idx_of`，整行 O(ncols²)） | 布局提进 `RecLayout`，**算一次用一辈子**；每列位置也预先算好。AM 在 `heap_am_build` 时算一次 | 解码里的布局推导彻底消失 |
| 3 | `storage/heap.c` | 扫描每行 `pager_get` + `pager_unpin`，而这两个函数**各自都要做一次哈希查找** —— 10 万行 = 20 万次哈希查找 | 扫页时**pin 住整页**（pin 住的页不会被逐出），一页只 get 一次 | **全查询 13.9 → 9.3 ms** |

修复后的相位分解（同一口径，同一台机器）：

| 阶段 | 修复前 | 修复后 |
|---|---|---|
| [1] scan | 3.3 ~ 3.4 ms | 3.6 ms |
| [2] + visible + decode | 10.1 ~ 10.6 ms | 6.9 ~ 8.1 ms |
| [3] + WHERE 求值 | 12.7 ~ 13.1 ms | 7.8 ~ 8.8 ms |
| [4] 完整查询 | **14.0 ~ 14.4 ms** | **9.2 ~ 9.4 ms** |

> **这三处修复对新旧两条执行路径同等生效**，所以不改变 A2 的比值口径 ——
> before/after 仍然是同一份代码上的"火山执行器 vs 批式执行器"。

### R2 的结论：3× 卡在 SPI 的逐行接口上（不是 memcpy）

R2 预判的是"攒批的 memcpy 占大头"。**实测不是** ——
memcpy 只占扫描阶段的一小部分。真正的墙是另外两处 SPI 逐行操作：

| SPI 逐行操作 | 约占 | 为什么向量化救不了 |
|---|---|---|
| `scan_next`（每行一次，含记录 memcpy） | ~3.6 ms（38%） | 执行器只能一行一行攒批（PLAN §1.2 的判决），逐行开销一分不少 |
| `decode`（每行一次，把记录解成 `DbValue[]`） | ~4 ms（43%） | `DbValue` 是 SPI 的值契约（272 字节/值）；执行器拿到的就是 `DbValue[]`，**物化这步省不掉** |

**实测证据**：把**同一行**反复解码 10 万次（数据全在 L1）只要 **3.1 ms**，
真扫一遍要 **~7 ms** —— 差值是记录数据的访存，不是计算。
所以瓶颈是"每行一次"的调用次数与物化，不是某一段算得慢。

**=> 不改 SPI，A2 的 3× 不可达。** 即使把过滤和投影做到极致，
剩下的也只有 `scan_next` + `decode` 两项 ≈ 7.6 ms，比值上限约 1.2×。

**=> 按 R2 的处置：记录数据，SPI 批接口列入 v1.2**（见 §四 新增第 18 项）。
v1.2 本来就是"读接口 copy-out 重构"的版本 —— 批接口属于同一类接口层工作，
放在那里比在 v1.1 中途改 SPI 更符合"一次只动一件事"的老规矩。

**v1.2 要做的 SPI 批接口（两个，都走能力协商）**

| 能力 | 内容 | 不实现会怎样 |
|---|---|---|
| `AM_CAP_BATCH_SCAN` | 一次给一批原始行，而不是一行一次 | 扫描阶段的逐行开销省不掉 |
| `AM_CAP_BATCH_DECODE` | 一次解一批，直接进列式批，**不物化 `DbValue`** | 解码阶段的 `DbValue` 物化省不掉 |

**关键：这两个都是"可选能力"** —— `caps` 位 + 函数指针为 NULL = 不支持，
执行器自动退回逐行路径。**blob / graph / vector 三个已验收的模态一行都不用改** ✓ ——
这正是 PLAN §1.2 担心被打破的那条底线（"把三个已验收的模态全部重新打开"），
而能力协商这套机制本来就是项目自己的设计。

### 步骤 2 · 批式扫描 + 列式求值

**产出**（R4：独立成文件，没往 `exec_scan.c` 里塞）

| 文件 | 行数 | 作用 |
|---|---|---|
| `src/query/exec_batch.h` | 107 | 批的数据结构（列数组 + 三态标记 + 选择向量） |
| `src/query/exec_batch.c` | 465 | 攒批、转置、投影、主循环、**逐行退路** |
| `src/query/exec_eval.c` | 288 | 列式表达式求值（形状检查 + 比较 + 三值逻辑） |
| `src/query/exec_scan.c` | 448（-63） | `exec_select` 只剩"绑定 + 结果集外壳 + 分派" |

**设计要点**

1. **批里不存 DbValue**：一列一个紧凑数组（INT 列每行 8 字节），
   一批 1024 行 = 8 KB，全在 L1 里；而 1024 行 × 4 列的 DbValue 是 1.1 MB。
2. **只把用得上的列放进批**：`SELECT id, grp … WHERE val >= 900` 只需要 3 列，
   第四列（TEXT）连数组都不分配，每行的文本也不用拷。
3. **三态标记**：bool 装不下 NULL，所以 WHERE 的中间结果是"假/真/空"三态，
   AND/OR 查表（`AND3`/`OR3`）。
4. **形状不支持就整条退回逐行路径**（不做"批内再降级"）——
   同一份语义只有一处实现，不会分叉。逐行退路与批式共用 `eval_expr` / `val_cmp`。
5. **LIMIT 的检查位置和逐行路径一致**：先查 LIMIT 再投影。

**A1 子集验收：对拍全绿** ✓

`bench/exec_bench.c` 的 29 条对拍 SQL（单谓词 / 多谓词 / AND / OR / NOT /
IS NULL / 星号投影 / 表达式投影 / LIMIT / LIMIT 0 / 常量在左 / 空表 / 含 NULL 的表）
**逐格全等** —— 批式路径与冻结的火山执行器结果一致。

**但性能只拿到 1.13×（不是 3×），原因就是上面那条 R2 判定**：

| | 耗时 | 说明 |
|---|---|---|
| 批式路径 | 8.6 ~ 9.1 ms | 转置 + 列式求值 + 投影 |
| 火山执行器 | 9.7 ~ 10.7 ms | 同一份代码上的对照基线 |
| 比值 | **1.10 ~ 1.17×** | 远不到 3× |

**为什么列式化只换来 10%**：列式求值省的是"过滤时逐列 `val_copy`"，
而那部分**已经被步骤 1 的 `val_copy` 前提修复吃掉了**（过滤阶段 3.6 → 1.1 ms）。
剩下的 81% 在 SPI 的逐行 `scan_next` + 逐行 `decode` 上，
**列式求值碰不到它们** —— 每行仍然要物化 4 个 272 字节的 `DbValue`。

**=> 这不是"向量化没用"，是"向量化用错了地方"**：
向量化要省的是**物化**，而物化发生在 SPI 的 `decode` 里。
列式批的接口（不物化 `DbValue`，直接进列数组）才能省掉它 —— 那就是 v1.2 的 SPI 批接口。
v1.1 这次把**执行器这一侧**该做的都做完了（列批、选择向量、三值逻辑、投影批式化），
接口那一侧留给 v1.2，两边合起来才是 3×。

**步骤 2 的验收结论**：对拍全等 ✅（A1 子集）；性能 1.13× ❌（A2 达标与否按 §3 R2 判定处理，见步骤 5）。

**产出**

| 文件 | 干什么 | 行数 |
|---|---|---|

| `src/query/lexer.c` | 浮点与指数字面量、整数字面量溢出检测 | 234 |

| `test/integration/test_agg_sqlite.c` | 25 条 SQL 对照 SQLite 3.49.1 | 407 |

| `bench/exec_bench_diff.c` | 对拍驱动（从 exec_bench.c 拆出） | 326 |

**设计**

- **建在列批上**：聚合是"一行进来、累加器动一下"的算子，天生吃列式数据 ——
  批里每列都是紧凑数组，累加器扫数组就行，
  不用像逐行路径那样每行物化一个 272 字节的 DbValue 再拆开看。
- **组键 = 类型字节 ‖ 值**：类型字节让 INT 1 与 TEXT "1" 不混组；
  整数大端 + 翻转符号位、浮点符号位翻转、文本转义（0x00 → 0x00 0xFF）+ 终止符，
  保证**编码的字节序 == 值的序**（输出按键排序，所以这条是硬要求）。
- **hash 组表**：FNV-1a + 开放寻址；负载到 75% 翻倍扩容。
  扩容会**换槽位** → 所以累加器住在组里（跟着组一起搬家）。
- **组数上限 `MAX_GROUPS = 4096`，超限明确报错**（不 spill）：
  spill 是另一个数量级的工程；静默截断会给出"看起来对其实错"的结果。
- **输出按组键排序** → 结果确定（SQLite 的分组顺序是未定义的，我们给一个确定顺序）。
- **WHERE 两条走法**：列式能求值 → 批内求值；不能 → 逐行求值（进批前就滤掉）。
  两条路的语义必须一致 —— 所以列式的比较语义照着 `val_cmp` 复刻。

**语义（对齐 SQLite 3.49.1）**

| 聚合 | 语义 |
|---|---|
| `COUNT(*)` | 行数 |
| `COUNT(col)` | 非 NULL 的个数 |
| `SUM(col)` | 全 NULL → NULL；整数列 → 整数；**整数溢出 → 报错**；出现实数 → 整体转实数 |
| `AVG(col)` | 恒为浮点；全 NULL → NULL |
| `MIN/MAX(col)` | 全 NULL → NULL |
| 无 GROUP BY | 恒 1 行（表空也有：COUNT(*)=0、SUM=NULL） |
| 有 GROUP BY | 每组 1 行；表空 → 0 行 |

> **为什么整数求和溢出要报错，而不是转浮点**
> SQLite 报 "integer overflow"，PG 报 "bigint out of range" —— 两个主流实现都报错。
> 转浮点是**静默丢精度**：9223372036854775807 + 2 = 9223372036854775809，
> 转 double 是 9223372036854775808.0 —— 差 1，但结果"看起来对"。
> 本项目的铁律是"错的答案比明确的报错坏得多"，所以报错 ✓

**对拍（A1 的聚合部分）**

- 冻结的火山副本（`bench/exec_volcano.c`）是 **v1.1 开工前**的执行器 ——
  那时**根本没有聚合**，它跑不了聚合查询。
  所以聚合这一块换一种对拍方式：另写一份**逐行参照实现**（`bench/exec_agg_ref.c`），
  两份实现走**不同的扫描方式、不同的分组方式、不同的输出排序**：
  - 当前实现：列批 + hash 分组 + 按编码键的字节序排序
  - 参照实现：逐行 + 线性分组 + 按 `val_cmp` 的值序排序
  两者顺序一致 ⟺ 键编码的不变式（字节序 == 数值序）成立 ✓
  **25 条聚合 SQL 逐格全等** ✓
- 另外与 **SQLite 3.49.1** 对照：**25 条聚合 SQL 逐格全等** ✓
  （浮点按 1e-9 相对容差比 —— SQLite 的 `sum/avg` 用 Kahan-Babuska-Neumaier
  补偿求和，我们是朴素累加，累加顺序不同最后一位可能差一点点，
  那是浮点累加的正常现象，不是语义不一致。）

**验收**

|---|---|

### 步骤 3 顺带撞出并修掉的既有缺陷（5 个）

聚合这一层第一次真正"吃"到值与列的类型，**把五个既有缺陷顶了出来**。
它们都不是步骤 3 引入的，但都在"静默给出错结果"这一类 —— 按项目的铁律必须修。

| # | 缺陷 | 症状 | 根因 | 修法 |
|---|---|---|---|---|
| 1 | **数字字面量溢出** | `INSERT ... VALUES (9223372036854775807)` 存进去是 **-1** | lexer 用 `i64 v = 0; v = v*10 + d` 累加 —— 有符号溢出是 UB，-O2 下结果被优化成垃圾 | lexer 改用 u64 累加 + 溢出检测；超范围**明确报错**。范围判断放解析器（`-9223372036854775808` 的幅值 2^63 超出 i64 上限，只有解析器知道前面有没有负号） |
| 2 | **写路径不转换类型** | INT 列插 5000000000 → 存 **705032704**（截断）；REAL 列插 5 → 存 **0.0**；TEXT 列插 5 → 存 **空串** | `val_to_record` 按列的类型**重解释**值，而值的类型来自字面量 | 写路径加 `coerce_to_col()`：显式转换 + 范围检查；装不下就**报错**（绝不写错值）。转换规则对齐 SQLite 的列亲和性 |
| 3 | **混类型比较拿垃圾字段比** | `WHERE int_col = '5'` 返回**值为 0 的行** | `val_cmp` 落到"按数值比"分支比 `a->i` 和 `b->i` —— 而文本值的 `i` 字段**恒为 0** | 混类型按**类型序**（NULL < 数值 < 文本 < 二进制，对齐 SQLite）：文本永远大于数值，两者永不相等。列式求值器同步改 |
| 4 | **索引下推的类型闸门** | 同上那条 SQL，若列上有索引 → 索引边界编码读错字段 → **漏行** | 索引键按列的类型编码，常量的类型来自字面量；类型不匹配时硬编码会读到错误的字段 | `index_key.c` 加类型闸门：类型对不上就**拒绝编码** → 退回全表扫描（慢一点，但绝不漏行） |
| 5 | **REAL 建不出来 + 没有小数** | `CREATE TABLE t (v REAL)` 报"不支持的类型"；`VALUES (1.5)` 报"缺少符号" | `parse_type` 没有 REAL 分支；lexer 只认整数 | 加 REAL（REAL/DOUBLE/FLOAT）+ 小数与指数字面量。**顺带**：负数字面量改成直接产出字面量（`-5` 不再是 `EX_UN(NEG)`），列式求值的形状检查因此能认它 —— 以前 `-5` 一律退回逐行 |

> 这五个都不是步骤 3 引入的，但都是"**看起来成功、其实数据错了**"。
> 第 1、2 条会**写坏数据**（静默），第 3、4 条会**读错数据**（静默漏行），
> 第 5 条是能力缺口。前四条各加了一条单元测试当门禁。

### 步骤 4 · 规则 CBO + EXPLAIN

**前置：先让 `nrows_est` 真的有值**

动手前发现一个更基础的问题：`sys_table` 的 `nrows_est` 列
**从来没有被写过** —— `write_table_row()` 里写的是 `v[4].is_null = true`，
读回来恒为 0。代价模型拿到 0 就等于没有代价，所以这一步的真正起点是它。

| 项 | 决定 | 理由 |
|---|---|---|
| 谁维护 | **写路径增量 + VACUUM 校准** | 写路径 O(1) 改内存；落盘只在 VACUUM（它本来就要扫全表） |
| 为什么不每次写都落盘 | 每插一行多一次元数据页写 + 一次 WAL | 10 万行插入 = 10 万次元数据写 —— 给"统计"付比业务更高的代价 |
| 为什么原地重写 | `heap_write_ver`（slot / RID 不变） | `sys_table` 的扫描**不做可见性过滤**，插新版本会让同一张表被登记两次 |
| 重启后的取舍 | 回到上次 VACUUM 的值（估算，够用） | "打开时扫全表统计"会把启动变成 O(n)；显式 `ANALYZE` 列进 v1.2 |

这与 PostgreSQL 的 `pg_class.reltuples` 由 VACUUM / ANALYZE 更新是同一策略。

**代价公式（`src/query/exec_cost.c`）**

| 项 | 公式 / 取值 | 说明 |
|---|---|---|
| `cost_seq` | `nrows × 1.0` | 每行一次元组访问 |
| `cost_idx` | `树高 + sel × nrows × 1.2` | 树高次页访问 + 回表（1.2 是回表惩罚） |
| `sel` 等值 | `1 / max(nrows, 1)` | 假设均匀分布 |
| `sel` 范围 | `1/3` | 无直方图的教科书默认值（System R / 早期 PG） |
| `sel` 其余 | `1.0` | 不知道就按"全中"算，倾向全扫（保守） |
| 小表规则 | `nrows < 64` → 恒全扫 | 索引的固定开销超过顺序读 64 行；且小表常在页内，走索引反而多跳几层 |
| 决策 | `cost_idx < cost_seq` 才走索引 | |

**树高为什么是估的**：执行器**不认识 B+tree**（那是 SPI 下面的实现细节，分层纪律）。
而树高对决策影响很小 —— 索引赢不赢主要看选择率，树高只贡献几个页访问的固定开销。
所以按"每页约 170 条（4KB / 24 字节复合键）"反推：10 万行 → 高度 3，1000 万行 → 高度 4。
（"实测树高缓存"列进 v1.2。）

**两层决策（缺一不可）**

```
门槛：模态说"能不能下推"（can_push）  —— 能力，不是代价
排序：我们算"值不值"（cost_idx vs cost_seq）—— 代价，不是能力
```

- 只有门槛没有代价 → 10 行的小表也走索引（比全扫还慢）
- 只有代价没有门槛 → 对不支持的模态瞎指挥

**虚拟表不做代价决策**：`blob_frames` / `graph_nodes` / `vec_items` 没有 catalog 行，
也就没有 `nrows_est`。它们的 push 是模态自己的优化 —— 拿不到行数就退回
"can_push 就推"的老行为，执行器不替模态算账 ✓

**谓词选择：从"找到第一个就推"改成"挑最窄的"**

原来的 `try_push` 沿 AND 树递归，**碰到第一个能下推的就推**。
`WHERE a = 1 AND b > 900` 里如果 `b > 900` 排在前面，就会白读 3 万行。

现在：收集 AND 树里所有能下推的叶子，按选择率排序，**推最窄的那个**。
（OR 的两个分支不能只推一个 —— 推了会漏掉另一边的行，所以只沿 AND 往下走。）

**EXPLAIN**

`EXPLAIN SELECT ...` → 单列多行（像 PG）：

```
Index Scan on big  (列 val)
  rows_est = 200
  Index Cond: (val = 20)
  Cost: seq = 200.00   idx = 3.20   sel = 0.0050
  Decision: index scan   (cost_idx < cost_seq)
```

**关键设计：EXPLAIN 与真正的执行共用 `plan_push()`**。
如果 EXPLAIN 自己算一遍、执行再算一遍，两份代码迟早分叉 ——
那时 EXPLAIN 说"走索引"、实际走了全扫，用户就再也不信它了。

**验收 A5**（`test/unit/test_cbo.c`，6 项）

| 项 | 结果 |
|---|---|
| 大表等值 → 走索引 | ✅ `Index Scan` + `cost_idx < cost_seq` |
| 大表范围 → 走索引 | ✅ `sel = 0.3333` |
| 小表（< 64 行）→ 全扫 | ✅ `Seq Scan` + 理由写明"小表" |
| 无索引列 → 全扫，但仍显示 rows_est | ✅ |
| EXPLAIN 输出两个代价 | ✅ `Cost: seq = ... idx = ...` |
| 多个 AND 谓词挑最窄的 | ✅ `a = 5 AND b >= 5` → 推 `a`（sel 0.0033 vs 0.3333） |
| nrows_est 维护（插入/删除/VACUUM/重启） | ✅ 100 → 90 → VACUUM 校准 → 重启后仍是 120 |

### 步骤 4 的行为变化：小表不再走索引

CBO 一上线，`test_index.c` 立刻红了 9 项 —— 它靠**返回顺序**证明走了索引
（全扫按插入顺序吐行，索引扫按 key 顺序吐行），而 5 行的小表现在被 CBO 判为"全扫更快"。

这不是 bug，是**正确的新行为**。改法：

| 原来 | 现在 |
|---|---|
| 5 行小表 + 索引 → 断言 key 顺序 | 5 行小表 + 索引 → 断言**仍按插入顺序**（小表恒全扫） |
| — | 新增 200 行大表 → 断言 key 顺序（真的走索引） |
| 所有断言用 `q()`（顺序敏感） | 集合语义用 `qs()`（按行排序后比）；顺序敏感的 3 条保留 `q()` |

**教训**：`qs()` 是按**字符串**排序的，所以 `20` 排在 `2` 后面、`5` 前面 ——
期望值要按字符串序写，不能按数值序。

### 步骤 5 · 性能验收（如实记录：不达标）

| 指标 | 改造前（火山） | 现在 | 比值 | 目标 |
|---|---|---|---|---|
| 完整查询（10 万行，选择性 10%，无索引） | 10.085 ms | 9.099 ms | **1.11×** | ≥ 3× |

**A2 不达标，差 2.7 倍。** 这与步骤 2 的判定完全一致，不是新问题：

```
scan 38% / decode 42% / filter 18% / 其余 2%
```

81% 在 SPI 的逐行 `scan_next` + 逐行 `decode` 上 ——
**每行仍然要物化 4 个 272 字节的 DbValue**，列式求值和聚合都碰不到它。

聚合（步骤 3）也没有让这条基准变快，因为基准 SQL 里没有聚合 ——
聚合的收益要单独测（本版没测，因为 A2 的口径是"扫描+过滤"）。

**处置**（已在步骤 2 记录，这里再确认一次）：
SPI 批接口（批扫描 + 批解码，直接进列数组）列入 **v1.2 步骤 0** + 验收 **A9**
（重新验收本版的 A2 ≥ 3×）。两个批接口走能力协商，blob / graph / vector 三个模态零改动。

**不注水**：1.11× 就是 1.11×，不是"接近 3×"，也不是"架构已经就绪"。

### 步骤 6 · 反向验证

| 注入 | 预期 | 实际 |
|---|---|---|
| **注入 1**：列式 AND 真值表把 `(真, 空)` 改成 `假` | NULL 语义测试必须红 | **起初不红** → 见下 |
| **注入 2**：`sel` 恒为 1/3（等值也不看基数） | A5 必须红 | ✅ `test_cbo` 红 2 项（挑最窄的谓词、sel 数值） |

**注入 1 起初不红 —— 这是本步骤最有价值的发现。**

原因有两层：

1. **顶层 WHERE 里"空"和"假"都是不匹配** —— 所以 AND 真值表写错了也看不出来。
   只有 `NOT (...)` 或 `(...) IS NULL` 能把两者区分开。
2. 我补了 `NOT (id > 0 AND name = 'zzz')` 之后**仍然不红** ——
   因为 `name` 是 TEXT，列式求值不支持文本比较，整条语句退回**逐行路径**；
   而注入点在**列式路径**的 `AND3` 表里。**两条路径是三值逻辑的两份实现。**

最终补了三条测试（`test/unit/test_query.c` §4b / §4c）：

| 用例 | 覆盖的路径 | 注入后 |
|---|---|---|
| `NOT (id > 0 AND name = 'zzz')` | 逐行（TEXT 列） | 多出一行 → 红 |
| `(id > 0 AND name = 'zzz') IS NULL` | 逐行（IS NULL 左边非列） | 少一行 → 红 |
| `NOT (a > 0 AND b = 99)`（`tri` 表，b 有 NULL） | **列式**（两边都是数值列） | 多出一行 → 红 |

**教训**：反向验证的价值不是"证明测试有效"，而是**暴露测试的盲区**。
一个注入不红，说明那条路径没被覆盖 —— 这比"注入红了"信息量更大。
