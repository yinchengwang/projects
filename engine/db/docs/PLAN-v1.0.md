## 一、方案

### 1.0 这一版要证明什么

DESIGN.md §7 路线图的原话：

> **v1.0** | 模态 3：向量（HNSW） | recall@10 对照 hnswlib 差 < 2 点

前两个模态各验证了 SPI 的一半：blob 验证了"虚拟表 + 能力协商 + 外部值"，
图验证了"高频点查 + 定长写路径"。向量要验证的是**最后一块**：

> **IndexAM 的 `knn` 口子**（v0.9 留的）+ **下推的"过滤 + ANN"配合**。

DESIGN.md §5.3 早就埋了这句话：

> 向量检索的"过滤 + ANN"是同一件事的两面。前过滤让索引失效，后过滤召回不足。
> 真正管用的做法是把过滤吸收进索引 —— 而"哪些过滤能吸收"只有模态自己知道。

判据两条：

1. `SELECT ... FROM vec_items ORDER BY vec <-> q LIMIT 10`（或等价 API）
   走 HNSW 而不是全表暴力扫 —— **索引真的被用上了**（IO 计数可证）。
2. recall@10 与 hnswlib 的差距 < 2 个百分点 —— **我们的 HNSW 是对的**，
   不是"能返回结果"就行。

### 1.1 范围

**做：**

1. `src/modalities/vector/` —— 向量存储：**列式布局**（对齐 Lance/Parquet）。
2. HNSW 索引：内存构建 + 落盘 + 增量插入。
3. `spi/vector_am.{h,c}` + `index_am` 的 `knn` 实现（第一个非 `E_NOTSUP` 的 knn）。
4. 虚拟表 `vec_items` 接进 SQL（复用注册表）。
5. 过滤 + ANN 的配合策略（§1.5 的判决）。
6. recall 验收框架（暴力扫做 ground truth + hnswlib 双重对照）。

**不做（明确划掉）：**

| 项 | 为什么 |
|---|---|
| 量化（PQ / SQ / binary） | 量化是为了省内存省 IO；先做精确 fp32 把 HNSW 本身做对，量化是它的正交优化 |
| 过滤吸收进 HNSW（filtered-HNSW） | 见 §1.5 判决：本版用"ANN 给超集 + 执行器过滤"，保守安全；吸收进图是激进优化，留待有真实工作负载后再做 |
| 多向量 / 稀疏向量 | 单模态单类型，混合检索是应用层的事 |
| 增量删除（HNSW 的删除很难做对） | 标记删除 + 重建（v1.2 的 vacuum/rebuild 一起处理）；本版只支持插入 |
| IVF / 其他索引 | 只做 HNSW，做深不做多 |

### 1.2 存储布局：列式，对齐 Lance/Parquet

这是第三个模态、第三种布局 —— blob 是"对象→帧→页"，图是"定长槽页"，
向量是**列式**：

| 候选 | 判决 |
|---|---|
| (a) 向量塞进 slotted page 当一行 | **否决** —— 128 维 fp32 = 512B，一页只能放 7 个向量；且按行存，相邻向量分散在页的各处，扫描/训练/量化都要跳读 |
| (b) **列式向量页**：一页连续放 K 个 fp32 向量，`向量 i` 的位置 = `页头 + i × dim × 4B`，页间顺序衔接 | **采纳** |

```
向量页（PT_VEC_DATA）：
  页头 8B（页类型 + 向量计数）
  数据区：(4096-8) / (dim × 4) 个向量连续排列

标量页（PT_VEC_META 系列，普通定长槽页，同图模态的 gstore）：
  每行 = (row_id, label, ...) —— 向量的标量属性
  row_id = 全局序号，第 i 个向量 == 标量表第 i 行（列对齐）
```

**列对齐是列式的灵魂**：第 `i` 个向量和第 `i` 行标量属性靠**序号**对应，
不需要指针。过滤标量列命中的 row_id 集合 → 直接换算出向量位置 →
这是"过滤 + ANN"和将来"量化训练"的地基。

**RID 的映射**：`vec_items` 虚拟表的一行 = 一个向量，
RID = `(data_page_of(row_id), row_id % K)` —— 纯算术（对齐 blob 的先例）。

### 1.3 HNSW：实现要点与落盘

对齐 hnswlib 的算法（Malkov & Yashunin 2016），逐条注明参数出处：

| 要素 | 决定 | 理由 |
|---|---|---|
| 距离 | L2 与内积两种（构建时指定） | 应用最广的两种；cosine 用归一化内积实现 |
| M（每层邻居数） | 16 | hnswlib 默认 |
| ef_construction | 200 | hnswlib 默认 |
| ef_search | 由查询方传（默认 64） | 召回/延迟的旋钮，不写死 |
| 层级分配 | `level = floor(-ln(uniform) × mL)`，`mL = 1/ln(M)` | 论文原式 |
| 邻居修剪 | 启发式（保留方向多样的邻居，e0/e1/e2 判据） | 论文 Algorithm 4；hnswlib 同款 |
| 入口点 | 单一 entry point，记录最高层 | 标准做法 |

**落盘格式**（PT_VEC_INDEX 页系列）：

```
索引头页：dim / count / M / entry_point / max_level / 数据页链头
邻接页：  定长槽页（同 gstore 复用！每槽 = 一个节点的邻居数组，
          M + M×2 双数组：上层 M 个、第 0 层 2M 个）
```

**复用 gstore 的定长槽页**是本版的一个结构决定：
邻接表节点是定长的（`2 + 2M 个 u32 row_id`），
图模态在 v0.11 刚把"定长记录 + 空闲链"这套原语写对并测透 ——
向量模态直接 include 它（`modalities/` 内部允许共享吗？
**不允许** —— 硬规则 3：模态之间不许互相 include。
正确做法：把定长槽页**下沉到 `storage/`（L1）**，
图和向量都依赖它。这是本版的一个前置重构，见执行计划步骤 1。）

**增量插入**：HNSW 天然支持（逐点插入 + 贪心搜近邻 + 修剪）。
插入并发：全局 latch 已覆盖（v0.10 硬规则 8：新入口必须加锁）。

### 1.4 knn 怎么接进 SPI

v0.9 的 `index_am.h` 早就留好了口子：

```c
/* B+tree 的实现返回 E_NOTSUP，向量模态是第一个真实现 */
int (*knn)(IndexAM *am, const void *query, u32 k,
           AmKnnResult *out);   /* out: row_id 数组 + 距离数组 */
```

**调用路径**（谁在什么时候调 knn）：
SQL 侧本版提供**两种入口**：

1. **C API 主路径**：`db_vec_knn(conn, label_filter, query, k, out)` ——
   遍历类 API 同图模态（SQL 表达不了 `ORDER BY 距离 LIMIT k` 的 ANN 语义，
   排序键是计算出来的，不是列值）。
2. **虚拟表辅助路径**：`vec_items` 支持标量谓词下推（label 等值 → 只扫匹配的 row_id），
   供 SQL 做元数据查询。距离排序**不进 SQL**（写进文档：这是有意的范围收缩，
   不是遗漏 —— 排序键计算在执行器侧需要新的算子类型，违反"下推结果是行源"的同构性）。

**IO 可证**：复用 v0.9 的 `db_blob_page_reads` 模式 ——
`db_vec_page_reads()` 前后对比，ANN 的页读数必须 **≪** 暴力扫描（10 万向量 = 1250 页）。

### 1.5 过滤 + ANN：给超集，不给子集

§1.1 说了本版不做 filtered-HNSW。但"过滤 + ANN"必须有个正确答案：

| 候选 | 做法 | 判决 |
|---|---|---|
| (a) 先 ANN 取 top-k，再过滤 | 召回不足：如果 top-k 都不满足过滤条件，结果**少于 k 且不可补** —— **静默丢数据** | **否决** —— 违反"下推只能给超集"铁律 |
| (b) 先过滤标量，再对幸存者暴力扫 | 正确但 O(N)，索引白建 | **否决**（作为默认路径） |
| (c) **ANN 扩大候选池（ef_search 拉高，候选 ef ≥ 4k）再过滤** | ANN 给超集候选，过滤后可能仍少于 k → **如实报告实际数量**，文档写清这是 ANN 的固有性质 | **采纳** |

**判决 (c) 的语义必须写死在 API 文档里**：

> `db_vec_knn` 返回的是"满足过滤条件的、ANN 能找到的最相似向量"，
> **不保证恰好 k 个**（可能少于 k）。这是 ANN 的固有性质（近似），
> 不是 bug。需要精确结果请用 `db_vec_knn_exact`（暴力扫，供回归对照）。

这延续 v0.9 的纪律：**保守的优化是安全的，激进的优化是危险的**。
hnswlib 的 filtered 检索也是同样性质（它的 pre-filter 模式同样不保证 k 个）。

#### 三个必须记录的判断

**① 规格里的"页头 8B"是错的，改成 20B**

`向量模态实现规格.html` 写的是"页头 8B（页类型 + 向量计数）"。
按 8B 写会**直接压坏两个公共字段**：

```
H_LSN   = 12   ← 重放幂等判断读它
H_CKSUM = 16   ← 校验和固定写在这里
```

这两个偏移是**所有页类型共用**的（`config.h` 里写死），
不归某个页类型自己支配。页头取 8B 的话，第 0 个向量从偏移 8 开始，
它的前 10 个字节正好被 LSN 和校验和覆盖 ——
**只坏每页的第一个向量**，而且不报错。

所以页头取 20B（= `HDR_SIZE`），与 slotted page、定长槽页保持同一约定。
代价：K 从 7.98 变成 7.96，对 128 维没有影响（都是 7）。

**② 向量需要内存目录，blob 不需要**

blob 的对象是**一次写完**的，写的时候没有别的东西插进来分配页，
所以一个对象的帧页连续 → `帧号 → 页号` 是加法。

向量不是：每插 k 个向量才分配一个数据页，而**标量页会在中间插进来**
（标量表是 gstore，它自己也会分配页）。所以数据页的页号**不连续**。

于是 `序号 → 页号` 必须查表。表放在内存里（`pages[]`），
打开时顺着页链走一遍重建 —— 和 blob 重建目录、gstore 重算 alive 同一个套路：
**磁盘上只存链，索引在内存里重建**。

**③ 扫描用两个顺序游标对齐，不是逐个向量去查标量行**

反面做法：每取一个向量就 `gstore_get` 一次标量行 ——
那是**随机读**，每个向量一次页读，列式省下来的 IO 全还回去。

正确做法：标量表也是按 row_id 顺序填的，所以它的一条**顺序游标**
就能和向量页的顺序一一对上。两次顺序扫描，总 IO = 数据页数 + 标量页数。

实测（100 个 128 维向量，K=7，15 个数据页）：

```
（扫 100 个向量读了 15 页）
```

**这条断言把"列式"从设计口号变成了可测的数字**：
行式存储要读 100 次，列式 15 次。

#### 又踩了一次坑 M2-6

标量记录一开始写成 `rec_size = 12`（row_id 8 + label 4）。
`gstore_get` 返回的是**整条记录**（含 4 字节公共头），
而 `gstore_alloc_with` 只拷**载荷区**（`init + GS_REC_HDR_SIZE` 起）——
所以载荷实际只有 8 字节，label 被静默截断；读的时候从第 0 字节取 row_id，
拿到的是"公共头 + row_id 的前 4 字节"。

两个错都不报错。修法：把"载荷长度"和"gstore 记录长度"分成两个宏：

```c
#define VEC_META_PAYLOAD  12u                            /* row_id + label */
#define VEC_META_REC      (GS_REC_HDR_SIZE + VEC_META_PAYLOAD)   /* 16 */
```

v0.11 在图模态的 schema 记录上踩过同一个坑。**这说明它不是偶发失误，
而是这个原语的接口没把这个约定讲清楚** —— 已在 `vstore.h` 里写明，
并把 `VEC_META_PAYLOAD` / `VEC_META_REC` 的区分做成宏名，不靠注释提醒。

#### ★ 一个必须记录的静默错误：满了就把边丢掉

第一版加边的写法是"先追加，满了就重挑现有邻居，再追加"：

```c
rc = link_add(h, e, id, lc);          /* 满了 → E_NOSPACE */
if (rc == E_NOSPACE) {
    shrink_node(h, e, lc);            /* 重挑现有邻居 —— 还是满的，直接返回 */
    rc = link_add(h, e, id, lc);      /* 还是 E_NOSPACE → 这条边被静默丢弃 */
}
```

**后果**：每个节点的表一旦填满（第 0 层 32 个）就**再也不接受新邻居**。
图退化成"新点只指向旧点"的有向图 —— 从入口点出发只能走到入口点附近那一小片。

实测（2000 点、8 维）：

```
第0层可达 35 / 2000      ← 只有 1.75% 可达
平均度 32.0  最大度 32   ← 每个节点的表都恰好是满的（这是征兆）
recall@10 = 0.125
```

**没有任何报错**。结构不变量测试（邻居数 ≤ 上限、无孤立点、层级分布）**全部通过** ——
因为图确实"每个点都有邻居"，只是它不再是一张**能走通的**图。

定位方法：**从入口点做一次第 0 层 BFS，数可达节点**。
这一步把"图的结构"和"搜索的实现"分开 ——
可达性 35/2000 说明问题在**建图**，不用去查搜索。

修法（hnswlib 的 `getNeighborsByHeuristic2` 同款）：
把**新候选也放进池子**，和现有邻居一起重挑 mmax 个。
新的可能挤掉一个旧的，也可能自己落选 —— 由同一个启发式判据决定：

```c
/* link_merge：满了不是丢新的，而是一起重挑 */
h->scratch[i]     = 现有邻居（带距离）
h->scratch[*pc]   = 新候选（带距离）
select_heuristic(..., *pc + 1, mmax, ls, &nsel);
```

修完：**可达 2000/2000，recall@10 = 0.999**。

**这条经验值得记住**：
"结构不变量全绿"不等于"图是对的"。
HNSW 的正确性有两个层次 ——
**局部**（每个节点的表合法）和**全局**（从入口点能走到任何点）。
只测局部会漏掉这一类错。

#### 另外两个实现决定

**① 层级分配不用 libm**

论文的式子是 `level = floor(-ln(u) × mL)`，`mL = 1/ln(M)`，
等价于 `P(level >= k) = M^-k`。

所以直接用**几何分布**抽：

```c
while (lvl < MAX_LEVEL && (rng_next(h) % m) == 0) lvl++;
```

分布完全相同，但一次浮点 `log` 都不用算 ——
也就不用给整个项目加 `-lm`（Makefile 和 30 多个测试的链接参数都不用动）。
实测层级分布：2000 点里 127 个有上层，期望 125。

**② 距离用平方 L2，不开方**

排序只需要"谁更近"，平方是单调的。
一次查询要算几千次距离，省下的这次 `sqrt` 很实在。

#### 验收（7 项全绿，2.7 秒）

| 项 | 结果 |
|---|---|
| 1. 小规模 200 点 | recall@10 = **1.000** |
| 2. 结构不变量 | 邻居数不超限、无孤立点、层级分布 127/2000（期望 125）、入口点确在最高层 |
| 3. **1 万 × 16 维** | recall@10 = **0.999**（M=16 efC=200 ef=64） |
| 4. ef 单调性 | ef=16 → 0.983，ef=64 → 0.997，ef=200 → **1.000** |
| 5. **暴力扫 == 朴素实现** | 与"全排序"写法逐条一致（连基准本身都要验） |
| 6. 增量插入 | 每插 2000 查一次：1.000 / 1.000 / 1.000 / 1.000 |
| 7. 边界 | 空索引返回 0（不报错）、k > n 返回实际数量、内积模式方向正确 |

所以基准用两种完全不同的写法互相验证（一个用容量 k 的最大堆，一个用全排序）。

#### 判决：索引是 checkpoint，不是日志

关系模态的 B+tree 早就是这个策略（db.c 里那句"索引不写日志，
崩溃后可能和堆不一致 —— 重建一遍"）。对 HNSW 更强：

1. 索引**可以从数据重建**（向量在 vstore 里，图是算出来的）
2. 索引页的写放大极大 —— 插入一个点要改它自己和最多 2M 个邻居
3. 图结构的"中间态"没有意义：崩在插入中途，那个点要么在要么不在

所以：正常关闭 / 显式 flush → 整份写进磁盘；崩溃 → 打开时发现 count 对不上 → 重建。
代价是 flush 为 O(n)（10 万点约 4700 万字节，1~2 秒），换来插入路径上一条索引日志都不写。

**页类型**：`PT_VEC_INDEX`（头页）+ `PT_VEC_LINK`（邻接表，定长槽页，走 gstore）。
复用 gstore 正是因为 v1.0 步骤 1 把它下沉到了 `storage/` —— 这一步用上了。

#### ★ 又一个静默错误：谁维护 count

`vix_rid_push` 第一版的写法是"调用方自己 `ix->count++`"：

```c
/* 库函数 */
ix->rids[ix->count] = rid;      /* 用 count 当写指针 */

/* 调用方 A（flush 追加） */  push(); count++;
/* 调用方 B（重建） */        push();      ← 忘了 count++
```

后果：重建路径里 2000 次 push **全写在 rids[0] 上**，容量也永远停在 64。

表现特别阴险：**打开时一切正常**（读回走的是 gstore 游标，不碰这张表），
直到下一次 flush 拿 `rids[id]` 去原地改写时才报错 —— 而那时离出错点已经很远：

```
[dbg] put 失败 id=2 rid=(0,32) rc=4 count=2000
```

`rid=(0,32)` 是垃圾值（正常应该是 `(42,2)`）。

定位方法：在 push 处和用之前各打一行 `rids[0]` ——
重建时是 `(42,0)`，用的时候变成 `(291,7)`（正好是**最后一条**记录的 RID），
一眼就能看出"所有写入都落在第 0 项"。

修法：**把不变量关进函数里**。`vix_rid_push` 自己维护 count，
调用方只负责给值；重建路径末尾加一条 `count == i` 的断言。

教训：**"谁分配谁维护"要贯彻到底**。数组和它的长度放在一起管，
调用方每多写一行 `count++`，就多一个忘记的机会。

#### 另外两个判断

**① `HNSW_MAX_LEVEL` 从 16 改成 5**

它有两个身份：内存里的层数上限，**和磁盘格式的一部分**
（每节点记录长度 = f(最大层数)）。

期望的最大层 ≈ log_M(N)：1 万 → 3.3，10 万 → 4.15，100 万 → 4.98。
给 16 只是白占内存（每节点每层 2 字节计数 + m 个 4 字节指针）。
分成两个常量迟早会漂移，然后读出垃圾 —— 所以内存和磁盘用**同一个**值。

改完 recall 不变（0.999），层级分布仍然对（127/2000，期望 125）。

**② 记录里存节点 id**

不存也能读（第 i 条记录就是第 i 个节点），但那样**错位了也不会报错**。
存一个 id，读的时候断言 `id == i` —— 和 vstore 标量表同一个防线。
这类"错位不报错"的坑在 vstore 那边已经踩过，这里提前防。

**代价**：定长记录意味着上层也要按最大层数预留，
10 万点 × 470 字节 ≈ **47MB**（向量数据本身 51MB）。
想省可以拆成两个 gstore（第 0 层 / 上层，上层只有 ~6% 的点需要），
但那是优化不是正确性，留到需要的时候做。

#### 三个判决

**① AM 适配器住在 `modalities/vector/`，不搬进 `spi/`**

和 v0.11 的 graph_am 同一个理由：spi/（L3）不许依赖 modalities/（L4）。
向量的存储在 modalities/vector/，适配器就得跟着住那儿。
（blob_am 住 spi/ 是因为 blob 的存储在 storage/（L1），那是向下依赖。）

**② `vec` 列是外部值 —— 于是"查元数据不读向量页"**

一行 = 12 字节（`[u64 row_id][i32 label]`），**向量本体不在行里**。
它是一个外部值，句柄 = row_id，要读才去 vstore 取。

所以 `SELECT row_id, label FROM vec_items`（10 万向量）
**一个向量页都不读** —— 只读标量表。
这是列式布局在 SQL 层最直接的兑现。

**③ 过滤 + ANN：给超集，如实报告**

`db_vec_knn_filtered` 的实现：候选池扩到 ≥ 4k → 按 label 过滤 →

两个方向的错都堵住了：
- 候选池不扩 → 命中不足时**静默丢数据**（违反"下推只能给超集"铁律）
- 过滤后不截断 → 返回 20 个而用户只要 5 个（"返回了用户没要的行"）

#### ★ 两个静默错误

**① 精确扫描的输出没排序**

第一版用"容量 k 的最大堆"选 top-k，然后直接 `out[i] = heap[hn-1-i]` ——
**堆的数组不是有序的**（堆只保证堆顶最大）。

表现特别难认：返回的**集合是对的**（召回率 1.000），
但**顺序是乱的**（0.25, 0.0, 0.08, 0.69, 0.34 …）。
下游按顺序取前 k 个就会拿到错的东西。

这类错只有"和另一个实现逐条对比"才看得出来 ——
集合对了、顺序错了，普通的断言（"结果里有这几个"）验不出来。
所以测试断言的是**距离序列逐条相等**，不是"集合相同"。

修法：先做堆排序（最大堆 → 升序），再按顺序抄。
（注意方向：最大堆做堆排序的结果是**升序**，
最大的被换到了数组末尾 —— 我在这上面又错了一次。）

**② REPL 的参数解析把维度读了两遍**

`VEC CREATE 4` 得到 dim=4、**M=4**（本该是默认的 16）。
原因：取 dim 用的是 `strtol(line, NULL, 10)`（不推进游标），
然后又从 line 重新扫一遍找 M。

正确做法：每次取参数都用 strtol 的 **endp** 推进游标，游标只前进不回退。

#### 一个必须诚实说明的 IO 事实

**ANN 查询读 0 页**，暴力扫读全部向量页。

原因：HNSW 索引**把向量带在内存里**（hnswlib 的模型）——
查询时算距离用的是内存副本，一个页都不碰。

所以 A4 的对比证明的是"索引让查询完全不用碰存储"，
但代价是**每个实例常驻 51MB**（10 万 × 128 维 fp32）。
这个取舍在 PLAN §1.7 R2 里已经记着，本版把它验证了。

（如果索引只存邻接表、遍历时从存储读向量，IO 对比才更有意思 ——
但那是另一套设计，本版不做。）

**基准规模**：10 万 × 128 维，100 个查询，k=10，M=16，efC=200，ef=64。

#### 判决 ①：A2 的验收标准本身是错的，必须修订

PLAN §1.6 A2 原文写的是"10 万 × 128 维**随机向量**，recall@10 ≥ 0.95（ef=64）"。

实测 **0.390**。但关键不在我们，在对照：

> **同一批数据、同样 M/efC/ef，hnswlib 的 recall@10 = 0.338。**

hnswlib 是业界事实标准。它在均匀随机高维数据上也只有 0.338 —— 比我们还低 5.2 个点。
所以"0.95"这个目标不是我们没做到，而是**在这种数据上谁都做不到**。

根因是数据的性质，不是算法：128 维均匀随机向量近乎等距（维度灾难），
"近邻"本身没有明确结构 —— top-10 内部的距离差极小，
微小的数值扰动就能改变 top-10 的成员是谁。这种数据是图索引的**已知最坏情况**。

两边的 ef 曲线**形状一致**（hnswlib 0.140→0.823，我们 0.153→0.856），
说明算法行为相同。

**修订 A2**（分两条，因为两种数据的性质完全不同）：

| 数据形态 | 判据 | 实测 | 结论 |
|---|---|---|---|
| 聚簇（100 中心 + 扰动，接近真实 embedding） | recall@10 ≥ 0.95 | **0.993** | PASS |
| 均匀随机（高维最坏情况） | **不低于 hnswlib 参照实现** | 每档都比它高 1.3~5.2 点 | PASS |

**两种数据形态都报。** 只报一种都会失真：
只报均匀会显得 HNSW 不行（其实是数据没有结构），
只报聚簇会掩盖"高维均匀数据"这个真实难点。

#### 判决 ②：A3 没有走退化方案 —— hnswlib 真的对照上了

PLAN §1.7 R3 预置了退化方案（hnswlib 装不上时改用论文数值区间）。
本机确实装不上：

- pip 找不到该平台的 wheel；
- 从源码编译它的 **Python 绑定**要求 MSVC（本机只有 MinGW）；
- 顺带一提：pybind11 3.1.0 编译 hnswlib 0.8.0 的绑定**能过**，
  但 `add_items` 一定段错误（绑定层与 pybind11 3.x 不兼容）。

**但 hnswlib 的核心是纯头文件（header-only 的 C++ 库）** —— 只要 g++ 就能用，
不需要 Python、不需要 pybind11。所以直接写 C++ 程序调它的 API：

```
tools/hnswlib_ref.cpp
  读 bench 导出的同一批数据 → L2Space + HierarchicalNSW
  → 在**本地**暴力扫算 GT（不读我们导出的 GT）
  → 逐档算 recall → 和我们的曲线逐档比
```

对照结果（10 万 × 128 维，各自独立算 GT）：

| ef | 均匀：hnswlib | 均匀：我们 | 聚簇：hnswlib | 聚簇：我们 |
|---|---|---|---|---|
| 16 | 0.140 | **0.153** | 0.746 | **0.836** |
| 32 | 0.233 | **0.256** | 0.893 | **0.945** |
| 64 | 0.338 | **0.390** | 0.977 | **0.993** |
| 128 | 0.507 | **0.557** | 0.990 | **0.998** |
| 256 | 0.669 | **0.719** | 0.990 | **0.999** |
| 512 | 0.823 | **0.856** | 1.000 | 0.999 |

**我们在每一个 ef 档位都不低于 hnswlib。**
这不只是"没差 2 点"，而是**逐档都更好**（差距 0.1~9.0 点，取决于数据和 ef）。

差距的来源是随机种子不同 → 层级分配不同 → 图结构不同。
两边的算法行为是同一套（曲线的形状一致）。

#### 判决 ③：主测量跑在模态层（不挂 WAL），公开 API 路径单列小规模

和 graph_bench 同款做法。理由也一样：

插入一个向量要改 **2 个页**（向量数据页 + 标量槽页），
每改一个页就是一条 WAL 整页镜像 = 8KB 日志。
实测 **19.5 KB 日志 / 向量** —— 10 万 ≈ **1.95GB**。

那不是"慢一点"，是磁盘放不下；而且它与 ANN 的性能**无关** ——
在挂着 WAL 的路径上量，量到的是日志 IO，不是算法的速度。

所以：

- **主测量**（A2 / A4 / A5 / 延迟）→ 模态层，不挂 WAL
- **公开 API 端到端** → 单独一小节，5000 条，量装载吞吐 + WAL 体积 + 正确性一致性

公开 API 路径的正确性由 `test/integration/test_vec_it.c` 负责（8 项全绿），
基准不重复验正确性。

#### 判决 ④：A4 的口径要改 —— "除以 0"没有意义

实测：暴力扫一次读 **14286** 页（= 10 万向量 ÷ 每页 7 个），
ANN 查询读 **0** 页。

原因：HNSW 索引**把向量带在内存里**（hnswlib 的模型），
查询时算距离用的是内存副本，一个页都不碰。

所以"暴力扫 / ANN"这个比值是除以 0，写成"1/999999"是自欺欺人。
有意义的说法是：

- 暴力扫一次 = 14286 页；ANN 查询 = 0 页
- **代价写在别处**：索引常驻 **93.3 MB**（向量副本 48.8 + 图结构上界 44.4），
  重开库读回索引 1468 ms（5000 条时）

这个取舍在 §1.7 R2 里已经记着，本版把它量化了。

#### ★ 静默错误 ①：A5 的"recall 塌了"是**测量 bug**，不是实现 bug

第一版跑出来：插到 1/4 时 recall 0.98，插满时 0.72 —— 一路下滑，
看起来就是"增量插入把索引搞坏了"。

**结论相反**，而且推理链很硬：

1. HNSW 的插入是**纯顺序**的 —— "分块插入 4 次"和"一次性插入"
   建出来的图**逐位相同**（停下来再插不改变任何一步的算法）。
   所以 0.72 **绝不可能**是增量插入造成的。
2. 真因是**给数据和查询分别造了一组随机中心** ——
   查询落在数据分布**外**，量的是"能不能从分布外找到一个近邻"。
3. 改成数据与查询**共用同一组中心**后：

| 规模 | 1/4 | 1/2 | 3/4 | 满 |
|---|---|---|---|---|
| 5000 | 1.000 | 1.000 | 1.000 | 1.000 |
| 100000 | 1.000 | 0.990 | 0.996 | **0.993** |

全程不塌，A5 PASS。

**教训**：数字掉下来的时候，先问"是不是尺子坏了"，再问"是不是被测对象坏了"。
两个"坏"要靠**受控实验**分开 —— 这里的受控实验就是"换成同一批数据再测一遍"。

#### ★ 静默错误 ②：A3 的判定取了错的 ef，报了个假的 FAIL

第一版只往结果文件里导出一个 recall 值。对照程序不知道那是哪个 ef 的，
于是拿**命令行给的最后一档 ef=512**去和 C 侧的 ef=64 比 —— 差 43 个点，报 FAIL。

**修法**：结果文件里显式写上主测量的 ef，并把**整条 ef 曲线**一起导出，逐档比。

（逐档比还有一个额外好处：能看出两边的**曲线形状**是不是一致，
而不只是某个点对不对。）

#### ★ 静默错误 ③：A3 判定的**方向**反了

原文"我们的 recall@10 与 hnswlib 差 < 2 点"，直译成绝对值比较 →
我们比 hnswlib 好 5.2 个点也报 FAIL。

A3 想抓的是"**我们比业界标准差很多**"（那说明有 bug）。
所以判据应该是：**我们不比 hnswlib 差 2 点以上**。
我们比它好不是缺陷。

#### ★ 静默错误 ④：曲线 ef 数组的类型不匹配

结果文件里 `curve_efs` 是 u16，读的时候按 u32 读进 u32 容器 ——
逐档对比表**全空**（表头打了、没数据）。

不崩、不报错，只是空表 —— 这种错最难发现，因为它看起来像"没数据可比"。

#### ★ 一个容差上的误报

`gt_check.py` 用 1e-9 比两边的 recall，结果两边都显示 0.8650 却报 FAIL：
C 侧的 recall 是 **float32** 存的，精度只有 ~1e-7，差值 9.5e-9 就超了 1e-9。
容差改成 1e-6。

教训：**比浮点数之前先确认两边存的是什么精度**，
否则"数值看起来一样"和"判定通过"是两件事。

#### 一个构建上的坑：基准程序各自带 main

把 `bench/` 接进构建（`make bench` + `build.sh`）时撞到的：

`bench/` 下有**两个**程序 —— `vec_bench.c` 和 `graph_bench.c` ——
它们**各自带一个 main**。第一版构建脚本用 `find bench -name '*.c'`
把三个 .c 一起链成一个可执行文件，结果：

```
multiple definition of `main'; build/bench/graph_bench.o: first defined here
```

**每个基准必须是独立的可执行文件。**
（`bench/vec_bench_util.c` 是 vec_bench 的附属，要和它链在一起。）

顺带另一个同源的问题：`test/run.sh` 用
`find build -name '*.o' ! -name 'main.o'` 收集主库对象 ——
基准对象落在 `build/bench/` 之后会被一起链进测试程序（同样撞 main）。
已加 `! -path 'build/bench/*'` 排除。

**两个错都是"跑一次构建"抓出来的**，不是看代码看出来的 ——
所以改构建脚本之后必须真的跑一遍。

| 指标 | 值 |
|---|---|

#### 顺带量到的两个事实

**① 均匀数据的建索引成本是聚簇数据的 3.6 倍**（245 vs 881 向量/秒）。

不是 IO 的问题（两边都不挂 WAL），是**修剪启发式**的工作量：
均匀数据里"多样的邻居"更难找，Algorithm 4 的候选集更大。
这解释了为什么均匀数据那一轮要跑 408 秒、聚簇只要 113 秒。

**② 10 万 × 128 维时索引常驻 93.3MB**（向量副本 48.8 + 图结构上界 44.4）。

图结构那 44.4MB 是**上界**（用 `VINDEX_PAYLOAD(m)` 算的定长记录长度）；
实际上绝大多数节点只在第 0 层（第 0 层 2m 条边、上面每层 m 条），
真实占用明显更小。用磁盘格式的那个宏来估，而不是自己估 ——
自己估的话常量一改就漂了，而漂了的估算没人会发现。

### 步骤 7 · 反向验证 + 文档 ✓

反向验证的意思是：**故意把实现改坏，确认测试会红**。
红不了就说明测试是瞎的 —— 那比没有测试更危险。

#### ★ 注入 1（跳过上层导航）：**原来的测试全绿，抓不住**

注入：`hnsw_search` 里把上层贪心下降关掉，只搜第 0 层。

PLAN §2 步骤 7 的预期是"recall 必须显著下降（A2 红）"。**实测没有红**：

```
test_hnsw ... 3. 1 万 × 16 维：recall@10 ≥ 0.9
    （recall@10 = 0.9990，M=16 efC=200 ef=64）    ← 注入前后一模一样
```

于是去量"上层到底贡献了什么"。先写了个临时诊断程序，
量出"不走上层 recall 掉到 0.000"—— **这个结论是错的**，
因为诊断程序自己踩了 v1.0 步骤 5 踩过的那个坑：
`res` 是**最大堆**，数组不是有序的，我却拿 `res.a[0..k-1]` 当"最近的 k 个"
（堆顶是最差的那个）。修正排序后，真相是：

| ef | 走上层 recall | 不走上层 recall | 走上层访问节点 | 不走上层访问节点 |
|---|---|---|---|---|
| 16 | 0.218 | 0.216 | 32532 | 36364 |
| 32 | 0.344 | 0.364 | 58316 | 62466 |
| 64 | 0.506 | 0.504 | 101137 | 101690 |
| 128 | 0.658 | 0.668 | 178944 | 182079 |

（5 万 × 128 维均匀数据，50 个查询）

**结论：在 10 万点以内、ef ≥ 16 的规模上，上层导航对 recall 和工作量都几乎没有影响。**
（论文里的 10~100 倍加速要到更大规模、更小 ef 才显现。）

所以"recall 必须显著下降"这个预期本身就是错的 ——
**上层在这个规模上不是 recall 的关键**。

**那怎么才能抓住这个注入？** 断言**机制**，不断言收益：

上层的作用是"把起点从入口点挪到更靠近查询的地方"。
那就断言"起点确实被挪过了" —— 这是一眼可辨的，不依赖规模、不依赖阈值。

为此加了三个诊断口（和已有的 `hnsw_neighbors` 同款定位）：

| 诊断口 | 作用 |
|---|---|
| `hnsw_last_entry()` | 最近一次搜索在第 0 层的**实际起点**（下降之后） |
| `hnsw_last_visited()` | 最近一次搜索在第 0 层访问的节点数 |
| `hnsw_visited_from()` | 从**指定**起点搜第 0 层，返回访问节点数 |

新增 `test_hnsw.c` 第 8 项：

```c
/* 50 个查询里，起点被上层挪过的必须 ≥ 90% */
CHECK(moved >= nq * 9 / 10);
```

- 注入 1 生效时：**0 / 50** → 红
- 撤回后：**50 / 50** → 绿

#### ★ 注入 2（候选池不扩大）：旧测试抓不住，**新加的一项抓住了**

注入：`db_vec_knn_filtered` 的候选池从 4k 改成 k。

PLAN §2 步骤 7 的预期是"正确性不红，但 A5 的中途检查点会红"。
实测**连 A5 也不红** —— 47 个测试文件全绿。

原因：旧的第 5 项用 `make_vec(0)` 当查询，而**它自己的 label 就是 0**
—— top-k 里一定有命中，候选池是 k 还是 4k 都返回 n > 0。

所以补了新的一项 `test_vec_it.c` 第 **5b** 项，用**手工摆的数据**
造出"满足条件的行**不在 top-k 里、但在 top-4k 里**"的情形：

```
位置   0   1   2   3   4   5   6   7
距离  0   1   4   9  16  25  36  49      （平方 L2）
label 0   0   0   0   1   1   1   1
```

查询 = 位置 0，要 k=2 个 label=1：

- 正确实现（候选池 4k=8）→ 看到全部 8 个 → 命中 v4,v5,v6,v7 → 截断到 2 → **返回 2 个**
- 注入（候选池 = k = 2）→ 只看到 v0,v1（都是 label 0）→ **返回 0 个**

0 个是**静默丢数据** —— 违反"下推只能给超集"铁律，
而所有其它断言都验不出来。

注入 2 生效时：第 5b 项红（返回 0 个，期望 2 个）；**旧的第 5 项仍然绿** ——
正好印证了这个缺口的存在。

#### ★ 诊断口自己踩的坑：堆的 max 标志

`hnsw_visited_from` 第一版用局部 `Heap res` 做结果集，
忘了置 `res.max = true`（结果集是**最大堆**，堆顶 = 最差的那个）。

后果：`h_top()` 返回的是"最好的"而不是"最差的"，
剪枝条件整个反了 —— 测出来的两个数字对不上（58912 vs 52335），
而同一份数据同一段代码本该给出**完全相同**的结果。

**"同一份代码在两条路径上给出不同结果"本身就是 bug 的信号** ——
不管哪个数字看着更合理。这个原则和"集合对、顺序错"是同一族。

#### 两条方法论

**① 反向验证的价值不在"抓到 bug"，在"发现测试是瞎的"。**

注入 1 抓不到，说明测试套件里有一整类错误（上层机制失效）是盲区。
**如果只跑正向测试，这个盲区会一直留着** —— 直到某天线上召回率异常才发现。

而且这次反向验证顺手纠正了两个**我自己的错误结论**：
"上层对 recall 至关重要"（诊断程序的堆序 bug）和
"上层能省 90% 工作量"（10 万点以内其实只省 0.5%）。

**② 断言要选"机制"，不要选"收益"。**

收益依赖规模、依赖数据、依赖参数 —— 阈值定多少都别扭，而且会骗人。
机制是二值的、不依赖规模的："起点被挪过了没有"。

当然，反过来也不成立 —— 机制在不代表收益在。
所以两件事都要记：**测什么**（机制）+ **量多少**（收益，实测 0.5%）。
