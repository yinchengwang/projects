# MM 编译期模态裁剪 —— profile 说明与实测

> 数据由 `sh tools/measure_build.sh` 产出，**不手写数字**。
> 真相源是 `tools/mm_profiles.mk`；本文件是它的人类可读副本。
>
> ⚠️ **每次改过模态文件归属（加文件、搬目录、改 `MM_FILES_*`）都要重跑一次度量。**
> 手写的体量数字必然过期 —— 本项目已经吃过一次亏（设计文档里的数字曾整体偏小 20%）。

### 这组数字说明什么

**裁剪确实有效，而且不是靠「少编几个文件」糊弄出来的：**

| 对比 | 编译单元 | 代码行数 | 二进制符号 |
|---|---:|---:|---:|
| `full` | 143 | 53196 | 1842 |
| `relational`（一个可变模态都不开） | 58（**−59%**） | 19384（**−64%**） | 972（**−47%**） |
| 最轻的单模态（`blob`） | 62（−57%） | 21024（−60%） | 1022（−45%） |
| 最重的单模态（`ft`） | 83（−42%） | 30195（−43%） | 1215（−34%） |

⚠️ **`relational` 不是 0** —— 那 58 个编译单元是 L0–L3 底座 + 关系模态本身。
**「关掉所有其他模态」最多只能省掉 59%，剩下 41% 是关系模态与底座。**
这个比例本身就是一条架构结论：**关系模态是底座，不是插件。**

⚠️ **两列「编译单元 / 目标文件」看起来一样**，这不是脚本写错了：
每个 `.c` 编出一个 `.o`，一一对应。保留两列是因为语义不同 ——
一个问「编了几份源码」，一个问「产出了几个目标文件」。
将来若引入 unity build，两列就会分叉。

⚠️ **构建秒数不能当性能指标看** —— 同一份代码在不同机器上差好几倍。
它的用途只有一个：**发现"构建变慢了"这个回归**（超过门禁值就红）。

## 用法

```bash
make MM=vector                  # 只编 vector 模态
make MM=vector OBJ_BASE=out     # 换输出根目录（产物落在 out_mm_vector）
make smoke                      # 构建 8 个 smoke（链接期模态独立证明）
sh tools/measure_build.sh       # 全部 9 个 profile 的度量
sh tools/mm_profiles_test.sh    # profile 真相源自检
```

> ⚠️ **换输出目录要用 `OBJ_BASE`，不是 `OBJ_DIR`。**
> `OBJ_DIR` 是**命令行变量**，在 GNU Make 里优先级最高，`override` 也压不住它 ⇒
> 所有 profile 会共用同一个目录 ⇒ 裁剪的 `.o` 与 full 的 `.o` 混在一处 ⇒
> **跑的是旧二进制**（正是 `Makefile` 头部警告的那个坑）。
> `OBJ_BASE` 不参与那条覆盖链，由它承接「用户想放的根目录」。

## 门禁现状

两条 S9 规则在 `tools/check_deps.sh` 里：

| 规则 | 状态 | 说明 |
|---|---|---|
| **S9①** `query/` 不许碰模态实现 | **已启用（阻断）** | 禁止词带路径口径：`modalities/`、`storage/heap`、`storage/blob`、`spi/blob_am`、`spi/index_am` |
| **S9②** 模态适配器必须在 `src/modalities/<m>/` 下 | **报告但不阻断** | 4 个文件还在 `src/spi/`，等 W-C 的 C-2/C-3 搬走 |

⚠️ **为什么 S9① 的禁止词必须带路径**：
`forbid()` 的实现是 `#include "[^"]*${bad}` —— **子串匹配**，`bad` 前面没有分隔符约束。
裸词 `heap` 会误伤**合法的** `#include "spi/heap_am.h"`
（query 通过 SPI 契约访问堆，这正是它该做的事）。
⇒ 一律写成 `storage/heap` / `storage/blob` / `modalities/` 这种带目录的形式。

⚠️ **为什么 S9② 当前不阻断**：
在搬家之前设成阻断 ⇒ `make check` **恒红** ⇒ 门禁失去意义
（一个永远红的检查和一个永远绿的检查一样没用）。
要立刻验它能不能抓：

```bash
MM_S9_ENFORCE=1 sh tools/check_deps.sh   # 预期：红，并列出 src/spi/*_am.c
```

## P3 评估：seam 能不能做成可发布的头文件包（D8 预备，**只评估、不实施**）

> 设计 §4.6 的 P3 阶段在三份计划里都没有落点，D8 判决是「方案 C 留预备」。
> 「留预备」= **有条件地不做**，不是没人管。本节记录评估结论与下次评估的触发条件。

| 评估项 | 问题 | 实测结论 |
|---|---|---|
| seam 边界是否还干净 | 底层四层（common/storage/query/spi）有没有 include 模态头？ | **是。零命中**（`grep '#include ".*modalities'` = 0 行） |
| 有没有模态头泄漏 | 同上，反向看 `modalities/` 是否引用了 `spi/` 之外的东西？ | **只引用 spi/ 的契约头**（11 处），没有越界 |
| 模态互相依赖 | `modalities/<a>/` 有没有 include `modalities/<b>/`？ | **0 处** —— `check_deps.sh` 的 L4 一直在守 |
| 契约面规模 | seam = spi/ 的 8 个头 / 多少行？ | **750 行**（`storage_am.h` 266 行最大） |
| 模态实现规模 | `src/modalities/` 下多少代码？ | **69 个 `.c` / 27268 行** |
| 现在拆的代价 | 多进程需要跨进程协调、事务边界、错误码映射 | **估 6–8 周**（见下） |
| 什么时候值得拆 | 触发条件是什么？ | 见下「触发条件」 |

### 现在拆的代价（估 6–8 周）

拆成「独立发布的头文件包 + 多进程/多语言运行时」要动的东西：

1. **事务边界**（2–3 周）：现在所有模态共享实例级 `pager` / `wal` / `txns`。
   拆出去就必须定义跨进程提交协议 —— 这是最难的一块，也是唯一会碰正确性的一块。
2. **错误码映射**（1 周）：`E_*`（内部）→ `DB_E_*`（公共）现在在进程内直接映射；
   跨进程要保序、要能带上下文。
3. **生命周期**（1–2 周）：现在关库顺序是靠 `db_instance.c` 里那段写死的顺序
   （模态 → catalog → clog → pager → wal，见坑 M4-48）。跨进程要变成引用计数 + 协议。
4. **接口稳定化**（1–2 周）：750 行的契约面要冻结、要版本化、要写兼容性策略。
5. **构建与发布**（1 周）：9 个 profile × 多平台 × 头文件包的一致性验证。

⇒ **这不是「抽个头文件就能发布」的量级**，是「改数据一致性模型」的量级。

### 触发条件（可判定，不是"感觉需要"）

任一条成立才重新评估：

1. **有两个以上互不相关的团队要用同一个模态实现** —— 且他们无法共用一个进程。
2. **需要一个非 C 的运行时**（比如 Python / Java 侧直接调模态），
   且 REST/gRPC 包装的延迟不能满足 SLO。
3. **单个模态的代码量超过 5 万行**（现在最大的 ft 是 **10,811 行** —— 9709 行在
   `modalities/ft/` + 1102 行适配层），内部协作成本已经超过拆分成本。
4. **模态要独立发版**：某个模态的迭代节奏与主核完全不同，
   且因共用构建而被迫同步发版 ≥ 3 次。

⚠️ **一条都不成立就不拆。** 现在 `MM=` 的 9 个 profile 已经给出了
「按需裁剪」的全部收益（编译单元 −59%、代码行数 −64%），
而**不需要**付出拆进程的代价 —— 这就是「方案 C 留预备」的实质。
