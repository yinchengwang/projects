# v0.7 执行方案与计划 · MVCC 与 vacuum

> 前提：v0.6（WAL + 崩溃恢复）已完成并全绿（98 项验收）。
> 本版目标：把「每条语句一个事务」升级成「真正的事务」，让并发读不阻塞写。

---

## 一、方案

### 1.1 范围

**做**：

1. **tuple 版本化**：写入时打 `xmin`/`xmax`，更新不原地改而是插新版本。
2. **事务管理**（`txn/txn.c`）：显式 `BEGIN` / `COMMIT` / `ROLLBACK`，事务表，状态机。
3. **MVCC 可见性**（`txn/mvcc.c`）：快照 + 可见性规则，判断某版本对某事务是否可见。
4. **快照隔离**：RC（语句级快照）/ RR（事务级快照）。
5. **vacuum**（`txn/vacuum.c`）：清理对所有事务都不可见的死版本，回收空间。
6. **全局 latch**（`txn/latch.c`）：一把大锁，先把临界区概念跑通。

**不做**（明确划掉，避免范围蔓延）：

- 写写冲突检测（RC/RR 下写写冲突直接报 `E_TXN` 失败，不等待）。
- SSI / 可串行化。
- 死锁检测。
- 细粒度 latch、锁升级、crabbing。
- B+tree 物理日志（仍靠 `exec_rebuild_indexes` 重建）。
- 日志截断、group commit。
- 索引的 MVCC 过滤（索引项仍指向所有版本，扫描时逐条回表判可见性）。

### 1.2 六个决定

#### A · 更新 = 插新版本（不复用旧 slot）

**决定**：任何 UPDATE 都走「标记旧版本 + 插入新版本」，**不做原地改**。

**为什么**：原地改会让「读者看到旧值还是新值」变成一个无法回答的问题 —— 值已经被覆盖了，
旧值不存在于任何地方，读者无从判断。插新版本则旧值还在，
每个读者按自己的快照判断能不能看到它。

**代价**：RID 会变，索引必须维护（删旧 key、插新 key）。这是 PG 的做法，
也是所有 MVCC 系统的共同代价。

**注意**：这改变了 v0.6 的 `heap_update` 语义（v0.6 是 `len <= old_len` 就原地改）。
新的 `heap_update` 永远返回新 RID。

#### B · 可见性规则（5 条，全部要能背出来）

设当前快照为 `snap`（记录了快照建立时所有活跃事务的 xid 集合）：

| 规则 | 条件 | 结果 |
|---|---|---|
| R1 | `xmin` 是快照开始前已提交的 | 可见（前提 R2 也满足） |
| R2 | `xmin` = 快照自身的事务 | 可见（自己写的自己看得到） |
| R3 | `xmin` 是快照开始后启动的事务 | **不可见** |
| R4 | `xmax` = 0 | 无删除标记，可见 |
| R5 | `xmax` 在快照前已提交 | **不可见**（已被删除） |
| R6 | `xmax` 在快照后提交或为 0 | 可见（删除对本快照不可见） |

简化实现：维护一个「快照时已提交的最大 xid」`snap_xmax`（commit counter 思路），
加上「快照时活跃事务的 xid 集合」`snap_xids`。

- R1：`xmin <= snap_xmax` → 已提交
- R2：`xmin == my_xid` → 自己
- R3：`xmin > snap_xmax && xmin 不在 snap_xids` → 快照后启动 → 不可见
- R5：`xmax != 0 && xmax <= snap_xmax` → 已删除 → 不可见
- R6：其余情况 → 可见

**为什么用 commit counter 而不是纯 xid 比较**：纯 xid 比较下，
「xid 小但还没提交」和「xid 大但已提交」无法区分。用「已提交的最大 xid」做分界线，
配合活跃集合打补丁，是 PG 早期的做法（PG 后来用 clog + xid 比较），
逻辑简单且足够正确。

#### C · 快照的实现：CC + 活跃集合

```
Snapshot {
    u32  snap_xmax;      /* 建立快照时，已提交事务的最大 xid */
    u32 *snap_xids;      /* 建立快照时，仍活跃（未提交）事务的 xid 集合 */
    int  n_xids;
    u32  my_xid;         /* 创建快照的事务 */
}
```

**建立快照的时机**：
- RC：每条语句开始时重建快照。
- RR：事务开始时建一次，整个事务复用。

**提交时如何推进 `snap_xmax`**：事务提交时把 `snap_xmax` 推进到自己的 xid。
这要求 xid 单调递增且提交顺序与 xid 顺序一致 —— 在**单写者**下成立。
本版是单线程/全局 latch 模型，所以安全。

#### D · xid 分配：全局计数器 + 活跃事务表

```
TxnTable {
    TxnEntry entries[64];
    u32  next_xid;
}
```

事务状态机：`IDLE → ACTIVE → COMMITTED / ABORTED`。

**为什么不能重用 xid**：MVCC 的可见性判断完全依赖 xid 的单调性和唯一性。
重用 xid 会让旧版本无法判断。

#### E · vacuum：只删「对所有快照都不可见」的死版本

**决定**：实现简化的 vacuum —— **不维护 hint bits**，每次扫描时**当场算可见性**。

**为什么先不做 hint bits**：hint bits 的价值是避免重复判断，但引入
「这个 bit 什么时候可以置上、什么时候必须重置」的复杂度（R4/R5 的边界）。
v0.7 先做正确版本，v0.8 再优化。

**vacuum 的判定**：
- 对每个版本的 `xmin`：如果 `xmin` 已提交，且**没有任何活跃事务**可能看到它
  （即 `xmin <= 所有活跃快照的 snap_xmax`）→ 死版本，可回收。
- 对 `xmax`：如果 `xmax` 已提交且已对所有快照可见 → 死版本。

**简化**：本版实现「整表 vacuum」，即扫描全表，把死版本的 slot 置为删除。
**不做**页内 compact 搬迁（页内 compact 会移动记录位置 → RID 变化 → 索引失效）。
页空间回收留给 v0.8 的页整理。

> **这是一个重要的教学点**：PG 的 vacuum 不只是"删死版本"，还要「搬移行」来回收空间，
> 因为 PG 的行存在页中间，删了留下空洞。搬移会改 RID，所以 PG 的索引存的是
> TID 且 vacuum 要同步改索引。这里我们不做搬移，所以 slot 永不复用的铁律仍然成立。

#### F · 并发模型：全局 latch

**决定**：一把全局 mutex（`latch.c`），保护所有共享状态。

**为什么不直接上细粒度**：并发 bug 只在特定时序暴露。
v0.7 的核心是**可见性规则**，如果同时引入 crabbing 和锁升级，
两个不确定叠加，调试成本会吃掉全部学习收益。

**锁的粒度**：事务表 + 快照建立 + vacuum 全程持锁；
纯读路径（可见性判断）尽量不持锁 —— 因为可见性判断只读快照数据，
快照是不可变的数据结构。

### 1.3 tuple 格式变化

v0.6 的 20B header 已有 `xmin`/`xmax`/`flags`，但**从未被写入**。v0.7 启用它们：

```
┌──────────┬──────────┬─────────┬──────────────┬────────────┬──────────────┬──────────┐
│ xmin 8B  │ xmax 8B  │ flags4B │ null bitmap  │  定长列区  │ 变长偏移数组 │ 变长数据 │
└──────────┴──────────┴─────────┴──────────────┴────────────┴──────────────┴──────────┘
```

- `xmin`：插入这个版本的事务号（0 = 系统事务，如 bootstrap）。
- `xmax`：删除/替换这个版本的事务号（0 = 未删除）。
- `flags`：
  - `REC_F_COMMITTED`（0x01）：xmin 已提交
  - `REC_F_ABORTED`（0x02）：xmin 已中止
  - `REC_F_OLDVER`（0x04）：已被替换（旧版本标记）

**`xmax` 的语义扩展**：从「删除」扩展到「替换」。
UPDATE 时旧版本的 `xmax` = 更新事务的 xid，表示「这个版本被这个事务换掉了」。

**flags 的维护**：由于不做 hint bits，`flags` 里的 COMMITTED/ABORTED 位
在 v0.7 里**只写不判**（写入时记录当时的状态，读取时以事务表为准）。
保留这两个位是为了 v0.8 做 hint bits 时格式不用改。

### 1.4 SQL 层面要加的语句

```
BEGIN;                 -- 显式开始事务
COMMIT;                -- 提交
ROLLBACK;              -- 回滚
```

**交互规则**：
- 没有显式 BEGIN 时，`db_exec` 仍然自动包一个单语句事务（保持 v0.6 行为，不破坏现有测试）。
- 显式 BEGIN 后，直到 COMMIT/ROLLBACK，所有语句在同一个事务里。
- 事务内出错（比如约束冲突）→ 不自动回滚整个事务，但语句本身失败；
  简单起见：**语句出错即回滚整个事务**（这是很多数据库的 "abort the transaction" 语义），
  需要显式 ROLLBACK 或重新 BEGIN。

**RR 下的原子性**：事务内多条语句在提交时一起可见（因为快照是事务级的）。
其他事务在提交前看不到任何一条。

### 1.5 可见性判断的放置点

```
exec_scan:  heap_scan_next → 取 tuple → mvcc_visible(snap, tuple) → 不可见就跳过
exec_insert: 写 tuple 时打 xmin = my_xid
exec_update: 旧版本打 xmax = my_xid → 插新版本打 xmin = my_xid
exec_delete: 旧版本打 xmax = my_xid
index_scan:  取 RID → 回表 → 同样做可见性判断（索引本身不过滤）
```

**索引为什么不过滤**：索引项只存 key + RID，不知道 tuple 的版本信息。
要么在索引项里也存 xmin（PG 的做法，索引项带 MVCC 状态），
要么回表判断。v0.7 选回表判断（简单），v0.8 可以优化。

### 1.6 验收

**单元测试 `test/unit/test_mvcc.c`**（核心，8 项）：

1. 插入的行对自己的事务可见。
2. 插入的行对其他事务**不可见**（未提交）。
3. 提交后，其他事务可见。
4. RR：事务开始后别人插入的行，**事务内始终不可见**（快照固定）。
5. RC：事务内第二条语句能看到别人新提交的行（快照刷新）。
6. UPDATE 产生新版本，旧版本对旧快照可见、新版本对新快照可见。
7. DELETE 后，行对旧快照可见、对新快照不可见。
8. vacuum 之后：死版本被清理，活版本完好，且索引仍正确。

**单元测试 `test/unit/test_txn.c`**（5 项）：

1. 事务状态机：IDLE → ACTIVE → COMMITTED。
2. COMMIT 后状态为 COMMITTED，ABORT 后为 ABORTED。
3. ROLLBACK 撤销本事务的所有修改（行数回到原样）。
4. xid 单调递增，不重用。
5. 嵌套 BEGIN 被拒绝（或定义为隐式提交）。

**集成测试 `test/integration/test_mvcc.c`**（4 项）：

1. 两个连接（两个 `DB` 句柄）并发：一个写、一个读，读不到未提交数据。
2. 写方提交后，读方（RC）能看到。
3. 读方（RR）在事务中途重新读，还是看不到事务开始后提交的数据。
4. 崩溃恢复后，MVCC 状态一致（已提交版本保留、未提交版本不可见）。

**v0.6 的回归**：所有 v0.6 测试必须继续全绿（98 项）。

**性能与正确性平衡**：
- 插入 1000 行、每个事务提交一次，开销不超过 v0.6 的 3 倍。

### 3.2 方案被推翻的地方

方案里写的和实际做出来的不一样，有三处。**这三处都不是"实现没做好"，是方案本身想错了。**

#### A · commit counter 被推翻 → 改用 clog

**方案原文**：维护"快照时已提交的最大 xid"（commit counter），
用 `xid <= committed_xmax` 表示已提交。

**为什么被推翻**：commit counter 表达的是"**现在**的最大已提交 xid"，
而快照需要的是"**快照那一刻**的提交状态"。两者不是一回事。

反例：

```
时刻 1：事务 A (xid=5) 开始
时刻 2：事务 B (xid=6) 开始并提交 → committed_xmax = 6
时刻 3：建立快照 → snap_xmax = 6
时刻 4：事务 A 提交 → committed_xmax 仍是 6
```

快照里的 `snap_xmax` 是时刻 3 的值 = 6。而 A 的 xid = 5 <= 6，
于是快照认为"A 在快照建立前就提交了" —— **错**。
A 是在快照之后才提交的，其他事务本不该看到 A 写的数据，现在却看到了。
这就是**脏读**。

**改法**：换成 PG 的 clog —— 每个 xid 存 2 bit 状态
（0=进行中 / 1=已提交 / 2=已中止），快照时逐个查询，得到精确状态。

**代价**：每个 xid 2 bit，40 亿个 xid 要 1GB 内存，太奢侈。
所以用**环形窗口**：只保留最近 4096 个 xid 的状态，窗口外一律按已提交处理。
（安全的理由：要走出窗口，说明中间已经过去 4096 个事务，那是很久以前的事。）

#### B · 快照模型从"CC + 活跃集合"改成 PG 的三元组

**方案原文**：`snap_xmax` + `snap_xids`（活跃事务 xid 集合）。

**实际实现**（对齐 PG）：

```c
typedef struct {
    u32  xmin;        /* 快照时活跃事务的最小 xid */
    u32  xmax;        /* 快照时 next_xid */
    u32  my_xid;      /* 快照所属事务 */
    int  n_xip;       /* 快照时正在运行的事务数（不含 my_xid） */
    u32  xip[SNAP_MAX_XIP];
} Snapshot;
```

`xmin`/`xmax` 是**分界线**，`xip` 是**例外清单**。
这样绝大多数 xid 用两次比较就能判定（落在区间外），
只有边界情况才查 clog —— 读路径的性能关键。

#### C · 实例与连接分离（方案里完全没提）

**实际实现**：`DbInstance`（共享）+ `DB`（连接私有）。

方案通篇假设"一个 DB 句柄 = 一个数据库"。但 MVCC 的意义恰恰是
**多个连接看同一个库、看到不同的时间点** —— 没有连接抽象就没法测这个。

**这个改动是被测试逼出来的**：最初用 `db_open(path)` 开两个句柄模拟两个连接，
结果读方看不到写方建的表（SELECT 报"表不存在"）。

根因不是 bug，是架构的必然：每个 `db_open` 都**独立地**打开缓冲池、
加载 catalog 副本、重建 freelist —— 两个句柄其实是两个互不相通的数据库实例。

所以引入 PG 的 postmaster/backend 模型：

| | 共享 | 私有 |
|---|---|---|
| 实例 | 缓冲池 / catalog / WAL / 事务表 | — |
| 连接 | — | 当前 xid / 快照 / 事务状态 / 隔离级别 |

### 3.3 四个真正的 bug（都是"静默出错"）

#### Bug 1 · `in_txn` 双字段不同步 → COMMIT 永远失败

**现象**：12 项集成测试失败，`COMMIT;` 永远报"不在事务中"。

**根因**：`db.c` 的 `DB.in_txn`（`db_exec` 检查它）
和 `exec.h` 的 `Db.in_txn`（`txn_start` 只设这个）是**两个独立字段**。
一个设了，另一个没设。

**修法**：删掉 `exec.h` 的冗余字段，事务状态只有一处存放。

**教训**：**同一个语义只能有一个存放处**。
事务状态属于"连接"的概念，归 `db.c` 的 `DB` 结构管；
`exec.h` 的 `Db` 只放内核执行真正需要的字段。

#### Bug 2 · WAL 的 xid 是共享状态 → 跨连接串号

**现象**：回滚 + 崩溃 + 重启后，未提交的数据复活了。

**根因**：`wal_set_xid(w, xid)` 把 xid 写进 WAL 对象。
但 WAL 是**实例级共享**的：

```
连接 A：wal_set_xid(w, 5)
连接 B：wal_set_xid(w, 6)      ← 覆盖了 A 的设置
连接 A 写数据 → 日志记录的 xid 是 6，不是 5
```

恢复阶段分析"哪些事务提交了"时，A 的记录被算到 B 名下 ——
**未提交的数据被判定为已提交**。这是静默的数据损坏。

**修法**：xid 随每次调用**显式传**下去，不能存在共享对象里。

```c
u32 wal_append_xid(Wal *w, u8 type, u32 xid, u32 page_id, ...);
```

`LogHookFn` 加 xid 参数，`heap` / `catalog` / `exec` 全链路透传。
undo 链（`prev_lsn`）同样按 xid 分槽维护。

**验证**：注入 bug 后 `test_mvcc_it` 立刻 2 项失败 —— 测试有效。

**教训**：**任何"当前是谁"的信息都不能藏在共享对象里**。
共享的对象（实例级 WAL / catalog / heap）必须让调用方显式传参。

#### Bug 3 · 陈旧 WAL 启发式误判 → 崩溃前未刷页时数据全丢

**现象**：新增的 WAL xid 回归测试失败，重启后 SELECT 直接报错。

**根因**：`db_open` 判断"孤儿 WAL"用的是"页数是否为 0"：

```c
if (pager_npages(pg) == 0 && wal_nrecords(inst->wal) > 0) {
    rc = wal_reset(inst->wal);   /* 把合法日志清空！*/
}
```

但 `db_abandon`（模拟崩溃）丢弃所有脏页 → 数据文件 0 字节。
重开时命中"孤儿 WAL"判定 → `wal_reset` 把合法日志清空 → **数据全丢**。

**修法**：改用"数据文件是否存在"（`fopen` 探测）而非"页数是否为 0"。

```c
bool datafile_exists = false;
FILE *probe = fopen(path, "rb");
if (probe) { datafile_exists = true; fclose(probe); }
```

**教训**：**启发式判据要看它真正想区分的东西**。
"孤儿 WAL"要区分的是"这个日志属于另一个库"，不是"这个日志没有配套数据"。

#### Bug 4 · 可见性判断漏了「区间内但不在 xip」这个分支

**现象**：多连接场景下，**写方自己都看不见刚提交的数据**。

**根因**：`xid_committed_in_snap` 的最后一个分支我写成了
"落在 [xmin, xmax) 之间但不在 xip 里 → 保守起见当作未提交"。

我以为这个分支"理论上不该发生"。**实际上它是主路径**：

- `snap.xmin` 的定义是"活跃事务的最小 xid"（**排除 my_xid**）
- 所以区间 `[xmin, xmax)` 会把很多**已提交**的事务圈进来
- 这些事务不在活跃表 → 不在 xip 里
- 但它们**已经提交了**，应该可见

**后果**：已提交的数据读不出来 —— 静默丢数据。

**修法**：查 clog 定论（对齐 PG 的规则 6）：

```c
/* 落在 [xmin, xmax) 之间但不在 xip 里 → 查 clog */
return txn_clog_state(t, xid) == TXN_CLOG_COMMITTED;
```

**为什么单连接测试抓不到**：单连接时 `xmin == xmax`，区间是空的，
永远走不到这个分支。**必须多连接（且有长事务占着区间）才暴露**。

**验证**：注入 bug 后单元测试 1 项 + 集成测试 3 项变红。

### 3.4 一个设计上的坑：vacuum 把自己算进去了

**现象**：`VACUUM` 语句能执行，但 `removed` 永远是 0。

**根因**：`mvcc_is_dead` 的保守规则是"只要还有活跃事务就不动"。
而 **vacuum 自己就跑在一个事务里** —— 它就是活跃事务。
于是判定永远为 false，vacuum 变成一个只会空转的语句。

**修法**：判断"还有没有活跃事务"时**排除执行者自己**：

```c
bool txn_has_active_except(const TxnTable *t, u32 exclude_xid);
bool mvcc_is_dead_except(const TxnTable *t, u32 exclude_xid, const u8 *buf, u16 len);
```

**教训**：**"保守"和"失效"是两回事**。
保守是"可能不该删但我先不删"，失效是"我永远不删"。
前者安全，后者是 bug —— 而且是那种看起来很"安全"的 bug。

**验证**：注入 bug 后单元测试 3 项 + 集成测试 2 项变红，
集成测试精确指出 `removed` 不再是 2。

### 3.5 补齐的两处方案缺口

方案明文承诺但一开始没做的，收尾时补上了。

#### A · 隔离级别（RC / RR）

**原状**：只实现了 RR（显式事务内快照固定），但方案 1.2-D 承诺两种都要有。

**补法**：

- `txn/txn.h` 加 `TxnIsolation` 枚举（RC / RR）
- `parser` 加 `SET TRANSACTION ISOLATION LEVEL { READ COMMITTED | REPEATABLE READ }`
- `db.c` 的 `DB` 加 `iso_level`（连接私有 —— 它描述的是"这个连接看世界的方式"）
- **RC 的实现只有一处**：每条语句执行前刷新快照

```c
if (db->iso_level == ISO_READ_COMMITTED && db->in_txn) {
    mvcc_snapshot(&db->inst->txns, db->xid, &db->db.snap);
}
```

**这是快照隔离最优雅的地方**：两种隔离级别**不是两套机制**，
而是同一个机制的两种"快照刷新时机"。可见性判断逻辑完全一样。

**默认 RC**（对齐 PG）。用户要 RR 必须显式声明。

**新测试暴露的连带影响**：默认级别从 RR 改成 RC 后，
原先 3 项依赖 RR 语义的集成测试立刻红了 —— 这恰好证明
RC/RR 的差别是**真实可观测的**，不是"实现了但没起作用"。

新增 `t8_rc_vs_rr`：同一场景、两个连接、只差一个 SET，
RC 看到 2 行、RR 看到 1 行 —— 差别必须可观测。

#### B · VACUUM 的 SQL 入口

**原状**：`vacuum_table` 已实现，但没有任何 SQL 入口，测试只能直接调函数。

**补法**：

- `parser` 加 `ST_VACUUM`
- `exec` 加 `exec_vacuum` → `resolve_table` 拿 heap → `vacuum_table`
- 返回一行三列：`scanned` / `removed` / `kept`

**一个必须注意的前提**：vacuum 的删除动作本身要写 WAL 日志，
日志里的 xid 必须是真正干活的这个事务。
好在 `db_exec` 已经保证了：任何非事务控制语句都在事务里跑。

### 3.6 顺手补上的两个安全网

| 位置 | 防的是什么 |
|---|---|
| `wal_hook` 的 ctx 指向 `DbInstance *` | 原来的 ctx 指向 owner 的 `DB` 结构，owner 先 `db_close` 时被 `free`，其他连接继续写日志就是访问已释放内存 |
| `heap` / `catalog` 的写接口全部加 xid 参数 | 共享状态串号的根源。删除 `wal_set_xid` / `heap_set_xid` / `catalog_set_xid` 这三个共享状态 API |
