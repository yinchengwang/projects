# 整体设计

> 这份文档是施工图。每加一个模块，回来对照一次；每个"为什么不选另一条路"都记在这里，
> 半年后你会需要它。
>
> 状态：v0.10 完成（全局 latch，真并发），152 项验收全绿。v0.11 起做图模态。

---

## 1. 目标与非目标

### 目标

1. **把八个模态的核心机制亲手实现一遍**，每个机制都要能量测、能解释数字。
2. **每一层可独立验证**：存储层不依赖索引层，索引层不依赖查询层。
3. **设计对齐业界真实实现**：抄 PG 的 AM 抽象、Neo4j 的定长记录、Lucene 的 segment、Lance 的列式布局。
4. **一条 SQL 能从文本走到结果**，并且崩溃后不丢不重。

### 非目标（明确划掉，防止范围蔓延）

| 不做 | 理由 |
|---|---|
| 分布式 / 副本 / 分片 | 另一个 3 年，且和"理解单机内核"无关 |
| SQL 标准全兼容 | 只做 SELECT/INSERT/UPDATE/DELETE + 少量 DDL |
| 存储过程、触发器、视图 | 对理解内核没有增量价值 |
| 优化器 join reorder（v1 前） | 没有统计信息时写 CBO 比 rule-based 更差 |
| SSI（可串行化隔离） | 单独要 6 个月，做到 RR 就够讲清 MVCC |
| 生产级性能 | 目标是"量级对齐"，不是"追平" |

## 2. 全景：一条 SQL 的旅程

```
"SELECT id, name FROM users WHERE age > 30 LIMIT 10"
```

| # | 阶段 | 数据结构 | 谁干的 | 关键动作 |
|---|---|---|---|---|
| 1 | 文本 | `char[]` | `main.c` REPL | 按 `;` 切分，逐条执行 |
| 2 | 词法 | `Token[]` | `query/lexer.c` | 关键字/标识符/数字/字符串/运算符 |
| 3 | 语法 | `AST` | `query/parser.c` | 递归下降，产出 `SelectStmt{targets, from, where, limit}` |
| 4 | 绑定 | `BoundStmt` | `query/plan.c` + `catalog` | 查 catalog 拿 schema 和 root_page；`name` 解析成列序号 |
| 5 | 逻辑计划 | `LogicalPlan` | `query/plan.c` | `Project(id,name) ← Filter(age>30) ← Scan(users)` |
| 6 | 物理计划 | `PhysicalPlan` | `query/optimizer.c` | 谓词下推；`age` 有索引则改 `IndexScan(root, 30, +inf)` |
| 7 | 执行 | `Tuple` 流 | `query/exec.c` | 火山模型，每个算子 `next()` 返回一个 tuple 或 EOF |
| 8 | 定位 | `RID` | `index/btree.c` | 范围扫描拿到 `(key, RID)` |
| 9 | 取行 | `Tuple` | `storage/heap.c` | `heap_get(RID)` → `record_decode()` |
| 10 | 读页 | `u8[4096]` | `storage/pager.c` | 命中或逐出载入；脏页刷盘前断言 WAL 已落盘 |

**WAL 是横切的**：第 7–9 步任何一次修改，都必须先 `wal_append` 再改页。这条不写在流程图上，写在纪律里。

### 关键约定

- **RID = (page_id: u32, slot_no: u16)**，打包成 `u64` 传递。它是索引和堆表之间唯一的桥。
- **索引里存的是 RID，不是行数据**。所以更新一行有两种做法：原地改（RID 不变）或插新版（RID 变，索引要改）。见 D2。
- **表 = schema + 页链根**。catalog 本身就是一张表，第 0 页存 bootstrap 指针指向它。

## 3. 数据模型

### 3.1 Tuple 布局

```
┌──────────┬──────────┬─────────┬──────────────┬────────────┬──────────────┬──────────┐
│ xmin 8B  │ xmax 8B  │ flags4B │ null bitmap  │  定长列区  │ 变长偏移数组 │ 变长数据 │
└──────────┴──────────┴─────────┴──────────────┴────────────┴──────────────┴──────────┘
                                    ceil(ncols/8)               2B × n_varlen
```

- `xmin` / `xmax` 是 MVCC 的事务 id，`xmin = 0` 表示系统事务（bootstrap），
  `xmax = 0` 表示**这个版本没有被删除也没有被替换**——它是当前的活版本，**绝不可回收**。
- `null bitmap` 按列序号置位，**必须存在**——不能用"值为 0"表示 NULL。
- 变长偏移数组每项 2B，相对 tuple 起点，指向变长区。
- **解码必须依赖 schema**，tuple 自身不自描述。schema 从 catalog 拿，这是 binder 的职责。

**v0.7 启用版本号**：这 20B 头从 v0.1 就预留好了，但直到 v0.7 才真正写入。
`xmin` = 插入这个版本的事务号，`xmax` = 删除/替换它的事务号。
UPDATE 的语义是「旧版本打 xmax + 插新版本」，**不原地改**（见 D2）。

**版本号由 exec/record 层负责，存储层不碰**：
堆表层只提供"写日志 + 改页"的原语，它不该假设 tuple 的格式。
存储层越界碰上层格式，单元测试（用裸记录）就会全挂 —— 这是 v0.6 踩过的。

### 3.2 索引 key 编码（一个容易翻车的细节）

B+tree 比较 key 用的是 `memcmp`，所以 **key 必须是"字节序 = 数值序"的编码**：

| 类型 | 编码 | 字节序 |
|---|---|---|
| 整数 | 定长二进制 | **大端**（否则 memcmp 结果错） |
| 浮点 | 符号位翻转 + 大端 | 同上 |
| 字符串 | 原字节 + `0x00` 转义 + `0x00 0x00` 终止符 | 按字节 |

**系统里同时存在两种字节序，必须记牢**：

- **页内元数据（偏移、长度、页号）→ 小端**，x86 友好，走 `put_u16/put_u32`。
- **索引 key → 大端**，保证 `memcmp` 等价于数值比较。

混淆这两者是"索引查不到数据"的经典原因，而且只在跨类型 key 时暴露。

#### 3.2.1 key 必须是复合键「值 ‖ RID」（v1.1 修的静默 bug）

**key 不只是列值，后面还要拼 8 字节大端的 RID。**

这条不是"为了多存点信息"，而是**一条不变式的必要条件**：

```
内部节点的不变式：左子树所有 key 严格小于 separator
```

叶子分裂时提升的 separator 是右页的最小 key，左页保留比它小的全部 key ——
**这条不变式只在 key 唯一时成立**。

如果 key 只有列值，同一列值的多行共用一个 key，
左页里就可能残留 `key[mid-1] == key[mid]` 的行 —— 不变式破了。
查找时 `descend` 用 `upper_bound`（第一个 sep > 查找键），
查找键恰好等于 separator 时会走到**右**子树，
左页里那些同值行**再也够不着**。

**症状：走索引的查询比全扫少行，而且不报任何错。**
（v1.1 的执行器基准第一次跑就撞上了：10 万行里 `val >= 900` 走索引返回 9999 行，
全扫返回 10000 行。）

带上 RID 之后 key 全局唯一，separator 严格落在左右两页之间，
不变式恒成立 —— **B+tree 本体一行都不用改**。

**文本为什么要加终止符**：复合键 = 值部分 ‖ RID。
如果值部分可能互为前缀（`"ab"` 是 `"abc"` 的前缀），
比较复合键时就会比较到 RID 字节去，顺序全乱。
终止符让"值部分"互不为前缀，比较一定在值部分里结束。

#### 3.2.2 key 编码有类型闸门：类型对不上就拒绝编码（v1.1 修的静默 bug）

**索引键按列的类型编码，但常量的类型来自字面量 —— 两者不一定一致。**

不一致时如果硬编码，读到的字段就是错的：

| 列的类型 | 常量的类型 | 硬编码的后果 |
|---|---|---|
| INT | TEXT `'5'` | 读 `v->i`（文本的 `i` 恒为 0）→ 边界编码成 0 → **漏掉真正的 5** |
| REAL | 整数 `5` | 读 `v->d`（整数的 `d` 恒为 0）→ 边界编码成 0.0 |
| TEXT | 整数 `5` | 读 `v->len`（整数的 `len` 恒为 0）→ 边界编码成空串 |

三种都是**静默漏行**（下推只是"少读一些行"，但少读就是数据错）。

所以 `index_key.c` 有一道**类型闸门**：常量的类型与列的类型不同族就
**拒绝编码**（返回 `E_NOTSUP`）→ 上层退回全表扫描。

> **慢一点，但绝不漏行** —— "多给行 = 慢；少给行 = 数据错"。

唯一的例外是 REAL 列配整数常量：比较语义本来就是"转成 double 再比"
（见 `val_cmp`），所以边界也转成 double —— **与比较语义完全一致** ✓

#### 3.2.3 值的比较：类型序（v1.1 修的静默 bug）

`val_cmp` 的比较规则（对齐 SQLite）：

| 情况 | 规则 |
|---|---|
| 任一边是 NULL | 结果为空（NULL 不参与比较） |
| 两边都是 TEXT | 按字节比（先比共同长度，再比长度） |
| **一边 TEXT 一边非 TEXT** | **按类型序**：文本 > 数值，**永不相等** |
| 任一边是 REAL | 按 double 比 |
| 其余 | 按 i64 比 |

**"一边 TEXT 一边非 TEXT"这条必须有**：
原来的代码落到"按数值比"分支去比 `a->i` 和 `b->i` ——
而文本值的 `i` 字段**恒为 0**（`val_text` 不碰它）。
结果 `WHERE int_col = '5'` 会把**值为 0 的行**判成相等。

那不是"文本等于 5"，那是"文本的垃圾字段等于 0" —— 静默给出错答案。

类型序（SQLite）：`NULL < 数值 < 文本 < 二进制`。

#### 3.2.4 写路径必须转换类型（v1.1 修的静默 bug）

**值的类型来自字面量，列的类型来自 CREATE TABLE —— 两者不一定一致。**

而记录编码（`val_to_record`）是**按列的类型重解释**的，所以写之前必须转换：

| 列的类型 | 值的类型 | 转换规则 |
|---|---|---|
| 数值列 | 整数 | 转成列的类型；**装不下就报错** |
| 数值列 | 实数 | 整数值的实数才能进整数列，否则报错 |
| 文本列 | 任意标量 | 转成文本（SQLite 的 TEXT 亲和性） |
| 布尔列 | 任意 | 非零即真 |

不转换的后果：`INT` 列插 5000000000 存成 **705032704**（截断）、
`REAL` 列插 5 存成 **0.0**、`TEXT` 列插 5 存成 **空串** ——
三种都是"看起来成功、其实数据错了"。

**装不下就报错**，不静默截断 ✓

### 3.3 页类型

| 值 | 类型 | 用途 |
|---|---|---|
| 0x01 | meta | 第 0 页，bootstrap：指向 catalog 根 |
| 0x02 | heap | 堆表数据页 |
| 0x03 | btree_inner | B+tree 内部节点 |
| 0x04 | btree_leaf | B+tree 叶子节点 |
| 0x05 | overflow | 大值分块链（关系模态，待做） |
| 0x06 | blob | blob 模态的帧页（v0.8） |

**blob 页的额外约定**：`H_FLAGS` 的 bit3（`BLOB_FLAG_HEAD`）标记「这是对象头页」。
头页和帧页的页类型都是 `PT_BLOB`，靠这个标志区分 ——
重启时扫全文件找带标志的页，就重建出了 blob 的对象目录。

## 4. 七个关键设计决策

### D1 · 堆表，不是聚簇索引

**选择**：B+tree 只存 `(key, RID)`，数据在独立的堆页里。

**为什么不选聚簇**：聚簇索引把行直接放在叶子节点里，范围扫描更快，但会让"回表"这个概念消失——而回表是理解二级索引、覆盖索引、索引选择率的起点。教学价值优先。

**代价**：范围扫描多一次 `heap_get`。可以接受。

---

### D2 · 更新 = 插新版本，RID 会变

**选择**：MVCC 更新不在原地改，而是插入新 tuple（新 slot），老 tuple 的 `xmax` 置为当前事务。索引需要插入新 RID 并标记旧 RID 为死。

**为什么不选原地更新**：原地改会让老快照读到新值，隔离级别是假的。代价是索引膨胀，靠 vacuum 回收。

**这条决策的连锁反应**：`heap_update` 的返回值必须包含新 RID，`index` 层要能处理"同一 key 多个 RID"（非唯一索引天然支持）。

---

### D3 · WAL 由上层写，pager 负责强制日志先落盘

**选择**：行级 undo-redo 日志，由 `heap.c` / `catalog.c` 在修改页之前 `wal_append`。pager 不写日志，只维护 `page_lsn`，但**在刷脏页前必须确保对应日志已落盘**。

**为什么不让 pager 自动写**：pager 不懂语义，只能记整页镜像（4KB/次），日志会膨胀 100 倍，而且讲不清 redo/undo 的分工。

**pager 的 WAL 钩子（v0.6 定稿）**：

```c
pager_set_wal_flush(pg, wal_flush_before_page, db);
```

刷页前调它；钩子自己去 `wal_fsync` 把日志刷下去。

**为什么做成"钩子"而不是"断言报错"**：断言版本一旦触发就是硬失败（数据库不可用）。
而钩子自己 fsync 只是慢一点，数据照样安全 —— **软降级优于硬失败**。

而且正常路径下这个钩子**永远不触发**：db 层每条语句结束都 fsync 日志，
脏页要到更晚（缓冲池逐出或 `db_close`）才被刷盘，那时日志早就在盘上了。

**代价**：每个修改路径都必须显式调 `wal_append`，漏一处就是崩溃丢数据。
缓解办法：把"先写日志再改页"封成一个宏 `MUTATE(pg, frame, code)`，让漏写变得困难。

---

### D3.1 · xid=0 是"系统事务"（v0.6 补）

**约定**：`xid == 0` 专门表示系统事务（catalog bootstrap、建表、写 meta 页），
**恢复时永远视为已提交**。

**为什么需要这条约定**：bootstrap 阶段还没有"用户事务"的概念，
日志里的 xid 是 0。如果恢复阶段按"有没有 COMMIT 记录"来判断，
bootstrap 的记录会被全部回滚 —— meta 页被回滚成初始值，
magic 归零，整个库打不开（`E_CORRUPT`）。

**教训**：隐含约定要升级成显式协议。与其让恢复阶段去猜"哪些记录是 bootstrap 的"，
不如在协议层面说清楚 xid=0 的含义。

**配套的两条安全网**：

| 场景 | 处理 |
|---|---|
| 数据文件是空的，但同名 WAL 有内容 | `wal_reset` 清空日志 —— 陈旧日志是孤儿 |
| 事务号跨会话 | `wal_max_xid()` 从日志读出最大 xid，作为新会话起点 |

第二条防的是更隐蔽的错：上次会话做到 xid=5 崩了，这次从 xid=1 开始，
恢复阶段会把上次那个未提交的 xid=1 判成已提交。

---

### D4 · 并发分三步走，不一步到位

| 版本 | 并发模型 | 目的 | 状态 |
|---|---|---|---|
| v0.1–v0.7 | 单线程 | 先把正确性做对，排除并发干扰 | ✅ |
| v0.8 | blob 模态 | 第二个模态，不涉及并发 | ✅ |
| v0.9 | SPI 定稿 + 接线 | 执行器模态无关 | ✅ |
| **v0.10** | **全局 latch（一把大锁）** | **引入临界区概念，跑通多线程不出错** | **✅** |
| **v1.2 步骤 1–2** | **copy-out + 按域 latch 框架** | **先把纪律立起来**：读接口不再返回内部指针；锁的**获取全序**与断言就位 | **✅** |
| **v1.2 步骤 3** | **catalog 域换成读写锁** | **第一个真正接上线的域**：公开 API 自己拿锁，内部走 `_locked`；大锁仍在 | **✅** |
| **v1.2 步骤 4a** | **txn 域自带保护** | 写路径域锁 + 读路径原子（clog 一 xid 一字节） | **✅** |
| **v1.2 步骤 4b** | **wal 域自带保护** | 每实例一把域锁：写路径与扫描路径持锁，读路径原子 | **✅** |
| **v1.2 步骤 4c** | **freelist + frame 域自带保护** | freelist：桶计数互斥 + 读路径也持锁；frame：**池级锁 + 每帧一把内容锁**（覆盖 get→unpin 的借用期）。⚠️ 同时**勘误了获取全序** | **✅** |
| v1.2 步骤 4d–7 | 大锁退役 + compact + checkpoint + 拆文件 | 拆掉大锁（4c 的缩小实验已证明可行：去掉大锁全套测试 58 PASS / 0 FAIL）；吞吐 ≥ 大锁 2× | 未做（v1.2 进行中） |

> 注：以上为**修正后的编号**。初版设计文档曾把并发模型提前到 v0.5/v0.6，实际执行时发现 WAL + 恢复的正确性问题（未提交事务回滚、xid 跨会话混淆）远比并发更难调，于是把并发整体后移，与 MVCC 一起做。
>
> **v0.7 的实际情况**：MVCC 的**语义**做完了（隔离级别、可见性、vacuum 全部有测试覆盖），
> 但**并发实现没做** —— 仍是单线程，多连接靠 `db_connect` 模拟。
> 理由：先把"谁能看到什么"测对，再测"并发下的实际表现"。
> 两个不确定叠加，调试成本会吃掉全部学习收益。

**为什么不一上来做细粒度**：并发 bug 只在特定时序暴露，而你同时还在调 B+tree 的分裂逻辑——两个不确定叠加，调试成本会吃掉全部学习收益。

**细粒度化的顺序（v1.2 步骤 1–4）**：**一次只动一件事**。

| 步骤 | 动什么 | 为什么是这个顺序 |
|---|---|---|
| 1 | copy-out（读接口改成拷出来） ✅ | 前提。没它，锁画细了也没用 —— 指针会悬空 |
| 2 | latch 框架（域编号 + 获取全序 + 断言） ✅ | 纪律先行。**不改任何调用点**，零行为变化 |
| 3 | 换 catalog 域（读写锁） ✅ | 先换元数据 —— 它最小、最容易验 |
| 4 | 换 txn（✅ 4a）/ wal（✅ 4b）/ freelist + frame（✅ 4c） | frame 放最后（每帧一把，量最大） |

**获取全序**（绝不逆序）：**`catalog(1) → txn(2) → frame(3) → wal(4) → freelist(5)`**。

⚠️ **v1.2 步骤 4c 勘误**：初版写的是 `catalog → txn → wal → freelist → frame`，
理由"写路径先 wal 后页"。**真实代码不是这样嵌套的** ——
WAL 钩子（`heap.c` 的 `wal_log`、`pager.c` 的 `flush_page`）与
`freelist_set(..., page_free_bytes(f->data))` 都是在**页还捏在手里**的时候调的，
所以**页比日志更外层**：真实的边是 **frame → wal** 与 **frame → freelist**。

计划那句"先 wal 后页"说的是**语义顺序**（日志必须先落盘才能刷页），
把它当成**锁的获取顺序**就错了 —— 语义顺序靠 WAL 规则保证（WAL 钩子 + page_lsn），
不靠锁顺序。反过来没有一条边：wal 锁里不会去碰页，freelist 锁里也不会去碰页。

实现按**获取序号**编号（`src/common/latch.h` 的 `LatchId`）。

**全序断言**：获取时检查"已持有的域的序号是否都比我小"，
违反 → **立刻 abort**。断言一直开（没有调试/发布之分）——
一个能抓到逆序的断言，不该在发布版里消失。

#### D4.1 · 锁画在哪：语句级大锁（v0.10 定稿）

v0.10 的问题不是"怎么加锁"，而是**"锁画在哪"**。三个候选：

| 候选 | 判决 |
|---|---|
| (a) 模块级临界区（pager / wal / txn 各加一次） | **否决** —— 前提是所有读接口改成返回拷贝（见 D4.2） |
| **(b) 语句级大锁（`db_exec` 全程持锁 + `db_blob_*` 各自持锁）** | **采纳** |
| (c) 只锁最热的两三处 | **否决** —— 竞态有 7 处，漏一处就静默损坏数据 |

```
db_exec(sql):
    latch_lock()
      解析 → 执行 → 结果构造
    latch_unlock()
```

| 性质 | 后果 |
|---|---|
| 锁覆盖整个语句 | 语句内所有共享状态访问都被保护，**不可能漏**（漏的只可能是"某状态没被任何语句碰到"） |
| 不在语句之间持锁 | 显式事务的多个语句之间不持锁 → MVCC 照常工作（RR 快照事务级、RC 语句级）✓ |
| 只有一把锁 | **不可能有锁顺序问题 → 不可能死锁**。细粒度化才重新引入这个问题 |
| 可重入 | 嵌套路径（`db_exec` → pager → WAL 钩子 → `wal_fsync`）不会自锁 |

#### D4.2 · 细粒度化的前置条件：读接口要 copy-out

**这是 v0.10 顺延下来的那一大块。v1.2 步骤 1 已完成（见 §D4.2.1）。**

当前的读接口返回的是**指向共享内存的指针**，不是拷贝：

```c
int catalog_table_cols(Catalog *cat, u32 table_id, const ColDesc **cols, int *ncols);
/* 返回的指针指向 catalog 内部的缓存 */

PageFrame *pager_get(Pager *pg, u32 pid);   /* 指向缓冲池里的页 */
db_blob_id  db_blob_id_at(DB *db, uint32_t i);/* 指向目录数组的元素 */
```

如果锁只覆盖 `catalog_table_cols` 这个函数本身，函数返回后锁就放了 ——
另一个线程这时 `CREATE TABLE`，catalog 扩容了列定义数组 →
**调用方手里的指针悬空** → 野指针。

> **要让模块级锁成立，所有读接口都得改成"拷出来"（copy-out）。**
> 这是接口层面的重构 —— 值得做，但不该和"引入锁"混在一起
> （两个不确定叠加，调试成本会吃掉全部学习收益）。
>
> PG 用 "MVCC + 每连接缓冲" 回避这个问题 —— 它的读路径本来就不共享页内存。

**所以这一版的纪律是**：新加一条读路径时，先问"它返回的是指针还是拷贝"。
返回指针的，暂时只能用语句级大锁保护。

##### D4.2.1 · copy-out 的实际边界（v1.2 步骤 1，勘误上文）

v0.10 说的是"**所有**读接口都得改成拷出来" —— **说宽了**。
逐个接口过堂之后的结论：

| 接口 | 处置 | 理由 |
|---|---|---|
| `catalog_table_meta` | **改 copy-out** | 返回 `&e->meta`，`e` 在 `cat->t` 数组里；建表时 `cat->t` 被 realloc → **真悬空** |
| `catalog_table_indexes` | **改 copy-out** | 返回 `e->idxs`，建索引时 realloc → **真悬空** |
| `catalog_table_cols` | **改 copy-out** | `e->cols` 是每表一份 malloc，**恰好**稳定 —— 但那是隐含前提（只有关库才 free），不是保证。统一成拷贝后契约没有例外 |
| `db_blob_id_at` | **不用改** | 它**按值返回** `BlobId`，本来就是拷贝。上文"指向目录数组的元素"是**写错了** |
| `pager_get` | **不改，靠 pin** | 页帧被 pin 住就不会被逐出 —— **pin 本身就是"逻辑引用"**，这是缓冲池设计的本意（PG 的 buffer pin 同款）。拷 4KB 页是灾难 |
| `db_graph_schema` / `db_graph_list_*` / `db_graph_hop*` | **不用改** | 本来就是拷贝出参（调用方给缓冲区 / 调用方 free） |
| SPI `am->columns` | **不改** | 模态给的是静态常量数组或实例级稳定的 schema；而且执行器现在会把它拷进自己的缓冲区 |

**准确的规则是**：copy-out 只针对**没有 pin 保护、且会随 catalog 变更而失效**的内部结构指针；
页数据有 pin 机制，本来就不需要拷。
细粒度化的真正工作量在"把 catalog 这类小结构改成拷贝语义"，
而**不是**把缓冲池的访问模式推倒重来。

**改完之后**：执行器的 `TableCtx` 里有一份**自持的副本**（列定义 + 索引列表），
`tc->cols` / `tc->idxs` 一律指向它 —— 于是"catalog 之后怎么变都与本次执行无关"，
细粒度锁才有立足点。验收见 `test/integration/test_copyout.c`（A2）。

#### D4.3 · 加锁点的纪律

| 纪律 | 说明 |
|---|---|
| **每条入口路径都要加锁** | blob 的 API 不走 `db_exec` —— 只锁 `db_exec` 等于 blob 裸奔 |
| **实例级共享状态才需要锁** | 连接的私有状态（当前 xid、快照）不需要 |
| **深度计数用线程本地** | "当前持锁深度"是每线程的状态，放共享对象就成了"连接 A 影响连接 B"（硬规则 5 的精神） |

#### D4.4 · catalog 域的读写锁（v1.2 步骤 3）

细粒度化的**第一个域**。catalog 是实例级共享的元数据，
读多写少（只有建表 / 建索引 / 改统计才写）→ **读写锁**，读读不互斥。

**锁画在哪一层**：**公开 API 自己拿锁**（`src/catalog/catalog_lock.c`），
内部实现一律走 `_locked` 版本：

```
catalog_table_cols(cat, tid, buf, cap, ncols):
    catalog_read_lock(cat)
      → catalog_table_cols_locked(...)      /* catalog.c 实现 */
    catalog_read_unlock(cat)
```

| 为什么这么拆 | 说明 |
|---|---|
| **单一出口** | 每个公开 API 只有一处 lock/unlock —— 加锁写在函数体内的话，多一个 `return` 就漏一次解锁 |
| **不递归取锁** | 内部函数互调走 `_locked`；POSIX 规定重复取读锁是未定义行为，有写者在等时会死锁，重复取写锁直接自锁 |

调用方**不要**自己拿锁 —— 拿两次就是递归取读写锁。

**三条使用纪律**（违反 → 打印 + `abort()`）：

| 纪律 | 为什么 |
|---|---|
| 读锁**可重入** | POSIX 明文禁止"重复取读锁"；实现上用线程本地计数，只有第一次才碰底层 rwlock |
| 写锁**不可重入** | 重复取写锁 = 自锁 |
| **不许升级 / 降级** | 读写锁的升级没有正确实现方式（读者一多就死锁） |

持锁状态存在**线程本地**的槽位表里（`_Thread_local`）——
"我持有什么锁"是当前线程的属性，不是共享状态。槽位**会回收**
（释放后可以给别的 catalog 实例用），否则一个线程先后开 4 个库就再也拿不到槽位。

取锁的同时向 latch 框架**记账**（`LATCH_CATALOG`，序号 1 = 全序最前），
于是"catalog 必须排在 txn / wal / freelist / frame 之前"是**机器检查**的。

**边界（别越读）**：catalog 锁只保护 catalog **内部结构**。
它指向的对象（`Heap*`、`BTree*`）的内部状态由别的域保护 ——
在步骤 4 之前，那些域仍然靠 `db_exec` 的大锁兜着。

**验收**：`test/unit/test_catalog_lock.c`（7 项）+ `test/integration/test_copyout.c`（A2 第 3 项）。
验证性缩小实验（临时去掉大锁）的结论：**catalog 域已能独立站住**，
暴露出来的竞态在 txn / heap / pager / WAL 域 —— 步骤 4 的活。

#### D4.5 · txn 域：写路径持锁，读路径走原子（v1.2 步骤 4a）

txn 域保护三样东西：`next_xid`、`clog`、活跃表。

| 路径 | 手段 | 为什么 |
|---|---|---|
| **写**（xid 分配 / 活跃表增删 / clog 写入） | 域内互斥锁 | 分配 xid 要"找空槽 + 占住它"，两个线程可能看上同一个槽 → 必须互斥 |
| **读**（clog 状态 / 活跃表查询） | **原子读，一把锁都不取** | 可见性判断**每读一行就要查一次 clog** —— 这是整个内核最热的读路径。每次取锁会让 10 万行的扫描多花几毫秒，A9 门槛（≥3×）会破 |

**clog 从"2bit 打包"改成"一 xid 一字节"**（4 KB）：不是为了内存（只多 3 KB），
是为了**并发** —— 2bit 打包时 clog 的写入是"读-改-写一个字节"，
两个线程改同一字节里**不同的 xid** 会互相覆盖 → 提交状态丢失 →
"已提交的数据读不出来"。一 xid 一字节之后，写入变成纯 store，原子操作不会丢更新。

**发布顺序**：分配 xid 时**先**重置 clog 槽位（环形窗口会复用槽位，
里面可能留着老事务的"已提交"），**再**发布 `next_xid` —— 反过来就是脏读。

**锁的粒度**：域锁是**进程级**的一把锁，不是每实例一把。
一个进程同时开两个库的情况极少，而进程级锁换来
"不需要 init/destroy、不需要改任何调用点"（`TxnTable` 在测试里是栈上对象）。

**验收**：`test/unit/test_txn_domain.c`（4 项）——
xid 唯一性 / 槽位复用不产生脏读 / 并发读 20 万次无脏读 / 活跃表上限。
**这个测试是真的会红的**：把域锁临时去掉，第 1 项立刻报"xid 重复 6 个"。

#### D4.6 · wal 域：它保护的不是内存，是**日志文件本身**（v1.2 步骤 4b）

catalog 域保护元数据，txn 域保护事务表 —— 出了错是"读到脏数据"。
wal 域不一样：`wal_append_xid` 里这三步必须是一个整体：

```
    lsn = last_lsn + 1;      ← 取号
    FSEEK(f, 0, SEEK_END);   ← 定位到文件尾
    fwrite(b, 1, n, f);      ← 写一条记录
```

两个线程同时进来：

| 后果 | 严重性 |
|---|---|
| 取到**同一个 LSN** | 恢复时日志顺序错乱（LSN 是 page_lsn / undo 链的排序依据） |
| 各自 fseek 到尾再 fwrite → **字节交错** | 半条 A、半条 B → CRC 失败 → 恢复**截断** → 截断点之后**所有**记录作废 |

第二条尤其致命：**一次并发写日志的竞态能废掉整段日志**，
而且没有报错、没有崩溃 —— 只是"数据不见了"。

| 路径 | 手段 | 为什么 |
|---|---|---|
| **写**（append / fsync / reset） | wal 域的互斥锁 | 取号 → 定位 → 写必须独占；`fsync` 也要独占（同一 `FILE*` 不能并发 fsync） |
| **扫描**（scan / read_payload） | **同一把**域锁 | 扫描与 append 争同一个 `FILE*` 和同一个 `scratch` 缓冲，不加锁会读到"写了一半"的记录 |
| **读**（last_lsn / nrecords / max_xid / flushed_lsn） | **原子读，一把锁都不取** | 热路径（每条语句结束都查 `flushed_lsn`） |

**锁的粒度**：**每实例一把**（`struct Wal` 里的 `pthread_mutex_t mu`），**不是进程级** ——
与 txn 域不同，理由有三：

1. WAL 是**实例级**资源（一个库一个日志文件），不同库之间没有任何共享状态，
   进程级锁会让不相关的库互相阻塞。
2. `Wal` 的生命周期完全由 `wal_open` / `wal_close` 管住 → **不需要改任何调用点**。
3. `wal_reset` 会**重开文件**，进程级锁下这个"重开"会牵扯到别的实例。

**发布顺序**：`last_lsn` 必须在 `fwrite` 成功**之后**才发布 ——
反过来读者会看到"已分配但没落盘"的 LSN，刷页时会误判"日志已落盘"。

**验收**：`test/unit/test_wal_domain.c`（4 项）——
LSN 唯一且连续 / 日志文件一条不差地扫回来 / append 与 fsync 混跑时计数器单调不减 /
undo 链按 xid 独立。
**这个测试是真的会红的**：拿上一步的 `wal.c` 跑同一个测试，
立刻报"LSN 重复 2087 个、2400 条只扫回 125 条"。

⚠️ **给步骤 4c 的约束（已作废，见 D4.7 的勘误）**：原文写的是
"刷页前要调 WAL flush 钩子，那时若已握着 frame 域的锁，
就是 frame(5) → wal(3) **逆序** → 全序断言 abort；
刷页路径必须**先落日志、再取 frame 锁**"。

**作废理由**：真实的嵌套边是 **frame → wal**（钩子就是在页被捏住时调的），
所以**持 frame 锁调 WAL 钩子恰恰是对的**。
WAL 规则要求"日志先落盘、页后落盘"，钩子必须在刷页的那一刻被调 ——
"先落日志再取 frame 锁"反而会让钩子与被刷的页脱钩。
要避免的是**反过来**（持 wal 锁去取 frame 锁）。

#### D4.7 · freelist 域 + frame 域：两个"派生数据"域（v1.2 步骤 4c）

这两个域有个共同点：**它们保护的都不是"权威数据"，而是派生数据**。

| 域 | 保护的 | 权威在哪儿 |
|---|---|---|
| freelist | 每页的剩余空间档位 + 每档有多少页 | **页本身**（`page_free_bytes(f->data)`）—— 档位是可以重建的派生量 |
| frame | 一帧的**页内容** + 池子的账本（哈希表 / Clock 手 / pin_count） | **文件**（页刷盘后才是权威） |

派生数据一旦和权威对不上，后果不是"读到旧值"，而是**更糟的东西**：

- freelist 的桶计数丢了更新 → `find` 返回**已经被别人占满的页** →
  调用方往里塞数据 → **页内 slot 目录被并发写坏** → 那一页的数据全丢。
- frame 的内容锁缺了 → 两个线程同时改一页 → **页内容被撕裂**（不是少一行，是张冠李戴）。

#### freelist 域：写路径的读-改-写，读路径的 `realloc`

`freelist_set` 做的是两个共享计数器的"读-改-写"：

```
    if (bucket[old]) bucket[old]--;
    bucket[new]++;
    levels[page_id] = new;
```

两个线程改的是**不同的页**，但很可能命中**同一个桶**（桶按档位分，不按页分）。
没有锁时两次 `bucket[old]--` 互相覆盖 → 桶计数比实际档位少 →
**`find` 会返回已经满了的页**。

⚠️ **读路径也必须持锁**（这是本步的实测修正）：
`freelist_grow` 用 `realloc` 扩 `levels[]` —— **指针会变**。
读者缓存了旧指针，扩容之后就是**悬空指针**。
所以 freelist 域的**所有**公开函数（`level` / `find` / `npages` / `count_at`）都持锁。

#### frame 域：两把锁，各管各的

| 锁 | 管什么 | 特点 |
|---|---|---|
| 池级锁 `pg->mu` | 哈希表（page_id → 帧下标）、Clock 手、`pin_count`、`npages` | 普通互斥量 |
| 内容锁 `pg->latches[i]` | **一帧的页内容** | **递归**互斥量 |

**内容锁覆盖 get → unpin 的整个借用期**：
从 `pager_get` 拿到帧到 `pager_unpin` 归还，这期间页的内容是**借给调用方**的。
这段时间里如果另一线程把这一帧逐出并载入了别的页，
调用方手里的指针就指向了**别的页的内容** —— 写进去的数据张冠李戴，且无报错。

**内容锁必须是递归的**：同一线程可能对同一页 `get` 两次
（B+tree 先取父页再取子页，中间又回头看一眼父页）——
不可重入的锁会自己把自己锁死。

**公开 API 一个字没改**（`pager_get` / `pager_unpin` 的签名、语义全不变），
所以 242 处调用点零改动 —— 这正是"锁画在模块内部"的红利。

#### 死锁怎么排除：一条不变式

> **持有内容锁 ⇒ 该帧的 `pin_count` ≥ 1**

由它推出两条：

1. `pin_count == 0` 的帧，**内容锁一定是空的**
   → 逐出路径（持池级锁 → 取受害者内容锁）**不会阻塞**在内容锁上
   → 不存在"池级锁等内容锁、内容锁持有者等池级锁"的环
2. 逐出路径只挑 `pin_count == 0` 的帧（Clock 的规矩），
   所以内容锁的持有者不可能是"正在被逐出的那一帧"

配套的顺序纪律：**任何等待池级锁的路径都不持有内容锁**。
唯一的例外是 `unpin`，它的顺序是
"查表（池级锁）→ **放内容锁** → 减 pin_count（池级锁）"——
它在等池级锁时**还没持有内容锁** ✓。

- `test/unit/test_freelist_domain.c`（4 项）：桶计数守恒（三个不变量）/

- `test/unit/test_frame_domain.c`（5 项）：同一页并发读-改-写不丢更新 /
  内容锁互斥 / pin-unpin 配对（含同线程重复 get）/ WAL 钩子在 frame 域内 / 逐出不串页。

**这两个测试是真的会红的**（把锁去掉再跑同一个测试）：

| **全套 `sh test/run.sh`** | — | ✅ **58 PASS / 0 FAIL** |

步骤 4b 留下的那批失败（heap 的 slot 分配 + pager 的 pin/unpin）
正是 frame + freelist 域要治的病。

⚠️ **"测试全绿"不等于"没有竞态"**：测试是抽样，竞态是概率事件。
能说的是"已知的失败面已经消失，且两个域各自有直接压它的单元测试
（不经过 `db_exec`）"。真正的"没有竞态"要靠步骤 7 的**反向验证**补。

### D5 · 隔离级别做 RC 和 RR，不做 SSI

**选择**：v0.7 做 RC（语句级快照）和 RR（事务级快照），不做可串行化。

> 注：初版文档写的是「v0.5 / v0.6 做 RR」，随实际执行顺序后移一位（WAL 占了 v0.6，MVCC 顺延到 v0.7），
> 实际执行时又补上了 RC —— 两种级别必须都在，才能看出差别。

**默认 RC**（对齐 PG）。用户要 RR 必须显式声明：

```sql
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
-- 这里的快照在事务开始时固定，之后不刷新
```

**RC 和 RR 的差别只有一处**：快照什么时候建。

| | 快照建立时机 | 效果 |
|---|---|---|
| RC | 每条语句开始时重建 | 能看到别人刚提交的 |
| RR | 事务开始时建一次，整个事务复用 | 事务开始后提交的，始终看不见 |

**可见性判断逻辑完全一样**（同一套 `mvcc_visible`）。
这就是快照隔离最优雅的地方：**隔离级别不是两套机制，
而是同一个机制的两种"快照刷新时机"**。

**为什么不做可串行化**：SSI 需要读写依赖图 + 冲突检测，单独 6 个月，而且对理解 MVCC 基础没有增量。

**代价**：写偏斜（write skew）在 RR 下仍可能发生。这个"缺陷"本身是很好的教学点——你会真正理解"快照隔离不是可串行化"。

---

### D8 · 实例与连接分离（v0.7 补）

**选择**：`DbInstance`（共享）+ `DB`（连接私有），对齐 PG 的 postmaster/backend 模型。

| | 共享 | 私有 |
|---|---|---|
| 实例 | 缓冲池 / catalog / WAL 文件 / 事务表（全局 xid 分配 + clog） | — |
| 连接 | — | 当前 xid / 当前快照 / 事务状态 / 隔离级别 / 错误信息 |

**为什么必须拆**：v0.6 之前一个 `DB` 句柄 = 一个连接 = 一套缓冲池 + 一份 catalog。
看起来"能开两个句柄连同一个库"，其实是**两个完全独立的数据库**：
各自有缓冲池、各自加载了 catalog 副本、各自维护 freelist。
A 建的表 B 看不见，A 写的页 B 也看不见。

这不是 bug，是架构的必然边界。**MVCC 的意义恰恰是
"多个连接看到同一个库的不同时间点"**，所以必须有一个共享实例。

**事务表必须共享，事务状态必须私有**：
xid 必须全局唯一（否则两个连接分配出相同的 xid，可见性判断立刻失效），
但每个连接的快照和事务状态是它自己的。

**这个改动是被测试逼出来的**：最初用 `db_open(path)` 开两个句柄模拟两个连接，
结果读方看不到写方建的表（SELECT 报"表不存在"）。
所以才加了 `db_connect`。

---

### D9 · xid 必须显式传，不能放共享对象里（v0.7 补）

**选择**：所有写路径的接口都带 `u32 xid` 参数，**没有任何"设置当前 xid"的 API**。

```c
/* 错：共享状态 */
wal_set_xid(w, xid);            /* 已删除 */
heap_set_xid(h, xid);           /* 已删除 */
catalog_set_xid(cat, xid);      /* 已删除 */

/* 对：显式传 */
wal_append_xid(w, type, xid, page_id, slot, slot_off, before, blen, after, alen);
heap_insert(h, xid, rec, len, &rid);
catalog_create_table(cat, xid, name, cols, ncols, &tid);
```

**为什么**：WAL / catalog / heap 都是**实例级共享**的。

```
连接 A：wal_set_xid(w, 5)
连接 B：wal_set_xid(w, 6)      ← 覆盖了 A 的设置
连接 A 写数据 → 日志记录的 xid 是 6，不是 5
```

后果：恢复阶段分析"哪些事务提交了"时，A 的记录被算到 B 名下 ——
**未提交的数据被判定为已提交**。这是静默的数据损坏。

**推广成一条铁律**：**任何"当前是谁"的信息都不能藏在共享对象里**。
共享的对象必须让调用方显式传参。

**undo 链（prev_lsn）同理**：它也是 WAL 上的共享状态，多连接下会串。
v0.7 的处理是按 xid 分槽维护（`PrevSlot prev[64]`），
每个事务的 undo 链独立。

---

### D10 · clog 而不是 commit counter（v0.7 补）

**选择**：每个 xid 存 2 bit 状态（0=进行中 / 1=已提交 / 2=已中止），环形窗口 4096 槽。

**为什么不用 commit counter**（"快照时已提交的最大 xid"）：
commit counter 表达的是"**现在**的最大已提交 xid"，
而快照需要的是"**快照那一刻**的提交状态"。两者不是一回事。

```
时刻 1：事务 A (xid=5) 开始
时刻 2：事务 B (xid=6) 开始并提交 → committed_xmax = 6
时刻 3：建立快照 → snap_xmax = 6
时刻 4：事务 A 提交 → committed_xmax 仍是 6
```

快照里的 `snap_xmax` 是时刻 3 的值 = 6。A 的 xid = 5 <= 6，
于是快照认为"A 在快照建立前就提交了" —— **错**，这是脏读。

**窗口化**：40 亿个 xid 各存 2 bit 要 1GB 内存，太奢侈。
实际上只有"最近"的 xid 才有查询价值（更老的要么提交要么中止，
中止的版本会被 vacuum 清掉）。所以只保留最近 4096 个，
窗口外一律按"已提交"处理 —— 安全的，因为要走出窗口，
说明中间已经过去 4096 个事务。

### D6 · 单文件 + 独立 WAL 文件

```
mydb.db       数据页（4KB 对齐）
mydb.db-wal   日志（追加写）
```

**为什么不用多文件表空间**：备份、迁移、调试都简单（`cp` 就能带走）。符合 SQLite 心智，出错时用十六进制编辑器就能看。

**代价**：单文件在大数据量下扩展性差。接受，这是学习项目。

---

### D7 · 元数据存成普通表

**选择**：catalog（表、列、索引的元信息）就是一张普通表，用同一套 heap + btree 存取。第 0 页只存一个 bootstrap 指针指向 catalog 根页。

**为什么不引入专门的元数据格式**：两种持久化机制 = 两套崩溃恢复路径 = 双倍 bug。用同一套机制，恢复逻辑只写一遍。

### 5.1 Storage AM —— 数据的物理组织（v0.9 定稿）

```c
/* src/spi/storage_am.h */
typedef struct StorageAM StorageAM;
typedef struct AmScan    AmScan;

/* 能力位。能力协商靠返回值，不靠类型判断 */
#define AM_CAP_SCAN     0x01u
#define AM_CAP_INSERT   0x02u
#define AM_CAP_UPDATE   0x04u
#define AM_CAP_REMOVE   0x08u
#define AM_CAP_EXTERNAL 0x10u   /* 支持外部值（大值不进值层） */
#define AM_CAP_PUSHDOWN 0x20u
#define AM_CAP_VACUUM   0x40u
#define AM_CAP_INDEX    0x80u

/* 可见性上下文：调用方显式传，不存在 AM 里（硬规则 5） */
typedef struct {
    const Snapshot *snap;      /* 当前连接的快照 */
    const TxnTable *txns;      /* 实例共享的事务表（clog 在里面） */
} AmVisCtx;

struct StorageAM {
    const char *name;          /* "heap" / "blob" / 将来的 "graph" / "vector" */
    u32         caps;

    /* schema：模态自己的列定义 */
    int  (*columns)(StorageAM *am, const ColDesc **cols, int *ncols);

    /* 扫描 */
    int  (*scan_begin)(StorageAM *am, AmScan **out);
    int  (*scan_next)(StorageAM *am, AmScan *s, Rid *rid, u8 *buf, u16 cap, u16 *len);
    int  (*scan_end)(StorageAM *am, AmScan *s);

    /* 按 RID 取一行 */
    int  (*get)(StorageAM *am, Rid rid, u8 *buf, u16 cap, u16 *len);

    /* 模态自己的字节串 → 值 */
    int  (*decode)(StorageAM *am, const u8 *buf, u16 len, DbValue *out);

    /* 这一行对当前快照可见吗 */
    bool (*visible)(StorageAM *am, const u8 *buf, u16 len, const AmVisCtx *vis);

    /* 写路径。xid 必须显式传（硬规则 5） */
    int  (*insert)(StorageAM *am, u32 xid, const DbValue *vals, Rid *out);
    int  (*update)(StorageAM *am, u32 xid, Rid rid, const DbValue *vals, Rid *new_rid);
    int  (*remove)(StorageAM *am, u32 xid, Rid rid);

    /* 版本回收（VACUUM）。没有版本的模态返回 E_NOTSUP */
    int  (*vacuum)(StorageAM *am, TxnTable *txns, u32 xid, AmVacuumStats *out);

    /* 重建索引。index_id = 0 表示全部索引 */
    int  (*reindex)(StorageAM *am, u32 index_id, u64 *rows_out);

    void *impl;                /* 模态私有状态 */

    /* 谓词下推（见 §5.3） */
    CanPushFn can_push;
    PushFn    push;
};
```

#### §5.1 的草图漏掉了五件事（v0.9 补齐）

这一版的首要产出不是"blob 能被查"，而是**"SPI 的设计对不对"**。
DESIGN.md §7 早就写明：*SPI 设计错了，v0.9 会立刻暴露，此时改动成本还小。*

对照执行器实际需要的东西，草图漏了五处：

| # | 漏了什么 | 不补会怎样 |
|---|---|---|
| 1 | **schema 访问器** | 绑定期没有列定义可对（列名 → 列号） |
| 2 | **解码回调** | 模态的字节串不是列式记录，执行器不能自己解 —— 只能硬套 record 格式，把所有模态逼成关系模态 |
| 3 | **可见性归属** | 每种模态的版本语义不同（heap 有 xmin/xmax，blob 没有版本）。统一到执行器 = 执行器要知道所有模态的内部结构 |
| 4 | **能力协商** | blob 只读、B+tree 没有 KNN。靠类型判断的话，加第 9 个模态就要改执行器 |
| 5 | **写路径的 xid** | 又要把 xid 藏进共享对象 —— **v0.7 付过血泪代价的那类错误** |

第 5 条尤其关键：SPI 是**所有模态写路径的入口**。
如果它不强制传 xid，这个错误会在每个模态里重犯一遍。

#### 关键约束：RID 是所有模态的统一寻址方式

图模态的"节点 id"要映射成 `(page_id, slot)` —— 定长记录天然满足（`slot = 记录序号`）。
这条约束保证了不同模态的数据能被同一个执行器扫描。

**RID 的空间是表内的**：每张表有自己的 RID 空间，
`blob_frames` 和 `blob_objects` 的 RID 互不相干，也不该互相比较。

#### 行的表示：字节串 + 模态自己的解码

`scan_next` / `get` 返回的是**模态自己的字节串**，不是列式记录。
关系模态返回 tuple 格式的记录；blob 模态返回它自己的行格式。

为什么不统一成一种字节格式：那种格式就是关系模态的格式 ——
强行统一等于逼所有模态都长成关系模态，那就不叫多模态了。
执行器要拿值，就调 `decode` —— **由模态自己解**。

#### 值类型为什么在 storage/

`DbValue` 从 `query/` 挪到了 `storage/`（L1）：
它是存储层、查询层、SPI 三方共用的契约语言。
放在 query/ 会让 spi/ 反过来依赖 query/，层次就倒了。

### 5.2 Index AM —— 加速结构（v0.9 定稿）

```c
/* src/spi/index_am.h */
typedef struct IndexAM     IndexAM;
typedef struct IndexCursor IndexCursor;

struct IndexAM {
    const char *name;          /* "btree" / 将来的 "hnsw" / "inverted" */
    u32         caps;

    int  (*insert)(IndexAM *am, const u8 *key, u16 klen, Rid rid);
    int  (*remove)(IndexAM *am, const u8 *key, u16 klen, Rid rid);
    int  (*search)(IndexAM *am, const u8 *key, u16 klen, Rid *out, int max, int *n);
    int  (*range)(IndexAM *am,
                  const u8 *lo, u16 llen, bool lo_inc,
                  const u8 *hi, u16 hlen, bool hi_inc,
                  IndexCursor **out);
    int  (*cursor_next)(IndexAM *am, IndexCursor *c, Rid *rid);
    int  (*cursor_end)(IndexAM *am, IndexCursor *c);
    int  (*knn)(IndexAM *am, const u8 *probe, u16 plen,
                int k, Rid *out, float *dist, int *n);
    void *impl;
};
```

**和草图的两处调整：**

1. **去掉 `create`**。索引的创建要写元数据（catalog），那是 catalog 层的事。
2. **写接口不带 xid**。因为**索引不写日志**（v0.6 的决定：索引崩溃后重建）。
   索引里没有"属于哪个事务"的概念，自然不需要 xid。

**`knn` 是给向量/地理留的口子**：B+tree 返回 `E_NOTSUP`，
优化器看到 `E_NOTSUP` 就退回全表扫描 ——
**能力协商靠返回值，不靠类型判断**。

**范围扫描返回的是候选行，不是精确结果**：
B+tree 只支持闭区间，开区间由适配层返回超集。
超集是安全的（调用方重新过滤），子集是危险的（静默丢数据）。

### 5.3 Pushdown —— 谓词下推（v0.9 定稿）

```c
/* src/spi/pushdown.h */
#define PD_EQ   '='
#define PD_LT   '<'
#define PD_GT   '>'
#define PD_LE   'L'
#define PD_GE   'G'
#define PD_NE   'N'

typedef struct {
    int     col_idx;       /* 列号 */
    int     op;            /* PD_* */
    DbValue val;           /* 比较的常量 */
} Predicate;

typedef int (*CanPushFn)(StorageAM *am, const Predicate *p);
typedef int (*PushFn)(StorageAM *am, const Predicate *p, AmScan **out);
```

**为什么需要它**：向量检索的"过滤 + ANN"是同一件事的两面。
前过滤让索引失效，后过滤召回不足。
真正管用的做法是把过滤吸收进索引 —— 而"哪些过滤能吸收"只有模态自己知道。

**下推的结果是一个行源，和全表扫描同构**：
都是"给我下一行的 (rid, 字节串)"。
于是执行器只有一种取行路径，**不需要为下推新增算子类型**。

**下推不改变正确性**：执行器拿到行之后**仍然完整求值一遍 WHERE**。
下推只是"少读一些行"，不是"替你判断"。
于是下推实现错了**最多是慢，不会是错** —— 除非它漏行。
所以下推的实现必须**保守**：宁可多给行，不能少给。

**谁决定能不能下推**：`can_push` 由**模态**回答。
执行器不知道哪些列有索引、不知道 blob 能不能按属性过滤 ——
它只负责把表达式翻译成 `Predicate`。

#### 5.3.1 下推的两层决策：能力 + 代价（v1.1 步骤 4）

v0.9 把索引选择下沉到 AM，`can_push` 回答的是**能力**问题：
"这个谓词，你的结构支持吗？"

但"能不能"不等于"值不值"。一张 10 行的表走索引要多跳几层树，
而整张表可能就待在一个页里 —— **全扫更快**。

所以 v1.1 在 `can_push` 之外加了第二层：**代价**。

```
门槛：can_push（模态回答）  —— 能力，不是代价
排序：cost_idx vs cost_seq（执行器算）—— 代价，不是能力
```

两层都要过：

| 情形 | 后果 |
|---|---|
| 只有门槛，没有代价 | 10 行的小表也走索引（比全扫还慢） |
| 只有代价，没有门槛 | 对不支持的模态瞎指挥 |

**统计从哪来**：只用 `nrows_est`（catalog 的 `sys_table` 里那一列）。
它是**估算值**，由写路径增量维护（O(1) 改内存）、VACUUM 校准并落盘 ——
与 PostgreSQL 的 `pg_class.reltuples` 同一策略。

**虚拟表不参与代价决策**：模态表没有 catalog 行，也就没有 `nrows_est`。
它们的 `push` 是模态自己的优化 —— 执行器拿不到行数就退回
"can_push 就推"的老行为，**不替模态算账**。

**EXPLAIN 与执行共用同一个决策函数**（`plan_push`）。
分开写迟早分叉，那时 EXPLAIN 说"走索引"、实际走了全扫，用户就再也不信它了。

**为什么叫"规则 CBO"**：一个 `nrows_est` 撑不起真代价模型
（没有列统计、没有直方图、没有相关性、没有页数）。
本版的目标只是**把"代价"这个概念引进决策** ——
公式（`src/query/exec_cost.c`）是可替换的骨架，将来加统计信息时只换公式，不动框架。

### 5.4 第一个模态：blob（v0.8 落地，v0.9 接进 SQL）

> **其余七个模态的对应内容在 `MODALITIES.md`**：图 §4 / 向量 §5 / 全文 §6 /
> 空间 §7 / 时序 §8 / 文档 JSON §9。那里有每个模态的完整落地设计、
> 事务语义归类、以及各自的关键坑清单。
> 下面这一节是**样板** —— 后面六个模态都照它的结构写。

blob 是**独立的大对象存储**：一个对象切成等长的帧，
读第 N 帧的 IO 量 ≈ 一帧（4KB），**与对象大小、帧号都无关**。

对标业界：S3/MinIO 的对象存储、MongoDB GridFS、Parquet/Lance 的分块文件。

#### 为什么它是独立模态，不是关系模态的大字段类型

| | 关系模态 | blob 模态 |
|---|---|---|
| 寻址 | RID (page, slot) | blob_id（页号 + 1） |
| 页类型 | `PT_HEAP` | `PT_BLOB` |
| 页归属 | 表的 freelist | blob 模块自己管 |
| 版本 | xmin / xmax | **无**（对象不可变） |
| 可见性 | MVCC 快照判断 | **无**（恒可见） |
| 删除 | 打 xmax + vacuum 回收 | v0.8 只增不减 |
| WAL | 行级日志 | 整页镜像（复用 `WAL_PAGEDATA`） |
| 目录 | catalog（4 张系统表） | blob 自己的目录（扫全文件重建） |
| 写能力 | 可写 | **只读**（对象不可变，SQL 侧返回 `E_NOTSUP`） |

**共享的底座**：pager（缓冲池）、WAL（崩溃安全）、
页格式（20B 页头 + crc16）、`LOG_PAGEDATA` 日志类型。

**这是 SPI 存在的意义**：模态是并列的，各自有物理组织，但共享底座。

#### 三个关键设计

**1. 帧号 → 页号用纯算术**

对象一次写完（不可变），页连续分配，所以
`第 N 帧 → 页号 base_page + N`。读一帧 = 1 次页读（+ 头页，可缓存）。

索引块的数据结构照样建了（为"页不连续"的未来留接口），
但快路径绕开了它 —— **为扩展留好接口，但不提前付代价**。

**2. blob 页不进任何表的 freelist**

表的 freelist 回答"哪一页能放下 N 字节的行"；
blob 页是"一整页装一帧"。语义不同，混用会写坏数据。

**3. blob 有自己的目录，不依赖 catalog**

`catalog` 是关系模态的元数据。blob 依赖它 = **模态之间互相依赖**，
这正是 SPI 明确禁止的。所以 blob 自己记目录，重启时扫全文件重建。

#### 一个容易搞错的错误码

页号空间是**共享**的 —— 关系模态的页也占页号。
而 `blob_id = 页号 + 1`，所以 `blob_id = 1` 可能指向**任何页**。

| 情况 | 错误码 | 为什么 |
|---|---|---|
| id 指向的页不是 blob 头页 | `E_NOTFOUND` | 「这不是 blob 对象」是正常情况 |
| 是 blob 头页但 magic/crc 不对 | `E_CORRUPT` | 真的是数据坏了 |

**返回 CORRUPT 会把用户误用说成"库坏了"，把排查方向带偏。**

#### blob 的事务语义

**不参与事务，WAL 的 xid 传 0（系统事务）。**

对象不可变（创建 → 写 → 定稿）⇒ 没有"回滚到旧版本"，
没有并发写同一对象的问题。但它**写 WAL**，所以崩溃后数据不丢。

xid=0 在恢复时视为"永远已提交" —— 正是我们要的：
blob 页写完的瞬间就是最终状态。

> 将来若支持"多段上传、最后合并"，就需要给它真正的 xid，
> 让未完成的对象在恢复时被清理。

### 5.5 blob 的行模型：帧才是行（v0.9）

**问题**：blob 是字节流，没有"行"。SPI 的 RID 模型要求"一行 = 一个可寻址的东西"。

| 候选 | 判决 |
|---|---|
| (a) 一行 = 一个对象 | 只看得到元信息；对象内部的帧**无法被寻址**（RID 指不到具体内容） |
| (b) 一行 = 一帧 | **采纳**：帧是 blob 唯一的可寻址单位；粒度也和别的模态对齐 |
| (c) 一行 = 一段变长字节 | 行没有稳定身份 → **RID 表达不了**，SPI 的核心约束直接崩 |

**为什么"帧"是对的**：

1. 帧是 blob 唯一的"可寻址单位"。对象是帧的集合，
   RID 要能定位到最小可读单位 —— 那就是帧。
2. **粒度对齐**：图模态的一行 = 一个节点，向量模态的一行 = 一个向量，
   blob 的一行 = 一帧。三个模态的行粒度都是**该模态的最小可寻址单元**。
   这正是 SPI 要求的统一，而不是"都长得像关系表"。
3. **可组合**：帧行带着 blob_id，就能定位回对象。

**RID 怎么定**：

```
blob_frames 的 RID = (页号 = base_page + frame_no, slot = 0)
blob_objects 的 RID = (头页页号 = blob_id - 1, slot = 0)
```

`slot` 恒为 0：一帧独占一页，一页一行 ——
和 §5.1 说的"定长记录天然满足 slot = 记录序号"是同一回事。

**RID → 行的反解**（已知限制）：遍历 blob 自己的对象目录，
找帧页区间包含该页的对象。代价 O(对象数)。
将来的修法是 blob 自己维护一张"页号 → 对象"的反查表。
注意这里用的是 **blob 自己的目录**，不是 catalog —— 模态之间不许互相依赖。

#### 两张虚拟表，不是一张

| 表 | 一行 = | 列 |
|---|---|---|
| `blob_frames` | 一帧 | blob_id / frame_no / data_len / data_off / data |
| `blob_objects` | 一个对象 | blob_id / nframes / frame_size / total_len |

为什么两张：对象级元信息（帧数 / 帧大小 / 总长）放在帧表里是**每行冗余一遍**。
一张表要么冗余要么缺。两张表各自语义干净，还顺带证明了一件事：
**一个模态可以提供多张表**。

`data_off` 是这一帧数据在数据文件里的字节偏移 = `页号 × 4096 + 20`。
它就是业界说的**外部引用**（Parquet 的 column chunk offset、
ClickHouse 的外部字符串引用都是这个形态）：
拿到 offset + length，任何人都能直接去文件里定位，不必经过数据库。

### 5.6 外部值：大值不进值层（v0.9）

一帧 4076 字节；`DbValue` 的文本上限是 255 字节。三条路：

| 路 | 做法 | 判决 |
|---|---|---|
| 1. 截断 | 只留前 255 字节 | **否决**。SQL 返回的值和实际内容不符 = 静默的数据错误，比报错更坏 |
| 2. 加大值类型 | `DbValue.s` 改成 4KB | **否决**。每值 4KB、每行 16 列 = 64KB；而且**值变大并不会让扫描变便宜** —— 扫描时把每帧内容读出来，1GB 对象就要读 1GB。而"只查帧号和长度"本该只读对象头 |
| 3. 外部值 | 值里存"句柄 + 取回方法"，内容**被需要时**才读 | **采纳** |

第 3 条是业界通例：

| 系统 | 做法 |
|---|---|
| PostgreSQL | TOAST：大值存进 TOAST 表，行里留 18 字节指针，读时 detoast |
| ClickHouse | 大字符串单独存成"外部表"，值是一个 16 字节引用 |
| Parquet / Lance | 列块单独存，行里是 offset + length；读某一列才去取那几页 |
| S3 / MinIO | 对象体在对象存储里，键 + 长度就是引用 |

```c
/* storage/value.h */
typedef int (*DetoastFn)(void *ctx, u64 key, u64 off,
                         u8 *buf, u16 cap, u16 *len_out);

typedef struct {
    bool is_null;
    u8   type;
    i64  i;
    u16  len;
    char s[VAL_TEXT_MAX];
    /* 外部值：内容不在 s[] 里 */
    bool      external;
    u64       ext_key;      /* 模态内部的对象标识（blob: blob_id） */
    u64       ext_off;      /* 模态内部的位置（blob: frame_no） */
    DetoastFn ext_fn;       /* 取回函数 */
    void     *ext_ctx;      /* 模态上下文 */
} DbValue;
```

**三条纪律**：

1. **外部值只在输出路径物化**。过滤、投影的中间过程**不**物化。
   这正是"扫描 blob_frames 不读帧页"的实现方式 ——
   不是靠优化器，是靠值的形态。
2. **比较时必须物化**（`val_cmp` 遇外部值先物化再比）。
   要么对，要么报错，**不能"近似比较"**。
3. **物化失败要报错，不能给空**。空的 TEXT 和"内容是空串"是两回事。

**外部值不持有堆内存** —— 它只持句柄和函数指针。
物化出来的缓冲由结果集自己管（`b_push` 里 free）。
这样 `DbValue` 依然可以按值随意拷贝，不会出现"谁负责 free"的问题。

### 5.7 虚拟表：模态怎么向 SQL 提供表（v0.9）

模态不能碰 catalog（硬规则 6）。那模态怎么让
`SELECT ... FROM blob_frames` 这条 SQL 能跑？

**注册表**：实例级（所有连接共享），存"名字 → StorageAM*"。

```
SpiRegistry:  名字 → StorageAM*
```

它是纯运行时结构，**不落盘**：blob 的两张表每次启动都重新注册
（blob 自己的目录扫一遍就出来了）。
关系模态的表不走注册表 —— 它们在 catalog 里，是持久化的元数据。

**解析顺序**：

1. catalog（用户建的表）—— 用户显式建的东西应该赢
2. 注册表（模态提供的虚拟表）
3. 都没有 → "表不存在"

**注册表不知道 blob 是什么** —— 它只知道"名字 → 一个 StorageAM"。
所以第 9 个模态接进来，只是多注册两条记录，执行器一行不改。

### 5.8 第二个模态：图（v0.11 落地）

blob 验证了 SPI 的"读 + 能力协商 + 虚拟表"路径。
图验证的是**另一半**：高频随机点查（`get` by RID）+ 定长写路径。

blob 一帧独占一页、对象不可变；图是**一页几十个节点、就地更新** ——
两种相反的访问形态，SPI 如果撑得住，设计才算真正站住。

#### 行模型：定长记录 + 双向邻接链

对齐 Neo4j 的记录布局（PLAN-v0.11 §1.2）：

```
节点记录（定长）：[in_use][first_out][first_in][NULL 位图][定长属性区]
边记录（定长 52）：[in_use][src][dst][out_prev][out_next][in_prev][in_next]
```

RID = (page, slot)，记录在页内的位置是**纯算术**（页头 + slot × rec_size）——
不用 slotted page 的 slot 数组。

边同时挂在两条链上：**src 的出链**和**dst 的入链**。
"谁指向我"和"我指向谁"同样高频；没有入链的话反向查询就是全表扫边，
100 万边每次几毫秒，p99 必炸。

#### 为什么用"定长槽页"而不是 slotted page

slotted page 的每一项都是为**变长记录**设计的：slot 数组用来算变长记录在哪，
变长区从页尾往上长，compact 会挪动记录。

图的记录是定长的 → 位置纯算术可得 → slot 数组纯属浪费一倍空间。
所以 storage 层另有一套页格式（`storage/gstore.{h,c}`）。

它和 `page.c` 并存，不是替换关系：
**变长记录用 slotted page，定长记录用定长槽页**。
两种布局各有各的适用面，硬统一成一种只会让两边都别扭。
（v0.11 它住在 `modalities/graph/`；v1.0 向量模态也要用它，
按硬规则 3 下沉到 L1 —— 纯搬家，逻辑没改。）

#### 属性 schema 是图的身份，必须落盘

节点记录里**没有**"这一列多宽"的信息 —— 宽度只存在于 schema 里。
所以 schema 不落盘 = 重启后整张图变成一堆看不懂的字节。

落盘方式是**第三个 gstore**（页类型 `PT_GRAPH_SCHEMA`）：
页分配 / WAL 整页镜像 / 重启接管全是 gstore 现成的能力，零新代码。

两条排除掉的路：
- 塞进节点记录 → 每条记录存一份 schema = 纯浪费，且改 schema 会改所有记录长度
- 塞进 catalog → 硬规则 6：catalog 不知道任何模态

**schema 一经确定不可更改**（记录布局定死，改了旧记录没法解释）。
磁盘上已有 schema 且与传入的**逐列相同** → 接管这张图；不同 → E_INVAL。

注意：只比记录总长是不够的 —— `INT4+INT4` 和 `INT8` 长度一样，布局完全不同。
必须逐列比名字、类型、宽度、可空性。

#### 事务语义：锁 + WAL，不做 MVCC

图记录是**可变**的（blob 对象不可变），所以 SPI 的 `visible()` 必须有人回答
"图行怎么判可见"。判决：**恒可见**。

| 方面 | 语义 |
|---|---|
| 可见性 | `visible()` 恒真（记录要么在用要么在空闲，没有中间态） |
| 隔离 | 写者互斥（全局 latch）+ 读不加锁 |
| 提交 | 语句级（每条语句一个隐式事务），不参与 BEGIN/COMMIT |
| WAL | 每次改页 → `WAL_PAGEDATA` 整页镜像；**xid 传 0**（系统事务） |
| 崩溃 | 已写的图操作全保留（页镜像重放），xid=0 恢复时永远视为已提交 |

这是"模态各自管自己的语义"（硬规则 6）的又一次体现：
heap 管 MVCC、blob 管不可变、graph 管"锁 + WAL"。
执行器三种都照单全收 —— 因为可见性判断本来就在 `am->visible()` 里。

**代价（已记录在风险清单）**：空闲记录立即复用 + 无版本链 =
读游标跨语句使用时可能看到记录被复用。图游标只在单语句内有效。

#### 两张虚拟表 + 两种下推

| 虚拟表 | 一行 | 下推形态 |
|---|---|---|
| `graph_nodes` | 一个节点（`node_id` + 属性列） | node_id 等值 → 直接定位；属性列 → **自滤**（全扫 + 逐行过滤） |
| `graph_edges` | 一条边（`src` / `dst`） | src / dst 等值 → **真下推**（沿邻接链，只读链上那几条） |

`node_id` / `src` / `dst` 用的都是**节点 id**（RID 的 u64 编码）。
边记录里存的就是 `rid_to_u64(端点 RID)`，两边编码一致 →
`WHERE src = X` 能反解出节点 RID → 沿它的出链走。

**自滤是比较"减法"**（会丢掉不满足谓词的行），所以它的比较语义必须和执行器
**逐字一致**（`ga_match` 照 `exec_scan.c` 的 `eval_expr` 抄）。
不一致就是静默漏数据 —— 比慢严重得多。

#### 怎么证明"真下推"而不是"全扫 + 过滤"

这两种实现**返回的行集完全一样**，光看查询结果验不出来。

所以加了一个可观测量：`GStore.rec_reads`（累计取出的记录条数）。
真下推只读匹配链上的那几条（= 锚点的度数），全扫读了全表每一条 ——
差一个数量级。

和 `db_blob_page_reads` 是同一个思路：**用可观测量证明"少读了"**，而不是靠读代码相信。

#### v0.11 的结果

执行器**一行没改**（`grep -rn graph src/query/` 零命中）。
这是 v0.9 定 SPI 时最想验证的事：加第 2 个模态 = 多写一个适配器 + 多注册两条记录。

10 万节点 / 100 万边，3 跳 p99 = **0.564ms**（目标 < 10ms）。
详见 PLAN-v0.11.md。

### 5.9 第三个模态：向量（v1.0 落地）

#### 它证明了什么

**列式存储 + 图索引可以在同一个内核里成立，而且执行器一行不改。**

向量模态是第三个模态（继 blob、图之后）。它比前两个多要一样东西：
**一个 ANN 索引**（HNSW），也就是 Index AM 的第二个实现。

#### 物理组织：列式，不行式

关系模态按**行**存（slotted page），向量按**列**存：

```
向量页（PT_VEC_DATA）：
  0  u8  页类型
  1  u8  标志（bit0 = 链头）
  2  u16 本页向量数
  4  u32 下一页
  8  u32 本页序号（用来校验寻址）
  12 u32 LSN          ← H_LSN，所有页类型共用
  16 u16 crc16        ← H_CKSUM，所有页类型共用
  20 ... 向量 0 | 向量 1 | ...（每个 dim × 4 字节，连续）
```

128 维 fp32 = 512B，一页 4096B 放 **7 个**向量（第 8 个差 16 字节放不下）。
寻址是**纯算术**：

```
row_id → 序号 = row_id / k → 槽号 = row_id % k → 偏移 = 20 + 槽号 × dim × 4
```

对标 Lance / Parquet 的列式布局，Milvus 的 segment 存储。

**页头取 20B 而不是规格里写的 8B** —— 8B 会直接压坏两个公共字段
（`H_LSN=12` / `H_CKSUM=16`），只坏每页的第一个向量，且**不报错**。

#### 列对齐：本模态最容易静默错的地方

第 i 个向量 ↔ 标量表第 i 行，靠**序号**对应，**没有任何指针**。
一旦错位（插入跳了一个 row_id、回收复用了序号），
查出来的向量和它的 label 就是**错配**的 —— 不报错，只是答案是错的。

三道防线：

1. row_id 全局单调递增，**永不复用**
2. 标量记录里**显式存 row_id**，读的时候断言它等于序号
3. 向量页头里存本页序号，重建时断言链序 == 序号

#### 向量是外部值 —— 于是"查元数据不读向量页"

`vec_items` 的一行是 **12 字节**（`[u64 row_id][i32 label]`），
**向量本体不在行里** —— 它是外部值，句柄 = row_id，要读才去 vstore 取。

所以：

```sql
SELECT row_id, label FROM vec_items;   -- 10 万向量，一个向量页都不读
```

这是列式布局在 SQL 层最直接的兑现。

#### HNSW：内存索引 + checkpoint 式落盘

- 参数对齐 hnswlib：M=16、efC=200、ef 默认 64、平方 L2
- 层级分配用几何分布（不用 libm）
- 启发式修剪（论文 Algorithm 4）：邻居要"在某个新方向上"，否则图会断成孤岛
- **索引是 checkpoint，不是日志**（同 B+tree）：关库 flush，崩了重建

```
vstore  向量数据（列式）+ 标量表   ← 真相来源
hnsw    内存索引                    ← 可重建
vindex  磁盘上的索引（checkpoint）  ← 可重建
```

#### 过滤 + ANN：给超集，如实报告

```c
候选池 = max(4k, ef)  →  按 label 过滤  →  截断到 k  →  如实报告实际数量
```

两个方向的错都堵住了：

- 候选池不扩 → 命中不足时**静默丢数据**（违反"下推只能给超集"铁律）
- 过滤后不截断 → 返回 20 个而用户只要 5 个（"返回了用户没要的行"）

#### v1.0 的结果

| 项 | 结果 |
|---|---|
| 执行器改动 | **零**（`grep -rn vector src/query/` 零命中） |
| recall@10（10 万 × 128 维，ef=64） | 聚簇 0.993；均匀随机 0.390 |
| 对照 hnswlib | **逐档都不低于** hnswlib（同一批数据、同样参数、各自独立算 GT） |
| ANN 页读 | 0（索引常驻内存）；暴力扫一次 14286 页 |
| 索引常驻内存 | 93.3 MB / 10 万 × 128 维 |

**均匀随机只有 0.390，但 hnswlib 在同一批数据上只有 0.338** ——
高维均匀向量是图索引的已知最坏情况（近乎等距，"近邻"本身没有结构）。
这条验收标准因此被修订（见 PLAN-v1.0.md §3 步骤 6）。

## 6. 崩溃恢复的整体流程

### 6.1 v0.6 实际实现

```
正常运行时（每条语句一个事务）：
  wal_append(BEGIN)
  → wal_append(INSERT/UPDATE/DELETE ...)   ← 先写日志
  → 改页（dirty），把日志的 LSN 写进页头      ← 再改页
  → wal_append(COMMIT)
  → wal_fsync                                  ← 提交点在这里

关闭时：
  pager_close（刷所有脏页，钩子保证日志先落盘）
  → wal_append(CHECKPOINT) → wal_fsync

崩溃后重启：
  阶段 1 · Analysis：从日志头扫到尾
          收集"哪些 xid 提交了"（xid=0 系统事务永远算已提交）
  阶段 2 · Redo：按 LSN 升序重放所有行级记录（含未提交事务）
          幂等靠 page_lsn >= record.lsn 就跳过
          插入必须用日志里记的 slot 原地填回，不能重算
  阶段 3 · Undo：对未提交事务的记录，按 LSN 降序应用 before 镜像
          回写前校验 slot 的页内偏移 —— 记录挪过位就放弃这次 undo
```

### 6.2 v0.6 简化的部分（相对 ARIES）

| ARIES 有 | v0.6 | 为什么 |
|---|---|---|
| ATT（活跃事务表）| 无 | 只扫全日志找 COMMIT，代价是 O(日志大小) |
| DPT（脏页表）| 无 | 靠 page_lsn 逐页判断 |
| CLR（补偿日志）| 无 | 回滚不写日志 —— 二次崩溃会重复回滚，但 page_lsn 挡住 |
| checkpoint 截断日志 | 无 | 日志只增不减，恢复时间随历史线性增长 |
| 周期 checkpoint | 仅关闭时 | 先把正确性做对 |

**代价**：日志无限增长。这是有意的取舍 —— 截断和 group commit 都是纯优化，
加进来会掩盖正确性问题。v0.7 再做。

### 6.3 三个容易做错的地方

1. **Redo 必须重放未提交事务**。这是 ARIES 的核心洞察——先全部重放，再回滚。如果只重放已提交的，页状态会不一致。
2. **Redo 的 slot 不能重算**。日志记了 slot 就必须用它原地填回。
   重算出来的 slot 和日志不一致时，undo 会删错行 —— 表现为"数据莫名少一条"。
3. **checkpoint 要在刷页之后写**。反过来的话：CHECKPOINT 先落盘，
   刷页时崩溃 → 恢复看到 CHECKPOINT 就认为"干净关闭"，不重放 → 数据丢了。

### 6.4 还没做的

- **B+tree 不写日志**：靠恢复后 `exec_rebuild_indexes` 重建。数据量大时太慢。
- **页撕裂**：假设页写入是原子的。真实场景要加 full-page-write。

## 7.5 可见性规则（v0.7 落地，必须能背出来）

快照三元组：`xmin`（快照时活跃事务的最小 xid）、
`xmax`（快照时 next_xid）、`xip[]`（快照时正在运行的事务号列表）。

### 插入者（tuple 的 xmin）可见性

| 条件 | 结果 |
|---|---|
| `xmin == 0` | 可见（系统事务） |
| `xmin == my_xid` | 可见（自己写的） |
| `xmin < snap.xmin` | 查 clog：已提交才可见 |
| `xmin >= snap.xmax` | **不可见**（快照后才启动） |
| `xmin` 在 `xip` 里 | **不可见**（快照时还在跑） |
| 区间内但不在 `xip` | **查 clog**：已提交才可见 |

### 删除者（tuple 的 xmax）可见性

| 条件 | 结果 |
|---|---|
| `xmax == 0` | 没被删 → 可见 |
| `xmax == my_xid` | 自己删的 → 不可见 |
| 删除者在快照时已提交 | **不可见** |
| 删除者在快照后才提交 / 还在跑 | 可见（删除对本快照不可见） |

**最后一行是"删除也要走 MVCC"的意思**：删除不是抹掉，是加一个标记。
事务 T 删了一行但还没提交时，新事务仍然看得到这一行；T 提交后才看不见。

### 一个极易写错的分支

「区间内但不在 `xip`」这一条，**必须查 clog**，不能"保守地当作未提交"。

因为 `snap.xmin` 的定义是"活跃事务的最小 xid"（**排除 my_xid**），
区间 `[xmin, xmax)` 会把很多**已提交**的事务圈进来 ——
它们不在活跃表，所以不在 `xip` 里，但它们**已经提交了**，应该可见。

写成"当作未提交"的后果是：**已提交的数据读不出来**（静默丢数据）。

**为什么单连接测试抓不到**：单连接时 `xmin == xmax`，区间是空的，
永远走不到这个分支。**必须多连接（且有长事务占着区间）才暴露**。

> 对照 PG：`HeapTupleSatisfiesMVCC` 的规则 6 就是"查 clog"。
> 差别只在 PG 的 `xmin` **不排除** `my_xid`，所以区间更小、
> 落进"区间内"的事务更少 —— 但那条规则依然是主路径，不是边角。

## 8. 风险清单

| 风险 | 为什么危险 | 缓解 |
|---|---|---|
| **B+tree 合并 bug** | 只在特定 key 分布下暴露，功能测试抓不到 | 用有序数组做参考实现，每次插入全量 diff |
| **WAL 幂等性** | 重复重放不报错，静默产生错误数据 | 每条记录带 LSN，重放前查 `page_lsn` |
| **MVCC 可见性顺序** | 只在多连接下出错，单线程测试全过 | 单连接时 `xmin==xmax`，区间是空的 —— **必须专门构造多连接场景** |
| **共享状态串号** | 已踩过：WAL 的 xid 跨连接串号，未提交数据被判为已提交 | 铁律：任何"当前是谁"的信息都不能藏在共享对象里，必须显式传参 |
| **vacuum 把执行者自己算进活跃表** | 已踩过：vacuum 变成只会空转的语句 | 判断活跃事务时排除执行者自己（`txn_has_active_except`） |
| **latch 死锁** | 单线程永不出现；出错时表现为挂死 | latch 顺序固定父→子，写进 code review 红线 |
| **hash 墓碑耗尽** | 已踩过：探测序列遇不到 EMPTY 就死循环 | 墓碑超 1/4 重建表（pager 已实现） |
| **未初始化内存** | 已踩过：测试自身 bug，伪装成"数据损坏" | 比较前 memset；ASan 全程开 |
| **下推漏行** | 少给行 = 静默丢数据，比报错危险得多 | 下推后**仍然完整求值 WHERE**；下推必须保守（宁可多给） |
| **外部值被提前物化** | 惰性没了 → "只查元数据"也读全部帧页，IO 暴涨 | 外部值只在输出路径物化；用页读计数做回归测试 |
| **执行器长出模态特判** | SPI 白设了；加第 9 个模态要改执行器 | 验收项：`grep blob src/query/exec*.c` 只有注释 |
| **资源泄漏在低负载下不可见** | 已踩过：blob 头页 pin 泄漏，单线程 + 少量对象永远测不到 | 并发 + 提高规模（建 400 个对象 > 256 帧）；t11 回归测试 |
| **测试自己把 bug 藏起来** | 已踩过：t2 用标志排序 → 两个 BEGIN 被拉开 → xid 永远撞不上车 | 用**屏障**让关键操作真正同时发生；审查测试的同步设计 |
| **漏加锁的入口路径** | blob 的 API 不走 `db_exec` → 只锁 db_exec 等于 blob 裸奔 | 每加一条入口路径就问"它加锁了吗"；`db_blob_*` 独立加锁 + 独立的并发测试文件 |
| **可重入性没有测试覆盖** | 反向验证第 2 轮：改成不可重入**没变红** | 当前无嵌套加锁路径，靠设计保证；已知盲区，如实记录 |
| **并发测试挂死** | 挂死比失败更糟 —— 整个套件卡住 | 看门狗（120 秒超时 → 打印 FAIL 并 exit） |
| **范围蔓延** | 最容易让项目死掉的原因 | 非目标表写死在本文档第 1 节 |
| **图的属性 schema 被后改** | 记录布局定死，schema 一改旧记录全成垃圾 | schema 落盘且**逐列比对**；不一致直接 E_INVAL，不给"读出垃圾"的机会 |
| **图的空闲记录被跨语句复用** | 无版本链 + 空闲立即复用 → 旧游标可能读到新记录 | 图游标只在单语句内有效（写进文档和 §5.8 的代价表） |
| **图的写放大（WAL 整页镜像）** | 加一条边改 4 个页 = 32KB 日志；100 万边 ≈ 32GB | 已量化记录在 PLAN-v0.11 §步骤 6；方向是"槽级日志"（记 52 字节而不是 4KB） |
| **CRC 成为写路径瓶颈** | 已踩过：逐位 CRC 让装载慢 3 倍 | 已换成查表版（值不变，test_crc.c 钉住）；**基准测试**是发现它的唯一手段 |

## 10. 已定的四个细节

这四点会冻结一段时间、改起来贵，先定死。

### 10.1 SQL 子集：单表 + 聚合，不做 JOIN

```
CREATE TABLE t (col type, ...);
INSERT INTO t VALUES (...), (...);
SELECT expr [, expr] FROM t [WHERE pred] [ORDER BY col] [LIMIT n];
SELECT agg(expr) FROM t [WHERE pred];
UPDATE t SET col = expr [WHERE pred];
DELETE FROM t [WHERE pred];
CREATE INDEX idx ON t (col);
BEGIN; COMMIT; ROLLBACK;
SET TRANSACTION ISOLATION LEVEL { READ COMMITTED | REPEATABLE READ };
VACUUM t;
```

谓词：`col op const`，`op ∈ {=, <>, <, <=, >, >=}`，支持 `AND / OR / NOT / IS NULL`。

**事务控制语句的语义（对齐 PG）**：

| 语句 | 规则 |
|---|---|
| `BEGIN` | 不在事务中 → 开一个；在事务中 → 报错（不做隐式提交） |
| `COMMIT` / `ROLLBACK` | 不在事务中 → 报错 |
| `SET TRANSACTION ISOLATION LEVEL ...` | 必须在事务内；一个事务内只能设一次；只对当前事务生效 |
| `VACUUM t` | 回收死版本，返回 `scanned / removed / kept` 三列 |

**事务内出错 → 整个事务标记为失败**（PG 的 "current transaction is aborted"）：
后续任何语句都报 `DB_E_TXN`，只有 `ROLLBACK` 被接受。

**没有显式 `BEGIN` 时，每条语句自动包一个单语句事务**（保持 v0.6 行为）。
自动事务用 RC（语句级快照和事务级快照效果一样），
显式事务默认也是 RC，要 RR 必须显式声明。

| 决定 | 理由 |
|---|---|
| **不做 JOIN（v1 前）** | 算法三小时能写完，难点是连接顺序——而那是 CBO 的活。先做 JOIN 会逼出一个假优化器 |
| **做无 GROUP BY 的聚合** | 便宜，但能验证"算子有状态"（累加器、LIMIT 提前终止） |
| **GROUP BY 放 v0.3.5** | 引入 hash 分组和 spill 概念，单独一版 |
| **UPDATE/DELETE 必须在 v0.3** | 没有它们 MVCC 无法验证 |

排除项：`JOIN` / 子查询 / `HAVING` / `DISTINCT` / 窗口函数。

### 10.2 类型系统：四个标量类型 + 一个模态类型

```c
typedef enum {
    T_INT4,   /* 4B 定长 */
    T_INT8,   /* 8B 定长：用来测"定长列宽度不同"时的 tuple 布局 */
    T_BOOL,   /* 1B：测单字节对齐和 null bitmap 边界 */
    T_TEXT    /* 变长：测偏移数组 */
} ColType;
```

| 决定 | 理由 |
|---|---|
| **砍掉 REAL/DOUBLE** | 浮点比较有 NaN 和精度坑，对理解存储无增量 |
| **保留 INT8** | i32/i64 混排是 tuple 偏移计算最容易错的地方，必须覆盖 |
| **向量列单独走 `VECTOR(dim)`** | 模态特有类型，不进通用类型系统；key 编码与比较规则完全不同 |

每个类型需要提供：宽度（定长/变长）、`encode`、`decode`、`compare`、`key_encode`（大端，供索引 memcmp）。

### 10.3 catalog：四张系统表

```sql
sys_table     (table_id, name, root_page, ncols, nrows_est, flags)
sys_column    (table_id, col_no, name, type, flags)      -- PK (table_id, col_no)
sys_index     (index_id, name, table_id, root_page, nkeys, is_unique, flags)
sys_index_col (index_id, seq, col_no)                    -- PK (index_id, seq)
```

| 决定 | 理由 |
|---|---|
| **`table_id` 从 1 开始，0 保留** | 避免与"无效 id"混淆 |
| **系统表 id 硬编码**（sys_table=1 … sys_index_col=4），**不查表** | 否则自举死锁：查 sys_table 得先知道 sys_table 在哪 |
| **索引列单独一张表** | 不用 `"1,2"` 逗号字符串，省掉解析器 |
| **`nrows_est` 由 analyze/vacuum 更新** | CBO 的唯一统计信息入口 |

**第 0 页（meta）** 只存 bootstrap：

```
magic "MDB1" 4B │ version 4B │ catalog_root 4B │ next_table_id 4B │ page_size 4B │ crc 4B
```

`page_size` 存进去，是为了换页大小后**立刻报错**而不是读出一堆垃圾。

**注意**：catalog 用 heap AM 存 → **实现顺序必须是 heap 在 catalog 之前**（见第 7 节修正）。

### 10.4 大值：按整行判断，不做列级

> **状态：设计已定，尚未实现**（计划在 SPI 接线之后）。
> v0.8 做的是 **blob 模态**（独立大对象存储，见 §5.4），
> 不是关系模态的大字段外置 —— 这两件事的区别见 §5.4 和 PLAN-v0.8.md。
>
> v0.9 把 SPI 接通了（§5.1–5.7），其中**外部值机制**（§5.6）
> 正是这条设计的前置：关系模态的大值外置可以复用同一套
> "句柄 + 惰性物化"的机制，不必另造一套。

一行总长 > `INLINE_THRESHOLD`（2048）→ **整行走 overflow 链**，页内 slot 只存 `(total_len, first_page)`。

overflow 页格式：`next_page 4B + used 2B + flags 2B` + 数据（每页最大 chunk 4088B）。

| 决定 | 理由 |
|---|---|
| **按整行，不按列** | 列级要给每列独立链 + 独立偏移，tuple 解码复杂度翻倍，且失去"一行在一个页"的局部性 |
| **单行上限 1MB**（约 256 个 overflow 页） | 超过直接拒绝，避免单行无限大把链写坏 |

**已知代价**：一行 3 个 TEXT 各 1KB（总 3KB）时整行外置要读 2 页，列级只需外置 1 列。但"一行多个大字段"正是 blob 模态要解决的场景，不该让关系模态背这个包袱。

**这条代价正是 v0.8 做 blob 模态的理由**：
需要"一行多个大字段"时，用 blob 模态存对象、关系模态只存 blob_id，
而不是把关系模态的 tuple 撑大。

## 11. 实现顺序（按依赖修正）

```
pager ✅
  └→ page（slotted page）✅
       └→ record（tuple 编解码）✅
            └→ freelist（页分配）✅
                 └→ heap（堆表 AM）✅        ← catalog 依赖它
                      └→ catalog（4 张系统表）✅
                           └→ btree（索引）✅
                                └→ query（parser → exec）✅
                                     └→ wal + recovery（横切，可提前埋钩子）✅
                                          └→ mvcc ✅
                                               └→ 模态（blob → 图 → 向量）
```

**关键**：`catalog` 必须在 `heap` 之后（它自己就是一张 heap 表），而 `query` 的 binder 依赖 `catalog`。这条顺序不能颠倒。

**v0.7 的实际依赖比方案多两项**：

```
mvcc（txn 表 + clog + 快照 + vacuum）
  └→ 实例 / 连接分离（db_connect）   ← 多连接才有意义
       └→ 隔离级别（RC / RR）          ← 需要连接私有的 iso_level
            └→ VACUUM 的 SQL 入口      ← 需要走 exec 层拿 heap
```

**v0.10 的实际依赖多一项**：

```
latch（全局可重入互斥量）   ← L0，不依赖任何东西
  └→ 语句级大锁              ← 覆盖 db_exec / db_blob_* / 生命周期
       └→ 真并发验收         ← 需要 pthread + 屏障 + 看门狗
```

**为什么 latch 放在 L0**：它只依赖 pthread（系统头）。
放高一层会让 common/ 之外的东西依赖它 —— 层次就乱了。

**下一版（v0.11，图模态）的依赖**：

```
定长记录存储（节点 / 边）
  └→ 图的 StorageAM 适配      ← 复用 v0.9 的 SPI
       └→ 图的虚拟表接进 SQL  ← 复用 v0.9 的注册表
```

**前置条件全部就位**：SPI 定稿（v0.9）、全局 latch（v0.10）、
执行器模态无关（v0.9）。图模态**不需要改执行器一行**。
