## 一、方案

### 1.0 这一版要证明什么

DESIGN.md 目标第 3 条点名的对标之一是 **Lucene 的 segment**。这一版学的是：

> **不变文件 + 后台合并**。索引 segment 写完就不可变；删除只打标记；
> 后台把小 segment 合并成大的（合并时才物理丢弃被删文档）。
> ——blob 的对象不可变、v1.5 时序的分区压缩、Lance 的 fragment，全是这一个思想。

判据两条：

1. **合并是透明的**：任意时刻触发合并，检索结果前后全等（用户视角合并不存在）。
2. **合并的代价是可解释的**：10 万文档分批插入，合并总 IO 呈
   `O(N × log_f N)` 量级（f = 合并因子），放大系数可测。

### 1.1 范围

**做：**

1. 英文分词器（小写化 + 非字母数字切分）。
2. 倒排索引：term 字典（有序数组 + 二分）+ posting list（`(doc_id, tf)` 有序对，delta 编码）。
3. BM25 评分（k1=1.2, b=0.75）；TF-IDF 作对照实现。
4. segment 物理格式（不可变）+ Tiered 合并 + tombstone 删除。
5. 虚拟表 `ft_docs`（文档元数据）+ 专用检索 API `db_ft_search`。
6. WAL 保护（`WAL_PAGEDATA` 整页镜像，第 4 个模态复用）。

**不做（明确划掉）：**

| 项 | 为什么 |
|---|---|
| 中文分词 | 分词器是独立工程（词典/统计模型），对理解倒排零增量 |
| FST / 前缀压缩的 term 字典 | 字典压缩是内存优化；有序数组 + 二分已能学 posting 机制 |
| 位置索引 / 短语查询 / 高亮 | 预留接口（posting 项留 pos 字段位），机制不做 |
| 近实时搜索（NRT / 内存 segment） | Lucene 的 NRT 是工程甜点，不是核心机制 |
| 多字段加权 schema | 单字段已覆盖全部评分机制 |

### 1.2 关键判决：检索语义走专用 API，不进 SQL 谓词

**这是本版最重要的边界判决**（对齐 v1.0 的"距离排序不进 SQL"先例）：

| 路径 | 内容 | 判决 |
|---|---|---|
| `db_ft_search(conn, term, top_k)` | 专用 API：返回 `(doc_id, score)` 按 BM25 排序 | **主路径** |
| `ft_docs` 虚拟表 | `(doc_id, doc_len, nterms, sealed)` —— 标量列，`doc_id` 等值/范围下推 | 元数据路径 |
| `match(col, 'term')` 进 SQL 谓词 | 需要 `PD_MATCH`、相关性排序键、执行器拥有全局统计（idf/avgdl） | **否决** |

**否决的理由**（写清楚，防止将来心血来潮去改）：

1. `pushdown.h` 的 `Predicate` 是 `(col_idx, op, DbValue)` —— 单值标量比较。
   相关性评分依赖**全局统计**（idf 随语料变、avgdl 随 segment 合并变），
   执行器根本无法独立重求值 —— **"下推给超集、执行器重判"的契约无法成立**。
2. 为单一模态改三个已验收模态共用的公共契约，违反 v0.9 的教训
   （接口是照着调用方的需要写的 —— 执行器不需要）。
3. 同性质先例已有三个：graph 遍历、vector knn、geo 窗口（v1.4）。
   **模态特有语义不进标量谓词系统** —— 这条边界在 v1.4 结束后写进 DESIGN 复盘。

### 1.3 segment 的物理形态

```
一个 segment = 三种页的区间（写完不可变）：

PT_FT_HEAD（段头页，1 页）：
  seg_id / doc_count / 创建 LSN / avgdl / 段内 max doc_id
  dict_page_start / dict_page_count / post_page_start / post_page_count

PT_FT_DICT（字典页，若干）：
  term 有序数组：[term_len, term_bytes, df, post_ptr]
  跨页二分查找（页内有序 + 页间有序）

PT_FT_POST（posting 页，若干）：
  (doc_id_delta, tf) 有序对数组，doc_id 用 delta 编码
  一个 term 的 posting 可能跨页链（页头带 next）
```

**为什么 term 用有序数组而不是哈希**：检索要"按字典序批量扫"（前缀查询的将来），
且**合并 = 多路归并**（有序对有序，天然归并）—— 哈希两头都不占。

**tombstone（删除标记）**：按 `seg_id` 组织的 doc_id 位图；
内存持有 + WAL 逐条追加（`WAL_FT_TOMB` 新记录类型，内容仅 `seg_id + doc_id`）；
重启时重放重建。**查询时过滤，合并时物理丢弃**。

> ⚠️ **本节是设计稿，落地有两处偏差**（步骤 2 实测后，见 §3 步骤 2 的设计决定 ② / ③）：
> 段头存的是 `total_len + doc_count`（不存 `avgdl`，读出来现算）；
> posting 除 `(doc_id_delta, tf)` 外**还带 `dl`**（4 字节/条，换掉第四种页类型）。
> **实际磁盘格式以 `src/modalities/ft/ft_internal.h` 为准。**
>
> ⚠️ **tombstone 的形态也变了**（步骤 3 实测后，见 §3 步骤 3）：
> 落地的是**全局 doc_id 集合**，不是"按 `seg_id` 组织的位图"。

### 1.4 评分与合并

**BM25**（k1=1.2, b=0.75）：

```
idf(t)   = ln(1 + (N - df + 0.5) / (df + 0.5))     ← Lucene 式，非教科书式
score    = Σ_t idf(t) · tf·(k1+1) / (tf + k1·(1 - b + b·dl/avgdl))
```

**为什么选 Lucene 式 idf**：教科书式的 idf 在 df=0 时为负、单文档语料时除零；
Lucene 式恒正且平滑 —— **抄业界实现，不抄教科书**（本项目的既定方针）。
TF-IDF 作为对照实现保留（验收 A2 用：两种评分对同一语料的排序差异要**可解释** ——
主要来自 BM25 的文档长度归一）。

**跨 segment 的统计合并**：`N`（总文档数）和 `avgdl` 是全局量 ——
检索时实时聚合各段头（段数 ≤ 阈值 8，聚合代价可忽略）。
**这正是合并的动机之一**：段越少，聚合越便宜（与 A4 的 IO 论证同向）。

**Tiered 合并**：

```
段数 > 8 时：挑"文档数之和最小"的相邻若干段合并成一个
  合并 = 字典多路归并（term 对齐）+ posting 拼接（重算 delta）+
         tombstone 过滤（被删文档物理丢弃）+ 重建段头
旧段页 → 回收（freelist，页号空间共享）
```

## 三、执行记录

### 步骤 0 · A3 收口：池级锁改造（2026-11-03）

**结论：A3 达标（3.09× – 3.82×，判据 ≥ 2×）。**

#### 为什么要做这一步

v1.2 步骤 7 把 A3 判为「未达标」（0.78× – 1.01×），
定位到缓冲池的池级互斥量 `pg->mu`，并写明「这一步是**结构性**改动，
不该混在『拆文件』这一步里做」。

于是它成了 v1.3 的第一件事。

#### 落地的东西

| # | 改动 | 文件 |
|---|---|---|
| 1 | **自研读写锁 `DbRwLock`**：读者快路径（`writer == 0 && waiting == 0` → `fetch_add` → 复查），写者才进互斥量并自旋等 `readers == 0` | `src/common/rwlock.{h,c}`（新） |
| 2 | 池级锁换自研读写锁：读路径（哈希查找 / pin / unpin）取读锁，改账本（逐出 / 分配）取写锁 | `src/storage/pager.{h,c}` |
| 3 | catalog 域锁换自研读写锁 | `src/catalog/catalog_priv.h`、`catalog_lock.c`、`catalog.c` |
| 4 | **每表页号表**：扫描只走本表的页 | `src/storage/heap.c` → 拆成 `heap.c` / `heap_scan.c` / `heap_compact.c` / `heap_internal.h` |
| 5 | `wal_bytes()` 改原子读（不再取 WAL 域锁）；`wal_fsync()` 把 fsync **移出域锁**（fflush 仍在锁内），`flushed_lsn` 只前进不后退 | `src/wal/wal.c` |
| 6 | 锁等待统计（**诊断用，默认关闭**）：`LS_ENTER/LS_LEAVE` 计数器 + `lockstat_dump()` | `src/common/lockstat.{h,c}`、`bench/probe_lockstat.sh` |

#### 三层根因（每一层都有实测证据）

| # | 根因 | 症状 | 证据 |
|---|---|---|---|
| 1 | winpthreads 的 `pthread_rwlock_t` **不允许并发读者** | 「读写锁」实际是互斥量 | 探针：1 线程 16.5M vs 自研 109M 次/秒；4 线程 3.1M vs **29M**（**8.9×**） |
| 2 | 堆表扫描**遍历整个页空间** | 4 个线程各扫自己的表，物理上都在 touch 全部 4 张表的页 → 内容锁变成全局串行点 | lockstat：**12,713 次真实内容锁冲突**，均匀分布在 4 张用户表 |
| 3 | COMMIT 的 fsync **持着 WAL 域锁** | 每条只读语句都要排在别人的 fsync 后面 | lockstat：WAL 锁平均等待 **35.2 us/次**；`wal_bytes()` 每条语句都要抢这把锁 |

#### 修好之后的锁等待（lockstat，4 线程 / 2000 行 / 200 轮）

| 域 | 修复前：总等待 / 真实争用 | 修复后：总等待 / 真实争用 |
|---|---|---|
| 池级锁 | 59.8 ms / 0 | 12.1 ms / **0** |
| catalog 域锁 | 1.5 ms / 0 | 1.6 ms / **0** |
| **帧内容锁** | **825.5 ms / 12,713** | **5.8 ms / 0** |
| WAL 锁 | 352.6 ms / 153 | 765.7 ms / 371 |
| txn 域锁 | 0.1 ms / 0 | 0.1 ms / 0 |
| freelist 锁 | 0.0 ms / 0 | 0.0 ms / 0 |

> WAL 锁的总等待**变大**不是退化：修复前线程大多堵在内容锁上，
> 排队到 WAL 锁前面的机会少；修复后语句跑快了，才真正排到 WAL 锁
> （= 排到磁盘 I/O）前面。剩下的这部分是**磁盘**，不是锁设计问题。

#### A3 实测

**配置甲 · 读重**（`bench/latch_bench.c` 的**默认配置**：5 万行/表、30 轮、4 线程）：

| 轮次 | 细粒度（条语句/秒） | 大锁基线 | **比值** |
|---|---|---|---|
| 1 | 5117.3 | 1535.1 | **3.33×** |
| 2 | 4653.1 | 1506.2 | **3.09×** |
| 3 | 5081.6 | 1601.6 | **3.17×** |
| （另一次单跑） | 5537.9 | 1449.2 | **3.82×** |

**线程扩展性**（细粒度）：1 线程 1710 → 2 线程 3289（1.92×）→ 4 线程 ≈5080（**2.97×**）；
大锁基线 4 线程 1535 ≈ 1 线程水平（**完全不扩展**）。

**配置乙 · 读轻**（2000 行/表、200 轮、4 线程）：**1.57× – 1.84×**，**未达标**。
墙钟拆开看：

```
墙钟 ≈ 并行读（1 线程读 73 ms，4 线程并行后仍 ≈73 ms）
     + 串行 fsync（80 次提交 × ≈2.75 ms ≈ 220 ms）
```

读轻时**磁盘占了大头**，而两个版本**受同一个磁盘限制**。
`bench/latch_bench.c` 的设计说明早就写明了判据口径：

> **③ 读要足够重**……读太轻的话，一次 commit 的 fsync（毫秒级）会把读的时间盖掉，
> 比值就变成「量磁盘」而不是「量锁」。**所以读必须重到 fsync 可以忽略。**

#### 三个设计决定

**① 为什么自己写读写锁，而不是调 `pthread_rwlock_t`。**
winpthreads 的实现**不允许并发读者**（见 §3 步骤 0 的根因 1）。
名字是「读写锁」，语义上是互斥量 —— 在**读多写少**的负载上，
它连「少写一点」的优势都占不到。
自研锁的实现只有一百行，读者路径无锁进入，是这个负载真正需要的形状。

**② 为什么 fsync 可以移出 WAL 域锁。**
三个前提，缺一不可：
- `fflush` **必须在锁内**（两个线程同时 `fflush` 同一个 `FILE*` 是未定义行为）；
- `fsync(fileno(f))` 是 **fd 级**调用，不依赖文件位置，和别的线程的 `write(2)` 并发是安全的；
- 并发的 fsync 允许「各刷各的」—— A 的 fsync 至少保证 A 自己那批字节落盘。
于是多个线程的 fsync 可以**重叠**，磁盘队列能流水。
另外 `flushed_lsn` 必须用 **max** 更新而不是 store ——
两个 fsync 完成顺序是随机的，慢的那个会把水位**倒退**。

**③ 为什么页号表不进 WAL。**
页链的更新（`tail->next`）本身是一次页修改，不写日志的话崩溃恢复后新页就成了孤儿 ——
整页数据「消失」。所以**不能改回页链**。
页号表是**纯内存**的：打开时由 `heap_open` 扫页重建，
不进 WAL、不影响崩溃恢复的正确性 ✓

#### 如实记录（不注水）

- **读轻配置（2000 行/表）确实没达标**（1.57× – 1.84×）。
  原因是磁盘 fsync 串行化，而且是在**锁已经修干净之后**测的
  （内容锁真实争用 = 0）。判据口径取基准的默认配置（读重）。
- fsync 的重叠只是「允许并发 fsync」，**不保证磁盘能并行处理**：
  实测每个提交仍要 ≈2.75 ms。要再往上走需要**组提交**（group commit），
  那是 v1.3 之后的独立课题，**本次不做**。

  算法是通用的，但**别的平台没有实测数据**。

  这是 v1.2 记下的欠账，不拆的话本步的改动会把它们推得更超标。

#### 三个设计决定

**① 为什么必须有 TF-IDF 这个「对照组」。**
教科书式 idf = `ln((N-df+0.5)/(df+0.5))` 在 df 大时**取到负值**，
而且**不做**文档长度归一。实测同一个查询 `quick fox`：

| 评分 | 排序 | 分数 |
|---|---|---|
| BM25 | doc2 → doc0 | doc2 = 1.1889、doc0 = 0.9063 |
| TF-IDF | doc0 → doc2（**顺序反过来**） | doc0 = −1.0217、doc2 = −1.5325 |

**同一个查询，排序完全不同** —— 这一条对照同时演示了
「为什么要 Lucene 式 idf」（恒正）和「BM25 的长度归一在修什么」。
**抄业界实现，不抄教科书**（本项目的既定方针）在这条对照上看得最清楚。

**② 线性扫描是「基准实现」，不是「临时方案」。**
A1 的验收是「倒排索引的 top-k 与线性扫描全等（含分数）」——
所以线性扫描的语义必须**钉死**，倒排那边照抄：

- 只有**至少命中一个 query 词**的文档才进结果（**不按分数正负过滤** ——
  TF-IDF 的 idf 可能是负的，命中了就是命中了）；
- query 里的重复词**不去重**（M4-12）；
- 排序：分数降序、分数相同按 `doc_id` 升序（M4-11）。

**③ 缓冲不足时报「需要的数量」，而且一个词都不写。**
半截词表比没有词表更难查 —— 调用方忘了看返回值，
半截词表会被当成完整词表用下去。所以用**两遍扫描**：先数再写（M4-8）。

#### 钉死的语义清单

| 语义 | 决定 | 坑 |
|---|---|---|
| token 的 `text` | 恒以 `'\0'` 结尾（下游很可能直接 `printf("%s", ...)`） | — |
| 超长词 | 保留前 63 字节、剩余整段丢弃、**不在截断处再切** | M4-7 |
| 非 ASCII 字节 | 一律当分隔符（本版只做英文分词） | M4-6 |
| `avgdl == 0` | 长度归一比例定义为 0，**绝不让 NaN 进排序** | M4-9 |
| 教科书 idf | 参数非正 → 0；参数为正时**可为负**，命中判定不看分数正负 | M4-10 |

#### 段格式（落地版）

一个段 = 三种页的区间，写完**不可变**：

| 页类型 | 页数 | 布局 |
|---|---|---|
| `PT_FT_HEAD` | 1 | 段头：`seg_id / doc_count / max_doc_id / dict_start / dict_count / post_start / post_count / n_terms / total_len / create_lsn`，字段一律从偏移 **20** 开始（页头 20B 是 slotted page 的标准头） |
| `PT_FT_DICT` | 若干 | **标准 slotted page**，**没有自定义区**。词条 = `u16 term_len` + term 字节 + `u32 df` + `u64 post_ptr`（14 + term 字节） |
| `PT_FT_POST` | 若干 | **自定义密集格式**：数据区从 `FPH_DATA`=28 开始；一个 run = 12 字节头（`first_doc_id / n_post / flags / next_run`）+ n × 12 字节 posting（`delta / tf / dl`） |

**字典页的"本页第一个词" = slot 0 的记录**（插入顺序 = 字典序）——
跨页二分先拿每页的第一个词比，再在页内 slot 上二分。

**倒排链的跨页**：一个 term 的 posting 填满一页就换页，`FTR_NEXT_RUN` 存**下一个 run 所在的页号**；
续接的 run 永远落在那一页的 `FPH_DATA` 处，所以页号就足够定位（无需 u64 的 `post_ptr`）。

#### 五个设计决定

**① 段对象在内存里只有段头，posting 一个都不缓存。**
字典页和倒排页都是**按需从页里读**的 —— 这是"IO 可证"（A5）的前提：
查一个词的页读 = 字典二分的页数 + 该词的 posting 页数，**与总文档量无关**。
段是不可变的，段对象唯一的写字段是 `page_reads`（纯统计）。

**② 段头存 `total_len` + `doc_count`，不存 `avgdl`（偏离 §1.3 设计稿）。**
`avgdl = total_len / doc_count`，而这两个都是整数；存 `f64` 到磁盘要处理字节序和结构体填充，不值当。
存整数、读出来现算，得到的 double 与线性扫描那边算出来的**逐位相同**
（两边都是 `(double)total_len / (double)doc_count`）—— A1 要求的就是这个。（坑 M4-15）

**③ posting 里带 `dl`（偏离 §1.3 设计稿）。**
BM25 的长度归一项需要每篇文档的词数 `dl`，而段的物理形态里**没有文档表**，
所以 `dl` 只能跟着 posting 走 —— 每个词重复存一遍。代价 4 字节/条，
收益是**不用引入第四种页类型**。备选方案（加一张 ordinal → (doc_id, dl) 的表）留到步骤 3 之后再评估。

**④ 倒排链只有一种布局，不做"猜几种可能"的兜底。**
猜布局会把"布局错了"变成"能读出来但是错的"—— 那是更坏的一种错。
所以只保留契约定义的那一种布局，链走到形状不对就报 `E_CORRUPT`。（坑 M4-14）

**⑤ 接口收口：`top_k > max_out` → `E_NOSPACE`。**
这是步骤 1 记下的"API 形状上的遗憾"的兑现 —— `ft_score_linear_bm25 / ft_score_linear_tfidf`
与 `ft_segment_search / ft_segment_search_tfidf` 现在都显式带 `max_out`，
调用方给小了会**报错**而不是越界（与 `config.h` 里 `MAX_GROUPS` 的同款规矩）。

#### 如实记录（不注水）

- **段列表在内存里**，调用方自己攥着 `head_page`。
  磁盘上的段目录属于步骤 4/5 —— 所以"**重开库还能找到段**"目前**不成立**。
- **没有 tombstone，没有合并** —— 那是步骤 3 的事。
- **没有段级专用 WAL 记录类型**：页的改动走 `LOG_PAGEDATA` 整页镜像

#### 四个设计决定

**① tombstone 是全局 doc_id 集合，不是"按 seg_id 组织的位图"（偏离 §1.3 设计稿）。**
理由三条：`doc_id` 由调用方给、**不稠密** → 位图需要一张稠密序号映射表，
而段的物理形态里**没有文档表**；"删一篇文档"时调用方只知道 `doc_id`、
不知道它在哪个段里（按段存就得先反查）；合并时按全局集合过滤语义更直白。
代价：集合只增不减（删掉的文档合并后其实可以清掉，但"它还在别的段里吗"不好判断）。

**② 跨段检索分两遍扫描。**
第一遍只查字典、聚出全局 `df(t)` / `N` / `avgdl`；第二遍才取倒排链打分。
为什么不一遍做：`idf` 与 `avgdl` 是**全局量**，一段里算不出来。
段数 ≤ 8 时聚合代价可忽略 —— 这正是合并的动机之一（段越少，聚合越便宜）。

**③ 字典多路归并用流式游标，内存 O(k) 页。**
k 路归并如果每一路都把整页读进内存，就是 O(k × 页大小)；
用游标（记住"当前路读到哪个 slot"）只占 O(k) 页。

**④ 段级页读不动，索引级改成差量累加（坑 M4-16）。**
`ft_count_page_read` 一行未改（段级仍是"该段自打开以来读过的页数"）；
索引自己维护累计计数器，每次检索取前后差值再累加。
⚠️ 附带修了一处**死计数器**：段的只读访问器原本刻意不记页读，
而索引检索走的正是那条路径 → 差量恒为 0。修法是
**查词与取倒排链记页读（检索路径），扫词表不记（全量扫描路径）**。

#### A7 · 崩溃恢复的三个设计决定

**① 段目录没有独立的目录页 —— 状态记在段头页自己。**
段头页新增 `FTH_STATE`（LIVE/DEAD/MERGING）与 `FTH_MERGE_TO`（目标段段号）。
段头页是**最后**写的，所以"段头页在盘上"≡"这个段建完了"
（崩在写段头页之前 → 那页的页类型不是 `PT_FT_HEAD` → 恢复扫不到）。
恢复时扫整个页空间认领段头页，按 `seg_id` 排序去重，逐个开段重建段数组。
段号**永不复用**（`next_seg_id = max(最大 seg_id, 最大 merge_to) + 1`）。

**② 合并的顺序必须崩溃安全（坑 M4-21）。**
"老段标 MERGING（指向新段段号）→ 写新段 → 老段标 DEAD"。
恢复时看目标段在不在：目标段存在 → 合并已完成 → 老段算 DEAD；
目标段不存在 → 合并没写完 → 老段还算 LIVE。两种情况都不丢文档、不重复计数。

**③ tombstone 集合落盘，而且**不只**靠 WAL。**
新增页类型 `PT_FT_TOMB`：一页就是一个**稠密 u32 数组**（一页 1018 个 `doc_id`），
满了就再开一页（全体取并集，不需要链表，不怕链断在半路）。
每次删除**两件事都做**：① tombstone 页**整页镜像**进 WAL（页是权威存储，
checkpoint 截断日志也删不掉它）；② 追加一条 `WAL_FT_TOMB` 逻辑记录（载荷 `u32 doc_id`）
—— 便于撤销未提交事务的删除。
恢复取**并集**：最终集合 = 页里的内容 ∪ (WAL 重放看到的 − WAL 回滚撤销的)。

**WAL 钩子**：`recovery_set_hook()` + `RecHookPhase`（REDO / UNDO）。
WAL 层只认识页类记录，**非页类记录原样转交上层钩子** ——
FT 语义由 db 层解释（`wal/` 是 L1，不许依赖 `modalities/`）。

#### 撞出来的真 bug · 字典页不连续（坑 M4-23）

**症状**：只要一个段的字典超过一页 —— 查不到（`E_NOTFOUND`）、命中 **0 篇**、
**静默丢词**（最坏，不报错只是词悄悄没了）。

**根因**：段头只记**连续区间**（`dict_start` + `dict_count`），
读侧（跨页二分、词条游标）都按连续区间读页；
而建段与合并**都是"一个词先写倒排、再写字典"**，两个写入器各自 `pager_alloc`
→ 倒排页与字典页**交替分配**、页号不连号 → 读侧把倒排页当字典页读。

**为什么之前没测出来**：词表 ≤ 约 170 个短词时字典正好一页，
而步骤 2、步骤 3 的测试语料都恰好在一页以内。
**是步骤 5 的基准一上量（10 万文档 / 词表 5000）才撞出来的**。

**修法（不改磁盘格式）**：**两趟**。第一趟只写倒排、顺手记下每个词的链头；
第二趟按**同一个词序**写字典、用第一趟记下的链头。建段与合并**两边都改了**。
代价：合并时字典页被读两遍（已计入合并页读）。

#### A4 · 合并代价（10 万文档 / 批 1000 / 词表 5000）

| 指标 | 实测 |
|---|---|
| 合并次数 / 合并因子 | 92 次 / f = 2.00 |
| 总 IO（结构口径） | 读 25483 页 + 写 21718 页 = **47201 页** |
| 总 IO（实测取页） | **869822 次取页** |
| **拟合 c（题目口径）** | **0.0284 页/文档** |
| 拟合 c（分层口径） | 0.0803 页/文档·层（模型 0.1069，**相对误差 24.9%**） |
| 实测层数 / 模型 | 5.09 / `log_f(N/b)` = 6.64（顶层因阈值 8 残缺） |
| 单次合并效率中位数 | 1.210（读掉的旧页 ÷ 写出的新页） |
| 检索耗时 | 合并前中位 0.037 ms → 合并后 0.035 ms（**合并不拖垮检索**） |
| 合并丢词 | **0 次** |

**两套口径差 34 倍，原因查清了**（坑 M4-25）：
倒排是按 term 分散存放的，合并时**每个 term 都要单独取一次页**，同一页被反复取
→ 取页次数 ≈ 老段的**词数**之和（实测 869822 vs 模型 849596 词次，误差 2.4%）。
真实磁盘 IO 落在两者之间（取决于缓冲池命中率：
缓冲池 4096 帧 ≈ 16 MB，而段总页数 3335 页 ≈ 13 MB，基本全命中）。
**结论**：合并路径的代价是 O(段内**词数**)，不是 O(段页数）——
词表越大，每次合并越贵。

**合并窗口的实际行为**（实测，不是定性）：

- 92 轮里只有 **3 轮**包含最老那段，平均起点 6.13 → 合并基本发生在索引的中后段；
- 结束时索引里 8 个段的文档数是 8000 / 15000 / 9000 / 15000 / 8000 / 14000 / 14000 / 17000
  —— **段大小很不均匀**（最大/最小 = 2.1）；
- **顶层残缺是真的**：段数恒为 8（阈值），**没有一个段覆盖全部数据**，最大段只占 17%；
- 没有残留"一个批大小"的新鲜小段 → 新批段都会被拉进合并，不是永远孤立。

这三条都是**真实行为，不是 bug**（"段大小不均衡"是 Tiered 的固有性质）。

### 怎么还的（这一轮的三条做法）

**① 欠账不是"改一个判断"，而是"改一个模型"。**

第 6、7 条欠账的根源是**口径没定死**：以前只有一个"取页次数"，
于是"合并很贵"这个结论既可能是真的、也可能是度量幻觉。
这轮把口径拆成**逻辑页读 / 物理读盘 / 唯一页数 / 段页数**四个，
再回头看，结论自己就变了：
合并的**逻辑**页读从 O(词数) 变成 O(页数)（优化），
而**物理** IO 从来就是 O(页数)（度量原来算错了）。
第 7 条的判据（C6）也因此**必须重新定义** —— 旧判据失效是优化生效的证据，不是回归。

**② 判据要能"打红"，也要能解释"为什么这次没打红"。**

新的 C6 = "合并的逻辑页读 ≈ **2 × 老段页数 + 新写页数**（每次合并容差 ±64 页）"、
新的 C7 = "物理读盘 ≤ 唯一页数"。
它们都写在 `bench/ft_bench_a4.c` 里，与旧判据并存于注释中（说明旧判据为什么废）。
**判据失效如果不能解释，就等于没有判据。**

⚠️ **2026-11-04 又打了一次红，是判据自己的错**（已修正，如实记录）：
改用 pager 的"逻辑页读"口径之后，C6 一度写成"逻辑页读 ≈ 2 × 老段页数（±0.6）"，
实测 2.95 倍 → 打红。查下来是**模型写错了**，不是实现退化：

1. **口径混用**：模型 2.0 是照着"合并实测取页次数"（`ft_index_merge_page_reads`，
   实测 ≈ 1.0 × 老段页数）推的，判定用的却是 pager 的**逻辑页读**
   （`pager_get` 与 `pager_alloc` **各算一次**，见 `pager.h` 顶部口径说明）。
   分母一样、分子差一笔"写入也算取页"，必然对不上。
2. **模型漏了两笔**：合并前还有**数页那一趟**
   （`ft_merge_count_pages`：读一遍源段字典页，把新段字节数数清楚）
   ⇒ 老段页被读**两趟**；新段的页由 `pager_alloc` 出来，也计一次逻辑页读。

修正后的模型对 92 次合并逐次成立（偏差 -36 ~ +39 页/次），
比值 2.95 与段大小**无关**（92 次都在 2.49~3.01）——
这才是"代价是 O(页数)"的真正证据：**比值是常数**。

另外 C7 这一轮打成 **`[SKIP]`**（空判据）：帧池装得下整个库 ⇒ 物理读盘 0 次、
唯一页数 0 次，两边都是 0。**判据"没打红"不等于"通过了"**——
本次如实打成 SKIP、不计入达标，并把"要调小帧池才有区分力"记进下面的欠账。

**③ 坑号必须全仓唯一。**

这一轮 6 个 agent 并行写代码，坑号一度撞成 3 组重号（M4-26~M4-32）。
最后按"文件归属"统一重编为 M4-26~M4-47，并逐条写进 `MODALITIES.md` §6.11。
教训：**并行写代码时，编号要由一个人统一分配**（或每人分配互不相交的号段）。

### 仍然欠着的（这一轮**没有**解决，如实记录）

1. **开机时的页回收未做**：空闲页池是**内存态**，重启即失效；
   "文件里那些已经没人引用的页"要等段目录页落地后（wave 2）才能在开库时认出来。
2. **旧目录链不回收**：被取代的旧目录链页留在文件里（已记 `FTC_PREV` / `FTR_PREV_CAT` 供以后回收）。
3. **失败合并产生的新段页只浪费、不回收**：半成品页绝不能进池（否则把垃圾页交给后续段，坑 M4-28）。
4. **段页数上界是保守值**（宁多勿少）：精确上界要额外读页头（倒排 `FPH_USED` / 字典 slot 目录），
   会污染"逻辑页读"这个指标口径，所以没做 —— 代价是前 2 轮合并文件仍增长。
5. **物理读盘这个口径当前测不出差别**：① 它是**文件级读**（read 系统调用级），
   不是硬件磁盘 IO —— 基准数据由本进程刚写入，操作系统页缓存会把它服务在内存里；
   ② 更根本的是**帧池装得下**（10 万文档的库 3335 页 vs 帧池 4096 帧）⇒
   物理读盘 0 次、唯一页数 0 次，判据 C7 是**空判据**（本次 `[SKIP]`）。
   要让它有区分力，必须把帧池调小到装不下库 —— 这件事还没做。
6. **WAL 日志格式不向前兼容**：新写的库用旧版本内核打开，那次删除会丢
   （升级前需 checkpoint + 重建）。
7. **按值撤销的固有歧义**：同一 doc_id 被两个事务各删一次时，撤销只能按值删，
   理论上可能撤掉别人的那一条（同一会话内 `ft_tomb_is` 会挡住重复删，跨崩溃边界才可能撞上）。
