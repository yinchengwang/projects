## 一、方案

### 1.0 这一版要证明什么

前六个模态各有独立存储；文档模态的判决是**寄生** —— 不建存储，做 heap 上的列类型。
要证明的是 schema-less 的真正难点不在存储：

> **schema-less 的难点在值表示与索引**：自描述文档怎么变成可寻址、可索引、
> 可比较的数据 —— JSONB（解析一次反复用）+ 路径索引（把声明过的路径物化成标量键）。

三个判据（每个都直指既有机制的最后检验）：

1. **外部值的最终检验**：大 JSON 文档走页链外置（blob 帧 → 向量 → **大 JSON**，
   外部值机制的第 3 个用户）—— v0.9 设计 foresight 的收官考试：
   `ext_fn` 从"按帧读"换成"按页链读"，**契约一行不改**。
2. **下推超集契约的闭环**：路径索引返回候选行 → 执行器**重新提取路径值再比较** ——
   通用谓词世界和文档世界的桥要靠"路径值 → 通用标量"的映射成立。
3. **执行器改动最小化（非零但有硬边界）**：寄生模态注定要碰执行器
   （路径求值发生在执行器）—— 改动的边界要事先定义、事后审计。

### 1.1 范围

**做：**

1. JSON parser（递归下降）+ **JSONB 二进制格式**（解析一次，按路径 O(子树) 访问）。
2. `JSON` 列类型：小文档内联进 heap 行；大文档外置页链（外部值）。
3. 路径表达式（`$.a.b[0].c`）+ 提取 → **通用标量映射**（TEXT/INT/REAL/NULL）。
4. 路径索引：`CREATE INDEX ON t (json '$.a.b')` —— 提取标量走现有 B+tree + index_key。
5. `json_match(doc, '$.a.b = 5')` 求值：有索引走索引（候选集），执行器重判。
6. `db_json_*` API + 对照 SQLite JSON1 全等测试。

**不做（明确划掉）：**

| 项 | 为什么 |
|---|---|
| JSON Schema 校验 | 应用层职责 |
| 多值索引（数组展开成多键） | 只索引标量路径；数组路径提取返回数组首元素？——**不**，返回 NULL（语义写死）|
| 部分更新（`$set` 语义） | 只做整文档替换（MongoDB 的文档级替换同款起点） |
| JSON 聚合 / 生成函数（json_group_array…） | 查询层糖 |
| MongoDB 查询语法（find 的操作符族） | SQL 谓词 + json_match 已覆盖机制 |
| 键字典 / 重复键压缩 | Lucene FST 同类的内存优化，不做 |

### 1.2 关键判决

#### 判决 1（本版核心）：路径提取值映射为通用标量 —— 超集契约的闭环

**问题**：下推契约（v0.9）要求"AM 给候选行，执行器重新求值 WHERE"。
但 WHERE 里的 `json_match(doc, '$.a.b = 5')` 要求执行器能**独立**判断文档。

**判决**：

```
JSONB 整体      → 不进通用类型系统（blob 同款：字节串 / 外部值）
路径提取值      → 映射为通用标量：
    string  → DbValue(TEXT)
    number  → DbValue(INT 或 REAL)
    true/false → DbValue(INT 1/0)
    null / 路径不存在 / 类型不匹配 → DbValue(NULL)
    object/array（非标量路径）→ NULL（语义写死，见 §1.1 不做表）
```

于是超集契约完整成立：**索引按提取值建的键，执行器用同一套提取规则重判** ——
两边的映射函数是同一个（`json_extract_scalar`），不可能语义分叉。
v1.3 §1.2 说过"相关性评分执行器无法重求值"（所以 match 不进 SQL）——
**JSON 路径值可以**，所以 json_match 进 SQL 是合法的。
一进一不进，判据是同一条：**执行器能不能独立重判**。

#### 判决 2（修正总览预判）：路径索引写入时同步维护，不存在"快照过期"

总览（PLAN-modality-expansion §4）预判"索引存标量快照、可能过期（文档更新了但索引项未删），
执行器重求值兜底"。**细化时被推翻**：

| 路径 | 分析 |
|---|---|
| 快照过期 + 重判兜底 | 过期意味着**索引里躺着死键**：没人删它，越积越多 —— 那不是"保守的超集"，是泄漏 |
| **写时同步维护**（采纳） | 文档更新 = 整替换（§1.1 已定）→ 写路径删旧键、插新键 —— **v0.5 的写路径维护索引原样适用**，B+tree 既有能力，零新机制 |

执行器重判**仍然保留**（它是超集契约的一半，防的是索引实现 bug 而非过期快照），
但"过期"这个设计借口不存在了。修正记录进执行记录。

#### 判决 3：JSONB 格式

```
JSONB = 长度前缀树形序列化（PG JSONB / MongoDB BSON 同思路）：

  [tag][payload]：
    tag ∈ { null, true, false, int32, float64, string, array, object }
    string  ：[len][utf-8 bytes]
    array   ：[count][element]×count          （顺序即语义）
    object  ：[count][[klen][key][element]]×count  （键按长度+字典序存放 → 二分可查）

  小文档（≤ 行内限）→ 内联 heap 行的列值
  大文档            → 外部值：PT_JSON_OVF 页链（ext_key = 首页号，ext_fn 沿链读）
```

**键排序**是 JSONB 相对裸文本的真实收益之一：对象键二分查找，
路径 `$.a.b` 的访问是"两次二分"，不是全文扫描。

#### 判决 4：事务语义 —— 三足鼎立的收官

| 模态 | 事务语义 | 出处 |
|---|---|---|
| heap（+ 本版 JSON 列） | **MVCC 版本链**（RC/RR） | v0.7 |
| blob | 不可变对象 | v0.8 |
| graph / vector / ft / ts | 锁 + WAL（语句级） | v0.10–v1.5 |

文档是 heap 行 → **继承 MVCC**：整文档替换走 UPDATE 两段式（旧版本打 xmax + 插新版本），
RR 快照下读到的文档**不撕裂**。三种语义到齐 —— 这张表是 DESIGN 复盘的素材。
